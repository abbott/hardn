# Migrating legacy SSH files into 00-hardn.conf (`pkg/host/sshd/migrate`, `pkg/config`)

> **Unit:** refactor plan Phase 2, `next/p2-sshd-migrate` (decision §3.17, approved 2026-10-17: migrate the legacy artifacts automatically, with a backup and a printed note; `permitRootLogin` takes `"no" | "prohibit-password" | "yes"` and still reads the old bool, with a deprecation warning; §3.19 for writing the canonical value back). V-numbers: V24 (the v0.3.2 → origin/main upgrade path: keys in `~/.ssh_<user>`, `manage.conf` and `listen.conf` left behind, `sshConfigFile` ignored), the migration half of V13 (`hardn.conf` loses to `50-cloud-init.conf`), V5 with D7 (which `AuthorizedKeysFile` the keys are under), V15's restore step (Alpine's whole `sshd_config`), D8 (`sshConfigFile` dead) and V11's config half (the key can say `prohibit-password`) ([side-effects.md](../refactor/phase0/side-effects.md) §8, §9). Risk R8 (plan §4).
> **Status:** built and tested on macOS against the recording fake (`hostfake`) only. `sshd -t` and `sshd -T` are answered by a small model of sshd's reading in the tests (`modelT`), not by sshd; legacy files are reconstructed from the v0.3.1, v0.3.2 and origin/main sources (§3), not captured from hosts. Nothing has run on Linux; §4 lists what is "written, not run (gate 5)".

`migrate.Find(ctx, sys, req)` reads the host and names every SSH file a legacy hardn wrote. `migrate.PlanFor(in)` turns those files, the settings hardn wants and the installed configuration into steps, with no I/O. `migrate.Check(ctx, sys, plan, opts)` validates the state the whole plan leads to with `sshd.Validate` and refuses one with fewer working login paths than the installed configuration, writing nothing, so its refusals show in a dry run; `plan.Reload(after)` is the `reload.Change` for the reload that follows. `migrate.Apply(ctx, sys, plan, opts)` runs `Check`, backs up every file it changes with `backup.Run` (RollbackRequired), checks nothing changed since the plan, validates each step's state, and writes atomically. It reloads nothing. In `pkg/config`, `permitRootLogin` reads the three strings and the old bool, the legacy loader refuses `prohibit-password` until the SSH code applies it, and `config.Save` writes the canonical string to the loaded path. *Since `next/legacy-rehome`* (decision 6 (a)): the refusal, `ErrRootLoginNotApplied` and `prohibitPasswordApplied` are deleted; a hardn.yml with `prohibit-password` loads and warns "isn't used".

## 1. Why

Brief §2 decides that hardn owns one drop-in, `/etc/ssh/sshd_config.d/00-hardn.conf`, read before every other drop-in. Every earlier hardn wrote somewhere else ([side-effects.md](../refactor/phase0/side-effects.md) §10): v0.3.x a `manage.conf` (or the `sshConfigFile` its `hardn.yml` named) and an `ssh.socket.d/listen.conf`; the unreleased builds after it a `hardn.conf` that `50-cloud-init.conf` beats; on Alpine every ref the whole `sshd_config`. A host upgraded from v0.3.2 to an origin/main build has `manage.conf` and `hardn.conf` both. Writing `00-hardn.conf` beside them leaves their lines in force where `00-hardn.conf` says nothing, `listen.conf` keeps overriding the socket's port (so `p2-reload` refuses a port change, `ErrSocketDropIn`), and deleting them blindly can drop the only `AuthorizedKeysFile` that names `~/.ssh_<user>`, where v0.3.x put the keys (R8). Never locking the user out (brief §3 principle 1) means the migration keeps every working login path and every key file, and can be undone.

## 2. Guarantees

### Finding the artifacts (`Find`)

1. **Read-only.** `Find` reads `sshd_config`, every `*.conf` in `sshd_config.d` that sshd's `Include` matches (a leading `.` never matches, following symlinks as sshd does, in C byte order), the fixed legacy paths and `FindRequest.ConfigFile`. It makes no other call (tested: every recorded call is a read).
2. **An artifact is recognised by what hardn wrote first**, never by its path alone:

   | Kind | Path | Recognised by |
   |---|---|---|
   | `KindManageConf` | `sshd_config.d/manage.conf` | its first two lines, `### Reference` and the cryptsus URL (v0.3.1 and v0.3.2), or `# SSH configuration managed by Hardn` |
   | `KindCustom` | `FindRequest.ConfigFile`, v0.3.x's `sshConfigFile` | the same, and it must be a `*.conf` in `sshd_config.d` |
   | `KindHardnConf` | `sshd_config.d/hardn.conf` | the same |
   | `KindListenConf` | `/etc/systemd/system/ssh.socket.d/listen.conf` | exactly `[Socket]`, `ListenStream=`, `ListenStream=<port>`, port 1 to 65535 |
   | `KindGeneratedMain` | `sshd_config` | `# SSH configuration managed by Hardn` first (origin/main, including its disable-root stub), or v0.3.x's Alpine template: `Protocol 2`, `StrictModes yes`, a blank line, `Port ` first, and its `HostbasedAcceptedKeyTypes …` line |

   `Generation` says which hardn wrote it (`GenV03`, `GenMain`). A legacy file is read with `ReadFileNoFollow` after an `Lstat`: a symlink or anything not a regular file is not an artifact.
3. **What hardn did not write, or sshd does not read, is left and said why** (`Found.Left`): a file at a legacy path without hardn's first lines (not hardn's, or edited at the top); a masked or linked `listen.conf`; an `sshConfigFile` that is relative or unclean (where v0.3.x wrote it is not known); one outside `sshd_config.d` or not `*.conf` (sshd never read it, so removing it gains nothing, and an Include of it would be refused by `sshd.Validate`); and an `sshConfigFile` of `sshd_config` itself, where v0.3.x wrote its drop-in over the main file: restoring a distribution's file there is not automated (§6, open for the maintainer). An `sshConfigFile` of `manage.conf`, `hardn.conf` or `00-hardn.conf` adds nothing (the first two are always looked at; the last is the target). Tested in a table: the stock host, v0.3.2, v0.3.2 upgraded to an unreleased build, the unreleased `-c` file, a custom drop-in, each `Left` case, and both Alpine generations.

### Planning (`PlanFor`, pure)

4. **The steps, in order:** write `00-hardn.conf` (`OpWriteDropIn`); remove each legacy drop-in (`OpRemove`); on Alpine, write `00-hardn.conf` and then `sshd_config` in the structure of Alpine's stock file (`OpRestoreMain`, one step, §2.12); remove `listen.conf` last (`OpRemoveSocketDropIn`). Each step has a `Note`, the printed note §3.17 asks for, saying what it does to which file and that a backup is kept; the caller adds where (`backup.Run.Dir`). Nothing to migrate is an empty plan, and `Desired` alone never makes one (the engine writes `00-hardn.conf` itself then). Tested per host shape, with goldens of every file written (`testdata/golden`).
5. **Login paths are kept; the effective configuration changes only as §2.6 (more key files read), §2.8 (listeners added for the socket) and §2.12 (sftp added on Alpine) say, and as `Desired` asks.** `00-hardn.conf` is `Desired` first, then the lines of the files it replaces (the legacy drop-ins, an existing `00-hardn.conf`, the generated Alpine `sshd_config`), in the order sshd reads them (`sshd.ReadOrder`):
   - a first-value keyword's line moves when it is the first line sshd reads for that keyword and `Desired` does not set it; otherwise it is dropped, with why (`Plan.Dropped`: "no effect: sshd reads … first", or "hardn's settings set …"). `00-hardn.conf` is read before every other drop-in and, in `IncludeFirst` mode, before the rest of `sshd_config`, so a line that won before still wins, and one that lost (to `50-cloud-init.conf`, say) is not promoted over the file that beat it. Tested: v0.3.2's `PasswordAuthentication no` stays behind `50-cloud-init.conf`'s `yes`;
   - an accumulating keyword's line (Port, ListenAddress, HostKey, HostCertificate, Allow/Deny Users/Groups, AcceptEnv) moves unless `00-hardn.conf` already has that line;
   - lines under a `Match` never move: a legacy file with a `Match` block is left (`Left`), and an existing `00-hardn.conf` with one is refused (`fs.ErrInvalid`).

   `Plan.Carried` lists the lines that moved.
6. **No key file stops being read (R8).** When the `AuthorizedKeysFile` line sshd reads first is in a file the migration replaces, or no line names one, `AuthorizedKeysFile` becomes one line naming every file `Desired`, the replaced files and the line sshd reads first name, or sshd's default from `Input.Before` (`.ssh/authorized_keys .ssh/authorized_keys2`) when no line names one. An unreleased build's bare `.ssh_%u` (V5: a file name where v0.3.x had a directory, and keys in `~/.ssh`, D7) adds `.ssh_%u/authorized_keys` and `.ssh/authorized_keys`. So a v0.3.2 host keeps `.ssh/authorized_keys .ssh_%u/authorized_keys`, and `Desired` can never narrow the list; dropping a path is a later, confirmed change. The union widens only across the replaced files, which is the R8 repair (v0.3.x and the unreleased builds named different files; origin/main wrote one line per path, of which sshd reads only the first). When the line sshd reads first is in a file the migration leaves (a site drop-in's `AuthorizedKeysFile none` beside an `AuthorizedKeysCommand`, say), the replaced files' lines had no effect: they are dropped with why, and `00-hardn.conf` has no `AuthorizedKeysFile` line, so that line stays first and no key file sshd ignored becomes read; with `Desired` setting one, its line also names that line's files. Tested: each case, with the effective value after `Apply`.
7. **`listen.conf` (v0.3.x).** On a socket host whose generator derives `ssh.socket`'s listeners from the sshd files (`SSHSocket`, `Generator` Yes) and with the stock first-line Include, its port moves into `00-hardn.conf` and the file is removed. On `ssh.service` and OpenRC hosts `ssh.socket` does not listen, so it had no effect and is removed. Otherwise it is left, with why: a socket host whose port lives in `ssh.socket.d` (Debian opted into the socket, or the generator masked: its `listen.conf` may be the administrator's own way of setting the port), a socket host where whether the generator runs is not established (`Generator` Unknown), an Unknown SSH mode, or no stock Include.
8. **The socket's listeners are kept (`Plan.Hold`).** `listen.conf`'s `ListenStream=<port>` is a dual-stack `[::]:<port>` where IPv6 is supported and `0.0.0.0:<port>` where it is not (§3); the plan holds `[::]:<port>`, both families, unless no listener `ssh.socket` has now is IPv6, and then `0.0.0.0:<port>`, so that no IPv6 listener the host may not bind is added (tested: an IPv4-only socket). On a socket host with the generator, every listener `ssh.socket` has now (`Input.Before.Listeners.Socket`) is held too, whenever the plan writes the files: the generator gives the socket the files' listeners at the next `daemon-reload`. That covers v0.3.x's missing `daemon-reload` (D9): until a reboot such a socket still listens on port 22, not on `listen.conf`'s port, and the plan keeps both (tested: `v032-ubuntu-unreloaded`). The socket's set must be read whole and must not be empty: `PlanFor` refuses (`ErrNotEstablished`) when it was not read, when `systemctl show -p Listen` printed a line hardn does not read (`sshd.Listeners.SocketComplete` false), or when it printed none, rather than hold nothing (tested: each). It also refuses when a held listener has to be added and a Port, ListenAddress or AddressFamily line is one hardn's model does not read (a host name, a service name). A held listener the files do not configure is added: as `ListenAddress <address>:<port>` lines when the files have a ListenAddress, otherwise as `Port <port>`. On such a host the socket's listeners are the ones that accept connections, and sshd's own set (`sshd -T`'s `listenaddress`) is configuration only (sshd uses the descriptors systemd passes, §3): so `Apply` keeps `Hold`, not sshd's set, and a port sshd's files name that the socket does not listen on is not kept. On a `listen.conf`-only host (no Port line, the socket on `listen.conf`'s 2230) the files then say `Port 2230` alone, and sshd's default 22, which nothing listened on, is not opened (tested: `listen-only-ubuntu`); 22 is kept only where the socket listens on it now (D9).
9. **No two listeners that cannot both be bound.** A ListenAddress line the plan moved or added is dropped (`Plan.Dropped`, with why) when the other ListenAddress lines already configure every listener it does: on an upgraded host, `manage.conf`'s `ListenAddress 0.0.0.0:2230` beside `hardn.conf`'s `Port 2230` and `ListenAddress 0.0.0.0`. Two sockets on one port of one family, at one address or one of them unspecified, cannot both be bound (§3), and the generator would hand both to `ssh.socket`. Lines of `Desired` and of the files the plan leaves are never dropped; an overlap that remains is refused by `Check`, and so by `Apply` (§2.15).
10. **`Plan.Keywords`** lists the keywords whose lines the steps write, move or remove (lower case, first word), with `port` when `listen.conf`'s port moves, and, on the Alpine restore, the keywords of every drop-in the new Include starts reading: `reload.Change.Keywords` for the reload that follows. On a socket host a migration of `listen.conf` is therefore a listener change (`daemon-reload` and a restart of `ssh.socket`); on Alpine a drop-in's `UsePAM`, `GSSAPIAuthentication` or `KerberosAuthentication` makes the reload refuse (`reload.ErrFlavour`) rather than signal a binary that may not be the one running (tested: a `UsePAM yes` drop-in).
11. **Refusals before anything is planned:** a `Desired` keyword that is not a plain word, a `Match` or `Include`, a directive with no argument, an argument with a line break or a NUL (`fs.ErrInvalid`); an unknown Include mode (`fs.ErrInvalid`); legacy drop-ins on a host whose first directive is not the stock Include (`ErrIncludeOther`: `00-hardn.conf` would not be read first, and [sshd-validate.md](sshd-validate.md) §6 leaves that mode to the maintainer). With no Include at all (an Alpine host upgraded from 3.18 or earlier), legacy drop-ins are removed with a note that sshd never read them. Arguments are written back quoted as sshd's `argv_split` reads them (tested: each form reads back as the same arguments).
12. **Alpine's generated `sshd_config` is restored only as an explicit step** (§3.17: "restore the distribution default structure only with an explicit plan step and backup"), on Alpine, in `IncludeNone` mode, without a `Match` block. The new file has the Include first, then the directives Alpine's stock file does not comment out (§3): `AuthorizedKeysFile .ssh/authorized_keys`, `AllowTcpForwarding no`, `GatewayPorts no`, `X11Forwarding no`, `Subsystem sftp internal-sftp` (left out when `00-hardn.conf` defines that subsystem: OpenSSH refuses a second definition; tested). Every line of the generated file goes to `00-hardn.conf`, which the Include reads first, so its values stay. Where the generated file does not set a stock line's keyword and the installed value (`Input.Before`'s `sshd -T`) differs from the stock one, `00-hardn.conf` keeps the installed value, so the stock line has no effect: neither generated file sets a forwarding keyword, so sshd's default `AllowTcpForwarding yes` stays (ProxyJump and VS Code Remote-SSH through the host keep working) rather than becoming Alpine's `no`, and the note says so; a generated file without `AuthorizedKeysFile` keeps sshd's default two files over the stock one (tested). A value to keep that `sshd -T` does not give is `ErrNotEstablished`. The stock lines therefore add only what the generated file lacked: sftp (V15). Whether a migrated Alpine host should take Alpine's forwarding defaults is the maintainer's call (§6); the migration does not make it. Once there is an Include, sshd also reads the other drop-ins in `sshd_config.d`; the note names them, and `Check`'s comparison refuses any that would narrow a login path (tested: a `MaxAuthTries 4` drop-in). Comments of the generated file are not kept. Off Alpine, or with an Include already, the file is left.

### Applying (`Apply`)

13. **Validated before anything exists, and checkable in a dry run.** `Check` runs `sshd.Validate` (`sshd -t`, `sshd -T`, one `-T -C` per `Match`) over the host with every step applied, compares the result with `Plan.Before` (§2.14, §2.15), and writes nothing but `Validate`'s copy in the run directory (tested: no other change). `Apply` runs `Check` first; then, before each step, it validates the host as it is with that step applied and compares again. A file is written or removed only after the state it leaves passed (tested: no write or removal of an sshd file without an `sshd -t` since the previous one; the Alpine step's two writes are validated together, since `00-hardn.conf` is read only once `sshd_config` has the Include). `listen.conf` is not sshd's and goes last, after every sshd state passed. The write comes before the removals, so every intermediate state configures at least what the final one does.
14. **Never fewer working login paths.** Every state is refused with a `*NarrowError` (`ErrFewerLoginPaths`), naming each keyword, when its `sshd -T` shows, against `Plan.Before`'s: a `yes` turned off among `PubkeyAuthentication`, `PasswordAuthentication`, `KbdInteractiveAuthentication`, `PermitEmptyPasswords`, `UsePAM`, `HostbasedAuthentication`, `GSSAPIAuthentication`, `KerberosAuthentication`; a lower `PermitRootLogin` (no < forced-commands-only < prohibit-password < yes); an `AllowUsers`/`AllowGroups` that newly restricts or no longer lists someone; a new `DenyUsers`/`DenyGroups` entry; a key file no longer in `AuthorizedKeysFile`; an `AuthenticationMethods` other than `any` that differs; any change to the algorithm lists, host keys, authorized-keys and principals commands and files, CA keys, revoked keys, `PubkeyAuthOptions`, `MaxAuthTries`, `ForceCommand` or `ChrootDirectory`; and a listener that accepts connections now no longer configured: `Hold`'s (both families for `[::]`), and sshd's own set (`Before.Listeners.SSHD`, where `[::]` is IPv6 only) except on a socket host with the generator, where the socket's set in `Hold` is the one that accepts them (§2.8). Widening is not a narrowing. Tested per rule: each authentication switch turned off, root lower and higher, users and groups no longer allowed or newly denied, a key file dropped and added, `AuthenticationMethods`, the ciphers, a host key, the authorized-keys command, `MaxAuthTries`, revoked keys, a CA, `ForceCommand`, listeners of both kinds, and the text of a `*NarrowError`. A `Before` without the values compared (`sshd -T` not read, a setting Unknown, a listener unread) is `ErrNotEstablished`. A narrowing that `Desired` asks for (`PasswordAuthentication no`) is refused here: it is the engine's change, after the migration, under confirm-or-revert (brief 2.3 step 6).
15. **No new overlapping listeners.** The final state is refused by `Check` (`ErrListenerOverlap`) when its `sshd -T` listeners have a pair §2.9 describes that `Before`'s do not (tested: a site drop-in's `ListenAddress 192.0.2.10:2230` beside the `0.0.0.0:2230` that `listen.conf`'s port needs).
16. **Backed up first, and as the plan read it.** After the whole-plan check and before the first change, every file a step writes or removes is backed up (`backup.Run.Backup`, `RollbackRequired`, so even with `enableBackups: false`, §3.16), `00-hardn.conf` too when absent (its rollback removes it). Each backup must then show the file as `PlanFor` read it (`Plan.Sources`: absent, or the same SHA-256); otherwise `ErrChanged`, naming the file, and nothing is written (tested for `manage.conf`, `listen.conf` and `00-hardn.conf` edited between plan and apply). The backup run directory then exists with its manifest, and restoring it changes nothing.
17. **Writes and removals** go through `host.WriteFileAtomicKeep` (an existing file keeps its mode and owner; a new `00-hardn.conf` is root's, `0644`) and the guarded `Remove` ([atomic.md](atomic.md) §2). `Apply` stops at the first error. `Report.Done` lists the steps carried out; an Alpine step that failed between its two writes is not in it, but its first write is in `Report.Backups` like every other, so `backup.Restore` of the run (under `context.WithoutCancel` after Ctrl-C) gives the host back as it was (tested: after every scenario, after a validation failure midway, and after an injected failure of a backup, the `00-hardn.conf` write, a removal, the `listen.conf` removal and the Alpine step's second write). A migrated configuration whose `sshd -T` lacks a compared value, and a plan whose files are not its `Sources`, are refused before anything is written (tested).
18. **Nothing is reloaded.** The running sshd, and `ssh.socket`, keep what they read until the caller's reload (`p2-reload`), and `Apply` changes no unit. A done context is refused before anything runs.
19. **The reload's input is the migration's (`Plan.Listening`, `Plan.Reload`).** `reload.PlanFor` needs `Change.Before` Known for a listener change, and on the hosts `Hold` exists for (D9, `listen.conf` only) `sshd.ReadEffective`'s listeners are not Known, because the socket and sshd's files disagree. The migration decides the set instead: `Plan.Listening` is the set configured to accept connections now (configuration, as every listener set is: [sshd-effective.md](sshd-effective.md) §2.5). On a socket host with the generator, when the plan writes the files, it is the socket's (`All` = `Before.Listeners.Socket`, which `Hold` keeps), Known when the socket's set was read whole and not empty (`PlanFor` refuses otherwise, §2.8), every `listenaddress` line of `sshd -T` was read, and detect shows `ssh.socket` active; their disagreement is resolved by holding the socket's set, so it is not required. Elsewhere it is `Before.Listeners` as `ReadEffective` gave it. `Plan.Reload(after)` is `reload.Change{Keywords: Plan.Keywords, Before: Plan.Listening, After: after's sshd listeners}`, with `after` from `Check` (at plan time) or `Report.After`. `Plan.SocketDropIns(d)` is `reload.ReadSocketDropIns`'s answer without the files the plan removes, so the reload planned before `Apply` does not refuse for `listen.conf` (`reload.ErrSocketDropIn`). Because `Listening.All` is the socket's set, not sshd's configured one, a port the migration adds (2230 on a D9 host) is in the reload's `Adds`, which `Execute` checks is free first (`reload.ErrInUse`). Tested: for every scenario, `reload.PlanFor` accepts `Plan.Reload` over `Check`'s result with `Plan.SocketDropIns` before `Apply`, and over `Report.After` with the drop-ins read again after it.

### `permitRootLogin` and saving (`pkg/config`)

20. **The YAML key takes `"no"`, `"prohibit-password"` or `"yes"`** (`config.RootLogin`), so a Proxmox VE host can say key-only (brief 2.5) once the SSH code applies it (§2.21). The old bool still works: `true`/`false` and YAML 1.1's spellings the bool field took (`on`, `Off`, `Yes`) read as `yes`/`no` and record a `config.Deprecation` (key, line, what was written, what to write instead); a bare `no`/`yes` is the string form, not deprecated. `Config.Deprecations()` returns them for the caller to show as warnings. **Nothing prints them on this branch**: printing is the caller's (`p3-output` or the slices'), not `LoadConfig`'s, because the legacy `SaveConfig` still writes the bool and would bring the warning back after the user fixed it. So §3.17's warning is owed (§6), and the example configuration and docs say the bool is deprecated without promising a warning. Any other value is the error the bool field gave, with the same text; every other key decodes and fails as before (tested).
21. **Legacy code never applies `prohibit-password` as `no`.** `PermitRootLogin`, the bool legacy code reads, is `true` exactly for `yes`, so the legacy SSH writers this binary still runs (`cmd/hardn`'s `ConfigureSSH`, through `FileSSHRepository`) would write `PermitRootLogin no` for `prohibit-password`. That is the direction that locks out: on a Proxmox VE host whose only key login is root's it ends it (R15). Before this unit the value was a YAML type error and hardn refused to run; the legacy loader (`LoadConfig`) still refuses it, now with `config.ErrRootLoginNotApplied`, behind `prohibitPasswordApplied` (false; flip to true once the SSH code applies `Config.RootLogin()`, p3-engine with p2-pve). The YAML decoding accepts it, so that code can read it (tested: the loader refuses it and loads the other values). The example configuration (`hardn.yml.example`, the embedded copy, `docs/configuration.md`) shows `permitRootLogin: "no"` and the values `"no"` and `"yes"` only, until the value is applied. The legacy `SaveConfig` encodes as before, the bool included, with one exception: a `prohibit-password` value is written as that string, since the bool would turn it into `no` (tested: the encoding is byte for byte yaml.v3's over the fields otherwise). *Since `next/legacy-rehome`* (decision 6 (a)): the refusal, `ErrRootLoginNotApplied` and `prohibitPasswordApplied` are deleted; a hardn.yml with `prohibit-password` loads and warns "isn't used".
22. **The canonical value is written only by `config.Save`** (§3.19): to the file the configuration was loaded from, `Config.Path()`, which `LoadConfig` records (the absolute path it read, or the default file it created); a `Config` not loaded from a file is refused (`config.ErrNotLoaded`), so no caller passes a path. It writes with `host.WriteFileAtomicKeep` (mode and owner kept; a new file `0644`), and `permitRootLogin` as its string (`"no"` and `"yes"` quoted, so YAML 1.1 readers do not take them for bools), so a deprecated bool becomes the value it meant. Comments in the file are lost; the caller says so before saving. *Amended by `next/s2-config-edit`* (the maintainer's decision of 2026-10-22, [config-edit.md](../engine/config-edit.md)): `Save` edits only the settings that changed, every comment kept but those of a list item it replaces or removes, with no warning; `permitRootLogin`'s string is written when its value changes, so a deprecated bool stays until then, and its warning (§6) is still owed. Nothing calls `Save` yet: replacing the 17 legacy `SaveConfig` call sites is the slices' work ([atomic.md](atomic.md) §7).

### Import rules

23. The package is under `pkg/host/sshd`, so depguard's `host-stdlib` (standard library and `pkg/host/...` only) and `sshd-through-host` (no `os`, `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` except `net/netip`, `plugin`) already cover its non-test files; no new rule was needed. Everything reaches the host through `host.System`. `pkg/host/sshd` gains a small exported read-order API for it (§5), in a new file, and `Listeners.SocketComplete`; the package imports `pkg/host/reload` for `Plan.Reload`'s types.

## 6. Not in this unit; inputs to later units

- **`p3-engine`:** the order, once per run before any other SSH change: `detect.Detect`; `sshd.ReadEffective` (with detect's SSH) as `Input.Before`; `Find` with the loaded `sshConfigFile`; `PlanFor`; `Check` with a run directory that is root's (`/run/hardn/<run-id>`, [sshd-validate.md](sshd-validate.md) §6) and, on Alpine, `reload.OpenRCFlavour`'s binary; `reload.PlanFor(reload.Input{SSH, Change: plan.Reload(checked), DropIns: plan.SocketDropIns(reload.ReadSocketDropIns(...))})`. All of that is plan time: show the plan, its notes, `Dropped`, and any refusal of `Check` or the reload (a dry run stops here). Then `Apply` with the same options and the run's backup store, and `reload.Execute` of the plan made from `plan.Reload(report.After)` with the drop-ins read again. `Plan.Listening` is the reload's `Before` (§2.19): the engine does not decide whether the listeners are Known. Any error after a step ran means restoring the run's backups and the reload with `Rollback`, under `context.WithoutCancel`. `Desired` is the engine's own settings for `00-hardn.conf`; a narrowing among them comes after the migration, as its own confirmed change.
- **`p3-engine`, every later write of `00-hardn.conf`:** after a migration `00-hardn.conf` holds the lines moved from the legacy files, under `# From …` headers, notably the `AuthorizedKeysFile` union that keeps `~/.ssh_<user>` keys working (R8), the listeners held for the socket, and the values kept on Alpine. From the second run `Find` and `PlanFor` give an empty plan, so every write of `00-hardn.conf` is the engine's: the moved lines are part of hardn's file from then on, and the engine must edit it line by line, keeping every keyword it does not set, never regenerate it from the configuration alone (that drops them; the login-path comparison or confirm-or-revert would then refuse or revert the change, but not silently keep the keys). The comparison it needs for `Risk()`, and `p2-revert` for its lockout-risk scope, is this unit's `narrowings` (unexported: its second consumer's needs are not designed yet; moving it to `pkg/host/sshd` is that unit's call).
- **`p2-revert`:** on a socket host the `listen.conf` migration is a listener change, so it is a lockout-risk change under confirm-or-revert: journal the backup run's entries (`Report.Backups`' `Seq`) and the reload; confirm from a new connection to a listener the reload's plan adds (`reload.Plan.Adds`, 2230 on a D9 host), or, with none, to one of `Plan.Listening.All` after the restart. **Superseded in part by `next/p2-vmtest`** ([README.md](README.md), `p3-engine`): `Apply` backs up and writes with no point between them, so `Report.Backups` can be journalled only after the files changed, not write-ahead (revert.md §7 item 1); the driver journals backups of `Plan.Sources` it takes first. **Closed by `next/p3-steps`** ([steps.md](../engine/steps.md) §2.7), by the engine's backups rather than a hook: `Options.Taken` names backups the caller took, and `Apply` takes none of its own, refuses a file a step changes that `Taken` lacks (`fs.ErrInvalid`) and checks each entry against the plan (`ErrChanged`). The engine backs up `Plan.Sources` and journals them before `Apply` runs, so the journal names every backup before any file changes, and the run holds one copy of each. A hook would need a journal write inside a change, which the engine does not make (it journals a change's undo before it runs and what ran after). Without `Taken`, `Apply` is as it was; §5's API list predates the field. The rollback of the `listen.conf` migration on a socket host, which `reload.PlanFor` refused once `listen.conf` was restored (`reload.ErrSocketDropIn`), is **fixed by `next/p2-revert-plans`** ([revert-plans.md](revert-plans.md) §2.8 to §2.10): journal the reload with `After` = `Plan.Listening.All` (the socket's listeners before the migration, §2.19) and `socketDropIns` = the paths of the plan's `OpRemoveSocketDropIn` steps; the rollback then plans it with `reload.Change.RestoredDropIns`, so `daemon-reload` gives the socket `listen.conf`'s port back and the socket is restarted only once it is configured for those listeners. Plan ufw over `Plan.Listening` too. **Not where the rollback could not finish**: that reload is `Plan.Rollback()` (`Keywords`, `After` = `Plan.Listening.All`, and on a socket host `RestoredDropIns` = the `OpRemoveSocketDropIn` paths), and `Plan.CheckRollback(drops)` plans it before anything changes, over the drop-ins as read then (what the restore gives back): where `listen.conf`'s lines do not give exactly the socket's listeners now (`reload.ErrRestoredListeners`: D9, `listen.conf` never in effect and the socket still on 22; or a socket configured for 22 beside `listen.conf`'s 2230), the rollback's `daemon-reload` would move the socket to `listen.conf`'s port alone and the rollback stop unfinished, so the migration is refused. And where `systemctl show -p Listen` is not what is bound (a `daemon-reload` since the socket was restarted: configured 2230, bound 22), the hold and the rollback, both read from configuration, would close the bound port for good: `reload.CheckInEffect` refuses it, with the applying session's port. `p2drive` runs both before `Arm`, and the engine must, unless the maintainer decides otherwise for D9 ([P-39](../refactor/proposals.md#p-39), [revert-plans.md](revert-plans.md) §2.10, §6).
- **`p2-pve`:** pass `PermitRootLogin prohibit-password` in `Desired`; a migrated `PermitRootLogin no` from a v0.3.2 `manage.conf` is then replaced, which `Apply` accepts as a widening. With the engine applying `Config.RootLogin()`, flip `config.prohibitPasswordApplied` to true, and only then document `prohibit-password` in the example configuration (§2.21). *Since `next/legacy-rehome`* (decision 6 (a)): the refusal, `ErrRootLoginNotApplied` and `prohibitPasswordApplied` are deleted; a hardn.yml with `prohibit-password` loads and warns "isn't used".
- **`p3-output` and the slices (owed to §3.17):** show `Config.Deprecations()` as warnings, with `Deprecation.String()`'s text or a registry code: nothing prints §3.17's deprecation warning yet (§2.20), so that part of the approved decision is open until `p3-output` does; switch the legacy `SaveConfig` callers to `config.Save` (which also stops the bool coming back); map `ErrFewerLoginPaths`, `ErrListenerOverlap`, `ErrChanged`, `ErrIncludeOther`, `ErrNotEstablished`, `config.ErrRootLoginNotApplied` (deleted since `next/legacy-rehome`, decision 6 (a)) and `config.ErrNotLoaded` to registry codes; print each `Op.Note` with the backup directory.
- **Open for the maintainer:** (a) a v0.3.x `sshConfigFile` of `sshd_config` itself (its drop-in written over the main file) is reported, not migrated: restoring the distribution's file there is a design choice per distribution; (b) a `manage.conf` or `hardn.conf` edited by hand above hardn's first lines is not recognised and stays (a backup-and-remove rule for "hardn's file, edited" would need its own approval); (c) on a socket host the migration adds `[::]` beside `0.0.0.0` on `listen.conf`'s port (the dual-stack socket `listen.conf` gave), and on a D9 host keeps port 22 beside it, because the socket listens on 22 until the reload; closing either is a later confirmed change, which the user may not expect from a migration; (d) §3.17 approved restoring Alpine's "default structure": the restore keeps the installed values where Alpine's stock lines differ (`AllowTcpForwarding yes` rather than `no`, §2.12), so forwarding still works after the migration; taking Alpine's forwarding defaults instead is a narrowing for anyone who forwards through the host, and is the maintainer's call, not the migration's.
- **Not here:** writing `00-hardn.conf` for anything but the migration; the reload; the confirm window; key files themselves (moving keys out of `~/.ssh_<user>` is not needed while `AuthorizedKeysFile` names it); legacy `disableRoot` (§3.11, an alias of `disableRootSSH`).
- **Size:** about 2,000 lines of non-test Go (much of it doc comments) and 2,000 of tests, against the plan's guideline of about 500: five artifact kinds over three init modes, the listener model the socket hold and the duplicate check need, the login-path comparison, the dry-run check and the reload's input, the config key and its save path, and a test per host shape and per failure path.
