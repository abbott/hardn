# Plan rollbacks and the listen.conf rollback (`pkg/host/revert/plans`, `reload.Change.RestoredDropIns`)

> **Unit:** refactor plan Phase 2, `next/p2-revert-plans`: the two gaps `next/p2-vmtest` found before anything runs on a VM ([README.md](README.md) open items; [revert.md](revert.md) §7; [pve.md](pve.md) §6; [vmtest.md](vmtest.md) §2.10, §2.11). Decisions it implements: brief §2 "Confirm-or-revert"; [revert.md](revert.md) §7's decision that a unit with its own checked rollback is journalled as one `plan` step; §3.17 (approved 2026-10-17) for the `listen.conf` migration whose rollback this fixes. V-numbers: V6 and V18 (no rollback), V12 and V24 with D9 (`ssh.socket` and v0.3.x's `listen.conf`), risk R8 ([side-effects.md](../refactor/phase0/side-effects.md)).
> **Status:** built and tested on macOS against the recording fake (`hostfake`) only. Nothing has run on Linux: every rollback here, the `listen.conf` one on Ubuntu above all, is "written, not run (gate 5)" (§4).

Two things are fixed. First, `cmd/hardn`'s registry of plan rollbacks was empty after the stacks merged, so `revert.Record` refused a `plan` step of every unit (`revert.ErrNoPlanRollback`) and nothing journalled could be undone by `hardn rollback <id>` or the timer for root's keys on Proxmox VE, sudoers, DNS or Alpine's updates. `plans.Registry()` now registers the four, and each rollback re-checks its plan, decoded strictly from the journal, with the unit's own guard before it acts as root. Second, the rollback of a `listen.conf` migration on an `ssh.socket` host restored `listen.conf` and then stopped, because `reload.PlanFor` refuses a socket drop-in with `ListenStream` (`reload.ErrSocketDropIn`); a rollback that names the drop-in as one it restored now plans the socket's reload with it. `p2drive` journals its sudoers change and applies the migration on socket hosts, except where `listen.conf` never took effect (D9).

## 1. Why

A change journalled as a `plan` step (brief 2.4; [revert.md](revert.md) §7) is undone only by its unit's rollback, registered by name: with none, the step is refused before it is written, so the change could not be journalled at all and a failure or the timer could not undo it. And a rollback that leaves the socket on the migrated files after restoring `listen.conf` is a rollback that never finishes: only `Abandon` ([P-35](../refactor/proposals.md#p-35)) clears it, leaving the host half restored. Brief §3 principle 1: never lock the user out; a change that cannot be undone is not applied.

## 2. Guarantees

### The registry (`pkg/host/revert/plans`)

1. **Four units, one name each, stable** (a journal written by one hardn is rolled back by the next): `pve-keys` (`pve.KeysUnit`, `pve.RollbackKeys`), `sudoers` (`sudoers.Rollback`), `dns` (`dns.Rollback`) and `alpine-updates` (`alpine.Rollback`). `plans.Registry()` returns them as `revert.Options.Plans`; `cmd/hardn`'s `revertPlans` is that registry, which `hardn rollback <id>` passes to `revert.Rollback`, and `p2drive` passes the same one to `Arm`, `Record` and its in-process `Rollback`. Tested: `TestRegistry`, `TestRevertPlansRegistered`.
2. **Decoded strictly from the journal.** A registered rollback reads the step's `plan` as one JSON document into the unit's plan type with unknown fields refused (`json.Decoder.DisallowUnknownFields`, §3), as [revert.md](revert.md) §2.2 refuses them in the journal itself: a field this version does not know may be one the rollback must act on. Data after the document, another type, a field of the wrong type: `plans.ErrPlan`. Tested: `TestDecode`, and an unknown field per unit in `TestRoundTrip`.
3. **Checked again by the unit's own guard before anything is read or written**, then the unit's rollback runs under `revert.Rollback`'s context (already without cancellation, [revert.md](revert.md) §2.17):
   - `pve-keys`: `KeysPlan.Check` (new, in `pkg/host/pve`): `Before` must be the SHA-256 of `Old`, and the edit of `Old` by `Added` and `Removed` must give `New`, `Added` and `Removed` again, under `PlanKeys`' line guards (`ErrBadKey`, and `ErrClusterKey` for an edit that leaves no key); otherwise `ErrPlanMismatch`, as `ApplyKeys` refuses a plan that does not follow. This matters because `UndoKeys` removes every key `Added` names: an `Added` edited to name root@web-01's own key would have removed it. `RollbackKeys` now runs `Check` first too. The node's own key and the cluster's nodes are not in the plan, so the guard on removing them is not rechecked here (`ApplyKeys` rechecks it on the keys as they are).
   - `sudoers`: `Plan.Check` (new, in `pkg/host/sudoers`), which `sudoers.Rollback` now runs first as well: the tool is sudo or doas; `Main` is `""`, `/etc/sudoers` or `/etc/sudoers-rs` (sudo), `""` (doas); every change is to one of hardn's own per-user files in the tool's drop-in directory (`hardn-grant-<stem>`, `hardn-env-<stem>`, `hardn-<stem>.conf`, [sudoers.md](sudoers.md) §2.2), once; its `Old` was read from that path, with no data for a file that did not exist; its mode is the tool's (`0440`, `0640`); a removal has no content and removes a file that existed; a write starts with hardn's header. With `restore`'s own rule (a file is put back only while it holds what the plan wrote), a journal edited by hand can no longer make the rollback write `/etc/sudoers` or any file but hardn's.
   - `dns`: `Plan.Check`, the existing `valid` exported: the plan must be what `PlanDNS` makes from its `From` and `Want`, so the bytes it writes back (`From`'s) re-derive the steps it undoes ([dns.md](dns.md) §2).
   - `alpine-updates`: `Plan.Check`, the existing `valid` exported: the steps must be `PlanUpdates`' from `From`, and `From.LegacyFile`, which the rollback writes back into `/etc/periodic/daily`, must be hardn's file, mode and owner included ([alpine.md](alpine.md) §2.7).
4. **A refused plan is never journalled.** `plans.PVEKeys`, `Sudoers`, `DNS` and `Alpine` make the `revert.Step` (`Op: plan`, the unit's name, the plan as JSON, a line for the log): each checks the plan, encodes it, and decodes and checks the encoding as the rollback will, so a plan that loses a field its rollback needs on its way through `encoding/json` is refused then, before the step it covers runs (`ErrPlan`, wrapping the unit's error). Tested: `TestStepRefuses`.
5. **A tampered entry is refused, not half undone.** For each unit, `TestRoundTrip` journals the step over the fake (`revert.Arm`, `Record`: `pending.json`), applies the unit's change, and rolls it back through the registry from the journal alone: the host is as it was and the journal gone. Then, from a fresh host each time, it edits the journalled plan as a hand edit would (the sudoers change naming `/etc/sudoers`, or bob's file as its old state; other bytes for DNS to write back, other nameservers; a script of its own for Alpine to write back, the legacy file `0777`, a step Alpine did not plan; root@web-01's key in `Added`, `Old` changed without `Before`; an unknown field in each): every one is refused with `ErrPlan`, the rollback ends `revert.ErrIncomplete`, and the refused step neither ran a command nor wrote anything outside `/var/lib/hardn`. The rollback stays incomplete, so the next `hardn rollback <id>` tries again; one that can never pass is given up with `Abandon` ([P-35](../refactor/proposals.md#p-35)) or by moving `rollback.json` aside, as [revert.md](revert.md) §2.16 says. With the registry's strict decoding and its checks removed (an overlay probe), every tampered case fails the test: the unknown fields are then accepted, and the other edits are refused only by the units' own rollbacks, without `ErrPlan`.
6. **These checks are against mistakes and edits, not a security boundary**: the journal is root's alone ([revert.md](revert.md) §2.3), and whoever can write it is root. They keep a damaged or hand-edited entry from making root's rollback act outside what the unit planned.
7. **Through `host.System`.** The package is under `pkg/host/revert`, so depguard's `revert-through-host` (no `os`, `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` but `net/netip`, `plugin`) and `host-stdlib` already cover it; no new rule. Probed in a scratch copy outside the repository: an `os` import in `plans.go` fails lint with `revert-through-host`.

### The rollback of a `listen.conf` migration on `ssh.socket`

8. **The fix is at the reload layer, with the journal naming what it restored** (the two options were the reload's `Rollback` mode, or a journal shape of the migration's own). `reload.Change` gains `RestoredDropIns`: for a `Rollback`, the `ssh.socket` drop-ins the rollback has put back that the change had removed. On a socket host `PlanFor` then does not refuse their `ListenStream` lines (`ErrSocketDropIn`), and plans what a listener rollback plans there: `systemctl daemon-reload`, the socket's configuration (`systemctl show -p Listen ssh.socket`) checked against `After`, `systemctl restart ssh.socket` (started whatever its state, [reload.md](reload.md) §2.6a), then `ss`. Why this layer: the hazard `ErrSocketDropIn` guards against (a drop-in the generator's listeners do not reach, so the restart binds where hardn did not plan) is checked there already, by the check after `daemon-reload` that stops the restart unless the socket is configured for every listener of `After` ([reload.md](reload.md) §2.4). What a rollback needs is a true `After`: the listeners the socket had before the change, which the migration knows (`migrate.Plan.Listening.All`, the socket's set on such a host, [sshd-migrate.md](sshd-migrate.md) §2.19). A journal of `OpRun` steps (`daemon-reload`, `restart ssh.socket`) would have skipped both checks, and a migration-specific reload kind would have duplicated `PlanFor`'s socket plan.
9. **Only for what the rollback restored.** The journal's `reload` entry gains `socketDropIns` (`revert.Reload.SocketDropIns`), which `revert`'s rollback passes as `RestoredDropIns`; `Journal.Check` refuses one that is not a clean absolute `*.conf` path in an `ssh.socket.d` directory, a repeat, or one on a reload of no listener keyword (`ErrJournal`, `TestJournalCheck`). Every other refusal stays: a forward change with `listen.conf` in place is `ErrSocketDropIn`; `RestoredDropIns` on a forward change is `fs.ErrInvalid`; a rollback whose journal does not name the drop-in, another drop-in with `ListenStream` beside it, and a restored drop-in named as the generator's (`addresses.conf`) are `ErrSocketDropIn`; a generator that is not Yes is `ErrNoGenerator` (`TestPlanForRefuses`). The regression test, `TestRollbackRestoresListenConf`, rolls back a migrated Ubuntu host: `listen.conf` and `00-hardn.conf`'s absence restored, then `daemon-reload`, the socket checked for `[::]:2230`, `restart ssh.socket`, `ss`, the journal cleared; the same journal without `socketDropIns` still stops at `ErrSocketDropIn` with nothing run after the restore, as `next/p2-vmtest`'s probe found.
10. **Not where `listen.conf` never took effect (D9).** v0.3.x wrote `listen.conf` without a `daemon-reload` (D9, §3), so until a reboot the socket may listen elsewhere (port 22) than `listen.conf` says (2230). The migration holds both ([sshd-migrate.md](sshd-migrate.md) §2.8), but its rollback restores `listen.conf`, whose `daemon-reload` would move the socket to 2230 alone, off the port the user connected on; the check after `daemon-reload` would then refuse the restart, by which time systemd may already have dropped the 22 descriptor (§3, [I]). So `p2drive` refuses `migrate --apply` on a socket host when the plan removes `listen.conf` and a listener the migration holds (`Plan.Hold`) is not one the socket listens on now (`Plan.Listening.All`): the D9 shape (`TestRefusedBeforeArm`). The engine needs the same check, or a decision (§6).

### `p2drive`

11. **The sudoers change is journalled** ([vmtest.md](vmtest.md) §2.10): `plans.Sudoers(plan)` is the one inverse step, recorded before the backups and `sudoers.Apply`. A plan with a lockout-risk change (a grant removed, or one that asks for a password: `sudoers.RiskLockout`, [sudoers.md](sudoers.md) §6) is a lockout-risk change under confirm-or-revert, with the timer, the session and `--timeout`/`--hardn` like the SSH commands, ended by `MarkApplied`; any other is journalled without a timer and cleared by `revert.Done` once applied. A failure after `Arm` rolls it back at once (`ReasonFailed`), with signals held; when `Apply` refused before it wrote anything (a configuration `visudo -c` already rejects, a file changed since `Read`, Ctrl-C), the plan step leaves the journal first, since its rollback would fail on the same cause and stay unfinished, and the rollback only ends the change. Tested: `TestSudoers` (the grant journalled before the backup and the write and cleared; `--grant none` armed and applied, then the timer's rollback through the registry putting the grant back), `TestSudoersRollsBack` (`visudo -c` refusing the installed grant: `Apply` restores, the change is rolled back and the journal cleared; `visudo -c` refusing every time: refused before any write, rolled back and cleared, which fails with the step kept).
12. **`migrate --apply` on a socket host** carries the migration out as on Debian, with the reload journalled with `After` = `Plan.Listening.All` and `socketDropIns` = the drop-ins the plan removes, and ufw planned over `Plan.Listening` (the listeners that accept connections now; sshd's and the socket's sets disagree on such a host, so `ReadEffective`'s may not be Known, [sshd-migrate.md](sshd-migrate.md) §2.19). Tested: `TestMigrateSocket` (Ubuntu with v0.3.2's files, rebooted since: applied, journal as described; the values check failing after the restart: `listen.conf` and `manage.conf` back, `00-hardn.conf` gone, then `daemon-reload`, the socket's check and its restart on `[::]:2230`, the journal cleared). The fake's `daemon-reload` and boot model `listen.conf`'s reset of the generator's listeners to its port.

## 4. Written, not run (gate 5)

Nothing here has run on Linux or as root. On the VMs of [vmtest.md](vmtest.md):

- **the `listen.conf` rollback on Ubuntu 26.04** (the v0.3.2-hardened image, [vmtest.md](vmtest.md) §4.8): `migrate --apply` not confirmed, so the timer's `hardn rollback <id>` restores `listen.conf` and `manage.conf`, removes `00-hardn.conf`, runs `daemon-reload`, finds `systemctl show -p Listen ssh.socket` naming `[::]:2230`, restarts `ssh.socket`, and `ss` shows 2230 bound; key login on 2230 with the legacy key file afterwards; whether the socket then holds a dual-stack `*:2230` as before the migration;
- **the D9 refusal** on the image before its reboot ([vmtest.md](vmtest.md) §4.8), and what `systemctl show -p Listen` shows on a host where `daemon-reload` ran after v0.3.x but `ssh.socket` was not restarted (configured 2230, bound 22): neither the D9 check nor the migration's hold, both of which read configuration, sees that state **[I]**;
- **the sudoers rollback by the timer**: `--grant none` not confirmed, then `hardn rollback <id>` from the systemd timer (sudo, sudo-rs) and the OpenRC sleeper (doas) putting the grant back and `visudo -c`/`doas -C` passing ([vmtest.md](vmtest.md) §4.4 step 13, §4.6), and `--grant password` confirmed from a new session where sudo asks the password (§4.4 step 14);
- **the DNS, Alpine and Proxmox VE keys rollbacks** from a journal, as root: no `p2drive` command makes those changes yet (vmtest.md §2, "What the driver does not cover"), so they are run by hand or by a later driver revision; until then [dns.md](dns.md) §4, [alpine.md](alpine.md) §4 and [pve.md](pve.md) §4 item 5 stay open for the rollback as for the apply.

## 5. API

```go
package plans // pkg/host/revert/plans (new)

const UnitPVEKeys = pve.KeysUnit /* "pve-keys" */; const UnitSudoers, UnitDNS, UnitAlpine = "sudoers", "dns", "alpine-updates"
var ErrPlan error
func Registry() map[string]revert.PlanRollback // revert.Options.Plans; a new map each call
func PVEKeys(p pve.KeysPlan, why string) (revert.Step, error)
func Sudoers(p sudoers.Plan, why string) (revert.Step, error)
func DNS(p dns.Plan, why string) (revert.Step, error)
func Alpine(p alpine.Plan, why string) (revert.Step, error)

package pve     // added: func (KeysPlan) Check() error; RollbackKeys runs it first
package sudoers // added: func (Plan) Check() error; Rollback runs it first (refused: ErrNotRestored and fs.ErrInvalid)
package dns     // added: func (Plan) Check() error (the guard Apply and Rollback run)
package alpine  // added: func (Plan) Check() error (the guard Apply and Rollback run)

package reload  // Change gains RestoredDropIns []string (Rollback only)
package revert  // Reload gains SocketDropIns []string `json:"socketDropIns,omitempty"`; schemaVersion stays 1
```

`schemaVersion` stays 1: the field is optional, and a hardn that does not know it refuses a journal that has it (unknown fields, [revert.md](revert.md) §2.2), which is the safe way round. The `Check` methods and `RestoredDropIns` are added to the pages' units by this one; their own API lists ([pve.md](pve.md) §5, [sudoers.md](sudoers.md) §5, [dns.md](dns.md) §5, [alpine.md](alpine.md) §5, [reload.md](reload.md) §5) predate it, except where this unit was asked to update them.

## 6. Not in this unit; inputs to later units

- **`p3-engine`:** pass `plans.Registry()` in `Options.Plans` to `Arm`, `Record` and `Rollback`, and journal each unit's change with its step function, before the unit's apply. **The D9 check** (§2.10) is the engine's to make before a `listen.conf` migration on a socket host, unless the maintainer decides otherwise: [P-XX-revert-plans](../refactor/proposals.md#p-xx-revert-plans) sets out refusing it until the socket listens where `listen.conf` says, a rollback that leaves the socket on the migration's listeners, and a rollback that holds them in a drop-in of hardn's; this unit refuses. **After an apply refused before it wrote anything**, for every unit, the engine drops the plan step from the journal (`Record` without it) before it ends or rolls back the change, as `p2drive` does for sudoers (§2.11): the inverse is not needed, DNS's and Alpine's would undo the same change made by others (their rule that `Rollback` is for a plan whose `Apply` returned nil, [dns.md](dns.md) §6, [alpine.md](alpine.md) §6), Proxmox VE's reverses the edit, not the write ([pve.md](pve.md) §2.12), and sudoers' would fail on the refusal's cause and stay unfinished. After an apply that wrote and failed, DNS and Alpine have undone their own steps unless they return `ErrNotRestored`, when the journal's rollback tries again; sudoers' and Proxmox VE's rollbacks act only where their own writes are, so they run in any case. A step whose apply never finished (hardn died) is rolled back as journalled.
- **`p3-output`:** a registry code for `plans.ErrPlan`.
- **A later driver revision, or the slices:** `p2drive` commands for DNS, Alpine's updates and Proxmox VE's keys, so that gate 5 runs their registered rollbacks (§4).
- **For the maintainer:** [P-XX-revert-plans](../refactor/proposals.md#p-xx-revert-plans) (D9, above; numbered at the merge). [P-35](../refactor/proposals.md#p-35) (giving up a rollback) gains a case: a journal entry its unit refuses keeps the rollback incomplete until it is abandoned.
- **Size:** about 490 added lines of non-test Go (the registry about 150, the four guards about 100, reload and the journal about 50, `p2drive` about 190) and about 950 of tests, against the plan's guideline of about 500 changed lines: four units' round trips and tampered entries need a fake host each, and the driver's sudoers and socket-migration paths their own scenarios.
