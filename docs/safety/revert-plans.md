# Plan rollbacks and the listen.conf rollback (`pkg/host/revert/plans`, `reload.Change.RestoredDropIns`)

> **Unit:** refactor plan Phase 2, `next/p2-revert-plans`: the two gaps `next/p2-vmtest` found before anything runs on a VM ([README.md](README.md) open items; [revert.md](revert.md) §7; [pve.md](pve.md) §6; [vmtest.md](vmtest.md) §2.10, §2.11). Decisions it implements: brief §2 "Confirm-or-revert"; [revert.md](revert.md) §7's decision that a unit with its own checked rollback is journalled as one `plan` step; §3.17 (approved 2026-10-17) for the `listen.conf` migration whose rollback this fixes. V-numbers: V6 and V18 (no rollback), V12 and V24 with D9 (`ssh.socket` and v0.3.x's `listen.conf`), risk R8 ([side-effects.md](../refactor/phase0/side-effects.md)).
> **Status:** built and tested on macOS against the recording fake (`hostfake`) only. Nothing has run on Linux: every rollback here, the `listen.conf` one on Ubuntu above all, is "written, not run (gate 5)" (§4).

Two things are fixed. First, `cmd/hardn`'s registry of plan rollbacks was empty after the stacks merged, so `revert.Record` refused a `plan` step of every unit (`revert.ErrNoPlanRollback`) and nothing journalled could be undone by `hardn rollback <id>` or the timer for root's keys on Proxmox VE, sudoers, DNS or Alpine's updates. `plans.Registry()` now registers the four, and each rollback re-checks its plan, decoded strictly from the journal, with the unit's own guard before it acts as root. Second, the rollback of a `listen.conf` migration on an `ssh.socket` host restored `listen.conf` and then stopped, because `reload.PlanFor` refuses a socket drop-in with `ListenStream` (`reload.ErrSocketDropIn`); a rollback that names the drop-in as one it restored now plans the socket's reload with it. `p2drive` journals its sudoers change and applies the migration on socket hosts, except where its rollback could not finish (`listen.conf` never in effect, D9, among them) or what is configured is not what is bound.

## 1. Why

A change journalled as a `plan` step (brief 2.4; [revert.md](revert.md) §7) is undone only by its unit's rollback, registered by name: with none, the step is refused before it is written, so the change could not be journalled at all and a failure or the timer could not undo it. And a rollback that leaves the socket on the migrated files after restoring `listen.conf` is a rollback that never finishes: only `Abandon` ([P-35](../refactor/proposals.md#p-35)) clears it, leaving the host half restored. Brief §3 principle 1: never lock the user out; a change that cannot be undone is not applied.

## 2. Guarantees

### The registry (`pkg/host/revert/plans`)

1. **Four units, one name each, stable** (a journal written by one hardn is rolled back by the next): `pve-keys` (`pve.KeysUnit`, `pve.RollbackKeys`), `sudoers` (`sudoers.Rollback`), `dns` (`dns.Rollback`) and `alpine-updates` (`alpine.Rollback`). Since Rocky/AlmaLinux unit 3a there are six: `firewalld-ports` (`firewalld.Rollback`) and `selinux-ports` (`selinux.RollbackPorts`), a port change's ([el-ports.md](../engine/el-ports.md) §1.4); each takes away only a port or label that is there, and checks only that zones and ports are well formed. `plans.Registry()` returns them as `revert.Options.Plans`; `cmd/hardn`'s `revertPlans` is that registry, which `hardn rollback <id>` passes to `revert.Rollback`, and `p2drive` passes the same one to `Arm`, `Record` and its in-process `Rollback`. Tested: `TestRegistry`, `TestRevertPlansRegistered`.
2. **Decoded strictly from the journal.** A registered rollback reads the step's `plan` as one JSON document into the unit's plan type with unknown fields refused (`json.Decoder.DisallowUnknownFields`, §3), as [revert.md](revert.md) §2.2 refuses them in the journal itself: a field this version does not know may be one the rollback must act on. Data after the document (a stray `]` or `}` included), another type, a field of the wrong type: `plans.ErrPlan`. Tested: `TestDecode`, and an unknown field per unit in `TestRoundTrip`.
3. **Checked again by the unit's own guard before anything is read or written**, then the unit's rollback runs under `revert.Rollback`'s context (already without cancellation, [revert.md](revert.md) §2.17):
   - `pve-keys`: `KeysPlan.Check` (new, in `pkg/host/pve`): `Before` must be the SHA-256 of `Old`, and the edit of `Old` by `Added` and `Removed` must give `New`, `Added` and `Removed` again, under `PlanKeys`' line guards (`ErrBadKey`, and `ErrClusterKey` for an edit that leaves no key); otherwise `ErrPlanMismatch`, as `ApplyKeys` refuses a plan that does not follow. This matters because `UndoKeys` removes every key `Added` names: an `Added` edited to name root@web-01's own key would have removed it. `RollbackKeys` now runs `Check` first too. `Check` refuses only an edit inconsistent with the rest of the plan: the node's own key and the cluster's nodes are not in the plan, so an edit that recomputes `Old`, `Before` and `New` around such an `Added` passes it. So the node-key guard now holds in both directions in `pkg/host/pve` itself (fixed in review): `UndoKeys` never removes a cluster node's root key (`ErrClusterKey`, nothing written; `TestPVENodeKeyInAdded`, where the rollback stays incomplete and the key stays), and `PlanKeys` refuses to add one (`TestPlanKeys`), so no plan it makes has an undo that guard refuses.
   - `sudoers`: `Plan.Check` (new, in `pkg/host/sudoers`), which `sudoers.Rollback` now runs first as well: the tool is sudo or doas; `Main` is `""`, `/etc/sudoers` or `/etc/sudoers-rs` (sudo), `""` (doas); every change is to one of hardn's own per-user files in the tool's drop-in directory (`hardn-grant-<stem>`, `hardn-env-<stem>`, `zz-hardn-<stem>.conf`, [sudoers.md](sudoers.md) §2.2), once; its `Old` was read from that path, with no data for a file that did not exist; an `Old` that existed is a file only root owns and can write (owner and group 0, no group or other write bit, no bit beyond the permissions), since the rollback writes it back with that mode and owner (fixed in review); its mode is the tool's (`0440`, `0640`); a removal has no content and removes a file that existed; a write starts with hardn's header. With `restore`'s own rule (a file is put back only while it holds what the plan wrote), a journal edited by hand can no longer make the rollback write `/etc/sudoers` or any file but hardn's, nor write one back others can write or own. **`Old`'s content is not checked**: `PlanFor` takes any content at hardn's names (on doas, an administrator's `hardn-local.conf` is user `local`'s file, [sudoers.md](sudoers.md) §2.5), so it cannot be re-derived, and a rollback writes it back as journalled; a syntax error in it is caught only after the write, by `visudo -c`/`doas -C` (`StageRestored`), which leaves the rollback incomplete with the broken file in place.
   - `dns`: `Plan.Check`, the existing `valid` exported: the plan must be what `PlanDNS` makes from its `From` and `Want`, so the bytes it writes back (`From`'s) re-derive the steps it undoes ([dns.md](dns.md) §2).
   - `alpine-updates`: `Plan.Check`, the existing `valid` exported: the steps must be `PlanUpdates`' from `From`, and `From.LegacyFile`, which the rollback writes back into `/etc/periodic/daily`, must be hardn's file, mode and owner included ([alpine.md](alpine.md) §2.7).
4. **A refused plan is never journalled.** `plans.PVEKeys`, `Sudoers`, `DNS` and `Alpine` make the `revert.Step` (`Op: plan`, the unit's name, the plan as JSON, a line for the log): each checks the plan, encodes it, and decodes and checks the encoding as the rollback will, so a plan that loses a field its rollback needs on its way through `encoding/json` is refused then, before the step it covers runs (`ErrPlan`, wrapping the unit's error). Tested: `TestStepRefuses`.
5. **A tampered entry is refused, not half undone.** For each unit, `TestRoundTrip` journals the step over the fake (`revert.Arm`, `Record`: `pending.json`), applies the unit's change, and rolls it back through the registry from the journal alone: the host is as it was and the journal gone. Then, from a fresh host each time, it edits the journalled plan as a hand edit would (the sudoers change naming `/etc/sudoers`, or bob's file as its old state, or its old state world-writable or alice's; other bytes for DNS to write back, other nameservers; a script of its own for Alpine to write back, the legacy file `0777`, a step Alpine did not plan; root@web-01's key in `Added`, `Old` changed without `Before`; an unknown field in each): every one is refused with `ErrPlan`, the rollback ends `revert.ErrIncomplete`, and the refused step neither ran a command nor wrote anything outside `/var/lib/hardn`. The rollback stays incomplete, so the next `hardn rollback <id>` tries again; one that can never pass is given up with `Abandon` ([P-35](../refactor/proposals.md#p-35)) or by moving `rollback.json` aside, as [revert.md](revert.md) §2.16 says. With the registry's strict decoding and its checks removed (an overlay probe), every tampered case fails the test: the unknown fields are then accepted, and the other edits are refused only by the units' own rollbacks, without `ErrPlan`. A keys plan edited consistently (root@web-01's key in `Added`, with `Old`, `Before` and `New` made to match) passes `Check`, and is refused by `UndoKeys` instead (§2.3, `TestPVENodeKeyInAdded`).
6. **These checks are against mistakes and edits, not a security boundary**: the journal is root's alone ([revert.md](revert.md) §2.3), and whoever can write it is root. They keep a damaged or hand-edited entry from making root's rollback act outside what the unit planned, with one limit: the content of the sudoers files a rollback writes back (§2.3).
7. **Through `host.System`.** The package is under `pkg/host/revert`, so depguard's `revert-through-host` (no `os`, `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` but `net/netip`, `plugin`) and `host-stdlib` already cover it; no new rule. Probed in a scratch copy outside the repository: an `os` import in `plans.go` fails lint with `revert-through-host`.
7a. **The journalled form is pinned** (fixed in review). A plan is its Go type as `encoding/json` writes it: field names, `iota` enums as numbers, display fields (`Why`, `Check`, `Findings`, `Evidence`) included; with unknown fields refused, a renamed field, a field dropped or an enum renumbered in one of the units would make a journal written by the hardn before it undecodable (the rollback incomplete until abandoned) or decode it as something else. `TestWireFormat` compares each unit's step, as its step function encodes it, with `pkg/host/revert/plans/testdata/<unit>.json`, and rolls the change back from that file as journalled; for an intended change, `go test ./pkg/host/revert/plans -run TestWireFormat -update`, and the diff shows what an older journal would no longer do. Each unit owns its name (`pve.KeysUnit`, `sudoers.Unit`, `dns.Unit`, `alpine.Unit`), which `plans` aliases.
7b. **`Record` does not check a plan's payload.** `revert.PlanRollback` is one function, the rollback, so `Record` checks only that a step's unit is registered and its plan is valid JSON ([revert.md](revert.md) §2.2, §7): a step built without the step functions, with a plan its unit refuses, is journalled and found only by the rollback, after the change (`ErrIncomplete` with `ErrPlan`). The engine builds every plan step with its unit's step function (§6); a check at `Record` would need `PlanRollback` to carry a check beside the rollback, an API change left for `p3-engine` to decide.

### The rollback of a `listen.conf` migration on `ssh.socket`

8. **The fix is at the reload layer, with the journal naming what it restored** (the two options were the reload's `Rollback` mode, or a journal shape of the migration's own). `reload.Change` gains `RestoredDropIns`: for a `Rollback`, the `ssh.socket` drop-ins the rollback has put back that the change had removed. On a socket host `PlanFor` then does not refuse their `ListenStream` lines (`ErrSocketDropIn`), and plans what a listener rollback plans there: `systemctl daemon-reload`, the socket's configuration (`systemctl show -p Listen ssh.socket`) checked against `After`, `systemctl restart ssh.socket` (started whatever its state, [reload.md](reload.md) §2.6a), then `ss`. **Before `daemon-reload`, the restored drop-ins must give exactly `After`** (`reload.ErrRestoredListeners`, fixed in review): each restored drop-in among `ReadSocketDropIns`'s files, not masked, alone under its name and sorting after the generator's `addresses.conf`; read in name order, their `ListenStream` values reset the list and then give `After` one for one (a port alone matching an unspecified address of either family; anything but a port, `IPv4:port` or `[IPv6]:port` refused). Why this layer: the hazard `ErrSocketDropIn` guards against (a drop-in the generator's listeners do not reach, so the restart binds where hardn did not plan) is refused before `daemon-reload`, and so is this one: the restored lines are read before they take effect, so the rollback never runs a `daemon-reload` that would move the socket to a set the check after it then refuses, which would leave the socket on `listen.conf`'s port and the rollback unfinished. The check after `daemon-reload` ([reload.md](reload.md) §2.4) stays as for any listener change; it is not that protection, since it runs once the configuration has moved. What a rollback needs is a true `After`: the listeners the socket had before the change, which the migration knows (`migrate.Plan.Listening.All`, the socket's set on such a host, [sshd-migrate.md](sshd-migrate.md) §2.19); `migrate.Plan.Rollback()` is that reload as journalled. A journal of `OpRun` steps (`daemon-reload`, `restart ssh.socket`) would have skipped every check, and a migration-specific reload kind would have duplicated `PlanFor`'s socket plan.
9. **Only for what the rollback restored.** The journal's `reload` entry gains `socketDropIns` (`revert.Reload.SocketDropIns`), which `revert`'s rollback passes as `RestoredDropIns`; `Journal.Check` refuses one that is not a clean absolute `*.conf` path in an `ssh.socket.d` directory, a repeat, one on a reload of no listener keyword, or one in a journal without backups (`ErrJournal`, `TestJournalCheck`); and the rollback, before the reload, refuses one that is not the path of one of the journal's backup entries of a file, which the restore put back (`ErrJournal`, fixed in review: an edited entry naming an administrator's `zz-admin.conf` beside `listen.conf` is refused in `TestRollbackRestoresListenConf` with nothing run after the restore). Every other refusal stays: a forward change with `listen.conf` in place is `ErrSocketDropIn`; `RestoredDropIns` on a forward change is `fs.ErrInvalid`; a rollback whose journal does not name the drop-in, another drop-in with `ListenStream` beside it, and a restored drop-in named as the generator's (`addresses.conf`) are `ErrSocketDropIn`; a generator that is not Yes is `ErrNoGenerator` (`TestPlanForRefuses`). The regression test, `TestRollbackRestoresListenConf`, rolls back a migrated Ubuntu host: `listen.conf` and `00-hardn.conf`'s absence restored, then `daemon-reload`, the socket checked for `[::]:2230`, `restart ssh.socket`, `ss`, the journal cleared; the same journal without `socketDropIns` still stops at `ErrSocketDropIn` with nothing run after the restore, as `next/p2-vmtest`'s probe found. `TestPlanForRefuses` covers the restored lines not giving `After`: `listen.conf` not in effect (D9), the socket on more, a port the socket did not have, the drop-in absent, masked, without a reset, of a path, read before `addresses.conf`, or of a name another drop-in has.
10. **Not where the rollback could not finish, nor where configured is not bound** (rewritten in review: the first version checked only that `Plan.Hold` was among the socket's configured listeners, which passed both hosts below). Two refusals before `Arm`, both in the library, so that `p2drive` and the engine make the same ones (§6):
    - **`migrate.Plan.CheckRollback(drops)`** plans `Plan.Rollback()` at plan time, over the drop-ins as they are before the change (what the restore gives back), with §2.8's check: a migration whose rollback the reload would refuse is not applied. That is the D9 host (v0.3.x wrote `listen.conf` without a `daemon-reload`, D9, §3: until a reboot the socket is configured for 22, `listen.conf` says 2230; the rollback's `daemon-reload` would move the socket to 2230 alone, off the port the user connected on), and a socket configured for 22 beside `listen.conf`'s 2230 (an administrator who added the port first, then v0.3.x): the migration would hold all four listeners, and its rollback's `daemon-reload` give the socket 2230 alone, so the rollback could only stop, unfinished, by which time systemd may have dropped the 22 descriptor (§3, **[I]**). Tested: `TestCheckRollback` (every migrate scenario: only those two refused), `TestRefusedBeforeArm`.
    - **`reload.CheckInEffect(ctx, sys, mode, configured, server)`** for every listener change `p2drive` makes (`migrate` with `Plan.Listening.All`, `port` with `sshd -T`'s listeners): the migration's hold, the forward reload's and the rollback's `After` all come from configuration (`systemctl show -p Listen`, `sshd -T`), which a `daemon-reload` without a restart of `ssh.socket`, or an edit not reloaded, leaves ahead of what is bound. On such a host (configured 2230, bound 22, where the session is), the restart drops 22 for good: the rollback restores the configuration, 2230, and deletes the ufw rule for 2230 the change added. It refuses a configured listener `ss` does not show bound, and, with the applying session's own end (`revert.ParseConn`'s `Server`), none covering it; a remote session whose connection is not established fails it, closed, and a console session has no port to keep ([reload.md](reload.md) §2.10a). Tested: `TestCheckInEffect`, and `TestRefusedBeforeArm` (configured 2230 and bound 22 with the session on 22, and on 2230; a port change where `sshd -T` shows 2231 and sshd still listens on 22; one from a session whose connection is not known).

### `p2drive`

11. **The sudoers change is journalled** ([vmtest.md](vmtest.md) §2.10): `plans.Sudoers(plan)` is the one inverse step, recorded before the backups and `sudoers.Apply`. A plan with a lockout-risk change (a grant removed, or one that asks for a password: `sudoers.RiskLockout`, [sudoers.md](sudoers.md) §6) is a lockout-risk change under confirm-or-revert, with the timer, the session and `--timeout`/`--hardn` like the SSH commands, ended by `MarkApplied`; any other is journalled without a timer and cleared by `revert.Done` once applied. The check it prints to confirm by is `sudo -n true`, or for a password grant `sudo -v`, which asks the password where `sudo -n` cannot (**[unverified]**, sudo(8) `-n`; fixed in review). A failure after `Arm` rolls it back at once (`ReasonFailed`), with signals held; when `Apply` refused before it wrote anything (a configuration `visudo -c` already rejects, a file changed since `Read`, Ctrl-C), the plan step leaves the journal first, since its rollback would fail on the same cause and stay unfinished, and the rollback only ends the change. Tested: `TestSudoers` (the grant journalled before the backup and the write and cleared; `--grant none` armed and applied, then the timer's rollback through the registry putting the grant back), `TestSudoersRollsBack` (`visudo -c` refusing the installed grant: `Apply` restores, the change is rolled back and the journal cleared; `visudo -c` refusing every time: refused before any write, rolled back and cleared, which fails with the step kept).
12. **`migrate --apply` on a socket host** carries the migration out as on Debian, with the reload journalled as `migrate.Plan.Rollback()`: `After` = `Plan.Listening.All` and `socketDropIns` = the drop-ins the plan removes, and ufw planned over `Plan.Listening` (the listeners that accept connections now; sshd's and the socket's sets disagree on such a host, so `ReadEffective`'s may not be Known, [sshd-migrate.md](sshd-migrate.md) §2.19). The applying session of the v0.3.2 hosts' tests is on 2230, where their sshd listens. Tested: `TestMigrateSocket` (Ubuntu with v0.3.2's files, rebooted since: applied, journal as described; the values check failing after the restart: `listen.conf` and `manage.conf` back, `00-hardn.conf` gone, then `daemon-reload`, the socket's check and its restart on `[::]:2230`, the journal cleared). The fake's `daemon-reload` and boot model `listen.conf`'s reset of the generator's listeners to its port.

- **the D9 refusal** on the image before its reboot (`migrate.Plan.CheckRollback`, [vmtest.md](vmtest.md) §4.8 step 6), and on the same image after a `daemon-reload` not followed by a restart (step 6a): whether `systemctl show -p Listen` then names 2230 while `ss` still shows 22 bound **[I]**, and `reload.CheckInEffect`'s refusal with the session on 22; a socket configured for more than `listen.conf` (§2.10) is on no image, and tested on the fake only;
- **the sudoers rollback by the timer**: `--grant none` not confirmed, then `hardn rollback <id>` from the systemd timer (sudo, sudo-rs) and the OpenRC sleeper (doas) putting the grant back and `visudo -c`/`doas -C` passing ([vmtest.md](vmtest.md) §4.4 step 13, §4.6), and `--grant password` confirmed from a new session where sudo asks the password (§4.4 step 14), with the `sudo -v` the driver prints;
- **the DNS, Alpine and Proxmox VE keys rollbacks** from a journal, as root: no `p2drive` command makes those changes yet (vmtest.md §2, "What the driver does not cover"), so they are run by hand or by a later driver revision; until then [dns.md](dns.md) §4, [alpine.md](alpine.md) §4 and [pve.md](pve.md) §4 item 5 stay open for the rollback as for the apply.

## 5. API

```go
package plans // pkg/host/revert/plans (new)

const UnitPVEKeys, UnitSudoers, UnitDNS, UnitAlpine = pve.KeysUnit, sudoers.Unit, dns.Unit, alpine.Unit // "pve-keys", "sudoers", "dns", "alpine-updates"
const UnitFirewalld, UnitSELinux = firewalld.Unit, selinux.Unit                                 // "firewalld-ports", "selinux-ports"
var ErrPlan error
func Registry() map[string]revert.PlanRollback // revert.Options.Plans; a new map each call
func PVEKeys(p pve.KeysPlan, why string) (revert.Step, error)
func Sudoers(p sudoers.Plan, why string) (revert.Step, error)
func DNS(p dns.Plan, why string) (revert.Step, error)
func Alpine(p alpine.Plan, why string) (revert.Step, error)

package pve     // added: func (KeysPlan) Check() error; RollbackKeys runs it first; PlanKeys refuses adding, UndoKeys removing, a node's root key (ErrClusterKey)
package sudoers // added: const Unit; func (Plan) Check() error; Rollback runs it first (refused: ErrNotRestored and fs.ErrInvalid)
```

## 6. Not in this unit; inputs to later units

- **`p3-engine`:** pass `plans.Registry()` in `Options.Plans` to `Arm`, `Record` and `Rollback`, and journal each unit's change with its step function, before the unit's apply: `Record` does not check a plan's payload (§2.7b). **Before `Arm`, the two refusals of §2.10**, which are library calls, not `p2drive`'s: `migrate.Plan.CheckRollback` for every migration, over the drop-ins read before it, journalling `Plan.Rollback()` as its reload; and `reload.CheckInEffect` for every listener change, with the applying session's `Server` (and refusing a remote session whose connection is not established). On the D9 host the maintainer may decide otherwise: [P-39](../refactor/proposals.md#p-39) sets out refusing it until the socket listens where `listen.conf` says, a rollback that leaves the socket on the migration's listeners, and a rollback that holds them in a drop-in of hardn's; this unit refuses. **After an apply refused before it wrote anything**, for every unit, the engine drops the plan step from the journal (`Record` without it) before it ends or rolls back the change, as `p2drive` does for sudoers (§2.11): the inverse is not needed, DNS's and Alpine's would undo the same change made by others (their rule that `Rollback` is for a plan whose `Apply` returned nil, [dns.md](dns.md) §6, [alpine.md](alpine.md) §6), Proxmox VE's reverses the edit, not the write ([pve.md](pve.md) §2.12), and sudoers' would fail on the refusal's cause and stay unfinished. Each unit says "wrote nothing" its own way: sudoers, an error with `Result.Installed` empty, `Restored` false and not `ErrNotRestored`; DNS and Alpine, an error with `Result.Done` empty; Proxmox VE, an error from `ApplyKeys` with a zero `backup.Result` (it refused before its backup; a failed write returns the backup's). After an apply that wrote and failed, DNS and Alpine have undone their own steps unless they return `ErrNotRestored`, when the journal's rollback tries again; sudoers' and Proxmox VE's rollbacks act only where their own writes are, so they run in any case. A step whose apply never finished (hardn died) is rolled back as journalled.
