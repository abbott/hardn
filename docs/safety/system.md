# System: the host seam (`pkg/host`)

> **Unit:** refactor plan Phase 2, `next/p2-system` **[plan adjustment: System v0 moved from P3 into P2]**.
> **Status:** built and tested on macOS with the recording fake and on real files in temporary directories only. Everything that needs a Linux host is listed in §4 as "written, not run (gate 5)". The legacy production path is gated off until the maintainer decides [P-32](../refactor/proposals.md#p-32) (§5).
> **Brought up to date** by `next/p2-vmtest`, the last Phase 2 unit, where later units superseded this page: §2 "Files and accounts" with items 7 and 8 (`next/p2-atomic`), §6's API (`next/p2-atomic`, `next/p2-revert`) and §7's inputs.

`host.System` is the one seam between hardn and the machine it hardens. Every Phase 2 primitive (atomic write, sshd validation, sudoers, UFW, reload, revert, Proxmox, Alpine, DNS) and the Phase 3 engine (`Change.Apply(ctx, sys)`, brief Phase 3 sketch) reach the host through it. `host.Real` is the machine; `hostfake.System` is a recording, in-memory host for tests. The legacy `interfaces.Commander` and `interfaces.FileSystem` have adapters over a `System`, so legacy and new code can share one execution path. Legacy *production* calls take it only once the maintainer approves [P-32](../refactor/proposals.md#p-32) (§5); until then the gate is off and they make the os/exec and os calls they made before.

## 1. Why

The Phase 0 audit found every hardening mutation going through `interfaces.Commander`/`FileSystem` with no context, no stderr, no exit code, non-atomic symlink-following writes and no record of what ran ([phase0-findings.md §6](../refactor/phase0-findings.md#6-architecture-map-originmain-the-worktree-base); V18, V20, V21 in [side-effects.md](../refactor/phase0/side-effects.md)). The primitives that keep a user from being locked out need a seam that reports exit codes faithfully, never involves a shell, never follows a symlink it was not asked to, and logs every command.

## 2. Guarantees

### Commands (`Run`, `RunInput`)

1. **One argv, never a shell.** `name` and `args` go to `exec.CommandContext` as separate argv elements; spaces, quotes, `;`, `$(...)` and globs carry no meaning. Go's os/exec never invokes a shell and expands nothing ([pkg.go.dev/os/exec](https://pkg.go.dev/os/exec), package overview). Tested through the exec seam with a command file literally named `a b;c` and metacharacter arguments; nothing executes.
2. **Fixed resolution.** A name without a slash is looked up only in `host.SearchPath` = `/usr/sbin:/usr/bin:/sbin:/bin`, in that order; the first regular file with an execute bit wins. An absolute path is used as is; a relative path (`./x`, `a/b`) is refused. Otherwise `ErrNotFound`, and nothing runs. `/usr/local` is left out on purpose: hardn runs packaged tools only. **hardn itself is the exception:** `install.sh` puts it in `/usr/local/bin`, so a re-invocation of hardn (the revert `hardn rollback <id>`) must name it by its absolute path (`os.Executable()`), both to `Run` and to a launcher (`setsid`, `systemd-run`) that is handed the `PATH` above.
3. **Pinned environment.** The command's whole environment is `PATH=/usr/sbin:/usr/bin:/sbin:/bin` and `LC_ALL=C`. Nothing is inherited from whoever started hardn (no `IFS`, `ENV`, `BASH_ENV`, `LD_PRELOAD`, `PERL5LIB` or locale), and output is in the C locale, so parsers see one language. The working directory is `/`.
4. **A non-zero exit is an error.** It returns `*host.ExitError` (exit code, argv, output tail; `Unwrap` gives the `*exec.ExitError`), so a failed check such as `sshd -t` exiting 255 cannot read as a pass. The `Result` is filled in on every return: `Stdout`, `Stderr`, `Combined`, `ExitCode` (-1 when it did not start or was ended by a signal) and `Tail` (the last `Options.TailLines` lines of `Combined`, default 20). **`Combined` keeps each stream's own order, but the interleaving across stdout and stderr is approximate:** `Real` gives os/exec two different writers, so os/exec makes a pipe and a copying goroutine for each, and the chunks reach `Combined` in scheduling order. `exec.Cmd.CombinedOutput` gave both streams one writer, hence one pipe and the exact order (Go `os/exec/exec.go`, `childStderr` and `writerDescriptor`).
5. **Context.** A done context before the start runs nothing. During the run, `exec.CommandContext` kills **the process `Run` started, and only that one**: its default `Cancel` is `cmd.Process.Kill()`, which "only kills the Process itself, not any other processes it may have started" ([pkg.go.dev/os/exec#Cmd](https://pkg.go.dev/os/exec#Cmd), fields `Cancel` and `Process`). `Run` sets no `SysProcAttr` (but while `OwnSessions` holds, *since `next/s3-hangup`*: below), so the command stays in hardn's process group; a pipeline's or a wrapper's children (`sh -c "yes | ufw enable"`, apt-get's dpkg) are reparented and run on after the cancel, and `Run` returns an error wrapping `ctx.Err()` while they may still be changing the host. Killing the whole group (`Setpgid` plus `kill(-pgid, SIGKILL)`, [kill(2)](https://man7.org/linux/man-pages/man2/kill.2.html)) is left out on purpose: a child in its own process group is a background job, so terminal Ctrl-C no longer reaches it and a read from the terminal stops it with `SIGTTIN` ([credentials(7)](https://man7.org/linux/man-pages/man7/credentials.7.html), "Process groups and sessions"), both changes to the legacy commands. It is an input to `p3-engine` and `p2-revert` (§7). *Since `next/s3-hangup`* (the maintainer, 2026-10-28: "Yes, catch it"; [engine.md](../engine/engine.md) §2.14), **`OwnSessions`** has `Run` and `RunInput` start each command in a session of its own until its release (`SysProcAttr.Setsid`, as `StartDetached`; [setsid(2)](https://manpages.debian.org/trixie/manpages-dev/setsid.2.en.html)): outside hardn's process group, and with no controlling terminal, so no `SIGTTIN` either. It is for the engine's hold around a rollback alone, which catches the hangup in hardn: a caught signal goes back to the default action on exec, so a command the rollback runs in hardn's group would die of the hangup sent to that group (by classic sudo, a shell or the kernel; *sudo-rs 0.2.13 sends it to hardn alone: [cmd-engine.md](../engine/cmd-engine.md) §3*). A process-wide count: `OwnSessions` calls nest (the hold's do not), the sessions ending with the last release; a release counts once, and one never released leaves every later command in a session of its own (the hold's release must run: [engine.md](../engine/engine.md) §2.14). Outside it nothing changes, and a cancelled context still kills only the command `Run` started (run on macOS through `go test -overlay`, not committed). Tested on macOS, not on Linux or the VMs: `TestOwnSessions`, through the exec seam (no `SysProcAttr` before, `Setsid` while one or two are held, none once both are released); for real, `pkg/engine/hold`'s `TestGroupHangupDuringHold` (a hangup sent to the process group during the hold: the command, `sleep`, runs to its end) and `TestReleaseGivesUpSessions` (the test binary, run through `Run`, prints its process group: not the caller's during the hold, the caller's after its release). Mutation-checked (`go test -overlay`, not committed): no `Setsid` fails `TestOwnSessions`, `TestGroupHangupDuringHold` and `TestReleaseGivesUpSessions`; `Setpgid` in its place fails `TestOwnSessions` alone, a signal sent to the group not telling the two apart, so that a session and not a group (no `SIGTTIN`, above) is held by that test's reading of the `SysProcAttr`; a hold whose release never gives the count up fails `TestReleaseGivesUpSessions`. *On the VMs since (2026-10-28, `440a7b0`, as root, amd64; [screen-backup.md](../engine/screen-backup.md) §4.2, the hangup rerun): during the engine's rollback on Debian 13 and Ubuntu 26.04, `systemctl reload-or-restart systemd-resolved.service` started in a session of its own (its session id its pid, not hardn's session, read from `ps`) and exited 0; on Debian it ran to its end after the hangup sent to hardn's process group, where, in the run's 43 (the session dropped the same way), the same command run in that group, by the change's own undo outside the hold, ended "signal: hangup". `ufw` and `rc-service` not run.* *On Ubuntu 26.04 too since (2026-10-28, `4a0079e`, as root, amd64; [screen-backup.md](../engine/screen-backup.md) §4.2, the gate's rerun, its 55, logs `55-huprollback-*`): during the journal's rollback under the hold, the same `systemctl`, in a session and process group of its own (pid, process group and session id 116951; hardn's session 116708, read from `ps`), ran to its end and exited 0, 33 s after the session dropped and `SIGHUP` was sent to hardn's process group as classic sudo would (sent by the run, with `/bin/kill`; its attempt at `440a7b0` had failed). Again on Debian 13 the next day, as at `440a7b0` (`55-huprollback-deb13-vm.*`).*

   `WaitDelay` is 10 s, so once the command has exited or been killed, a daemon it started that still holds the output pipes cannot hang `Run`; after it, os/exec closes the pipes ([pkg.go.dev/os/exec#Cmd](https://pkg.go.dev/os/exec#Cmd), field `WaitDelay`). Exit 0 with pipes held past it is still success. **For the holder that is not just lost output:** its later writes to them fail with `EPIPE`, and a Go program that writes to fd 1 or 2 without `signal.Notify` for `SIGPIPE` exits with `SIGPIPE` ([pkg.go.dev/os/signal](https://pkg.go.dev/os/signal), "SIGPIPE"). So a process meant to outlive `Run` (the OpenRC revert's detached `setsid … hardn rollback <id>`) must not inherit `Run`'s pipes: it needs stdin, stdout and stderr on `/dev/null` (or a log file), which `Run` cannot give it today (§7).

   **Every `System` method refuses a context that is already done**, `Real`'s and the fake's alike. A rollback after cancellation (Ctrl-C, exit 130) must therefore run under `context.WithoutCancel(ctx)` with its own timeout, or each of its steps is refused.

   **`pkg/host/hangup`**, *since `next/s3-hangup`* (the maintainer, 2026-10-28, answering [cmd-engine.md](../engine/cmd-engine.md) §11: "Yes, fix it": "Make hardn stop writing to its terminal once a hangup is caught, so that under sudo-rs a full pty cannot hang it mid-apply"): a package of its own beside `System`, the standard library alone (rule `host-stdlib`, §6). **Why:** under sudo-rs 0.2.13, once the SSH session drops, sudo-rs keeps the pty it gave hardn open but stops reading it, so a write to it blocks in the kernel once its buffer is full (`n_tty_write`), and with it the apply or the rollback that wrote it; at `440a7b0` hardn hung so on Ubuntu 26.04, mid-apply, holding the run lock, deaf to `SIGTERM` (cmd-engine.md §11). **What:** a `Terminal` (`New`) and its writers (`Writer(w)`). Until its hangup is `Seen`, each `Write` goes to `w`, one at a time, in order, and returns what `w`'s returned, a failure included; after it, `Write` writes nothing and returns `len(p)` and no error, so a report written there does not fail the run. A `Write` under way when `Seen` is called returns so at once, `w`'s own `Write` left to finish or block on its own: each is made on a goroutine of its own, with a copy of `p`, a turn channel keeping them one at a time, so writers over one file would each wait their own turn (one writer per file). `Seen` may be called any number of times, from any goroutine, and cannot be undone. hardn's own `Terminal` is the package's (`Seen`, `Writer`). **Who calls it:** `cmd/hardn` writes its stdout and stderr through `Writer`, but a regular file (`hardn -g > report.txt`), kept as is, and the legacy menus' own prints, to `os.Stdout` itself (no hangup is caught while they run), and calls `Seen` as each hangup comes in every window where it catches `SIGHUP` ([cmd-engine.md](../engine/cmd-engine.md) §2.6); `pkg/engine/hold` calls it on `SIGHUP`, before its line ([engine.md](../engine/engine.md) §2.14). Outside those windows `SIGHUP` keeps Go's default action: hardn dies, which also ends a write blocked in the kernel. **Tested** on macOS (run): `TestWriter` (order, a failure returned, 200 writes after `Seen` dropped, a second `Seen`, another `Terminal` unaffected), `TestWriterGivesUpOnABlockedWrite` (a write blocked on `w` returns at once after `Seen`, a later one too, `w` given a copy of `p`), `TestWriterOneAtATime`, `TestStd`; and `TestWriterOnAnUnreadTerminal`, on a real pty whose master is never read, its slave opened as stdout is, a blocking file outside Go's poller (`os.NewFile`; the test checks that `SetWriteDeadline` fails): on macOS the second 1 KiB write blocked, and returned once `Seen` was called, a later one too. Its Linux pty helper is written, not run (§4). Mutation-checked (`go test -overlay`, not committed): a writer without its turn, its copy of `p`, its re-check of `Seen` once its turn comes, or its goroutine fails a test. *On the VMs (2026-10-28, `4a0079e`, Ubuntu 26.04, as root, amd64; [screen-backup.md](../engine/screen-backup.md) §4.2, the gate's rerun, logs `50-*` to `59-*`), hardn itself, not these tests: in the run's 54, the like-for-like of `440a7b0`'s 43 (where hardn hung 87 s in `n_tty_write`), the session dropped during `dns.Apply`'s own undo's reload, and hardn rolled back and ended, gone 35 s after the drop; in its 52, a save held about 28 s after the drop was rolled back, and hardn ended (whether 28 s of redraws fill the pty was not measured). On Debian 13 the next day, where the hang was never seen, as at `440a7b0`; Alpine 3.23 not run.*
6. **Every run is logged.** `host.RunLog` writes one entry per command to the `io.Writer` given at construction; every line starts with `run <n>: `, so overlapping runs stay apart:

   ```
   run 3: $ ufw allow 2230/tcp
   run 3: | Rule added
   run 3: exit 0
   ```

   Stdin is recorded by length only (`stdin: 42 bytes (not logged)`), never its content: it can hold a key or a password. Logging is **best effort**: a failing writer never stops a command, because a rollback must still run on a full disk; `Real.LogErr` returns the first write error. The log's path and rotation are `p3-output`'s business: until then the shared `host.Real` behind the legacy gate discards it.

### Files and accounts

**The no-follow rules below are about the last path component;** even `O_NOFOLLOW` covers the last component only ("Symbolic links in earlier components of the pathname will still be followed", [open(2)](https://man7.org/linux/man-pages/man2/open.2.html), `O_NOFOLLOW`). As this unit shipped, every method followed symlinks in the parent directories, so V21 stayed open. **`next/p2-atomic` closed V21 for the operations that change files** ([atomic.md](atomic.md) §2.5): `WriteFileAtomic`, `Chown`, `Chmod`, `Remove` and the new `ReadFileNoFollow` and `ResolveSymlink` reach the target's directory by a guarded walk (`openat(O_NOFOLLOW|O_DIRECTORY)` from `/`, one component at a time) that follows a symlink only in a directory owned by root (or hardn's user) and writable by neither group nor others, and refuse any other with `host.ErrSymlinkParent`. So when alice replaces `~alice/.ssh` with a link to `/root/.ssh`, `Chown` and `WriteFileAtomic` of `~alice/.ssh/authorized_keys` are refused and root's keys stay as they were. `MkdirAll`, `RemoveAll`, `Rename`, `WriteFileInPlace` and the reads still follow every link in the parent directories ([atomic.md](atomic.md) §2.9): none of them may be used on a path under a directory another user controls.

7. **`WriteFileAtomic` refuses a symlink.** A symlink at the target, dangling or not, is refused with `ErrSymlink` and left untouched with its target; so is a directory (`EISDIR`). It writes a new file in the target's directory (`os.CreateTemp`), sets the owner, then the mode, and renames it over the target, so readers see old or new content, never a mix, and the new file has exactly the given mode and owner. The owner goes first because `chown(2)` clears the setuid and setgid bits of an executable, "since Linux 2.2.13" for root too ([chown(2)](https://man7.org/linux/man-pages/man2/chown.2.html), NOTES). `rename(2)` overwrites a symlink at the new path itself rather than writing through it ([rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)), so a link planted after the check is not followed either. On any failure after the temporary file exists, it is removed and the target is untouched (tested by a chown to root that fails unprivileged). That was the naive version this unit shipped; **`next/p2-atomic` replaced it** with the durable write brief 2.1 asks for ([atomic.md](atomic.md) §2.1-2.4): after the guarded walk, a temporary file created `O_CREAT|O_EXCL|O_NOFOLLOW` and `0600`, the data, the owner then the mode, an fsync, a re-check that the target is not a symlink, the rename, and an fsync of the directory; a failure up to the rename leaves the target as it was, and a failed directory fsync is `host.ErrNotDurable`. Relative paths are refused, a symlinked parent another user can change is `ErrSymlinkParent`, and the backups (`pkg/host/backup`, §3.16) are that unit's too.
8. **`Chown` and `Chmod` never follow a symlink at the path.** Both refuse one with `ErrSymlink`. As this unit shipped, `Chown` changed the path itself with `lchown(2)`, which "does not dereference symbolic links" ([chown(2)](https://man7.org/linux/man-pages/man2/chown.2.html)); since `next/p2-atomic` both reach the path by the guarded walk and change it through an `O_NOFOLLOW|O_NONBLOCK` descriptor (`fchown`, `fchmod`), so they change regular files and directories only, and refuse a file with other hard links in a directory another user can change (`host.ErrHardLink`; [atomic.md](atomic.md) §2.5, §2.8). The rest of this item describes `Chmod` as this unit built it. `chmod(2)` follows a symlink, and `fchmodat`'s `AT_SYMLINK_NOFOLLOW` depends on the kernel ([chmod(2)](https://man7.org/linux/man-pages/man2/chmod.2.html), ENOTSUP; Go's `syscall.Fchmodat` returns `EOPNOTSUPP` where `fchmodat2` is missing), so `Chmod` opens the path with `O_NOFOLLOW` ("If the trailing component … is a symbolic link, then the open fails, with the error ELOOP", [open(2)](https://man7.org/linux/man-pages/man2/open.2.html)) and `O_NONBLOCK`, and changes the mode through the descriptor: a link planted after the check is refused. Because it opens the path, `Chmod` changes regular files and directories only (anything else is `fs.ErrInvalid`, checked before and after the open), and an unprivileged process cannot change a file it cannot read; hardn runs as root. This is what brief §2.3 step 1 needs (`~/.ssh` 0700, `authorized_keys` 0600 on existing files), which `MkdirAll` cannot do (it sets the mode only on a directory it creates) and `chmod(1)` would do through a link ("for each symbolic link listed on the command line, chmod changes the permissions of the pointed-to file", [chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)).
9. **Reads follow symlinks; `Lstat` and `Readlink` do not.** `ReadFile`, `Stat`, `ReadDir` (sorted by name) are the os package's; `Readlink` returns a link's target as stored (`EINVAL` for anything else), which is what `p2-pve` (Proxmox's `authorized_keys` link into `/etc/pve/priv`), `p2-dns` (which manager owns a symlinked `/etc/resolv.conf`, brief §2.5) and `p2-detect` (the pid-namespace inode, which `/proc/<pid>/ns/pid`'s link content carries, "the namespace type and inode number" as in `pid:[4026531836]`, [namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html)) read. `Remove`, `RemoveAll` and `Rename` act on a symlink itself; `Rename` refuses an existing directory at the new name with `EEXIST`, even an empty one, as `os.Rename` does before calling `rename(2)` (Go `os/file_unix.go`, `rename`).
10. **No in-place write in `System`.** `os.WriteFile` semantics (truncate, follow the symlink, keep the mode) exist only as `LegacySystem.WriteFileInPlace`, for the legacy `interfaces.FileSystem` adapter. The method is not in `System`; it is exported on `Real` and the fake, and no lint rule stops new code from asserting a `System` to `LegacySystem`, so keeping new code off it is review's job.
11. **Accounts.** `LookupUser` and `LookupGroup` use os/user and return `ErrUnknownUser` / `ErrUnknownGroup`. Release builds are `CGO_ENABLED=0` (`.slsa-goreleaser/*.yml`), so os/user uses its pure-Go implementation, which reads `/etc/passwd` and `/etc/group` itself ([pkg.go.dev/os/user](https://pkg.go.dev/os/user)): accounts that only NSS knows (LDAP, sssd) are not found.
12. **Service control is a `Run` call** (`systemctl reload ssh`, `rc-service sshd reload`). There is no systemd API here. Which unit, which verb and which init system is `p2-detect`'s and `p2-reload`'s: the service is `ssh` on Debian, Ubuntu and Proxmox and `sshd` under OpenRC on Alpine, and the `sshd` unit alias is missing on fresh Ubuntu 24.04 ([phase0-findings.md §10](../refactor/phase0-findings.md#10-verify-list-brief-9), "Service names / init"; plan `p2-reload`).

### The line scan (`ScanLines`), *since `next/s1-readers`*

`ScanLines(ctx, name, yield)` hands the regular file `name` to `yield` a line at a time, for the Logs screen's last lines and total, `-p`'s pipe form and "can this file be read and does it hold anything" ([readers-system-details.md](../engine/readers-system-details.md) §2). `ReadFile` reads the whole file, and hardn's log is never rotated (`pkg/output/audit.go:22`).

- **Refusals, without blocking.** It opens what `ReadFileNoFollow` opens, through one helper (`openRegular`): lstat first, then `O_NOFOLLOW|O_NONBLOCK`, then fstat. A FIFO with no writer or a device is refused with `fs.ErrInvalid` and never read; a directory with `EISDIR` (run: `TestScanLinesRefusesWithoutBlocking`, on a real FIFO and `/dev/null`; `TestContract`).
- **No symlink at the path, and guarded.** A symlink at `name` is refused with `ErrSymlink`; one on the way is followed only from a trusted directory, else `ErrSymlinkParent` (run: `TestContract`). This is `System`'s rule for the guarded operations (`pkg/host/guard.go`), against `ReadFile`, which follows: what it reads is shown to whoever asked, so a link planted at the path must not show them a file only root can read.
- **Bounded.** At most `scanChunk` (32 KiB) and `MaxLine` (64 KiB) and two bytes held, whatever the file holds. A line past `MaxLine` reaches `yield` as soon as that is known, `Line.Cut` set, and the read goes on at the next line, where origin/main's scanner stops silently and loses the rest (gallery-system-details.md §2.10). So a large file with no newline costs `MaxLine` to look at and is one line to read through (run: `TestScanReaderIsBounded`). `Line.Text` is valid during the call alone.
- **Lines.** No newline at the end is still a line, an empty line is a line, one `\r` before the end of a line goes, a `\r` elsewhere stays (run: `TestContract`).
- **One moment.** It reads no further than the size `fstat` gave at the open, so the size and the lines agree and a writer that keeps appending cannot keep hardn reading (run: `TestScanLinesStopsAtTheSize`). So a file reporting size 0, as `/proc`'s do, reads as empty: `ReadFile` is for those.
- **Context** is asked before each read, not only on entry, unlike the other file operations (run: `TestScanLinesContextDuringTheRead`). `yield` returning false stops the read with no error, so there is no sentinel to register, and a caller's own error stays the caller's.
- **No run-log line,** on a host that has a run log (run: `TestScanLinesNoRunLog`).

### The interactive child (`RunInteractive`), *since `next/s1-readers`*

`RunInteractive(ctx, env, name, args...)` runs one named program as a child with hardn's own stdin, stdout and stderr, so it has the terminal, and waits for it: the seam decision 7 (a) of [gallery-system-details.md](../engine/gallery-system-details.md) §5 accepts, for the Logs screen's pager. `Run` pipes output and gives no terminal (`pkg/host/real.go`, `start`).

- **Off a terminal it runs nothing,** where stdin or stdout is not one, and returns an error: a child that has the terminal may do otherwise off one, as `less` on a pipe acts as `cat`, passing a log's bytes through raw, and the pipe can end at a terminal, `hardn | tee` (run: `TestRunInteractiveNeedsATerminal`; `less` by hand on 581.2, GNU's [I]). The fake has no terminal to ask about, and does not refuse.
- **No shell, the name as `Run` resolves it**, the working directory `/`, `Args[0]` the name (run: `TestRunInteractiveCommand`, through the exec seam).
- **The environment is exactly `env` and `Run`'s `PATH`** (`InteractiveEnv`), which no entry of `env` replaces: nothing is inherited, for `commandEnv`'s reason, no `PATH`, `IFS`, `ENV`, `LD_PRELOAD` or locale from whoever started a root process (run: `TestRunInteractiveExactEnvironment`: `env(1)` as a real child prints the three lines passed, under a parent holding `PAGER`, `LESS`, `LESSOPEN`, `LESSCLOSE`, `LESSKEY`, `EDITOR`, `VISUAL`, `SHELL`, `HOME`, `LD_LIBRARY_PATH`, `TERM` and `LC_ALL`). The run log holds the argv and the exit, not `env`.
- **A non-zero exit is an `*ExitError`,** `ExitCode` -1 when ended by a signal (run: `TestRunInteractiveExit`).
- **The terminal's signals.** hardn registers nothing for SIGINT or SIGQUIT outside a prompt's read, an apply and a rollback's hold (`pkg/engine/hold/hold.go:117`, which ignores them): `ReadLine` catches SIGINT for its own call (`pkg/ui/prompt/reader.go:319`, `:348`), the screens' apply and `hardn confirm` catch SIGINT, SIGTERM and SIGHUP for theirs (`cmd/hardn/engine.go:45`, `cmd/hardn/confirm.go:42`), and otherwise Go's default ends hardn (`cmd/hardn/status.go`'s `readStatus`). So Ctrl-C at the child, sent to the foreground group, child and hardn both, would end hardn. While the child runs, hardn **catches** SIGINT and SIGQUIT on a channel nothing reads (`catchTerminalSignals`): exec gives a caught signal its default action in the child and keeps an ignored one ignored, so `signal.Ignore` would take Ctrl-C from the child. One hardn started with ignored, as a background job's, is left alone, as `ReadLine` leaves it, as catching it would hand the child a signal its parent's parent had ignored. `signal.Stop` then puts each back; another registration stays and gets the signal as well (run, on a pseudo-terminal, typing `\x03` and `\x1c` at the master of a process that is session leader and foreground group, its child `sh`: `TestRunInteractiveCtrlC`, `TestRunInteractiveCtrlBackslash`, `TestRunInteractiveKeepsRegistrations`: the child's trap runs; hardn goes on; a second Ctrl-C ends it by SIGINT, and Ctrl-\ by Go's SIGQUIT; a registration held around the call still gets it; ignored stays ignored, in the child too).
- **`OwnSessions` does not apply:** the child stays in hardn's session and group, or it has no terminal (run: `TestRunInteractiveCommand`, under `OwnSessions`).
- **Context.** A done ctx runs nothing. Done while the child runs: SIGTERM, which it can act on, then SIGKILL after 5 s, an error wrapping `ctx.Err()` (run: `TestRunInteractiveContext`, with a trap and with SIGTERM ignored). A caller holding `signal.NotifyContext` around the call gets this on Ctrl-C too, so a screen does not hold one: `cmd/hardn`'s are around an apply and `hardn confirm`'s clean-up alone (`screenApplyContext`, `confirmSignals`).
- **The terminal's modes.** A child that ends with them changed, killed or crashed in raw mode, has them put back from before the call (`keepTerminal`), so the next prompt reads cooked (run: `TestRunInteractiveTerminalModes`: `stty raw -echo`, then a line typed reads whole).
- **Real less on a pseudo-terminal, this Mac's 581.2** (run: `TestRunInteractiveLess`): with `LESSSECURE=1` and `--` before the path the file shows, `!` says "not available", `q` ends it, exit 0. **Not run:** a person's real terminal; GNU less 668 under hardn; as root; on Linux at all (`pty_linux_test.go` is written, vetted by `make check-cross`).
- **`RunBounded`,** a free function and no method, runs a command through any `System` under a limit, and returns a grace past it whether or not the command has ended, leaving it behind: for a read a person waits for (run: `TestHungCommand`, `TestPagerBound`, `TestBoundOnARealChild`). *Since `next/s1-readers`.*
- **Known limits, written, not run:** Ctrl-Z stops the group, hardn with it, and `fg` resumes both, as any foreground program's child; a SIGTERM or hangup sent to hardn alone ends hardn by what it has at the call and leaves the child to its terminal.

### The fake (`pkg/host/hostfake`)

13. **Scripted commands, in the mocks' style, failing closed.** `Respond(Response{Stdout, Stderr, ExitCode, Err}, name, args...)` scripts one argv; several responses for one argv are used in order and the last repeats. A non-zero `ExitCode` gives `*host.ExitError` whose `Err` reads `exit status N`, as `Real`'s `*exec.ExitError` does, so the legacy adapter shows the same text over either; `Err` is returned verbatim, as `MockCommander` returns its errors. Unscripted commands go to `Handler` if set (it runs without the fake's lock, so it can model a command's effect on the fake). **Without a `Handler` an unscripted command fails with `hostfake.ErrUnscripted`** (exit -1, recorded with the error): unlike `MockCommander`, a test that forgets to script `sshd -t -f …` or `systemctl is-active ssh.socket` gets an error, not a made-up pass. A `Handler` returning `Response{}` opts into `MockCommander`'s empty success; the characterization harness answers every command from the mocks' maps that way. The fake refuses the command names `Real` refuses before looking for a file (empty, relative path) with `host.ErrNotFound`; it has no executables, so it cannot refuse a name missing from `SearchPath`.
14. **An ordered record** of every call (`Calls`, `Runs`; `Call.String` for failure messages), stdin and written data included, and the same run log as `Real`.
15. **An in-memory file system with modes, owners and symlinks**, seeded with `AddFile`, `AddDir`, `AddSymlink` and inspected with `Entry` (neither recorded). `host.Owner(fi)` reads the owner from either System's `fs.FileInfo`. A contract test runs the same 16 cases against `host.Real` in `t.TempDir()` and against the fake: write in place through a symlink, atomic write refusing a symlink, rename over a symlink and onto an existing directory, remove and remove-all on links and non-empty directories, stat versus lstat, sorted directory listings, mkdir over a file, chown and chmod refusing a link and a missing path, readlink. The fake has no umask, no hard links, no permission checks (it acts as root) and no setuid, setgid or sticky bits; it resolves `..` in a link target lexically and follows at most 40 links, then `ELOOP` (Linux's limit: "the maximum number of symbolic links that will be followed while resolving a pathname is 40", [path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)). It refuses relative paths and a trailing slash with `fs.ErrInvalid` rather than model a trailing slash's rules (path_resolution(7)), so where it departs from a host it fails where the host would not, never the other way round.

## 5. The legacy adapters and the one execution path

`interfaces.SystemCommander{Sys}` and `interfaces.SystemFileSystem{Sys}` implement the legacy interfaces over a `System`/`LegacySystem`. `SystemCommander` returns `Result.Combined` where `CombinedOutput` returned its one buffer, and unwraps `*host.ExitError` to the error behind it, so legacy callers still see `exit status 1` (over `Real`, the `*exec.ExitError` itself; over the fake, an error with the same text). `SystemFileSystem.WriteFile` keeps `OSFileSystem`'s semantics: create the parent (0755), then write in place, through a symlink.

`interfaces.OSCommander` and `OSFileSystem`, which `NewProvider` and `osdetect` construct, delegate to one shared `host.Real` **only when `const legacyThroughHost` in `pkg/interfaces/system_adapter.go` is `true`. It ships `false`:** with it on, every legacy production command changes in the ways listed below, none of them is tied to an approved §3 row or V-number, and brief §3 principle 2 asks for approval first. [P-32](../refactor/proposals.md#p-32) asks the maintainer; the recommendation is to flip it after `next/p2-vmtest` has run the legacy operations on the VMs (§4). Off, both types make exactly the os/exec and os calls they made before (their old bodies are kept, behind the gate); the adapters themselves are still tested, and so is the wiring, through the goldens below. With it on, legacy production commands change in these ways, all **written, not run** (§4):

- resolved from `SearchPath` only (was: hardn's `PATH`; with sudo, its `secure_path`). Of the commands the legacy adapters run, only `uv`, which the Python package path installs with `pip3 install uv`, is likely to land outside it, in `/usr/local/bin` **[unverified]**; that path is unreachable on origin/main ([phase0-findings.md §6](../refactor/phase0-findings.md#6-architecture-map-originmain-the-worktree-base), "Dead or unreachable");
- the environment is exactly `PATH` and `LC_ALL=C` (was: inherited whole, so children lose `HOME`, `TERM`, `LANG`, `USER` and `SUDO_*`; hardn's own reads of them are unchanged), and the working directory `/` (was: hardn's);
- a command not found reports `host: "x": not in /usr/sbin:/usr/bin:/sbin:/bin: command not found` (was: os/exec's "executable file not found in $PATH");
- the combined output keeps each stream's order but interleaves stdout and stderr only approximately (was: exact, one pipe; §2.4);
- after exit, at most 10 s of waiting for held pipes, then the pipes are closed under whoever holds them, whose later writes fail with `EPIPE` or `SIGPIPE` (was: unbounded wait; §2.5);
- every command is also written to the run log, which discards until `p3-output` gives it a path.

Cancellation does not change: legacy callers pass `context.Background()`. File operations make the same os calls as before.

**Goldens.** The P0.7 characterization goldens pass unchanged (no `-update`). They record the seam itself, so they also run a second time through the adapters: `TestOperationGoldensThroughSystem` and `TestHostInfoGoldenThroughSystem` wrap `SystemFileSystem`/`SystemCommander` over a `hostfake.System` scripted from the same mock maps and compare byte for byte with the same golden files (compare-only; `-update` regenerates from the mocks). A deliberately broken adapter fails them. The environment and resolution changes above sit below the seam, in `host.Real`, so no golden can show them; §4 covers them.
