# The revert timer across a reboot (`hardn rollback --boot`, the boot unit)

> **Unit:** refactor plan Phase 3, `next/p3-revert-boot` (plan §2, Phase 3 row `p3-revert-boot`; [P-34](../refactor/proposals.md#p-34) (c), decided by the maintainer 2026-10-19: re-arm at boot). No V-number: the timer lost at a reboot is [revert.md](revert.md)'s own gap (§2.20, §7). Brief 2.4 and §3 principle 1.
> **Status:** built and tested on macOS against the recording fake (`hostfake`), and through `cmd/hardn`'s seams with no binary run. Nothing has run on Linux: no boot unit has been installed, enabled or started at a boot, and no timer re-armed. Everything host-specific is "written, not run (gate 5)" (§4); the VM steps are [vmtest.md](vmtest.md) §4.10.

The revert timer is runtime state: a transient systemd timer, or an OpenRC sleeper with its pidfile in `/run/hardn`. A reboot inside the confirm window loses it, and the change stays applied and unconfirmed until someone runs hardn. Now, before it arms the first timer on a host, hardn installs a boot unit (`hardn-boot.service` on systemd, the `hardn-boot` init script on OpenRC), shown as a step of the plan. At boot, before sshd reads its files, the unit runs `hardn rollback --boot`. That command re-arms the timer for what remains of the window, or rolls the change back at once when the deadline has passed. It acts only on a journal written by the same hardn binary, whose timer is not running.

## 1. Why

[P-34](../refactor/proposals.md#p-34): a reboot can come from anyone. The user may reboot on purpose inside the window, or a locked-out user may power-cycle the host from the provider's console, or something else may reboot it. Before this unit, the next run of hardn said the change was overdue ("its timer did not run (a reboot stops it)"). A user the change had locked out could not reach that run over SSH, and nothing undid the change at boot. The maintainer chose (c): a deliberate reboot keeps the change open for confirmation, and a power cycle after the deadline recovers the host. The risk P-34 names is a boot-time action that nobody watches. It must never act on a change the user meant to keep (confirmed, also late), nor on a journal from a hardn that has since been replaced.

## 2. Guarantees

### The command (`hardn rollback --boot`, `revert.Boot`)

1. **A flag on the existing subcommand, and no other CLI change.** `--boot` is a bool flag local to `rollback`, with no short form. It takes no `<id>`, because it acts on the change the journal holds, and it does not combine with `--abandon` (both are usage errors from cobra, with nothing run: `TestRevertBootCommand`). Without the flag, `rollback` and `rollback --abandon` are unchanged. As `hardn rollback`, it needs root (otherwise exit 1, with nothing read) and refuses `-n` (exit 2), and it holds off `SIGHUP`, `SIGINT` and `SIGTERM` while it runs ([revert.md](revert.md) §2.17), since it may roll back. It passes `revertPlans`, the registry `hardn rollback` passes ([revert-plans.md](revert-plans.md)). No other flag, key, default or subcommand changes (§3.11 is not approved).
2. **Only this binary's journal, whose timer is not running** (`TestBoot`). Since this unit, `Arm` records three things in the timer: the hardn binary the timer runs (`timer.hardn`, its checked path), the SHA-256 of that file's content (`timer.hardnSHA256`), and the boot's id (`timer.boot`, from `/proc/sys/kernel/random/boot_id`) (§2.11). At boot, `cmd/hardn` passes its own path (`os.Executable`, resolved with `filepath.EvalSymlinks`). `Boot` then acts on a lockout-risk change in `pending.json` only when all of these hold:
   - the timer is not running. One started in an earlier boot is not: a reboot stopped it. One started in this boot is checked: `systemctl is-active hardn-revert-<id>.timer` printing `active`, or on OpenRC the pidfile naming a process whose `/proc/<pid>/cmdline` is the sleeper's argv, as a cancel checks it ([revert.md](revert.md) §2.9). If it is there, there is nothing to do (`BootNothing`, reason `timer-runs`). This makes the command idempotent: run again in the same boot, by hand or by systemd, it re-arms nothing twice. If it is not there (`inactive`, no pidfile, another command line), the change is taken as after a reboot, and the log says so. That covers a re-arm stopped between its journal write and its timer's start (a kill of the command, an OOM: §2.5), and a `systemctl soft-reboot`, which restarts userspace, stopping the transient timer, but keeps the kernel, and so the boot id (§3). If its state cannot be read (`systemctl` fails or prints another state, an unreadable pidfile), it is `BootLeft` (`timer-unknown`). `TestBoot` has a row for each; `TestBootOpenRC` covers the sleeper gone, then there.
   - `timer.hardn` is this hardn's path, and `timer.hardnSHA256` is the SHA-256 of that file now, read without following a symlink at the path.
   - `timer.boot` is recorded, and this boot's id can be read.

   Anything else is `BootLeft`: reported, not acted on, with the two ways on (`sudo hardn confirm` from a new SSH connection, or `sudo hardn rollback <id>`; `doas hardn` on a doas host, [revert.md](revert.md) §9.1). That covers a journal written before this unit (it has none of the three fields; [`testdata/pending-p2.json`](../../pkg/host/revert/testdata/pending-p2.json) is Phase 2's golden), another binary's path, the same path with other content (hardn upgraded or replaced since), and a missing boot id. **This is a decision of this unit, as P-34's Risk asks.** A binary that did not write the journal may read it differently, and a boot-time action that nobody watches is the case where that matters most. The cost: a change whose hardn was replaced inside its window gets no boot-time recovery. The next run's overdue notice still says how to undo it ([revert.md](revert.md) §2.20).
3. **Then, by the journal and the clock**:
   - **no `applied`** (a reboot interrupted the apply): rolled back at once. It cannot be confirmed (`CheckConfirm`, [revert.md](revert.md) §2.11), and no check after the apply has passed its files, which sshd is about to read. Keeping it until the deadline would only delay the rollback the timer makes anyway. **A decision of this unit**: P-34 names only "the remaining window" and "the deadline has passed".
   - **a wall clock that reads before the change was created** (no RTC, a clock reset): not trusted. What remains of the window cannot be told, so the timer is re-armed for the whole window (`ClockUntrusted`, said in the log and the command's output). Its deadline is then the re-arm's time plus the window, **by that clock**. Once the clock is corrected (by NTP, usually soon after boot), that deadline is wrong, and so is what reads it: the notices, `Confirm`'s messages and the rollback's reason (§2.12). The timer is not affected: `--on-active=` counts from the timer's start (systemd.timer(5)), the sleeper's `sleep` counts seconds, and `Confirm` does not read the clock.
   - **past the deadline** (`Journal.Deadline`, §2.12): rolled back at once (§2.4).
   - **otherwise**: re-armed for what remains, rounded up to the second, at least 1 s, and **never longer than the window** (`TimeoutSeconds`). The deadline stays the one the change was armed with. A window of 180 s armed at 12:00:00 and rebooted at 12:01:40.5 is re-armed for 80 s (`TestBoot`, "inside the window"). There is no floor of `MinTimeout` here: a re-arm keeps the window the user already had, and does not open a new one.
4. **A rollback at boot starts nothing** (`TestBoot`, `TestBootSocketHost`). It is `revert.Rollback` with `ReasonTimeout`, as the timer's would be, so it leaves `reverted.json` and the next run's notice. In the boot unit's start it also sets the new `Options.NoStart`: every reload runs as one journalled with `ifUp`, so `Step.Start` is dropped ([revert.md](revert.md) §2.14 step 3). The boot unit runs before `ssh.service` and `ssh.socket` (§2.13), so they are not up yet:
   - **Debian, Proxmox VE (`ssh.service`):** the files are restored, the ufw undo runs, and the gated reload finds the unit inactive and skips it (`reload.StepReport.NotUp`). sshd then starts after the unit and reads the restored files.
   - **Ubuntu (`ssh.socket`):** the files are restored. `systemctl daemon-reload` reruns `sshd-socket-generator` over them (it ran at boot over the change's files), and `systemctl show -p Listen ssh.socket` must show the restored listeners. The restart is gated and skipped. `ssh.socket` then starts after the unit and binds what the restored files say.
   - **Alpine (OpenRC):** `rc-service sshd reload` is gated on `/run/openrc/started/sshd`, which does not exist yet, so it is skipped.

   **Why no start:** a `systemctl start ssh.service` or `systemctl restart ssh.socket` run from a unit ordered before them would queue a job that waits for that same unit to finish, while `systemctl` waits for the job (§3). It would also start sshd early, ahead of its own ordering. If sshd's unit is up after all (the order did not apply), it is reloaded or restarted as usual, never started (`TestBootSocketHost`, `up`).

   **Only in the unit's start** (`TestInBootUnitStart`; `TestBoot`, "run by hand after the boot"). `NoStart` is set when the command runs in the boot unit's start: `systemctl is-active hardn-boot.service` prints `activating`, as a oneshot service does while its `ExecStart=` runs, or OpenRC has `/run/openrc/starting/hardn-boot` (§3). Run by hand at another time (the unit `active`, `failed` or `inactive`; OpenRC not starting it), for instance after a boot unit that failed and was fixed, the rollback is `hardn rollback <id>`'s: a unit that is down is started, and if it does not come up the rollback did not finish (`reload.ErrUnitDown`, exit 1), rather than "rolled back" with sshd still down. When that cannot be told (`systemctl` fails or prints another state, no init system running), no unit is started, and the log says so: a start left out leaves a down unit down, while one made from the unit's start would wait on the unit.
5. **The re-arm cannot resurrect a change that was confirmed or rolled back.** The re-armed journal (the new timer: its argv with the remaining seconds, its deadline, this boot's id, the same `hardn` and `hardnSHA256`) is written over `pending.json` before the timer starts, as `Arm` writes it, through `rewritePending`. Then the journal is read again:
   - `rollback.json` holding the change means a rollback claimed it in between: the `pending.json` just written is removed, and the result is `BootNothing` (`claimed-meanwhile`, `TestBootFaults`).
   - `confirmed.json` holding it means a `hardn confirm` from the console claimed it: the same, and no timer starts (`confirmed-meanwhile`, `TestBootConfirmedMeanwhile`). A confirmation after `Boot`'s read but before a rollback at boot claims the change makes that rollback find nothing to do: `BootNothing`, `claimed-meanwhile` (`TestBootFaults`).

   A re-arm stopped between that write and the timer's start leaves a journal that names a timer of this boot which never started; the next run in the same boot finds it not there and re-arms it again, or rolls the change back (§2.2). On systemd the timer is `systemd-run` with `--unit=hardn-revert-<id>`, which is free because transient units do not survive a reboot. On OpenRC it is the sleeper, with its pidfile, and its new argv in the journal, so a confirmation's cancel recognises its `/proc/<pid>/cmdline` ([revert.md](revert.md) §2.9; `TestBootOpenRC`). After the re-arm, `hardn confirm` from a new SSH connection confirms the change and stops the new timer (`TestBoot`, `TestBootOpenRC`): the connections the journal saw at `MarkApplied` are gone, so no `ErrOldConnection` applies.
6. **When the timer cannot be re-armed, the change is rolled back at once**, as in item 4. That covers no timer for the init system detected now, hardn failing `CheckExecutable`, and a timer that does not start (`TestBoot`), and a journal that cannot be written (`TestBootFaults`). A change that no timer would ever roll back is exactly what P-34 is about. The cost is a deliberate reboot whose change is undone. That is safe, and the change can be applied again.
7. **Left to its own path**:
   - a rollback in `rollback.json` that did not finish is `BootLeft`, with the command to finish it (`sudo hardn rollback <id>`) or give it up (`sudo hardn rollback --abandon <id>`, [revert.md](revert.md) §8). At boot its runner is never alive, since `alive` compares the boot id.
   - a rollback whose runner still runs (the command run by hand) is `BootNothing`.
   - a change with no timer (`risk: other`, an apply that did not finish) is `BootNothing`: the next run's notice says how to undo it, as before.

   In none of these cases is anything run or written.
8. **Nothing journalled: nothing to do**, and the boot unit is removed (§2.17). A change confirmed in the window, or late (after a reboot, past its deadline: `Confirm` does not read the clock, [vmtest.md](vmtest.md) §4.9), is in `confirmed.json`, not `pending.json`. The command says which change was confirmed last (`TestBoot`, "confirmed before the reboot", "confirmed late, after a reboot").
9. **Logged.** Every decision goes to `Options.Log` as one `revert: boot: change <id> (<summary>): <action>: <why>` line. The rollback's own lines follow ([revert.md](revert.md) §2.19), and so do the boot unit's install and removal lines. `cmd/hardn` sends both these lines and the run log of every command to `/var/log/hardn.log` and to the console, which under the systemd unit is the unit's journal (`journalctl -u hardn-boot.service`). Under OpenRC the console is the boot console, and the log file is the record.
10. **Exit codes:**
    - 0: nothing to do, re-armed, or rolled back.
    - 1: `BootLeft`, a rollback that did not finish, a journal that cannot be read, or not root. At boot the systemd unit then shows as failed (`systemctl --failed`), and sshd still starts (§2.13). For `BootLeft` this is not the brief's meaning of 1 ("Error. Anything already applied was rolled back"): the change is not acted on and stays applied. `p3-output` decides it (§6).
    - 2: `-n`.

    `BootResult.Reason` says why, as a stable value (`no-change`, `timer-runs`, `deadline-passed`, `other-binary`, …; §5), set beside the sentence in `Why`, so that `p3-output` maps reasons to its registry codes without reading the words (`TestBoot` checks it on every row).

### The journal

11. **Three optional timer fields; the wire format stays compatible.** `timer.hardn`, `timer.hardnSHA256` and `timer.boot` are `omitempty` and keep `schemaVersion` 1. A journal Phase 2 wrote still decodes and passes `Check` (`TestDecodePhase2Journal`). Unknown fields are still refused ([revert.md](revert.md) §2.2), and `TestWireFormat`'s plan files are unchanged. `testdata/pending.json` gained the three fields (`TestArmSystemd -update`, reviewed); `pending-p2.json` keeps the Phase 2 form. **The other direction does not hold:** a hardn from before this unit refuses a journal with these fields as unknown (`ErrJournal`), as it refuses any field it does not know. So a hardn downgraded inside a confirm window can neither confirm nor roll back the change: the timer runs the binary at its path, now the older one. Do not downgrade hardn while a change is journalled; if it happened, put back the binary that armed the change, then confirm it or roll it back. `Check` refuses:
    - `hardn` without `hardnSHA256`, or `hardnSHA256` without `hardn`;
    - a `hardn` that is not clean, or is not in the timer's argv;
    - a `hardnSHA256` that is not 64 lower-case hex digits;
    - a `boot` with whitespace or longer than 64.

    `Arm` hashes the binary after `CheckExecutable` and fails when it cannot read it, journalling nothing (`TestArmHashFails`). A boot id it cannot read is left out and logged, and the boot command then leaves that change alone (§2.2).
12. **`Journal.Deadline` is the timer's deadline** when the journal has one. `Arm` sets it to `created` plus the window, as before, so nothing changes until a re-arm with an untrusted clock moves it (§2.3). Notices, `Confirm`'s messages and the rollback's reason then follow the re-armed timer's deadline, which is by the clock at boot. They match the timer only while that clock stays as wrong as it was: the re-armed timer's rollback is `timeout` once its own deadline has passed, where `created` plus the window would read it as `requested` (no `reverted.json`, [revert.md](revert.md) §4's last item). **Once the clock is corrected** they do not: `Notices` may call the change overdue ("its timer did not run (a reboot stops it)") while the re-armed timer still counts down, and a `hardn rollback <id>` before that timer is classed `timeout`. Nothing unsafe follows (§2.3), but `p3-engine`'s countdown, which reads `Deadline()`, must not take it as exact (§6).

### The boot unit (`PlanBootUnit`, `ReadBootUnit`, `EnsureBootUnit`, `RemoveBootUnit`)

13. **systemd: `/etc/systemd/system/hardn-boot.service`**, `0644` root's, pinned byte for byte ([`testdata/hardn-boot.service`](../../pkg/host/revert/testdata/hardn-boot.service), `TestPlanBootUnit`): `Type=oneshot`, `RemainAfterExit=yes`, `ExecStart=<hardn> rollback --boot`, `WantedBy=multi-user.target`. **Its order**, checked line by line in the test:
    - `Before=ssh.service ssh.socket`, so that an immediate rollback restores the files before sshd reads them (item 4). This covers Debian's and Proxmox VE's `ssh.service`, Ubuntu's `ssh.socket`, and the `ssh.service` that socket starts.
    - `DefaultDependencies=no`. The defaults would order the unit `After=basic.target` (systemd.service(5)), and basic.target comes after sockets.target and so after `ssh.socket`. With `Before=ssh.socket` that would be an ordering cycle, which systemd breaks by dropping a job.
    - So the unit names its own order: `After=local-fs.target` (the journal in `/var/lib`, hardn in `/usr/local/bin`), `After=sysinit.target` (the transient timer a re-arm creates requires and follows sysinit.target, systemd.timer(5), so `systemd-run` does not wait on a target that is not yet reached), `After=ufw.service` (the rollback's `ufw delete` finds ufw's rules loaded; an `After=` on a unit that is not installed orders nothing), plus `Conflicts=` and `Before=shutdown.target`, the shutdown ordering the defaults would have given.
    - **Ordering only.** There is no `Requires=`, `Wants=`, `BindsTo=` or `RequiredBy=` on sshd's units (the test refuses them), so sshd starts whatever this unit does, including when it fails.
    - `TimeoutStartSec=7min`. A oneshot's start timeout "is disabled by default" (systemd.service(5)), and sshd waits for this unit, so a bound is needed. It is above everything `Boot` can take, 6 min 30 s (`TestBootUnitTimeout`): its own steps before a rollback (the journal read, the hash, the timer's state, the re-arm) under `bootStepTimeout`, 1 min; a rollback under its own `RollbackTimeout`, 5 min, which a re-arm that hung to its bound still gets in full; and the unit's removal after it under `cleanupTimeout`, 30 s. Under a shorter bound, systemd's stop at the timeout could land inside the rollback (signals are held, so after `TimeoutStopSec=` it is a `SIGKILL`), before sshd starts. It is the backstop for a hardn that hangs outside a command.

    `RemainAfterExit=yes` keeps the unit active once it has run, so systemd does not run it again in the same boot. `timer.boot` makes a second run harmless anyway (§2.2).
14. **OpenRC: `/etc/init.d/hardn-boot`**, `0755` root's, in the default runlevel ([`testdata/hardn-boot.openrc`](../../pkg/host/revert/testdata/hardn-boot.openrc)): `need localmount`, `after bootmisc firewall`, `before sshd`, and a `start()` that runs `<hardn> rollback --boot`. `firewall` is a virtual service: Alpine's `iptables`, `nftables` and `ufw` scripts `provide firewall` (§3), so the unit starts after whichever of them is in a runlevel, and with none it orders nothing (ufw is not added to a runlevel by `ufw enable`, [ufw.md](ufw.md) §6). Per OpenRC's service-script guide, `after`/`before` set "start order only" and need sets a hard dependency, so sshd starts whatever this service does. sshd is never `need`ed or `use`d (the test refuses both).
15. **Planned and shown, before the first `Arm` on a host** (`PlanBootUnit`, pure; `ReadBootUnit`, read-only). The plan line names what will be written and run, or says that the unit is installed and enabled already. `PlanBootUnit` refuses a hardn path the unit or the script could not name unquoted (only letters, digits and `/._+-`; no space, no systemd `%` specifier, nothing the shell reads: `ErrExecutable`) and an init system that is not running (`ErrNoTimer`, as for the timer). The path and the binary are hardn's (`Options.Hardn`), the same one the timer runs.
16. **Installed idempotently, atomically, checked first** (`EnsureBootUnit`, `TestEnsureBootUnit`):
    - **Refused while a change is journalled** (`TestEnsureBootUnitPending`): `pending.json` or `rollback.json` there is a `*PendingError` (`Is(ErrPending)`), as `Arm`'s, before anything is written or run, also when the unit is installed as planned already. The unit is the journalled change's boot-time recovery. Rewritten for another hardn binary (a second command run with another `--hardn`, or a second hardn install), it would run that binary at boot, which leaves the change alone (§2.2), so a second change that `Arm` then refused would have taken the first one's recovery away under a "not applied". `p2drive` refuses such a command at its plan already (§2.18).
    - A unit installed as planned (same content, mode `0644`/`0755`, owner root) and enabled (its link is a symlink to it: `multi-user.target.wants/hardn-boot.service`, `/etc/runlevels/default/hardn-boot`) is left as it is. Nothing is written or run (`Already`). `ReadBootUnit`'s state carries the file's content, mode and owner (`BootUnitState.Data`, `Mode`, `UID`), so a plan can show a diff of a different file against `BootUnit.Data` (`pkg/diff`).
    - A missing or different file is replaced. First a copy is written in the change's run directory under the unit's own name and checked: `systemd-analyze verify --recursive-errors=no <copy>`, which fails on a warning about this unit alone; without the option, verify exits 0 "regardless whether warnings arise" (systemd-analyze(1)). Verify catches, among other things, an `ExecStart=` binary that is not there or not executable. On OpenRC the check is `sh -n <copy>`, the script's syntax. A checker that is not installed (`host.ErrNotFound`) checks nothing: the log says the unit is written unchecked. Any other failure refuses the unit (`ErrBootUnit`), and the copy is removed either way.
    - A file already at the path is backed up into the change's backup run (`backup.Optional`; nothing rolls it back, since the unit outlives the change), then the unit is written with `WriteFileAtomic`, root's, with its mode.
    - Then `systemctl --no-reload enable hardn-boot.service` or `rc-update add hardn-boot default` runs, unless the link is there, and the link must be there afterwards (`ErrBootUnit`). `--no-reload` skips the implicit `daemon-reload` that `enable` would do (systemctl(1)): systemd reads the unit at the next boot, and a `daemon-reload` now would rerun `sshd-socket-generator` on a socket host over files the plan has not always checked are in effect. The new file leaves every unit's `NeedDaemonReload` at `yes` until the next `daemon-reload`, so `systemctl` warns ("changed on disk … Run 'systemctl daemon-reload'") on the units it is asked about: on Debian 13 the change's own `systemctl reload ssh.service` printed it ([vmtest.md](vmtest.md) §4.9, the Phase 3 run). That is harmless and kept; a port change on a socket host runs its own `daemon-reload` anyway.
    - **A failure refuses the change**: nothing is armed (p2drive: "not applied"). A lockout-risk change whose timer a reboot would lose, with nothing to re-arm it, is what P-34 (c) closes. Each failure is tested: the journal, the unit or its link unreadable, the copy or the unit not written, the check refusing, the stale file's backup failing (the file then stays as it was), the enable failing or making no link, a file where the link goes, an unclean work directory.
17. **Removed at a boot that finds nothing journalled** (`RemoveBootUnit`; `TestRemoveBootUnit`, `TestBoot`).
    - **When:** at the end of `hardn rollback --boot`, when nothing is journalled: nothing was, it was confirmed meanwhile, or the boot's own rollback finished. That boot's run is the unit's last. The unit therefore lives from the first `Arm` on a host until the first boot after the change ends, and the next lockout-risk change installs it again (§2.15). Between changes, no hardn runs at boot.
    - **How:** it runs `systemctl --no-reload disable hardn-boot.service` or `rc-update del hardn-boot default` while the link is there, then removes the file, and checks that neither is left. On systemd it then runs `systemctl daemon-reload` (`BootUnit.Reload`): the removal left every unit's `NeedDaemonReload` at `yes`, and `systemctl` warned on `ssh.service` until a reload (found by the Phase 3 VM run, [vmtest.md](vmtest.md) §4.9). At boot the files are those `sshd-socket-generator` read at this boot, or those the boot's rollback restored and reloaded, so the rerun changes nothing, and a `daemon-reload` from this unit at boot is run (the Ubuntu 26.04 rollback at boot ran one). A failed reload is logged, and the unit is removed all the same (`TestRemoveBootUnitReloadFails`). A failure part-way is `BootResult.RemoveErr`, a warning (exit 0), with `Removed` false (`TestRemoveBootUnitFailures`, `TestBoot`).
    - **Only hardn's file is removed.** A file at the path that holds anything but the unit hardn installs (edited by hand, an older hardn's text, or not hardn's at all) is disabled, kept and reported (`ErrBootUnit`: "check it, then remove it by hand"), since nothing backs it up at boot (`TestRemoveBootUnitFailures`, `TestRevertBootCommand`). Disabled, it no longer runs at boot; the next lockout-risk change backs it up and replaces it (§2.16).
    - **Never while a change is journalled:** `pending.json` or `rollback.json` there is a `*PendingError` (`Is(ErrPending)`), and nothing changes.
    - **Not removed by `hardn confirm` or `hardn rollback <id>`**, a decision of this unit. Those run while an engine may be about to `Arm` the next change (the run lock is `p3-steps`'), and the boot unit is harmless when nothing is journalled.
    - An uninstall (`p7-install`) calls the same primitive.
18. **`p2drive` installs it with every lockout-risk command** (`port`, `keyonly`, `pve-root`, `ufw-enable`, `migrate --apply`, and `sudoers` when its plan is lockout-risk), shown in the plan and run after the backup run is opened and before `Arm` (`TestPort2230`, `TestPortOpenRC`, `TestBootUnitInstalled`):
    - `--plan-only` and every plan-time refusal install nothing;
    - a change journalled already refuses the plan ("refused before anything changed", the `*PendingError`), before the unit is shown or touched: a second command with another `--hardn` leaves the first change's unit as it was ("a change journalled already");
    - an installed unit is left as it is;
    - a stale one is backed up into the change's run, unjournalled, and replaced;
    - a check that refuses the copy arms nothing.

    The unit runs the `--hardn` binary, the one the timer runs. `backup.Open` now runs before `Arm`, so a relative `--backup-path`, which `backup.Open` refuses, is refused before anything changes rather than rolled back after the timer. `backup.Open` reads no directory: one that cannot be written is found at the first backup, the stale unit's here, or the change's own after `Arm`.

### Through `host.System`

19. Everything is in `pkg/host/revert`, which depguard's `revert-through-host` and `host-stdlib` cover (no `os`, `syscall`, `net` but `net/netip`, …). There is no new package and no new rule. The hash is `crypto/sha256` over `ReadFileNoFollow`. hardn's own path comes from `cmd/hardn` (`os.Executable`), as for the timer ([revert.md](revert.md) §2.23).

## 6. Inputs to later units, open items, size

- **`p3-engine` and `p3-steps`.** Before the first `Arm` of a lockout-risk change, check `ReadState` and refuse the change while one is journalled, before the boot unit is shown, as `p2drive` does (`EnsureBootUnit` refuses it anyway, with a `*PendingError`, before it writes anything: §2.16). Then plan `PlanBootUnit` over detect's `Init` and `Options.Hardn`, and show it with `ReadBootUnit` in the plan, with a diff of a different file from `BootUnitState.Data`. In the apply, `EnsureBootUnit` runs before `Arm`, with the change's run directory and backup run, and a failure refuses the change, as `p2drive` does (§2.18). The countdown reads `Deadline()`: after a re-arm with an untrusted clock it is by the clock at boot (§2.12), so say "about", or count down to the timer's own trigger time, as [vmtest.md](vmtest.md) §4.9 already asks. The run lock should cover `EnsureBootUnit` with `Arm`, and `hardn rollback --boot`'s removal: a boot command run by hand between another process's `EnsureBootUnit` and its `Arm` would find nothing journalled and remove the unit (at boot, nothing else runs). [README.md](README.md) lists it under `p3-engine`. **Closed by `next/p3-engine-boot`** ([engine-boot.md](../engine/engine-boot.md)): the engine plans the unit as a change of its own, `StageBoot`, shown first, refused while a change is journalled, and installs it under the run lock before `Arm` (§2.1 to §2.5); `p2drive` holds the same run lock (§2.10); `Boot` tries it once, never waits, holds it to its end, and keeps the unit while an apply holds it (§2.11), as `RemoveBootUnit` does (§2.12). Also changed there: `Boot` reads the journal, and writes a re-armed one only over the journal it read, under a journal lock (§2.7), and a change of this boot whose timer is not there while another hardn holds the run lock is left to that hardn's apply when it is not applied yet (`apply-runs`, `BootReasonApplyRuns`), and left to the person, not re-armed, when it is (`run-lock-held`, `BootReasonRunLockHeld`, `BootLeft`): two new reasons, which §5's list predates. The countdown's "about" is `p3-output`'s still.
- **`p3-output`:** registry codes for `ErrBootUnit`, and for each `BootReason` (the stable values of §5, so no consumer reads `Why`), and the words of the command's lines, which are provisional. **An exit-code decision too**: `hardn rollback --boot` exits 1 for `BootLeft` (§2.10), where the brief's 1 is "Error. Anything already applied was rolled back"; here the change is not acted on and stays applied. `hardn confirm`'s and `hardn rollback`'s refusals already exit 1 the same way. Before the codes are released, `p3-output` registers this meaning of 1 or gives it a code of its own. The boot-time rollback leaves the timer's notice, "rolled back at …, because it was not confirmed within 180s", also for an apply a reboot interrupted, or a timer that could not be re-armed. The unit's journal has the true reason. A notice of its own is `p3-output`'s to shape.
- **`p7-install`:** an uninstall calls `RemoveBootUnit` (never while a change is journalled).
- **Known limits.**
  - A rollback that both claims and finishes between `Boot`'s read and its write leaves `pending.json` written again, re-armed. The timer then rolls the change back a second time, which is idempotent. This is the same limit as `Record`'s ([revert.md](revert.md) §7). *Closed by `next/p3-engine-boot`* for a rollback of this hardn: its claim, and `Boot`'s comparison and write, are under the journal lock ([engine-boot.md](../engine/engine-boot.md) §2.9).
  - Rebooted repeatedly with an untrusted clock inside each window, the change is re-armed for the whole window each time.
  - After a re-arm with an untrusted clock, the journal's deadline is by the clock at boot. Once that clock is corrected, the notice may call the change overdue while its timer runs, and a `hardn rollback <id>` before the timer is classed `timeout` (§2.12). The timer and `Confirm` are not affected.
  - In the boot a timer was started in, one that has fired reads `active` as well (§3, `RemainAfterElapse=`). Its rollback claims the change first (`rollback.json`, which `Boot` leaves to that rollback), so a change still pending beside a fired timer means that rollback did not get as far as its claim (its binary did not run, or it could not read or claim the journal); a run by hand in that boot then says the timer is there. The run log has the timer's failure, and `hardn rollback <id>` undoes the change.
  - After a reboot, an `sshd-session` that happens to get the pid and start time of one the journal saw at `MarkApplied` is refused as an old connection (`ErrOldConnection`). Another new connection confirms.
