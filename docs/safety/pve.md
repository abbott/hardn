# Proxmox VE: root key-only, SSH on 22, the cluster's keys and pve-firewall (`pkg/host/pve`)

> **Unit:** refactor plan Phase 2, `next/p2-pve` (decision §3.18, approved 2026-10-17: no SSH port change on Proxmox VE; brief §2 decision "Proxmox hosts: no UFW, and root SSH stays key-only"; brief 2.5). V-numbers: V8 on Proxmox VE (the port), V10 (UFW on Proxmox VE) and V11 (`PermitRootLogin no` on Proxmox VE) ([side-effects.md](../refactor/phase0/side-effects.md)); risk R15 (plan §4); the open item `next/p0-hazards` left to this unit (legacy `ConfigureSSH` can write an `AllowUsers` that excludes root). The choice to add root to such an `AllowUsers`, rather than refuse it, is [P-36](../refactor/proposals.md#p-36).
> **Status:** built and tested on macOS against the recording fake (`hostfake`) only, with synthetic Proxmox VE 9 fixtures (`pkg/host/pve/testdata/pve9`) written from the sources in §3, not captured from a host. Nothing has run on Linux or on Proxmox VE; §4 is the manual checklist, "written, not run (gate 5)".

On a Proxmox VE host hardn keeps root's SSH login key-only and never `no`, keeps sshd on port 22, keeps root reachable by key from the other nodes, edits root's keys through Proxmox VE's link to the cluster-wide file and never over it, never locks root's password, and reports `pve-firewall` instead of using UFW. `pve.PlanSSH` and `pve.CheckPort` apply those rules to what hardn is about to write; `pve.CheckSSH` reads `sshd.ReadEffective`'s values and the Match blocks of sshd's files against them; `pve.ReadKeys`, `PlanKeys`, `ApplyKeys`, `UndoKeys` and `RollbackKeys` edit `/root/.ssh/authorized_keys`; `pve.CheckAccount` guards root's password; `pve.ReadFirewall` reads `pve-firewall`'s state.

## 1. Why

origin/main treats Proxmox VE as Debian: it enables UFW (V10), writes `PermitRootLogin no` (V11), changes the SSH port before anything allows it (V8) and writes an `AllowUsers` that can leave root out (`docs/refactor/p0-hazards.md`, "Still open", on `next/p0-hazards`, which is not in this stack). On Proxmox VE each of those can cut a cluster apart: the nodes log in to each other as root, by key, on port 22, for the console proxy, migration and replication; UFW competes with `pve-firewall` and can cut off the web UI on 8006 and corosync; and root's `authorized_keys` is a link to a file every node shares, so renaming a new file over it breaks the link, and any key hardn adds or removes there applies to every node (plan R15; [phase0-findings.md §10](../refactor/phase0-findings.md#10-verify-list-brief-9), "Proxmox join / detection"). Brief §3 principle 1: never lock the user out.

## 2. Guarantees

### Which hosts (`Applies`)

1. **Only on Proxmox VE, and never on a guess.** Every entry point that decides whether a rule applies takes `detect.Detect`'s `Proxmox` fact ([detect.md](detect.md) §2.8): `PlanSSH`, `CheckPort`, `CheckSSH`, `CheckAccount`, `ReadKeys`, `ApplyKeys`, `UndoKeys` and `ReadFirewall`; `RollbackKeys` detects it itself (item 12). `PlanKeys` works on what `ReadKeys` read, and `RootGroups` is not Proxmox VE's. `Installed` Yes applies the rules; No leaves the input as it is (`PlanSSH` returns a copy, `CheckPort` and `CheckAccount` return nil) or is `ErrNotApplicable` (`CheckSSH`, `ReadKeys` and so `ApplyKeys` and `UndoKeys`, `ReadFirewall`); anything else is `ErrProxmoxUnknown`, wrapping detect's reason, never "not Proxmox VE": V10 and V11 are critical. The rules that need the cluster file system (the keys, the firewall) also need `ClusterFS` Yes: pmxcfs leaves `/etc/pve` as an empty directory when it stops, so with it down the files are not there (§3).
2. **No UFW.** UFW is the `ufw` unit's, and its `ufw.Applies` already returns `ErrNotApplicable` on Proxmox VE and `ErrProxmoxUnknown` when that is not established ([ufw.md](ufw.md) §2.1); `TestNoUFW` pins it from this side. The firewall status on Proxmox VE is `ReadFirewall` (item 14).

### SSH settings hardn writes (`PlanSSH`, `CheckPort`)

3. **`PermitRootLogin prohibit-password`, always.** `PlanSSH(p, desired, root)` takes the settings hardn wants in `00-hardn.conf` (`[]migrate.Directive`, as [sshd-migrate.md](sshd-migrate.md) §6 hands them on) and sets every `PermitRootLogin` to `prohibit-password` (`no`, `yes` and `forced-commands-only` alike; `without-password` is the same value, sshd_config(5)), and adds one when `desired` has none: Proxmox VE's installer and `pvecm` write `PermitRootLogin yes` into `sshd_config`, which the drop-in must beat (§3). Each change is a `FindingRootKeyOnly` whose detail ends "root: key-only (required by Proxmox clustering)", the wording brief 2.5 asks for. It never writes `no` on Proxmox VE, whatever the configuration says (V11).
4. **SSH stays on port 22 (§3.18).** A `Port` other than exactly 22 (a second port, a service name) and a `ListenAddress` with an explicit port other than 22 (`0.0.0.0:2230`, `[::]:2230`) are refused with `ErrPortChange`, whose text gives the reason: "cluster SSH and pve-firewall's management rule use port 22". A `ListenAddress` with no port, or on 22, passes the port rule. `CheckPort(p, ports)` is the same rule for a port change itself: nil for no change or `{22}`, `ErrPortChange` for anything else on Proxmox VE, `ErrProxmoxUnknown` when that is not established. Nothing here moves a host that already listens elsewhere back to 22; `CheckSSH` reports it (item 6).
5. **root stays reachable by key from the other nodes, as far as these checks go.** sshd's checks, in sshd_config(5)'s terms (§3), have to let root in with a node's key:
   - an `AllowUsers` with no entry matching root from every host (`root`, `r*`; not `root@192.0.2.0/24`, since the other nodes' addresses are not read) gets `root` added to its first line, with a `FindingRootAdded` (`AllowUsers alice` becomes `AllowUsers alice root`). [P-36](../refactor/proposals.md#p-36) asks the maintainer whether to keep this or refuse instead;
   - refused with `ErrRootExcluded`: a `DenyUsers` entry whose user part matches root (with or without a host); a `DenyGroups` pattern matching one of root's groups, or any `DenyGroups` when root's groups are not established; an `AllowGroups` matching none of them; `PubkeyAuthentication no`; an `AuthenticationMethods` with no list that is `any` or exactly `publickey` (a node's `BatchMode` login offers its one key, and `publickey,publickey` "requires successful authentication using two different public keys"); an `AuthorizedKeysFile` that names neither `.ssh/authorized_keys`, `%h/.ssh/authorized_keys`, `/root/.ssh/authorized_keys` nor `/etc/pve/priv/authorized_keys` (origin/main's `.ssh_%u` alone, V5); a `PubkeyAcceptedAlgorithms` (or its alias `PubkeyAcceptedKeyTypes`) that accepts neither `rsa-sha2-512` nor `rsa-sha2-256`, the signatures of the nodes' `ssh-rsa` root keys (a list of patterns, `!` excluding; a `+` or `^` list keeps the default set, which has both; a `-` list removes what its patterns match); and `ListenAddress` lines that are all loopback (`127.0.0.1`, `[::1]:22`, `localhost`), which no other node can reach;
   - a `FindingRootUnreachable` saying it is not established, not a refusal: `ListenAddress` lines that leave out every address of a family (no `0.0.0.0`, no `::`, or only in a routing domain: `ListenAddress 192.0.2.10`, `ListenAddress 0.0.0.0` alone), and an `AddressFamily` other than `any`. These replace sshd's default of every address, and the nodes' addresses and family are not read;
   - `root` comes from `RootGroups(ctx, sys)`: a `Groups{Names, Known}` of root's primary group (`LookupUser`) and every `/etc/group` line listing root. A group file with no line for root's group id is `fs.ErrNotExist`, as is a missing file; with `Known` false only the group `root` counts.

   That is the whole of what is checked. Not read: `RequiredRSASize`, `MaxAuthTries`, `ForceCommand`, `ChrootDirectory`, `PubkeyAuthOptions`, what a `ListenAddress` host name resolves to, and the other files' lines (`PlanSSH` sees hardn's settings; `CheckSSH` sees the result). Patterns are sshd's `*` and `?` (ssh_config(5), PATTERNS). A `Match` or `Include` line is refused with `fs.ErrInvalid`, as `migrate.PlanFor` refuses it, since these rules read every line as global. `PlanSSH` never changes its input slice.

### SSH as sshd reads it (`CheckSSH`)

6. **Read from `sshd -T` and from the files, never guessed.** `CheckSSH(p, in)` takes an `SSHInput`: `Effective`, `sshd.ReadEffective`'s ([sshd-effective.md](sshd-effective.md)); `Main` and `DropIns`, the files sshd read (`migrate.Find`'s), for their `Match` blocks; and `Root`, `RootGroups`' answer. It returns three facts as `detect.Tri`, with findings saying why any is not Yes:
   - `RootKeyOnly`: `PermitRootLogin` is `prohibit-password` (OpenSSH 10.0p1, on Proxmox VE 9, prints `without-password`, which `Effective` already reads as `prohibit-password`), globally and in every `Match` block. Another value, global or in a block (`Match Address 192.0.2.0/24` with `PermitRootLogin yes`), makes it No with a `root-not-key-only` finding naming the value and, for a block, its file, line and `Match` line. Unknown when the global value is not established or the files were not given;
   - `RootByKey`: root can log in with a key from the other nodes. Each keyword of item 5 is checked on the effective value: any that keeps root out makes it No, and one that is not established or restricts root to some hosts (a `USER@HOST` pattern) makes it Unknown. `AuthorizedKeysFile` must read root's file or, failing that, `AuthorizedKeysCommand` be `none` for a No (a command may supply root's keys: Unknown). `PubkeyAcceptedAlgorithms` is the list sshd resolved and printed. The listeners must be established (`Listeners.Known`) and cover every address of both families: all loopback is No (`ListenAddress 127.0.0.1` alone), anything narrower than `0.0.0.0` and `::` is Unknown. sshd -T's `listenaddress` lines follow `AddressFamily` (servconf.c resolves the default addresses for that family, §3), so `AddressFamily inet` shows as IPv4 only there; on a socket-activated host the socket's listeners are read instead, a `[::]` there being dual-stack ([reload.md](reload.md) §3);
   - **`Match` blocks**, read from the files with `sshd.ReadOrder` (Evaluate's reading order: the drop-ins at the stock `Include`, a drop-in's own blocks ending with it). A line of a checked keyword under a `Match` block that may keep root out (`Match Group root` with `PermitRootLogin no`, `Match User root` with `AuthenticationMethods publickey,password`, a drop-in's `PubkeyAuthentication no`) makes `RootByKey` Unknown; one that lets root in where the global value keeps it out (`PermitRootLogin no` globally, `prohibit-password` for the cluster's network) turns that keyword's No into Unknown; an `AuthorizedKeysCommand` counts for `AuthorizedKeysFile`. A block's criteria are not evaluated, so which connections it matches, the nodes' among them, is not established. Without the files (`Main` nil) `RootByKey` is Unknown and `RootKeyOnly` at best Unknown. `Effective.Overrides` is not read: the probes only show connections they could make (an untargeted block is probed as `hardn-probe`, not as root), and the files show every block;
   - `Port22`: the Port set is `{22}` and every listener, sshd's `listenaddress` lines and on a socket-activated host `ssh.socket`'s `Listen` entries, is on 22; otherwise No, with a `FindingPortNot22` naming each and the reason. Unknown when the Port set or the listeners are not established: on Debian and Proxmox VE `ssh.socket` is opt-in and has no generator ([phase0-findings.md §10](../refactor/phase0-findings.md#10-verify-list-brief-9)), so its `ListenStream` can differ from `sshd_config`, which sshd's package reports as `sources-disagree` with `Listeners.Known` false; a socket on 2230 while sshd -T says 22 is Unknown, never "port 22" (tested).

   `sshd -T` prints `authenticationmethods any` when none is set, `authorizedkeysfile` with sshd's default files, `authorizedkeyscommand none` when none is set, and `pubkeyacceptedalgorithms` with the resolved list (§3), so a missing line is Unknown, not a default. Off Proxmox VE `CheckSSH` is `ErrNotApplicable`, and `ErrProxmoxUnknown` when that is not established.
7. **Proxmox VE's own `PermitRootLogin yes` is not drift.** A `shadowed` conflict ([sshd-effective.md](sshd-effective.md) §2.9) whose other line is `PermitRootLogin yes` in `/etc/ssh/sshd_config` is reported as a `FindingProxmoxRootLogin` ("expected, not drift"), with its file and line. The same keyword at `no`, in a drop-in, or as an `overridden` line (read before hardn's) is not Proxmox VE's line and is not classified so (tested). Before hardn writes its drop-in, `yes` is simply the value: `RootKeyOnly` is No, with a `root-not-key-only` finding. On a host without the stock Include, where hardn's block sits at the top of `sshd_config`, `pvecm create` and `add` rewrite hardn's own first `PermitRootLogin` line to `yes` ([sshd-validate.md](sshd-validate.md) §2.1, `clobberable`); `CheckSSH` then reports `RootKeyOnly` No, as it should.
8. **What `CheckSSH` does not see.** It reads configuration (`sshd -T` and the files), not what a daemon that has not reloaded runs with; the files passed in should be read with `ReadEffective`, as a change between the two readings is not detected. Only the keywords of item 5 are read. A `Match` block's criteria are never evaluated, so a block that may change root's login is Unknown, never a guessed Yes or No (only its `PermitRootLogin` value is read for `RootKeyOnly`). The caller reports `ReadEffective`'s findings (`match-untargeted`, `sources-disagree`, `effective-unknown`) beside these.

### Root's keys (`ReadKeys`, `PlanKeys`, `ApplyKeys`, `UndoKeys`, `RollbackKeys`)

9. **Through the link, never over it.** `ReadKeys` refuses anything but the state Proxmox VE keeps: `/root/.ssh/authorized_keys` a symlink, resolved with `ResolveSymlink` (so one in a directory another user can change is `host.ErrSymlinkParent`, [atomic.md](atomic.md) §2.6), to exactly `/etc/pve/priv/authorized_keys`, which exists. A regular file, a missing link, a link elsewhere and a missing cluster file are `ErrKeysLink` (`pvecm updatecerts` restores that state, and `pveproxy` runs it at every start, §3; hardn does not); pmxcfs not mounted is `ErrClusterFSDown`, so nothing is ever written into the empty `/etc/pve` directory under the mount point; any other read error is the host's (tested). It reads the file with `ReadFileNoFollow`, the cluster's node names from `/etc/pve/nodes`, and this node's own root key from `/root/.ssh/id_rsa.pub` when there is one. `ApplyKeys` writes with `host.WriteFileThroughSymlink` (atomic.md §2.3), so the new file is renamed over the cluster file inside `/etc/pve/priv`, and the link itself is never written, renamed or replaced (tested: no call names it, its target is unchanged, and `backup.Restore` restores through it).
10. **Edits keep every other line.** `PlanKeys(k, KeyEdit{Add, Remove})` is pure. A line to add must be one authorized_keys key line (sshd(8), AUTHORIZED_KEYS FILE FORMAT: optional options, with spaces only inside double quotes; a key type; a base64 key whose blob starts with that type's name, RFC 4253 §6.6; a comment), else `ErrBadKey`; it is appended unless a line with the same type and key is there (options and comment are not compared, so a key is never there twice). A key to remove is named by any line with its type and key, and every line with them goes. Comments, blank lines, options and order are kept byte for byte. **Removing a cluster node's root key is refused** with `ErrClusterKey`: this node's (`id_rsa.pub`), or one whose comment is `root@<node>` for a node in `/etc/pve/nodes` (the other nodes log in with them; the comment convention is **[unverified]**, §3), and so is an edit that leaves no key. Every plan that changes the file carries a `FindingClusterWide`: "the change applies to root on every node of the cluster". `Narrows()` (a key removed) marks a lockout-risk change for `p2-revert`; adding one is not.
11. **Backed up first, and never over a change it did not plan.** `ApplyKeys(ctx, sys, p, run, plan)` needs a backup run (`ErrNoBackup` without one) and reads the keys again: it refuses with `ErrKeysChanged` when their SHA-256 or the link's target is not what the plan was made from (another node, or `pvecm updatecerts`, wrote the file meanwhile: pmxcfs replicates it). It then plans the plan's `Added` and `Removed` again on the keys it read, with `PlanKeys`' guards (`ErrClusterKey`, `ErrBadKey`), and refuses with `ErrPlanMismatch` when that is not the plan's `New`, so a plan changed or lost on its way (a hand-built one, `New` dropped in a round trip, `Added` edited) writes nothing (tested). It takes a `RollbackRequired` backup of `/root/.ssh/authorized_keys` (which records the link, its target and the cluster file's content, atomic.md §2.12), then writes with mode `0600` and the owner left alone: pmxcfs accepts a chmod to `0600` under `priv/` and no other, and a chown only to root and `www-data` (§3). A backup that fails stops the write; a write that fails (pmxcfs is read-only without quorum, §3) leaves the file as it was and returns the backup taken with the error (both tested with the fake failing). A plan with no change writes nothing.
12. **The undo keeps other nodes' keys.** `UndoKeys` reverses a plan on the file as it is now: it removes every line with a key the plan added, puts back each line the plan removed that is not there verbatim (a key removed from two lines, one with `from=`, gets both back; tested), and leaves every other line. Restoring the whole file from the backup would drop a key another node wrote in the meantime (tested: bob's key, added "on another node" after the apply, survives the undo). While the keys are still what the plan was made from it writes nothing (tested), so it is harmless before `ApplyKeys` has run, as `p2-revert`'s write-ahead journal needs. It is the inverse of the edit, not of the write: when another node added a key the plan added, or removed one it removed, the undo reverses that too; it does not guard node keys (it only removes what the plan added) and does not compare-and-swap, so a write by another node between its read and its write can still be lost. `RollbackKeys(ctx, sys, plan)` is `UndoKeys` with Proxmox VE detected again (`detect.DetectProxmox`), as `p2-revert`'s rollback runs it, from the journal in another process; `KeysPlan` round-trips through `encoding/json` with every field (tested), and `KeysUnit` (`"pve-keys"`) names it there (§6). Run either under `context.WithoutCancel` after Ctrl-C ([system.md](system.md) §2.5).

### Root's password (`CheckAccount`)

13. **Never locked, deleted or expired.** `CheckAccount(p, user, op)` returns `ErrRootPassword` for root on Proxmox VE for `OpLockPassword` (`passwd -l`, `usermod -L`), `OpDeletePassword` (`passwd -d`) and `OpExpireAccount` (`usermod -e 1`, `chage -E 0`), whether pmxcfs is up or not: the cluster join logs in to the existing node's API as `root@pam` with the password (§3), and the web UI's `root@pam` login uses it too **[I]**, while SSH stays key-only. `ErrProxmoxUnknown` for root when that is not established; nil for any other user, or another host. Changing root's password is not one of these ops. No code path in hardn locks a password today (legacy included); this is the guard the user-management slice calls.

### The firewall, read-only (`ReadFirewall`)

14. **Read, never changed or run.** `ReadFirewall(ctx, sys, p)` reads `/etc/pve/firewall/cluster.fw` and `/etc/pve/local/host.fw` (pmxcfs's link `local` → `nodes/<node>`, the directory pve-firewall reads `host.fw` from) and runs exactly one command, `systemctl is-active` of the unit that applies them: `pve-firewall.service`, or `proxmox-firewall.service` when `host.fw` sets `nftables: 1`. It never runs `pve-firewall status`, which takes the firewall's lock and compiles the rules, never touches UFW, iptables or nftables, and writes nothing (tested on every case: no call that changes the fake, and the one run). With pmxcfs not mounted it makes no call at all and every field is Unknown with `Err` wrapping `ErrClusterFSDown`. Off Proxmox VE it is `ErrNotApplicable` or `ErrProxmoxUnknown`; the only other error is a done context.
15. **The facts, read as pve-firewall reads its files.** Each file is read as Firewall.pm's `generic_fw_config_parser` reads it (§3): each line trimmed of spaces and tabs; `#` lines and blank lines skipped; a section header only in its exact form, in any case and alone on its line: `[OPTIONS]` and `[RULES]`, and in `cluster.fw` also `[ALIASES]`, `[GROUP name]` and `[IPSET name]` (these two with an optional `# comment` and a name of the form pve-firewall accepts); any other line belongs to the section before it, so `[OPTIONS] # datacenter` starts no section and a CRLF line end makes no header. A trailing `#` comment is cut from rules and IP set entries, never from options, whose forms are those of `parse_clusterfw_option` and `parse_hostfw_option`. **A line that names one of the options read here in another form** (`enable: 0 # maintenance`, `policy_in: ACCEPT # temporary`, `enable : 1`), **or outside a section**, pve-firewall skips with a warning and applies the default instead; here it makes that option Unknown, with `Err` naming the file and line (tested), rather than a value pve-firewall does not apply. A missing file is its defaults; a file that cannot be read makes what it decides Unknown.
   - `Enabled`: `cluster.fw`'s `enable` is 0 (also when unset) for off and 1 for on; a number above 1 is a time stamp that keeps the firewall on until 60 seconds after it and then off, which is Unknown here. `host.fw`'s `enable` is 0 or 1, 1 when unset. Yes needs both on, No either off;
   - `PolicyIn`: `cluster.fw`'s `policy_in`, `ACCEPT`, `DROP` or `REJECT` in any case, `DROP` when unset; `""` when not established;
   - `NFTables`: `host.fw`'s `nftables`, 0 or 1, 0 when unset;
   - `Unit` and `Service.Active`: the word systemctl printed (`IsActive()` reads it as detect does); a systemctl that fails to run leaves it `""`;
   - `Management`: the entries of `cluster.fw`'s IP set `management`, as written; pve-firewall adds the cluster's local network to that set itself (`pve-firewall localnet` shows it; not run);
   - a non-empty IP set `blacklist` is a `FindingBlacklist`: every host's firewall drops traffic from it;
   - `Err` is set whenever a field is Unknown, and says why; it wraps `ErrStateUnknown`.
16. **How far 22 and 8006 are let through (`Reach`).** "Allowed" is never a bare yes, because pve-firewall's own rule allows both ports only from the management IP set (§3):
   - not established whether the firewall is on, or the service not active (a stopped service leaves whatever rules it loaded, which are not read; a running one rereads the files every 10 seconds): `ReachUnknown`;
   - firewall off, service running: `ReachNotFiltered` (pve-firewall filters nothing; other packet filters are not read);
   - `nftables: 1`: `ReachUnknown`, with a `FindingNotModelled` (proxmox-firewall is a tech preview and its rules are not read);
   - otherwise `ReachAnywhere` for policy `ACCEPT`, `ReachManagement` for `DROP` or `REJECT` (an accept rule may let more sources in), **unless something may drop the port first**. pve-firewall drops the blacklist's sources, then applies the host's rules, then the cluster's, all before its built-in management rules (§3). So with the firewall on, a non-empty `blacklist` makes both ports `ReachUnknown` (its entries are not compared with the management set or the sources that reach the port), and so does every enabled rule in `host.fw`'s or `cluster.fw`'s `[RULES]` that may drop or reject a new TCP connection to the port, with a `FindingRuleMayBlock` naming the file and line. "May" is decided conservatively: `ACCEPT`, a macro with `(ACCEPT)`, an `OUT` or `FORWARD` rule, a disabled (`|`) rule, a rule for another protocol (`-p udp`) and one whose numeric `-dport`/`--dport` list leaves the port out cannot; a `GROUP` (security groups are not read), any other macro (its ports are not read), a port by name and anything else may, including a line pve-firewall would reject.

   `Reach`'s `String` is a stable code, `unknown`, `not-filtered`, `anywhere` or `management` (`TestReachCodes`); the words a status shows are `pkg/ui`'s.

### Through `host.System`

17. Every read and write goes through `host.System` and is in the run log; the package's non-test files may not import `os`, `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` (`net/netip` excepted, for a `ListenAddress`'s address) or `plugin` (depguard rule `pve-through-host`, checked with a probe file importing `os`). Finding codes are stable (`TestFindingCodes` walks every kind up to the last): `root-key-only`, `root-allowed`, `proxmox-root-login`, `port-not-22`, `root-unreachable`, `cluster-wide-keys`, `rule-may-block`, `blacklist`, `firewall-not-modelled`, `root-not-key-only`.
