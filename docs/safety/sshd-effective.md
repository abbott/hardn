# sshd effective values (`pkg/host/sshd`)

> **Unit:** refactor plan Phase 2, `next/p2-sshd-effective` (brief 2.2, "after installing it, run `sshd -T` and confirm the effective values"; brief §3 principle 3; brief §2 decision "hardn's SSH settings live in `00-hardn.conf`"). V-numbers: V13 (another drop-in decides the value; status read from files, not `sshd -T`), the post-install half of V7 (`sshd -T` after activation), and the configured listener set that V9's and V12's fixes need (`p2-ufw`, `p2-reload`) ([side-effects.md §8](../refactor/phase0/side-effects.md)). Brief corrections it implements: [phase0-findings.md §12](../refactor/phase0-findings.md#12-proposed-adjustments-to-the-brief), rows 20 and 21 (C byte order; accumulating keywords compared as sets).
> **Status:** built and tested on macOS against the recording fake (`hostfake`) only, with `sshd -T` and `systemctl show` answers written in the format of their sources (§3), not captured from a host. Nothing has run on Linux; §4 lists what is "written, not run (gate 5)".

`sshd.ReadEffective(ctx, sys, req)` answers, once a configuration is installed: what does sshd read from the installed files, which listeners do sshd's files and `ssh.socket`'s unit configure, and which other files' lines beat, add to or lose to hardn's? It runs `sshd -T` (and one `sshd -T -C` per `Match` block) against the installed files, reads `ssh.socket`'s listeners when the socket may hold them, reads the files, and returns an `Effective` and a `[]Finding`. `sshd.Evaluate(in)` is the same computation over given inputs, with no I/O (for example `Validate`'s `Report.Effective` and `Report.Probes` with the candidate's files). Every source is configuration: neither shows what a running daemon that has not reread its files uses, nor which sockets are bound (§2.5).

## 1. Why

hardn's status was read from files (V13), and the drop-in it wrote, `hardn.conf`, sorts after `50-cloud-init.conf`, so cloud-init's `PasswordAuthentication yes` won and nothing said so ([side-effects.md](../refactor/phase0/side-effects.md), V13). sshd uses the first value it reads for most keywords, but keeps every value of Port, ListenAddress, AllowUsers and a few more, so a stray `Port 22` in any file keeps that port open after hardn moves to 2230, and a stray `AllowUsers bob` widens access ([phase0-findings.md §12](../refactor/phase0-findings.md#12-proposed-adjustments-to-the-brief), row 21). On Ubuntu 24.04 and 26.04 systemd holds the listening socket, so sshd's own Port says nothing about what accepts connections until `daemon-reload` and a restart of `ssh.socket` (V12). A firewall that allows the wrong set locks the user out (brief §3 principle 1).

## 2. Guarantees

### Effective values (`Effective`)

1. **sshd's own answer.** The values come from `sshd -T`'s output, one `keyword value` per line, never from grepping a file (brief §3 principle 3). Keywords are lower-cased (OpenSSH 10.4 and 10.5 print mixed case) and an alias reads as its keyword (sshd prints `kbdinteractiveauthentication`, but `challengeresponseauthentication` would read the same); every line is kept in `Effective.Keywords`. `sshd -T` reads the files on disk: a daemon that has not been reloaded or restarted since they changed still runs with what it read before.
2. **The lockout-relevant settings are typed and normalised.** `PermitRootLogin` (`prohibit-password`, `forced-commands-only`, `yes`, `no`), `PasswordAuthentication`, `KbdInteractiveAuthentication` and `PubkeyAuthentication` (`yes`, `no`) are `Setting{Value, Known}`, compared case-insensitively, with `without-password`, which OpenSSH before 10.1 prints, read as `prohibit-password` (one value in sshd's table). A value outside that list (sshd prints `UNKNOWN` or `unset` for some), a keyword printed twice with two values, or a missing keyword is Unknown (`Known` false, `Value` ""), with a `FindingUnknown`.

   **`UsePAM`** (`yes`, `no`; added by `next/p4-kbd-pam`, [check-ssh.md](../engine/check-ssh.md) §8) is read the same way, but for one case: **no `usepam` line is a build without PAM**, Known `no`, with `BuiltWithoutPAM` true. `sshd -T` prints `usepam` only in a build with PAM, before `permitrootlogin`, `pubkeyauthentication`, `passwordauthentication` and `kbdinteractiveauthentication`, which it prints whatever the build; in a build without PAM `UsePAM` is an unsupported keyword, logged and ignored, so PAM is not used whatever the files say (§3). That reading needs one of those four lines in the output; without any, `UsePAM` is Unknown too ("sshd -T printed no usepam"). On Linux PAM is keyboard-interactive's only device ([check-ssh.md](../engine/check-ssh.md) §2.11), which is what SSH Auth reads it for. Both fields describe the binary `sshd -T` ran (`EffectiveRequest.Binary`), not the daemon running: on Alpine that may be another build, a container's entrypoint choosing it, or `sshd.pam` started before `UsePAM yes` was removed, which a reload does not replace ([reload.md](reload.md) §2.6, **[I]**); SSH Auth weighs both ([check-ssh.md](../engine/check-ssh.md) §2.11, §6).
3. **Accumulating keywords are sets.** Port, AllowUsers, AllowGroups, DenyUsers, DenyGroups and AcceptEnv are `Set{Values, Known}`: every value sshd printed, in its order, without repeats; no line is the empty set. Port must be one or more numbers from 1 to 65535, or it is Unknown.
4. **Listeners are the configured listener set, not Port, and not bound sockets.** `Listeners.SSHD` comes from sshd's `listenaddress` lines (`0.0.0.0:22`, `[::]:22`, optionally ` rdomain <name>`), since a `ListenAddress` with a port of its own listens on a port Port does not list. A line that is not an address and a port is a `FindingUnknown`; the other lines are still read.
5. **The socket's listeners are added when the socket may hold them.** `SocketMayListen(ssh)` is true for `SSHSocket`, and for an Unknown SSH mode when detect asked systemd about `ssh.socket` and did not establish that it is neither enabled nor active (for example `ssh.socket` and `ssh.service` both enabled, which detect calls `ErrConflict`; or a Debian host opted into the socket, its port in `ssh.socket.d/listen.conf`, with `ssh.service` still enabled). `ReadEffective` then runs `systemctl show -p Listen ssh.socket` and reads each `Listen=<address> (Stream)` line into `Listeners.Socket`, with `SocketRead` true. `Listeners.All` is the union of the entries read, each listener once (0.0.0.0 and :: kept apart). Every entry that could be read is in `All`, whatever else failed (a bad `listenaddress` line, no `listenaddress`, unreadable `sshd -T` output keep the socket's), but `All` is complete only when `Known`: with `Known` false a source may be missing or unreadable, and the finding says which. `Known` needs, all of: every source read; with `SSHSocket`, the two sources agreeing, comparing every unspecified address as one (systemd's dual-stack `[::]:22` and sshd's `0.0.0.0:22` plus `[::]:22` accept the same connections); the files agreeing with `sshd -T` on Port (§2.6); and detect showing the unit that listens up (§2.6a). Disagreement between sshd and the socket is `FindingDisagree`; an entry that is not an IP address, a port and `(Stream)`, or no entry at all, is `FindingUnknown`. With the SSH mode Unknown the listeners are Unknown too (`FindingUnknown`: it is not known whether sshd or the socket listens), and the two sources are not compared.

   **What `Known` does not say.** Both sources are configuration. `sshd -T` reads the files; `systemctl show -p Listen` prints the socket unit's configured ports whether or not a descriptor is open (§3). So `Known` is true while nothing is bound on a listener it names: on a socket-activated host after `daemon-reload` (which rewrites the socket's `ListenStream`) and before `restart ssh.socket`, the two sources agree on the new port; on an `ssh.service` or OpenRC host, as soon as the files name a new port, before the reload. A port the running daemon still holds from before an unapplied change is then not in `All`. Options on the service's command line (`-f`, `-p`, `-o`, `-4`, `-6`) override the files and are not read (§3, **[unverified]** whether any host passes them).

6. **The files are checked against sshd.** For the typed settings and the sets, `Evaluate` predicts from the files what `sshd -T` should print: the first value outside any `Match` block, or every such value for a set. Where the files say something and sshd prints something else (a file changed between the two reads, or a rule this package does not model), the value is Unknown with a `FindingDisagree` naming both, never one of the two; when it is Port, the listeners (read from the same `sshd -T` output) are Unknown as well. A keyword with any line under a `Match` block, or a Port given as a service name, is not predicted, so no disagreement is claimed for it. `UsePAM` is not checked: a build without PAM ignores the files' `UsePAM` (§2.2).

   6a. **The unit that listens must be up.** With `SSHSocket`, `ssh.socket` must be active (`Socket.IsActive()` Yes: `active`, `reloading`, `refreshing`); with `SSHService`, `ssh.service` (`Service.IsActive()` Yes); with `SSHOpenRC`, OpenRC must have started sshd (`OpenRC.Started` Yes). A failed or stopped unit, or a state detect did not read, makes the listeners Unknown with a `FindingUnknown` naming the state: nothing may accept connections on them. These are detect's facts, read when detect ran ([detect.md](detect.md) §2.7); "up" is not "bound" (§2.5).
7. **Match probes.** `ReadEffective` probes each `Match` block as `Validate` does (`sshd -T -C`, the connection built by the same mirror of sshd's matching, [sshd-validate.md](sshd-validate.md) §2.6; an untargeted block is a `FindingMatchUntargeted`). Where a probe prints a typed setting or a user, group or environment set differently from `sshd -T`, it is an `Override{Block, Conn, Keyword, Value}`: a connection like `Conn` gets `Value` (a set's values joined by spaces). A probe whose output is not `sshd -T`'s form is a `FindingUnknown` at its block. A probe whose block may not apply to its connection shows nothing certain about the block ([sshd-validate.md](sshd-validate.md) §6).

### Conflict report (`Effective.Conflicts`)

8. **The read order is sshd's.** The configuration is flattened as sshd reads it: `sshd_config`'s lines, with every drop-in's at the `Include` line, in C byte order. `Evaluate` sorts the drop-ins it is given into that order and leaves out any the Include does not read (outside `sshd_config.d`, not `*.conf`, a leading `.`), so a caller's order cannot change the report. A drop-in starts under the `Match` block its Include is under (none for the stock first-line Include) and its own `Match` blocks end with it; `sshd_config`'s run to its end. Only `IncludeLine` is followed (`ReadEffective`, like `Validate`, refuses any other Include). Aliases read as their keyword (`ChallengeResponseAuthentication` and `SKeyAuthentication` as `kbdinteractiveauthentication`, `DSAAuthentication` as `pubkeyauthentication`, `HostDSAKey` as `hostkey`, and three more), and each `Subsystem` name is a keyword of its own (OpenSSH 10.3 keeps the first definition of each name; 9.2 refuses a second one, so there `sshd -T` fails first, §3).
9. **hardn's lines** are `Owner`: by default all of `00-hardn.conf`; in `IncludeNone` mode the caller names its block's lines in `sshd_config` (`Owner{File: MainConfig, First, Last}`). For each keyword hardn's lines set outside a `Match` block, every other line that sets it is reported, in read order, as a `Conflict{Kind, Keyword, Hardn, Other, Match, SameValue}` and a `Finding` at the other line:

   | The other line | Kind | Meaning |
   |---|---|---|
   | outside a Match block, accumulating keyword | `accumulates` | it adds values: `Port 22` elsewhere keeps 22 open |
   | outside a Match block, read before hardn's | `overridden` | sshd uses it, not hardn's (only the first such line, which wins; reported even when its value is hardn's, since hardn does not control it) |
   | outside a Match block, read after hardn's, another value | `shadowed` | no effect while hardn's line is there (cloud-init's `50-cloud-init.conf`, Proxmox VE's `PermitRootLogin yes` in `sshd_config`): reported, never edited (brief 2.2) |
   | under a Match block | `match-override` | for the connections the block matches, sshd uses it in place of hardn's |

   A line of hardn's own under a `Match` block is a `match-override` finding too: it applies only to the connections that block matches. A later line with hardn's value is not reported. `SameValue` says whether the other line's arguments, normalised as the settings are (case, `without-password`, port numbers; as sets for an accumulating keyword), equal hardn's line's, so the caller can tell an `overridden` line that sets hardn's own value from one that does not (always false for `shadowed`).

   `ConflictsKnown` says the report is established, so an empty one means nothing else sets hardn's keywords. It is false without the files, and false with a `FindingUnknown` when `Owner` is not a range of lines (`First` > `Last`, one end 0, a relative path; `ReadEffective` refuses such an Owner with `fs.ErrInvalid` before anything runs) or when hardn's lines set no keyword in the files read (`00-hardn.conf` absent or empty, the default Owner on an `IncludeNone` host).
10. **The byte-order rule, exactly.** Among the names the Include reads (ending in `.conf`, not starting with `.`), a drop-in beats `00-hardn.conf` for a first-value keyword exactly when its name is less than `00-hardn.conf` byte by byte (strcmp). So `0-*`, `00-a…` to `00-g…`, and also `00-h.conf`, `00-hardn-x.conf` (`.` and `-` sort below letters) and `+plus.conf` (`+` is below `0`) beat it; `000-*`, `00.conf`, `00_x.conf`, `00-hardn0.conf`, `A-upper.conf` and the legacy `hardn.conf` do not. Tested on a fixture directory with each of these names, plus `.hidden.conf` and `00-hardn.conf.bak`, which are never read (`testdata/effective/byteorder`): were `.hidden.conf` read, it would be the line that overrides `PasswordAuthentication`, and were the `.bak` read (right after hardn's file), its `MaxStartups 99` would shadow hardn's `MaxStartups 10`; a mutation that lets `included` match `.conf.bak` fails the test. The read order matches the order the audit measured with a real sshd (§3).
11. **Read-only, through `host.System`.** `ReadEffective` makes reads (`Stat`, `ReadFile`, `ReadDir`) and runs exactly `sshd -T -f /etc/ssh/sshd_config`, one `sshd -T -f /etc/ssh/sshd_config -C <spec>` per `Match` block (`EffectiveRequest.Binary` names another sshd, such as Alpine's `sshd.pam`) and, when `SocketMayListen`, `systemctl show -p Listen ssh.socket`. Tested: the exact runs of every fixture and of each `SocketMayListen` case, and no call that changes the fake. The package's depguard rule `sshd-through-host` ([sshd-validate.md](sshd-validate.md) §2.11) covers the new files.
12. **Errors are for I/O and for files the model cannot follow; Unknown is for output.** `ReadEffective` returns an error, and no values, when a command cannot give an answer: `sshd -T`'s errors (and a Match probe's) are classified as `Validate`'s are (`*EnvError` for a missing `/run/sshd`, `*ConfigError`, `*UnexpectedError`, the host's own), and `systemctl show` failing is its `*host.ExitError`. The files are read as `Validate` reads them, and what its file model cannot follow is refused the same way: `ErrUnsupportedInclude` (an Include other than `IncludeLine`, including another spelling of it), `ErrNotRegular`, and `fs.ErrInvalid` for a NUL byte. The conflict report, the check against the files and the Match probes all depend on that model, so a host `Validate` refuses gets an error here, not values without them (a caller such as `p4-check-ssh` reports it as Unknown, §6). A bad `Conn` or `Owner` is `fs.ErrInvalid`. Output it cannot read makes values Unknown with findings; `Evaluate` never returns an error. A done context is refused before anything runs.
13. **Finding codes are stable.** `FindingKind.String()` is the code: `clobberable`, `include-not-first`, `match-untargeted`, `sshd-warning` (from `Validate`), and `overridden`, `shadowed`, `accumulates`, `match-override`, `sources-disagree`, `effective-unknown`. `TestFindingCodes` pins all ten. `ReadEffective`'s findings are `Validate`'s about the installed files (`clobberable`, `include-not-first`, `match-untargeted`), then `Evaluate`'s.

## 5. API

package sshd

const SocketUnit = "ssh.socket"

type Setting struct { Value string; Known bool }      // Value lower case; "" when Unknown
type Set struct { Values []string; Known bool }       // Has(v) bool
type Listener struct { Addr netip.Addr; Port uint16; RDomain string } // String()
type Listeners struct {                                // Ports() []uint16
	SSHD, Socket   []Listener
	SocketRead     bool
	SocketComplete bool       // added by next/p2-sshd-migrate: SocketRead, and every Listen line read
	All            []Listener // complete only when Known
	Known          bool       // configured set established; not "bound"
}
type Origin struct { File string; Line int; Text string }
type Conflict struct { Kind FindingKind; Keyword string; Hardn, Other Origin; Match Block; SameValue bool }
type Override struct { Block Block; Conn Conn; Keyword, Value string }
type Owner struct { File string; First, Last int }     // zero: all of HardnDropIn; String()
type File struct { Path string; Data []byte }

type Effective struct {
	Keywords map[string][]string
	PermitRootLogin, PasswordAuthentication, KbdInteractiveAuthentication, PubkeyAuthentication Setting
	UsePAM          Setting // added by next/p4-kbd-pam: a build without PAM reads Known "no"
	BuiltWithoutPAM bool    // added by next/p4-kbd-pam: sshd -T printed no usepam line
	Port, AllowUsers, AllowGroups, DenyUsers, DenyGroups, AcceptEnv Set
	Listeners      Listeners
	Conflicts      []Conflict
	ConflictsKnown bool
	Overrides      []Override
}

func SocketMayListen(s detect.SSH) bool

type EffectiveInputs struct {
	Effective []byte; Probes []Probe
	SSH detect.SSH; Socket []byte // Socket when SocketMayListen(SSH)
	Main []byte; DropIns []File; Owner Owner
}
func Evaluate(in EffectiveInputs) (Effective, []Finding) // pure

type EffectiveRequest struct { SSH detect.SSH; Binary string; Conn Conn; Owner Owner }
func ReadEffective(ctx context.Context, sys host.System, req EffectiveRequest) (Effective, []Finding, error)

// FindingKind gains FindingOverridden, FindingShadowed, FindingAccumulates,

func CanonicalKeyword(keyword string, args []string) string

## 6. Not in this unit; inputs to later units

- **`p2-ufw`:** with `Listeners.Known`, allow `Listeners.All` (`Ports()`) plus the new port. With `Known` false, do not enable or narrow the firewall on `All`: a source may be missing or unreadable (the finding says which). Even when Known, `All` is configuration (§2.5): a port the running daemon still holds from before an unapplied change is not in it, so that unit needs a bound-socket source of its own (**[unverified]** which: for example `/proc/net/tcp` and `/proc/net/tcp6` read through `host.System`).
- **`p2-reload`:** `Listeners.Known` is not the plan's "verify the real listener". After `daemon-reload`, on a socket-activated host, it is Known with the new port before `restart ssh.socket` has bound it (§2.5). The real-listener check needs the restart's exit status plus a bound-socket source or a connection test, **[unverified]** which. `ReadEffective` after the restart still shows that the configuration agrees and the unit is up. Pre-existing `ssh.socket.d/*.conf` files are that unit's to report.
- **`p3-engine`:** after installing and reloading, compare the values it wanted with `Effective`; an Unknown is not a pass, and an empty `Conflicts` is a pass only with `ConflictsKnown`. Whether an `overridden` conflict whose value equals hardn's should stop a change is policy for the maintainer to decide; `Conflict.SameValue` gives the comparison.
- **`p2-pve`:** a `shadowed` `PermitRootLogin yes` in `sshd_config` is Proxmox VE's own line, not drift.
- **`p2-sshd-migrate`:** the legacy `hardn.conf` and `manage.conf` show as `shadowed` or `accumulates`; `Evaluate` over the candidate's files and `Validate`'s outputs shows the report before anything is removed. `Validate`'s `Report` carries the files' paths but not their contents, so that unit re-reads them, and a file changed between the two reads shows as `sources-disagree`; a `Report` field for the assembled files would be a change to `p2-sshd-validate`'s API, for that unit to make.
- **`p3-output`:** map the finding codes (§2.13) into `findings[]`, with `Conflict`'s files and lines.
- **Phase 4 (`p4-check-ssh`):** status from `Effective`, the listener set from `Listeners` (with its `Known`), per-connection values from `Overrides`. A host whose files `Validate` refuses (§2.12: another Include, a NUL byte) gives an error, which that unit reports as Unknown; values without the file model would be a later addition, for the maintainer to ask for.
- **Not modelled:** a `[::]` socket with `BindIPv6Only=ipv6-only` is compared as if dual-stack (§2.5); `Match` blocks are reported, not evaluated beyond the probes; options on the service's command line (§3).
- **Size:** about 1,600 changed lines of Go across the unit (about 940 of them non-test, much of it doc comments) against the plan's guideline of about 500: the unit reads three sources (sshd -T, the socket, the files) and checks them against each other and against detect's unit states, and its tests cover each source's failure forms.
