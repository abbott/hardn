> **Unit:** refactor plan Phase 2, `next/p2-sudoers` (brief 2.2 "sudoers"; decisions §3.17, sudoers file names, and §3.21, doas alongside sudo, both approved 2026-10-17). Brief corrections it implements: [phase0-findings.md §12](../refactor/phase0-findings.md#12-proposed-adjustments-to-the-brief), rows 25 (sudo-rs) and 26 (doas).
> **Status:** built and tested on macOS against the recording fake (`hostfake`) only. `visudo` and `doas` are modelled by a test handler that accepts or rejects a file; their messages are written in the tools' style, not captured from a host. Nothing has run on Linux; §4 lists what is "written, not run (gate 5)".
> **Since `next/s9-control`** (refactor plan slice 9, unit (b), its first part, from `next/s9-gallery` at af5904a): the reading back that slices 9 and 5 need ([gallery-environment.md](../engine/gallery-environment.md) §3.2, §8, the Made here calls adopted 2026-10-29): the user's whole Policy from hardn's files (`PolicyOf`, `EditedError`), who ran hardn (`Invoker`), origin/main's `env_keep` line (`ReadLegacy`, decision 3 (a)), and the legacy finding's detail in the user's words (§2.13 to 2.16; the decisions, §7). Built and tested as above, on `hostfake`.

`sudoers.Choose(facts, want)` picks the elevation tool from `detect`'s facts. `sudoers.Read` reads what a plan needs, `sudoers.PlanFor` plans the files for a set of per-user policies (pure), and `sudoers.Apply` installs a plan over `host.System`: the whole configuration is checked first, each candidate is checked as a copy before it is renamed into place, and the whole configuration is checked again after, with the old files put back if that fails. `sudoers.Rollback` puts a plan's files back.

## 1. Why

origin/main writes `/etc/sudoers.d/<user>` with `os.WriteFile`, without `visudo`, named after the raw user name, so a name with a `.` is silently skipped by sudo; and the grant overwrites the `env_keep` line `setup-sudo-env` wrote to the same file (V16, [side-effects.md](../refactor/phase0/side-effects.md) rows 17 and 18). A sudoers file sudo cannot parse breaks sudo for everyone, and a grant sudo never reads is a grant hardn reports that does not exist: with root's SSH login disabled in the same run, either is a lockout (brief §3 principle 1). On Alpine sudo is not installed at all; doas is the default (V14; §3.21).

## 2. Guarantees

### Choosing the tool (`Choose`, pure)

1. **From detect's facts, never re-detected, installing nothing** ([detect.md](detect.md) §2.10). `want` is `ToolSudo` or `ToolDoas` to name one, `ToolUnknown` to take the one installed:

   | Host (stock install) | `Choose(facts, ToolUnknown)` |
   |---|---|
   | Debian 13, 12; Ubuntu 24.04 | `ToolSudo`, `Flavor` `SudoOriginal` |
   | Ubuntu 26.04 | `ToolSudo`, `Flavor` `SudoRS` |
   | Alpine 3.24, 3.23 (`setup-alpine`) | `ToolDoas` |
   | Alpine with both installed | `ToolUnknown`, `ErrAmbiguous`: the caller names one |
   | Proxmox VE 9 (no sudo **[I]**), or any host with neither tool | `ToolNone` (NotApplicable), `ErrNoTool` |
   | doas without sudo, not Alpine | `ToolUnknown`, `ErrUnsupported` |
   | a tool's presence not established, where it decides (on a host that is not Alpine, sudo absent and doas not established: installed, doas would be `ErrUnsupported`) | `ToolUnknown`, wrapping detect's error |
   | the distribution not established, where it decides (doas present or not established, or doas named) | `ToolUnknown`, wrapping `Platform.Err`; never "not Alpine" |

   A named tool that is absent is `ToolNone` with `ErrNoTool`. doas is configured only on Alpine, whose package reads `/etc/doas.d` (§3); elsewhere it is ignored when sudo is present. With `ToolUnknown` wanted, `ToolNone` is said only when both tools are established as absent: plan row `p4-risk` leaves NotApplicable out of the score while Unknown adds a factor, so an Unknown is never turned into one. **Branch on `Tool`:** `Choice.Err` is set exactly when the tool is not usable. **sudo and sudo-rs take the same path:** the rules hardn writes and the `visudo` flags it runs are the same for both, and on Ubuntu 26.04 `visudo` is sudo-rs's (§3); they differ in the main file they read (item 5). An Unknown flavour does not stop a plan unless `/etc/sudoers-rs` exists (item 5); `Choice.FlavorErr` says why it is Unknown, and the tool is still `ToolSudo`. Tested: `TestChoose`; the plan and apply tests run on the sudo and the sudo-rs facts and assert the same files and the same commands (`TestPlanContent`, `TestApplySudoFlavours`).

### File names (§3.17)

2. **Fixed prefixes, then the user name encoded one to one.** sudo: `/etc/sudoers.d/hardn-grant-<stem>` (the grant) and `/etc/sudoers.d/hardn-env-<stem>` (the `env_keep` line), **separate files**, so a grant never overwrites the environment line again (V16). doas: `/etc/doas.d/hardn-<stem>.conf`, one per user (item 6). `<stem>` keeps lower-case letters, digits and `-`, writes `_` as `__` and any other byte as `_` and two hex digits: `alice` → `alice`, `alice.smith` → `alice_2esmith`, `bob_smith` → `bob__smith`, `bob$` → `bob_24`. So a sudo name **never contains `.` and never ends in `~`**, the names sudo and sudo-rs skip (§3), two users never share a file, and no user's file is another user's under the other prefix (`env-alice`'s grant is `hardn-grant-env-alice`, alice's environment file `hardn-env-alice`). Tested: `TestFileNames`, over names built to collide.
3. **Order.** sudo reads `/etc/sudoers.d` in sorted lexical order and **the last matching rule wins**, the opposite of sshd (§3). Every hardn name starts with a lower-case `hardn-`, which sorts after the digit-led and upper-case names the distributions and cloud-init use (`README`, `90-cloud-init-users`, `20-wheel.conf`), so hardn's rule for a user comes after theirs and wins; the main `/etc/sudoers`' rules (`%sudo` on Debian and Ubuntu) come before its `@includedir` (§3). What could still win over hardn's rule is reported, not edited (item 5).
4. **User names hardn writes into a rule:** `^[a-z_][a-z0-9_.-]*\$?$`, at most 32 bytes (`CheckUser`, `ErrUserName` otherwise). That is a superset of the legacy menu's `^[a-z][a-z0-9_-]*$` ([side-effects.md](../refactor/phase0/side-effects.md) row 12); it has no upper case, so a name is never a sudoers alias or `ALL`, and no `#`, `%`, `+`, `!`, `,`, `=`, `:`, space or `~`, which sudoers reads as a uid, a group, a netgroup, a negation or a separator. For doas, the keywords of doas.conf(5) (`permit`, `persist`, `nopass`, …) are refused as well: as a bare word in a rule each is read as itself (§3). Variables are `^[A-Za-z_][A-Za-z0-9_]*$`, each once (`ErrVarName`). This is a check, not the whole defence: every file is still validated by the tool itself (item 8).

### Content and planning (`Read`, `PlanFor`)

5. **Read reads, PlanFor is pure.** `Read(ctx, sys, choice, users)` makes only reads. sudo's main file (`State.Main`, carried into `Plan.Main`) is `/etc/sudoers`, except that **sudo-rs reads `/etc/sudoers-rs` instead when it exists** (by `stat`, so a symlink to a file counts and a dangling one does not), and so does its `visudo -c` (§3); the sudo project's sudo never reads it. With the flavour Unknown and `/etc/sudoers-rs` present, which file is read is not established, and `Read` refuses (`ErrNotIncluded`). The main file must have `@includedir /etc/sudoers.d` (or the older `#includedir` form, §3), and `/etc/sudoers.d` must be a directory; doas's `/etc/doas.d` must be a directory, not a symlink to one, as Alpine's doas checks it (§3). Otherwise `ErrNotIncluded`: **a grant in a directory the tool does not read is refused, never reported as done**. hardn creates neither directory. It lists the directory's entries the tool reads, in its order (sudo: no `.`, no trailing `~`; doas: names ending in `.conf`), and reads hardn's files for the users named with `ReadFileNoFollow`, so a symlink at one is refused (`host.ErrSymlink`) and a directory there is the host's `EISDIR`. `PlanFor(state, policies)` then decides the changes with no I/O. Findings (`Plan.Findings`), which never stop a plan, for **every** policy:
   - `sudoers-later-file`: an entry the tool reads after the first of hardn's files that will hold a rule for the user (sudo: `hardn-env-<stem>` when the policy keeps variables, which sorts before `hardn-grant-<stem>`; otherwise the grant), other than hardn's own files: a rule there that matches the user wins (for `Defaults`, a later `env_keep =` may replace hardn's `+=` list **[unverified]**). A policy that removes all of hardn's files has no rule for a later file to override and gets none: any file may grant that user, and parsing other files' rules is not this unit's (§6). hardn's own files are recognised **by name alone**, decoded with item 2's inverse (so `hardn-zzz` or a non-canonical `hardn-grant-z_61` is reported); their content is not read, so a file in hardn's namespace holding someone else's rule (on doas, an administrator's `hardn-local.conf` decodes as user `local`'s file) is not reported;
   - `sudoers-after-include`: lines of the main file after the `@includedir` (sudo reads them after the drop-ins), with their line numbers. A line starting with `#` is a comment, except `#include`/`#includedir` and `#` followed by a digit, which at the start of a line is a user ID: `#1000 ALL=(ALL) !ALL` is a rule (§3);
   - `sudoers-legacy-file`: origin/main's `/etc/sudoers.d/<user>` (V16), saying whether sudo reads it before hardn's first file (hardn's rule wins) or after (the old one may win), and, for a policy that grants nothing (`GrantNone`), that a grant in it still applies: removing hardn's grant does not take sudo away while that file exists. It is reported, never removed: migrating it is the user-management slice's. **Its detail is in the user's words** since `next/s9-control`, as the plan's review shows it as it is (§2.16; [gallery-environment.md](../engine/gallery-environment.md) §7 item 22; proposed): read after hardn's first rule, "`<file>` may override hardn's rule"; for a policy that grants nothing, "`<file>` may still let `<user>` use sudo"; both, "`<file>` may override hardn's rule and still let `<user>` use sudo"; otherwise "`<file>` is from an earlier hardn; hardn's rule wins". The other two kinds keep their details, which `steps.SudoersFinding` words (§2.16).

   Tested: `TestPlanFindings`, `TestPlanFindingsPolicies`, `TestReadMain`, `TestReadRefuses`, and every call `Read` makes is a read (`TestPlanContent`).
6. **The rules.** sudo keeps origin/main's lines exactly (brief §3 principle 2; `ConfigureSudo` and `setup-sudo-env` in `pkg/adapter/secondary`), each in its own file under the header `# Managed by hardn`:

   | Policy | sudo | doas (Alpine) |
   |---|---|---|
   | `GrantPassword` | `alice ALL=(ALL) ALL` | `permit persist alice` |
   | `GrantNoPassword` | `alice ALL=(ALL) NOPASSWD: ALL` | `permit nopass alice` |
   | `Env: [HARDN_CONFIG]` | `Defaults:alice env_keep += "HARDN_CONFIG"` (second file) | `setenv { HARDN_CONFIG }` on the same rule: `permit persist setenv { HARDN_CONFIG } alice` |
   | `GrantNone`, no `Env` | hardn's files removed | hardn's file removed |

   doas's rule takes the shape of Alpine's own `20-wheel.conf` (`permit persist :wheel`). **On doas the environment cannot be a separate file:** doas takes the action *and the options* of the last matching rule alone, and `setenv` is an option of a rule (§3), so a later `setenv` rule for alice would also decide whether her password is asked. `Env` without a grant is therefore refused on doas (`ErrEnvNeedsGrant`) rather than silently granting her doas. sudo's files are mode `0440`, doas's `0640` (the mode Alpine's package gives `/etc/doas.conf`), both `root:root`. Tested: `TestPlanContent` pins every byte.
7. **Idempotent, with a risk per change.** A file already holding exactly the content, mode and owner is not planned; a wrong mode or owner alone is rewritten (`TestPlanIdempotent`: after `Apply`, the same policies plan nothing). Each `Change` carries `Old` (the file as `Read` found it), `Check` (the validation, naming the real path, for the plan view) and `Risk`: `RiskLockout` when it removes a user's grant or writes one that asks for a password, which a user created without one cannot give (V17; a cloud image's default user, granted `NOPASSWD` by cloud-init, is one), `RiskNone` otherwise. The engine decides what a lockout-risk change needs (brief Phase 3 `Risk()`).

### Installing (`Apply`)

8. **Validated before it takes effect, in this order, stopping at the first failure:**
   1. the run directory: `Options.RunDir` absolute and clean, with none of the characters `sshd`'s check refuses (space, quotes, backslash, `#`, glob characters; `fs.ErrInvalid`), every directory from `/` a real directory owned by root and writable by neither group nor others (`ErrUnsafeRunDir`), as `sshd.Request.RunDir` ([sshd-validate.md](sshd-validate.md) §2.9), so one run directory passes both units' checks or neither; `RunDir/sudoers-validate` must not exist (`fs.ErrExist`) and is created `0700`;
   2. **the whole configuration as it is** (`StageBefore`): sudo `visudo -c`, which checks `Plan.Main` and the files it includes (on sudo-rs, a rule using a tag sudo-rs ignores, such as `LOG_INPUT:`, fails this check although sudo-rs runs with it: refused as `ErrRejected`, §3); doas, which has no such check, each file it reads in its order (`/etc/doas.conf`, then each regular `*.conf` in `/etc/doas.d`): owned by root and writable by neither group nor others (`ErrPerms`; doas itself refuses to run otherwise, §3), and `doas -C <file>`. A configuration that is already broken is refused before anything is written, so a later failure is the plan's own;
   3. **each candidate, as a copy** (`StageCandidate`): the exact bytes, with the mode and owner it will have, written to `RunDir/sudoers-validate/<name>` and checked with `visudo -cf <copy>` or `doas -C <copy>`. Only root can change the copy between its writing and the check (V20: origin/main's `setup-sudo-env` wrote a predictable `/tmp/hardn_sudoers_temp` as root);
   4. each file is read again and must be as `Read` found it (`ErrChanged`), so neither a concurrent edit is overwritten nor a rollback restores the wrong content;
   5. **the writes**: `WriteFileAtomic` (same-directory temporary file, fsync, rename, directory fsync; [atomic.md](atomic.md) §2.1), `root:root`, or `Remove`;
   6. **the whole configuration again** (`StageAfter`), as in step 2.

   **Up to step 5 nothing under `/etc` changes** (tested for a broken configuration before, a rejected candidate, a changed file, an unsafe run directory and a cancelled context). Once created, the copies are removed under `context.WithoutCancel`, bounded by `Options.RestoreTimeout`, on every path (`Result.Cleanup` holds a removal error and does not change the outcome). The atomic write's leftover temporary file after a crash, `.<name>.hardn-<random>`, contains a `.` (sudo skips it) and does not end in `.conf` (doas skips it), §3. An empty plan runs nothing.
9. **Recoverable.** When a write or `StageAfter` fails, every file written (and the one whose write failed, which an atomic write leaves as it was or as planned) is put back as in item 11, last first, under `context.WithoutCancel` (a Ctrl-C mid-way still restores: `TestApplyCancelledMidway`) bounded by `Options.RestoreTimeout` (`DefaultRestoreTimeout`, one minute, when not positive; the removal of the copies has the same bound: `TestApplyRestoreTimeout`), and the whole configuration is checked once more (`StageRestored`). **The outcome is typed:** `Result.Restored` is true when every file is back and that check passed; otherwise the error wraps `ErrNotRestored` (a file not put back, one another writer changed, left alone with `ErrChanged`, or a failed `StageRestored` check, whose `*CheckError` is in the error's tree after the `StageAfter` one). `Result.Installed` still lists what was written, including what was then put back. So an error with neither `Restored` nor `ErrNotRestored` changed nothing under `/etc`. Tested: `TestApplyRejected` (an old grant restored, a new environment file removed), `TestApplyRemove` (a removed grant put back with its mode and owner), `TestApplyDoasRejected` (doas at each stage), `TestApplyWriteFails`, `TestApplyRestoreFails` (the restored check fails), `TestApplyRestoreWriteFails` (a file cannot be put back).
10. **Errors are typed.** A failed check is a `*CheckError{Stage, Path, Argv, Tail, Err}`: `Path` is the real file (a candidate's target; `Plan.Main`, `/etc/sudoers` or `/etc/sudoers-rs`, for `visudo -c`), `Argv` what ran (naming the copy for a candidate), `Tail` the tool's last output lines. `errors.Is(err, ErrRejected)` holds only when the tool rejected the file (a `*host.ExitError`) or doas's ownership rule did (`ErrPerms`); a check that could not run (no `visudo`: `host.ErrNotFound`; a cancelled context) is a `CheckError` that is not a rejection (`TestCheckErrorNotRejected`). Every error wraps its cause for `errors.Is`/`errors.As`.
11. **`Rollback(ctx, sys, plan)` undoes only what the plan wrote.** Last first, each file is read again: as `Read` found it, it is left; holding exactly what the plan wrote (content, mode, `root:root`; absent, for a removal), it is put back as `Read` found it (written with its old mode and owner, or removed if it was absent); anything else was written by someone else and is left alone, reported as `ErrChanged`. So a concurrent edit is never undone, including one `Apply` refused with `ErrChanged` (`TestRollbackChanged`); a writer who happened to write exactly the plan's bytes cannot be told from the plan. Then it checks the whole configuration (`StageRestored`). Every failure wraps `ErrNotRestored`. A plan whose `Tool` is not sudo or doas (one lost in a journal round trip) is refused with `fs.ErrInvalid` before anything is read or written (`TestRollbackTool`). It is idempotent (`TestRollback`). After Ctrl-C, run it under `context.WithoutCancel` with a timeout: every `host.System` method refuses a done context ([system.md](system.md) §2.5).
12. **Through `host.System` only.** depguard rule `sudoers-through-host` denies the package's non-test files `os` (with `os/exec`), `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` and `plugin`; `host-stdlib` already holds `pkg/host/**` to the standard library and `pkg/host`. Tests run only against `hostfake`; nothing executes `visudo`, `doas` or `sudo`.

### Reading back (`PolicyOf`, `Invoker`, `ReadLegacy`; `next/s9-control`)

13. **The user's whole Policy, from hardn's files** (`PolicyOf(state, user)`, pure). `PlanFor` takes the user's whole state, so a Policy with no grant removes hardn's grant and one with no variables removes `hardn-env-<stem>` (item 7; for slice 9 a lockout-risk change, [gallery-environment.md](../engine/gallery-environment.md) §3.2, §7 item 20). `PolicyOf` gives back the Policy hardn's files in a `State` hold, for sudo, sudo-rs and doas, so that a caller changes one part and carries the other. A file reads back only when its content is **byte for byte** what `PlanFor` writes for some grant and variable list (item 6): sudo's grant file one of the two grant lines, its environment file `Defaults:<user> env_keep += "<list>"`, doas's rule `permit persist|nopass [setenv { <list> }] <user>`, each under the header, the list one space between names `PlanFor` takes (item 4: none empty, each once). So, for every tool, grant and variable list hardn writes, planning the Policy read plans nothing (`TestPolicyOf`: sudo, sudo-rs and doas × the three grants × none, one, several and 24 seeded random lists of variables; doas without a grant takes none, item 6; `TestPolicyOfAfterChanges`: from any of those policies to any other, the last one reads back). A file that is not there gives nothing (no grant, no variables). **Anything else is an `*EditedError` naming the file** (`ErrEdited`, `SUDOERS_FILE_EDITED`), one per file, joined when both of sudo's files are edited, the grant's first, never a guess: a comment or a rule added, the header or the final newline missing, `ALL=(ALL:ALL)`, another user's line, `env_keep =`, an empty list, two spaces, a name repeated or not a variable's, doas's `keepenv`, a group, `as root`, a `setenv` value, a rule without `persist` or `nopass`, two rules (`TestPolicyOfEdited`, 21 contents). The mode and owner are not read: a wrong one is rewritten by the next plan, the same bytes `0440` or `0640` `root:root`, as for any Policy (item 7; `TestPolicyOfMode`). Errors besides: `ErrUserName`, and `fs.ErrInvalid` for a user `Read` did not read or a tool that is not sudo or doas (`TestPolicyOfRefuses`).
14. **Who ran hardn** (`Invoker(tool, getenv)`). `SUDO_USER` under sudo and sudo-rs, `DOAS_USER` under doas, the variable each tool sets to the invoking user's name (§3), each tool's own and never the other's; `USER` is not read (origin/main fell back to it, root's own at a root login: gallery-environment.md §7 item 5). Unset or `root` is no one (`""`, no error): hardn was not run through the tool by a user, which slice 9's decision 2 (a) refuses. A name `CheckUser` refuses is `ErrUserName`, as the name goes into a rule; a tool that is neither is `fs.ErrInvalid`. `getenv` is the caller's lookup (`os.Getenv` in hardn), so the package reads no environment of its own (item 12) and a test or the gallery passes a map (`TestInvoker`, 14 cases).
15. **origin/main's `env_keep` line** (`ReadLegacy(ctx, sys, state, user)`, slice 9's decision 3 (a): the screen says the variable is kept by that file). `Legacy.Path` is `/etc/sudoers.d/<user>` when sudo reads it, an entry of `State.Entries` named as the user; none on doas, where the file is not there, or for a name sudo skips (`alice.smith`, as origin/main wrote it: `keep_dotted`). `Legacy.Keeps`: the file holds **origin/main's line exactly as origin/main wrote it**, `Defaults:<user> env_keep += "HARDN_CONFIG"` (`file_environment_repository.go:69`; the characterization's `environment/keep_*.golden` and `ops/setup_sudo_preservation/*.golden`), as a line of its own, and not continued from the line before (one ending in `\`, which the Users check reads as joined too). A line commented out does not count, where origin/main's substring check counted it (gallery-environment.md §7 item 4; `keep_commented`), nor an indented one, another list, or another user's. It reads that one file with `ReadFileNoFollow` (a symlink there is `host.ErrSymlink`) and changes nothing (`TestReadLegacy`, 14 cases: each call a read, the file as it was). The line is `sudoEnv`'s own, one definition (`envLine`). What else the file says is not read: a later `env_keep -=` or `env_keep =` for the user, in it or in a later file, is not seen (§6).
16. **The plan's findings on the engine's change** (`steps.Sudoers`, [steps.md](../engine/steps.md) §2.10): since `next/s9-control` they ride on the change with their codes and sources (`steps.SudoersFinding`), where they were dropped (gallery-environment.md §7 item 21). The later file's detail is "`<file>` may override hardn's rule" (slice 9's decision 7, decided), a line after the includedir "Line `<n>` of `<file>` may override hardn's rule" (proposed), and the legacy file's sudoers' own (item 5, proposed), so each names its file in the review, which shows the detail alone.

## 5. API

```go
package sudoers

const MainConfig = "/etc/sudoers"
const SudoersRS = "/etc/sudoers-rs" // sudo-rs reads it instead when it exists
const DropInDir = "/etc/sudoers.d"
const DoasConfig = "/etc/doas.conf"
const DoasDir = "/etc/doas.d"
const SudoMode, DoasMode fs.FileMode = 0o440, 0o640
const WorkDir = "sudoers-validate"
const Header = "# Managed by hardn\n"

var ErrNoTool, ErrAmbiguous, ErrUnsupported, ErrUserName, ErrVarName, ErrNotIncluded, ErrEnvNeedsGrant,
	ErrRejected, ErrPerms, ErrChanged, ErrUnsafeRunDir, ErrNotRestored error

type Tool uint8 // ToolUnknown (zero), ToolNone (NotApplicable), ToolSudo, ToolDoas; String()
type Choice struct { Tool Tool; Flavor detect.SudoFlavor; FlavorErr, Err error } // Err set exactly when Tool is not usable
func Choose(f detect.Facts, want Tool) Choice // pure; want ToolUnknown: the one installed

func CheckUser(t Tool, name string) error
type Names struct { Grant, Env string } // Env "" for doas
func FileNames(t Tool, user string) (Names, error)

type Grant uint8 // GrantNone, GrantPassword, GrantNoPassword; String()
type Policy struct { User string; Grant Grant; Env []string }

type File struct { Path string; Exists bool; Data []byte; Mode fs.FileMode; UID, GID int }
type FindingKind uint8 // FindingLater "sudoers-later-file", FindingAfterInclude "sudoers-after-include", FindingLegacy "sudoers-legacy-file"
type Finding struct { Kind FindingKind; File string; Line int; Detail string }
type State struct { Choice Choice; Main string; Entries []string; Files map[string]File; Findings []Finding }
func Read(ctx context.Context, sys host.System, c Choice, users []string) (State, error) // reads only

type Risk uint8 // RiskNone, RiskLockout; String()
type Change struct { Path string; Old File; Data []byte; Mode fs.FileMode; Remove bool; Risk Risk; Check []string; Why string }
type Plan struct { Tool Tool; Main string; Changes []Change; Findings []Finding }
func PlanFor(st State, policies []Policy) (Plan, error) // pure

// next/s9-control: reading back
var ErrEdited error // SUDOERS_FILE_EDITED
type EditedError struct { Path string } // Unwrap: ErrEdited
func PolicyOf(st State, user string) (Policy, error) // pure
func Invoker(t Tool, getenv func(string) string) (string, error) // "" for none or root
type Legacy struct { Path string; Keeps bool }
func ReadLegacy(ctx context.Context, sys host.System, st State, user string) (Legacy, error) // reads that one file

type Stage uint8 // StageBefore, StageCandidate, StageAfter, StageRestored; String()

const DefaultRestoreTimeout = time.Minute
type Options struct { RunDir string; RestoreTimeout time.Duration }
type Result struct { Installed []string; Restored bool; Cleanup error }
func Apply(ctx context.Context, sys host.System, p Plan, opts Options) (Result, error)
func Rollback(ctx context.Context, sys host.System, p Plan) error // only what p wrote; failures wrap ErrNotRestored
```

The `FindingKind`, `Stage`, `Risk`, `Grant` and `Tool` words are stable (`TestCodes`); they are in-memory values with no `MarshalText`, so `p3-output` maps them to its own schema, as for detect's enums ([detect.md](detect.md) §6).

## 7. Decisions of `next/s9-control` (engineering; say if you'd rather otherwise)

- **The reader parses, then checks against the writers:** a file reads back only when its bytes equal `sudoGrant`, `sudoEnv` or `doasRule` for what was parsed, so a parse that drifts from the writers fails closed (`EditedError`), never reads as another Policy; the gallery's stand-in tried each grant against `PlanFor` instead.
- **Content, not mode or owner:** a file of hardn's with the right bytes and the wrong mode reads back, and the next plan rewrites it (item 7), rather than refusing a Policy hardn wrote.
- **Both files edited, both named:** `errors.Join` of one `EditedError` per file, the grant's first; `errors.As` gives the first.
- **`Invoker` here, not in the control:** the tool decides the variable, and the name goes into a rule, so it needs `Tool` and `CheckUser`; the caller's `getenv` keeps the package free of the process's environment (item 12).
- **`ReadLegacy` here, not in the control:** the line is `sudoEnv`'s (one definition, `envLine`), which entries sudo reads is `State`'s, and the legacy finding is already this package's; it is a separate read, not part of `Read`, so `Read`'s calls (and the Users check's, `pkg/engine/controls/users`) do not change.
- **A line continued from the one before does not count**, as the Users check joins such lines (`users/rules.go`, `lines`): failing closed says Not kept, and the Environment screen's item 1 then writes `hardn-env-<stem>`, which keeps the variable either way.
- **The legacy finding's words are sudoers' own detail**, not `steps`', because they depend on the policy (its grant, hardn's first rule), which a `Finding` does not carry; adding fields to `Finding` would change the journalled plan ([revert-plans.md](revert-plans.md) §2 item 7a). The later file's and the after-include line's words are `steps.SudoersFinding`'s, from the file and line alone.
- **The after-include line is worded too** ("Line `<n>` of `<file>` may override hardn's rule", proposed): its detail named no file ("a rule here"), item 21's defect for the later file.
