# Alpine: automatic updates, AppArmor and Lynis (`pkg/host/alpine`)

> **Unit:** refactor plan Phase 2, `next/p2-alpine` (brief 2.5 "Alpine"; brief §2 decision "Alpine: automate updates with `apk-cron`; don't automate AppArmor"; decision §3.20, origin/main's `apk-upgrade` once apk-cron is installed, approved 2026-10-17). Decision §3.21 (doas) is `p2-sudoers`' ([sudoers.md](sudoers.md)). V-numbers: V23, on Alpine (Run All claims AppArmor and Lynis ran; here they get statuses that say what is true; wiring them into Run All is slice 7's) ([side-effects.md](../refactor/phase0/side-effects.md)).
> **Status:** built and tested on macOS against the recording fake (`hostfake`) only, with `apk`, `rc-update` and `rc-service` modelled by a test handler whose answers follow the tools' sources (§3), not captured from a host. Alpine container images run no OpenRC and no crond, so all of the updates path is VM-only. Nothing has run on Linux; §4 lists what is "written, not run (gate 5)".

`alpine.ReadUpdates` reads the state of automatic updates, `Updates.Status` reports it, `alpine.PlanUpdates` plans what makes it Configured (pure), and `alpine.Apply` runs the plan over `host.System`, checking that each step took effect and undoing the steps it ran when one fails; `alpine.Rollback` undoes a plan. `alpine.CheckAppArmor` and `alpine.Lynis` are reports only: hardn does not change either on Alpine.

## 1. Why

origin/main's Alpine update path is dead code that would write `/etc/periodic/daily/apk-upgrade` (`apk update && apk upgrade --available`) in place with no backup, then run `rc-update add crond default` and `rc-service crond start` with their failures only logged (`pkg/updates/updates.go:30-60`; [v032-reference.md](../refactor/phase0/v032-reference.md) §4.10, v0.3.2 wrote the same file); its status reads only whether that file exists (`pkg/security/status.go:415-421`). Alpine ships the same job as a package, `apk-cron`, and the brief decided to use it (brief §2, 2.5). AppArmor needs bootloader changes and a reboot on Alpine, which a tool that must never lock the user out does not automate (brief §2); Lynis is not packaged there at all. Run All on origin/main prints that both ran when neither did (V23).

## 2. Guarantees

### Automatic updates: reading and status

1. **Only on an Alpine host OpenRC booted.** `ReadUpdates(ctx, sys, facts)` takes detect's facts ([detect.md](detect.md)) and never re-detects: another distribution is `ErrNotAlpine` (another unit's), a distribution not established is `ErrUnknown` wrapping detect's error (never "not Alpine"), an init system not established (`Init.Kind` unknown, from a read error or detect's `ErrConflict`) is `ErrUnknown` wrapping detect's error too (never "OpenRC did not boot"), and an Alpine whose established init system is not OpenRC with `Running` Yes is `ErrNoOpenRC`: the Alpine container image's case (OpenRC installed, not running), or systemd. All of this is decided before anything is read (`TestReadUpdatesRefuses`). A caller shows `ErrNoOpenRC` as Unknown (a decision of this unit: no crond can run there, and NotApplicable would leave it out of the risk score).
2. **Reads only.** It runs `apk info -e apk-cron` and `rc-service crond status`, and `Lstat`s `/etc/periodic/daily/apk` and `/etc/init.d/crond`, `Stat`s `/etc/runlevels/default/crond` (followed, as OpenRC's `access(F_OK)` follows it, so a dangling link is "not in the runlevel") and reads `/etc/periodic/daily/apk-upgrade` with `ReadFileNoFollow`, so a link planted there is never followed. Tested: every call `ReadUpdates` makes is a read or one of the two queries (`TestReadUpdates`), and nothing is read for a refused host (`TestReadUpdatesRefuses`).
3. **Each fact is a value; Unknown is never a guess.** `Package` is Yes only for exit 0 with `apk-cron`, `apk-cron-<version>` or nothing as the output (the exit status is the number of names not installed, and the verbosity, which `/etc/apk/config` can set, only changes what is printed, §3), No only for exit 1 with no output on either stream; anything else is Unknown. `Crond` follows OpenRC's status exit codes: 0 started, 3 stopped, 32 crashed (marked started, its daemon gone); 4, 8 and 16 (stopping, starting, inactive) and anything else are Unknown; no `/etc/init.d/crond` is `CrondMissing`. `Script` is installed only as a regular file with an execute bit, since run-parts runs nothing else (§3). `Updates.Err` joins the reason for every Unknown field. Tested: `TestReadUpdatesUnknown` (each read error, status exits 4, 8 and 16, other `apk info` output, a file replaced between the `Lstat` and the read).
4. **Status** (`Updates.Status`, pure), the plan row's "package AND runlevel AND running":

   | State | When |
   |---|---|
   | Configured | apk-cron installed with its executable daily script, crond in the `default` runlevel, crond started |
   | NotConfigured | apk-cron not installed, whatever else is true (origin/main's script running daily is a finding, below) |
   | Partial | apk-cron installed and one of the rest fails: the script missing or not executable, crond not in the runlevel (runs until the next boot), stopped or crashed (runs from the next boot), or not installed |
   | Unknown | a fact that decides is Unknown: the package, or, with nothing already failing, the script, the runlevel or crond |

   A failing condition decides Partial even when another is Unknown, and "not installed" decides NotConfigured. The daily script is part of "installed": deleting it is a way to stop the job while keeping the package, and Configured would then be false. `Evidence` lists what each read said. Tested: `TestStatusAndPlan`.
5. **The legacy file is recognised by its bytes and by who can change it.** `/etc/periodic/daily/apk-upgrade` is hardn's (`LegacyHardn`) only as a regular file holding exactly `#!/bin/sh\napk update && apk upgrade --available\n`, origin/main's content (and v0.3.2's), owned by root and writable by neither group nor others (origin/main wrote it 0755 as root); any other mode, 0700 say, is kept as read, permission bits only. It is reported as `alpine-legacy-script`. Anything else there (edited by the administrator, CRLF line ends, a symlink, a directory, hardn's bytes with another owner or a group or other write bit) is `alpine-foreign-script`: never removed, and reported because two daily upgrade jobs would run. The owner and mode rule means a rollback only ever writes back a file that only root can change. Tested: `TestFindings`.

### Automatic updates: planning and applying

6. **The plan** (`PlanUpdates`, pure), in this order, each step only when needed:

   | Step | Command | Undo |
   |---|---|---|
   | `install` | `apk add apk-cron`, once `apk add --simulate apk-cron` lists that one change | `apk del apk-cron`, once `apk del --simulate apk-cron` lists that one change |
   | `runlevel` | `rc-update add crond default` | `rc-update del crond default` |
   | `start` (crond stopped) | `rc-service crond start` | `rc-service crond stop` |
   | `restart` (crond crashed: `start` only warns on a service still marked started, §3) | `rc-service crond restart` | `rc-service crond stop`: crond then reads stopped, not crashed (no daemon either way) |
   | `remove-legacy` (origin/main's file) | remove `/etc/periodic/daily/apk-upgrade`, after a backup | write `LegacyContent` back, mode and owner as read |

   The legacy file goes last, once apk-cron is in (§3.20). A configured host plans nothing; after `Apply` the next plan is empty (`TestApplyOriginMainHost`). `PlanUpdates` refuses, rather than guess: an Unknown fact it needs (`ErrUnknown`, wrapping why), no crond service (`ErrNoCrond`; hardn installs no cron daemon), and apk-cron and its script disagreeing (`ErrScript`: a script with no package, which `apk add` would not simply replace in `/etc`, or a package whose script was removed, which `apk fix apk-cron` reinstalls, §3, if that is what the administrator wants). None of these steps can lock a user out: there is no confirm-or-revert timer, and a failure is undone (brief 2.4). Each `Change` carries `Argv`, `Undo` and `Why` for the plan view.
7. **Before anything changes, `Apply` refuses** a done context, a plan that is not what `PlanUpdates` makes from its own `From` (steps added, dropped, reordered or naming other commands, or a `From.LegacyFile` that §2.5 would not read as hardn's: `fs.ErrInvalid`, so a hand-edited journal can neither run what it names nor have a script of its own written into `/etc/periodic/daily`), a plan that removes the legacy file with no `Options.Backups` (`ErrNoBackup`), and a host whose state differs from `From` in any field a step depends on (`ErrChanged`; a read error there is returned as itself). Then, when the plan removes the legacy file, it takes the backup through `p2-atomic` (`backup.Run.Backup`, `RollbackRequired`, so it is taken even with `enableBackups: false`, as `TakenAnyway`, §3.16), refusing when the backup fails and when the copy's SHA-256 is not hardn's content's (the file edited between the re-read and the backup). Tested: `TestApplyRefuses` (in every case nothing is run and nothing outside the backup run is written), `TestApplyOriginMainHost` (the copy and the manifest are written before `apk add`).
8. **Each step is checked.** `apk add` commits the whole world, so it may change other packages in the same commit (apk-add(8); a world file edited by hand and not yet applied, apk-world(5), openssh-server among them, §3). So `apk add --simulate apk-cron` runs first, which changes nothing, and `apk add` runs only when the one package change it lists is `Installing apk-cron`; any other change is refused, named, with `ErrOtherPackages`, and output listing no change (a quiet apk) with `detect.ErrUnrecognised` (`TestApplyOtherPackages`). A world changed between the simulation and the commit is not caught. After its command, `Apply` reads the effect back: apk-cron installed with its executable script; the runlevel link present (`rc-update add` exits 0 for a runlevel that does not exist, §3, so the exit code proves nothing); crond started; for the legacy file, re-read just before the removal (still exactly hardn's bytes, mode and owner, else `ErrChanged`) and absent after it. A command that succeeds without its effect fails with `ErrNotEffective`.
9. **Recoverable.** When a step fails, every step that acted, the failed one included (its effect may be partly there), is undone last first under `context.WithoutCancel(ctx)`, bounded by `Options.RestoreTimeout` (`DefaultRestoreTimeout`, two minutes, when not positive), so a Ctrl-C mid-way still undoes (`TestApplyCancelled`). A step refused before its action (the simulation in §2.8; the legacy file no longer hardn's on its re-read, so not removed) acted on nothing and is not undone: the administrator's file is left as they left it, and the undo of the steps before it completes. Each undo is checked too. `Result.Done` lists the steps that acted, `Result.Restored` says their undo completed (false with `Done` empty: nothing changed); otherwise the error wraps `ErrNotRestored` (`TestApplyNotRestored`). `Result.Legacy` is the backup, whose `Entry` names the copy in `<backupPath>/<run-id>/`: the note §3.20 asks for. Tested: `TestApplyFails` (`apk add` failing, or succeeding with no effect; no `default` runlevel; crond failing to start, or dying at once; a crashed crond that `restart` does not bring back; the legacy file edited during `apk add`; its removal failing), each leaving the host as it read before, except that the undo of `restart` leaves crond stopped where it read crashed (the same thing in practice: no daemon), and that the edited legacy file stays the administrator's.
10. **`Rollback(ctx, sys, plan)`** undoes a plan's steps, last first, each only when its effect is there: the legacy file, when absent, is written back with `WriteFileAtomic` as the constant `LegacyContent`, never bytes from the plan, with the mode and owner the plan carries, which §2.7's check holds to permission bits only, root's and no group or other write; anything else at its path is left alone (`ErrChanged`); crond is stopped when not stopped (a crashed crond, which `restart` replaced, then reads stopped); taken out of the runlevel when in it; apk-cron removed when installed, once `apk del --simulate apk-cron` lists that one change (else `ErrOtherPackages`, apk-cron left installed, `TestRollbackOtherPackages`). A plan that does not follow from its `From` (§2.7) is refused with nothing undone (`TestRollbackRefuses`: other legacy bytes, a setuid bit, a group write bit, another owner, steps dropped). It goes on past a failure and wraps every failure, that refusal included, in `ErrNotRestored`; it is idempotent (`TestRollback`, `TestRollbackLeavesOthers`, `TestApplyLegacyOnly`). It cannot tell its own change from the same change made by someone else since (crond started by hand, say) and undoes that too: so it is for a plan whose `Apply` returned nil. After an `Apply` that failed, `Apply` has already undone what it did; after one refused before any step, there is nothing to undo, and a `Rollback` would undo what others did (apk-cron installed meanwhile, say). After Ctrl-C, run it under `context.WithoutCancel` with a timeout: every `host.System` method refuses a done context ([system.md](system.md) §2.5).
11. **The atomic write's leftover is never run.** A crash during the rollback's write can leave `.apk-upgrade.hardn-<random>` in `/etc/periodic/daily` ([atomic.md](atomic.md) §2.2). busybox run-parts skips a name starting with `.` (§3), which settles atomic.md's unverified row for this directory.

12. **crond's other jobs** (`OtherJobs`, slice 7 decision 6, R2; *slice 7 (b)*): every file busybox run-parts runs under `/etc/periodic/{15min,hourly,daily,weekly,monthly}` (a regular file, a link followed, with an execute bit, a name of letters, digits, `_`, `-` and `.` not starting with `.`) but apk-cron's `apk` and origin/main's `apk-upgrade`, then every crontab crond loads in `/etc/crontabs` (a regular file whose name has no `.`, as busybox crond's directory scan skips) but root's holding `StockCrontab`, the VM's 283 bytes; a missing directory has none, and one hardn cannot read is the error, never "no jobs" (`TestOtherJobs`, `TestOtherJobsUnreadable`). A file named for no user is listed though crond ignores it: listing more only keeps crond.

### AppArmor and Lynis (reports)

12. **AppArmor** (`CheckAppArmor`, reads only). In a container (`Container.Detected` Yes) it is NotApplicable: the host's kernel decides (brief 2.5); with the container check Unknown it is Unknown, and nothing under `/sys` is read, since inside a container `/sys/module` shows the host's kernel ([detect.md](detect.md) §6). Otherwise `/sys/module/apparmor/parameters/enabled` decides: `Y` is Configured ("report it normally", brief 2.5); `N` (built in but not selected at boot, Alpine's default, §3) and a kernel with no `/sys/module/apparmor` are NotApplicable, `Enabled` No; any other content, `/sys/module/apparmor` there without its parameter, or no `/sys/module`, is Unknown. **Enabling is never automated**: with `Enabled` No, `Note` says what it takes (the `apparmor` package, `rc-update add apparmor boot`, the kernel parameter `lsm=<the modules /sys/kernel/security/lsm lists, without capability>,apparmor` or `apparmor=1 security=apparmor`, and a reboot), then where the parameter goes for the bootloader found: extlinux (`default_kernel_opts` in `/etc/update-extlinux.conf`, then `update-extlinux`), GRUB (`GRUB_CMDLINE_LINUX_DEFAULT` in `/etc/default/grub`, then `grub-mkconfig -o /boot/grub/grub.cfg`), Limine (`kernel_cmdline:` in `/boot/limine/limine.conf`), EFI stub (`cmdline=` in `/etc/kernel-hooks.d/secureboot.conf` for a unified kernel image, or the boot entry's arguments) and Raspberry Pi (`/boot/cmdline.txt`). The bootloader is recognised by the file setup-disk (or secureboot-hook) writes for it (§3): one found names that one, none or several give all five. A file is a hint, never proof. Tested: `TestCheckAppArmor`, `TestBootloaderNote`.
13. **Lynis** (`Lynis`, pure) is NotApplicable on Alpine, "not packaged in any stable Alpine branch" (plan §3.12: "Lynis Debian/Ubuntu only"; §3).
14. **Through `host.System` only.** depguard rule `alpine-through-host` denies the package's non-test files `os` (with `os/exec`), `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` and `plugin`; `host-stdlib` already holds `pkg/host/**` to the standard library and `pkg/host`. Tests run only against `hostfake`; nothing executes `apk`, `rc-update`, `rc-service` or reads a real `/sys`.

## 6. Not in this unit; inputs to later units

- **`p3-engine`:** the updates control's `Check` is `ReadUpdates` then `Status` (`ErrNoOpenRC` as Unknown, `ErrNotAlpine` as another control's), `Plan` is `PlanUpdates`, `Change.Apply` is `Apply` with a `backup.Run` for the run, and `Change.Rollback` is `Rollback`. ## 7. CVE-2026-123158: sshd's password bypass (`openssh.go`)

> **Unit:** the advisory of 2026-11-05 (CVSS 8.1), scope (a) detect and report, (b) Create refuses, approved by the maintainer; hardn upgrading openssh is §7.1's (2026-11-08), which also took the roadmap's "Run All turns password login off on an exposed host" over: Run All upgrades instead.
> **Status:** built and tested on macOS against `hostfake` only; nothing of it has run on a host (gate 5).

**The CVE**, published on 2026-11-05 with OpenSSH 10.6p2 and Alpine's post (https://alpinelinux.org/posts/2026-11-05-openssh-password-authentication-bypass/), as the unit's brief has it, checked against those sources on 2026-11-07. On musl without PAM, sshd's `sys_auth_passwd` borrows another account's salt when the stored field is shorter than 2 characters, and musl's SHA-256/512 crypt returns `*` for a key over 256 bytes, so any password of 257 to 1024 bytes matches a field of exactly `*`. A host is exposed when sshd checks passwords without PAM (Alpine's `openssh-server`, or `-pam`, `-krb5` with `UsePAM no`), `PasswordAuthentication` is yes for some account, a login account's field is exactly `*` (root only with `PermitRootLogin yes`), at least one account has a `$5$` or `$6$` hash, and the package is unfixed. `!` is locked and not affected (and without PAM blocks key login too, which is why Create writes `*`).

**The fixed releases** (`opensshFixed`, the same for `openssh-server`, `-pam` and `-krb5`; Alpine bumped the pkgrel, so `sshd -V` still prints the old upstream version and only apk's version tells):

|---|---|
| 3.24 | 10.3_p1-r2 |
| 3.23 | 10.2_p1-r1 |
| 3.22 | 10.0_p1-r11 |
| 3.21 | 9.9_p2-r1 |

**What hardn does.** SSH Auth reports `SSH_PASSWORD_BYPASS`, `SSH_SSHD_UNFIXED` or `SSH_FIX_UNKNOWN` ([check-ssh.md](../engine/check-ssh.md) §11); the first forces the risk level Critical ([risk.md](../engine/risk.md) §6.4). Create refuses a new user, whose field is `*`, on an unfixed host with a password path on ([control-users.md](../engine/control-users.md) §7). The version is apk's installed database, `/lib/apk/db/installed`, its records' `P:` and `V:` alone (`ParseInstalled`), compared by apk's grammar (`CompareVersion`); a version outside it is `Unknown`, never a guess.

**What it reads, and what not.** The package, not the binary sshd runs from, so it reads fixed as soon as the package is upgraded. *Since 2026-11-08* that is known to hold for every new connection: each runs the `sshd-session` (and `sshd-auth`) on disk, while the listener keeps the old binary until sshd is reloaded (§7.1's probe). **[I]** `CompareVersion`'s order across token kinds (a letter against an extra component) is apk-tools' `version.c` as read, not run against `apk version -t`; the fixed table differs only in a revision or a suffix number.
