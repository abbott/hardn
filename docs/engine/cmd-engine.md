## 1. Why

`cmd/hardn` built no `engine.Options` before this unit: outside the tests only `hardn confirm`'s clean-up reached the engine, through `pkg/engine/confirm`. This is the first unit in which the hardn binary reaches the plan/apply engine from its own flags and menu, so the options are assembled once, here, for the DNS pilot and for every slice's unit (d) after it.

## 2. What is built

### 2.1 The options, assembled once (`engineOptions`, `cmd/hardn/engine.go`)

| Option | From | Note |
|---|---|---|
| `Revert.Log` | `revertFileLog{}`: hardn's log, `/var/log/hardn.log`, alone | as `hardn confirm`'s clean-up has it: the console shows the report or the screen. **Settled:** this `Log` (§8, decision 2) |
| `Revert.Now` | `revertNow` | as `hardn confirm` and `hardn rollback` |
| `Revert.Plans` | `revertPlans` (`plans.Registry()`) | **Settled: needed.** A DNS change journals its undo as the `dns` unit's kept plan (`revert.OpPlan`), which `revert.Record` refuses without its rollback; `engine.New` would fill in the same registry, and it is set so that the rollback here and a later `hardn rollback <id>` undo with one registry |
| `Revert.Hardn` | `revertExecutable()` (`os.Executable`, resolved), as `hardn rollback --boot` | **Settled: not needed for DNS**, which arms no timer (brief 2.4): the engine reads it only for a lockout-risk plan (`pkg/engine/plan.go:233-235`, `boot.go:46`). Set for the next slices' lockout-risk changes; left empty when this hardn's path cannot be read, so that such a plan is refused ("the revert timer") rather than armed to run nothing |
| `Session` | `revert.ReadSession(ctx, sys, revertGetenv, revertPID())`, as `runConfirm` reads it | journalled with the change, and required of a lockout-risk plan, which the engine refuses when it is not established. A read that fails is logged to the file and its partial session kept |
| `Backups` | `cfg.BackupSettings()`: `backupPath`, `enableBackups` | the engine's backups are rollback-required, taken whatever `enableBackups` says (§3.16) |
| `PID` | `revertPID()` | the run lock's holder line |
| `Detect`, `Hold` | the engine's own: `detect.Detect`; `nil`, which is `hold.Signals` over `Log` | through seams (`engineDetect`, `engineHold`) for the tests |
| `Progress` | the caller's | a screen's flow, per change (`newEngine`); none for `-g` |
| `Timeout`, `Margin`, `JournalTimeout`, `Revert.Dir`, `RunDir` | the engine's defaults | no flag or key changes them (§3.14's `--confirm-timeout` is a later slice's) |

`newEngine(sys, o)` is a screen's `NewEngine`: a copy of `o` with the flow's `Progress`, one engine per change.

### 2.2 The host and its logs

`engineHost` is `host.NewReal(host.Options{RunLog: revertFileLog{}})`: every command's argv, output and status goes to hardn's log alone, as the clean-up's does. Both paths build it once per run (per visit of the screen).

### 2.3 The main menu's 3 (`runDNSScreen`, `cmd/hardn/dns.go`)

- **How `pkg/menu` reaches it:** a hook `cmd/hardn` sets, `MainMenu.SetDNS(func() error)`, from `withDNSScreen` at `main.go:190`. `pkg/menu` builds no engine and imports neither the engine nor the screens; it imports `pkg/ui/nav` for `nav.ErrQuit` alone.
- **What it runs:** `pkg/screens/dns.Run` with `prompt.Stdin()` (the one line reader every legacy prompt shares), stdout's `term.Env` (`stdoutEnv`), the host of §2.2, `detect.Detect` once per visit, the `*config.Config` `cmd/hardn` loaded (the one the main menu holds), `NewEngine` over §2.1's options, `ApplyContext` `engineSignals` (§2.6; *since `next/s3-hangup`* `screenApplyContext`, which wraps it), `DryRun` read from that configuration as the item is chosen (as the legacy menus read it, so the Dry-Run item and `-n` apply), `LogPath` the legacy log, `Now` revert's clock. The screen starts from a cleared screen, as the legacy DNS menu's `PrintHeader` cleared it.
- **What it returns:** nil, back to the main menu, which draws itself again with the list as saved (the screen adopts each save into that configuration); `nav.ErrQuit` ends hardn as the main menu's q does (it clears the screen and returns, exit status 0); the end of the input exits 130, Ctrl-C at a prompt ends hardn by SIGINT, and any other error is printed and exits 1, as at every legacy prompt (`endHardn`, factored out of `readLine` unchanged).
- **The audit log:** not written. `cmd/hardn` has no audit writer yet (its first is `next/p3-startup`'s, [output.md](output.md) §7), so `Options.Ran` is nil.

### 2.4 `-g` (`configureDNS`, `cmd/hardn/dns.go`)

In its place in the flag sequence, after the root check and the configuration's load, as before: `dnsctl.Controls(cfg)` (hardn.yml's own list, so nothing is saved) planned, then applied without a question, through the engine with §2.1's options (`runControls`, a flag's run of its controls, which the next slices' flags reuse, §7); the report is `output.Human`'s on stdout. `StopUDHCPC` is false: on Alpine, `DNS_UDHCPC` is reported and `udhcpc.conf` left as it is. A refused plan is reported with its code and how to go on (`resolvconf manages DNS here (DNS_MANAGED)`, "To go on: …") and never applied; a failed apply is rolled back and reported so. The legacy lines ("Failed to configure DNS: …", "DNS configured successfully", and after `-g` alone "Script completed selected hardening operations.") are gone: the report is the whole of it.

### 2.5 Exit statuses, `-n -g`, and the other flags

- **`-g`'s status** is `output.ExitCode`'s (Phase 3's, [reference](../reference/output.md) §3): 0 applied or nothing to change; 1 refused, failed or rolled back; 130 interrupted. *Since `next/s3-hangup`, but in one case:* 130 for a change applied when a signal came after the apply's last step or while the report is written (below, decision 18).
- **`-n -g`** is no longer refused: `-g` left `operationFlags`, the list `RefuseDryRunOperations` refuses, so its dry run is the plan alone (`mode` `plan`), shown with output's dry-run footer. Nothing is written but the engine's run directory, `/run/hardn/<id>`, which the plan makes and removes; on a host with no `/run/hardn` the plan makes that too and leaves it, empty (mode 0700, on tmpfs, so gone at the next boot), as every `Engine.Plan` does (`MkdirAll`, then `removeRunDir` of `<id>` alone). Its status: **3 with changes to make**, 0 with none, 1 refused (§8, decision 4). `-n` with any other operation flag is refused as before (exit status 2, before the root check), the message naming those flags only.
- **With other flags in one invocation** (origin/main logged each failure and went on, V25): the flags run in their order as before, each reporting as before; `-g`'s status, when not 0, is hardn's once the flags after it (`-p`, `-e`) have run (`defer exit(code)` in its block, `main.go:410-414`). An interrupted `-g` ends hardn at once with 130, the flags after it not run. *Since `next/s3-hangup`* (the maintainer, 2026-10-28: "Yes, catch it"), so does a `-g` whose apply or report a signal reached without interrupting the apply, once `-g` is reported (`runControls`: `signalled`, the apply's signal context done, read after the report, so that a signal while the report is written counts). *Since `4a0079e` ("Yes, fix it"; §2.6), `signalled` is also a hangup the terminal's watch caught: one before `engineSignals`' registration, which the watch alone catches, the apply not cancelled, ends `-g` the same way once reported (run, on hostfake: `TestConfigureDNSFlagWithOthers`' "a hangup as engineSignals registers": applied, 130, `-e` not run).* `SIGTERM` or a hangup during the rollback of a failure (the engine's hold catches both; it ignores Ctrl-C) ends hardn with the failure's status, 1. Any of the three after the apply's last step, or while the report is written, the change applied, ends it with **130, not 0**, `-g` alone too, so that a script never reads 0 for a run whose later flags did not run (decision 18): there hardn's status is not `output.ExitCode`'s, and the report says the change applied ("Operation Successful"). After a failure's rollback, Ctrl-C has no registration left (the hold's `signal.Ignore` ended it, and its release gives SIGINT Go's default), so during the report it ends hardn by SIGINT, as before (read; the hold's `notified-then-released`, run). Run on macOS, on hostfake (`TestConfigureDNSFlagWithOthers`, §9): a hangup during the rollback, 1, `-e` not run; for each of SIGINT, SIGTERM and SIGHUP, after the apply's last step and as the report begins, 130, the change applied, `-e` not run. Before this branch, these signals were swallowed (the apply's context cancelled, nothing reading it) or, a hangup during the rollback, discarded by the hold, and the flags after `-g` ran, with `-g`'s 1 or 0 (read). `-e`'s own failure still exits 1 at once. `-r` with `-g` runs `-r` alone, as before (its block returns first). **With another legacy flag** (`-w -g`, `-u -g`, ...), the legacy completion line, "Script completed selected hardening operations.", still prints at the end whatever `-g`'s status, under its refusal's report too: accepted, as the legacy flags report as before (origin/main printed it after any flag's logged failure, V25), and the exit status is the run's verdict (§8, decision 11).

### 2.6 Signals

Both paths register `signal.NotifyContext` for SIGINT, SIGTERM and SIGHUP (`engineSignals`, over `engineSignalSet`) **around each apply alone**, as engine.md §2.14 asks of the engine's caller: a signal during an apply cancels it, and the engine rolls the change back here with the signals held (SIGINT ignored, SIGHUP and SIGTERM caught; *before "Yes, catch it"*, SIGHUP ignored with SIGINT), rather than Go's default ending hardn with the change half applied and journalled.

- **`-g`** (`runControls`) registers once its plan is made, around the apply and its report, and ends hardn with 130 when interrupted; *since "Yes, catch it"*, after a signal that reached that registration without interrupting the apply, once reported: with 1 after `SIGTERM` or a hangup during the rollback of a failure, with 130 for a change applied (§2.5, decision 18).
- **The DNS screen** registers for each change's apply through `dnsscreen.Options.ApplyContext` (the screen's flow engine applies under it, `planning.Apply`), stopped once the apply returns; the screen then goes on, reading the host again. *Since `next/s3-hangup`, not after a hangup (below).*
- **After a hangup the screens end hardn** (*since `next/s3-hangup`*; the maintainer, 2026-10-28: "Yes, end on hangup"). The DNS and Backup screens' `ApplyContext` is `screenApplyContext`: `engineSignals`, with a SIGHUP channel of its own, buffered, registered before `engineSignals`' registration. Its stop, once the apply has returned, the change rolled back (or finished: *Other windows*, below), finds the SIGHUP there, logs "hangup during the apply: hardn ends" to the log file, and ends hardn by SIGHUP (`endByHangup`: `signal.Reset`, then SIGHUP to itself, as `prompt.Reraise` does for SIGINT; 130 if hardn still runs 500 ms later, SIGHUP ignored). Ctrl-C and SIGTERM during an apply are unchanged: rolled back, the screen goes on. A hangup that interrupts `-g`'s apply is unchanged: rolled back, 130 (`runControls` keeps `engineSignals`). *Since "Yes, catch it"*, one that reaches it without interrupting it, during the rollback of a failure or after the apply's last step, ends hardn once `-g` is reported, with 1 or 130 (§2.5, decision 18).
  - *Why:* hardn ended at its next prompt, its input gone; sudo-rs (Ubuntu 26.04's sudo) keeps that input open, so hardn waited there until killed ([screen-backup.md](screen-backup.md) §4.2).
  - *Through the hold:* as first built, its `signal.Ignore` ended this registration as it ended `engineSignals`', but the SIGHUP that cancelled the apply came before the hold, and os/signal sends a signal to every channel then registered for it (§3), so it waited in the channel. *Since "Yes, catch it" (decision 17), the hold catches SIGHUP and leaves both registrations of it be: its release is `signal.Stop` of its own channel (engine.md §2.14), so a hangup during the rollback, or after it before the stop, reaches this channel too (below).* The buffer matters (unbuffered fails, run), and so does the order, the channel first. *Corrected after review: the first build said the order did not matter.* A hangup between the two registrations, a window of microseconds, then reaches the channel alone: the apply, not cancelled, finishes, and hardn ends after it. Registered the other way, such a hangup cancels the apply unseen, and the screen goes on. `TestScreenApplyContext` holds the order (run: the swap fails it).
  - *What is on the screen:* hardn ends before the flow draws the change's report (the failure, the rollback, the log's path), as `planning.Apply` returns; the steps' lines the apply wrote are there (run, on hostfake). On a terminal the steps are drawn in place, the rolled-back state included (read, not run). Off a terminal the last line can be a step's `Done` for a change then rolled back: Backup's "[+] Save the configuration  Done" (run, on hostfake); the log says it was rolled back (read).
  - *Not seen, as first built:* **a hangup during the rollback.** The hold ignored SIGHUP (`SIG_IGN`, so that the commands the rollback runs ignored it too: engine.md §2.14), so the kernel discarded it, and hardn went on to its next prompt, as before this branch (run: `TestScreenApplyContext`). Under sudo-rs that prompt never ends (§4.2's finding; not run for this case). Nothing in `cmd/hardn` could see such a hangup without changing the hold (read). *Seen since "Yes, catch it" (the maintainer, 2026-10-28; decision 17):* the hold catches it and logs "hardn: SIGHUP received; the rollback finishes first" to the log file (the engine's own hold over `Revert.Log`, read), the rollback finishes, and the stop finds the SIGHUP in the channel and ends hardn once the apply has returned (run, on hostfake: `TestScreenHangupDuringRollback`, DNS and Backup, a change that fails and a hangup during the engine's own hold: hardn ends once, after one apply, its signal context stopped and the hold released, the file as before; `TestScreenApplyContext`'s "SIGHUP during the hold"). The commands the rollback runs are in sessions of their own (`host.OwnSessions`), out of reach of the hangup sent to hardn's process group (run on macOS with `sleep`: hold's `TestGroupHangupDuringHold`; not with `ufw` or `systemctl`, not on Linux; *with `systemctl` on Debian 13 since, below; on Ubuntu 26.04 its session of its own seen, no hangup sent to the group; there too at `4a0079e`, the hangup sent to the group (below)*). The group gets it from classic sudo, a shell or the kernel; sudo-rs 0.2.13 sends it to hardn alone (§3).
  - *Run on the VMs* (2026-10-28, `440a7b0`, as root, amd64; [screen-backup.md](screen-backup.md) §4.2, the hangup rerun, logs `41-hupapply-*`, `43-hupundo-*`, `44-huprollback-*`): on Debian 13 (sudo) and Ubuntu 26.04 (sudo-rs), a hangup during a Backup save rolled it back and ended hardn, "hangup during the apply: hardn ends"; and a DNS change failed by Ctrl-C during its reload (made to take 20 s), then a second Ctrl-C during `dns.Apply`'s own undo, and the session dropped during the journal's rollback, the "Seen since" case: the rollback's `systemctl` in a session of its own (its session id its pid, read from `ps` before the drop), the hold's line (twice on Debian), that `systemctl` exiting 0, "rollback …: done", then the end line, hardn gone, the drop-in absent. - **After a hangup hardn stops writing to its terminal** (*since `4a0079e`*; the maintainer, 2026-10-28, to §11's "under sudo-rs, hardn hangs mid-apply once its terminal output blocks": "Yes, fix it": "Make hardn stop writing to its terminal once a hangup is caught, so that under sudo-rs a full pty cannot hang it mid-apply; then rerun Ubuntu's checks, the group hangup included"; decision 19). `cmd/hardn`'s stdout and stderr go through one writer each, `termStdout` and `termStderr` (`terminalWriter`, `cmd/hardn/output.go`, over `pkg/host/hangup`'s `Writer`): until the hangup is seen (`hangup.Seen`), each write goes to the file, one at a time, in order, returning what the file's returned, a failure included; after it, nothing is written and the write reports success (`len(p)`, no error), and a write under way then returns at once, the file's own left to finish, or block, on a goroutine of its own, with a copy of what it was given. Through them: `engineStdout` (the screens' output and `-g`'s report), `confirmStdout` (`hardn confirm`'s clean-up report), `stderr` (the command line's refusals), `revertStderr` (the next-run notices), fatih/color's `Output` and `Error` (the legacy logger's console lines: `hardn rollback`'s and `hardn confirm`'s), and pkg/logging's fallback when `/var/log/hardn.log` cannot be opened (`logging.FallbackOutput`, new; before, that fallback wrote `os.Stderr` itself): the first four as they are declared, fatih/color's and the fallback set by `init`, before `main` opens the log. The legacy menus' own `fmt.Print` calls write to `os.Stdout` itself; no hangup is caught while they run (read).
  - *The watch:* `watchHangup`, around every window in which `cmd/hardn` catches SIGHUP, registered first, before the signals that cancel the work, so that no hangup they catch goes unmarked. It marks the terminal gone (`terminalGone`, `hangup.Seen`) as each hangup comes, not at its stop: the write that would block is the apply's or the rollback's own, before any stop. Its stop, once: `signal.Stop`, then the channel closed (os/signal sends it nothing once `Stop` returns, §3), then a wait until the watch has read it to its end, so that a hangup still held there is marked. The windows: the screens' apply (`screenApplyContext`'s SIGHUP channel is the watch's, in the same place, before `engineSignals`; its stop, once, ends hardn when the watch saw a hangup, as before); `-g`'s apply and report (the watch, then `engineSignals`, both stopped as `runControls` returns; a hangup the watch alone catches ends `-g` once reported, as a signal does: §2.5); `hardn confirm`'s clean-up (the watch, then `confirmSignals`, stopped after it; the report is written after the stop, where a hangup is Go's default, death, as before); `hardn rollback` and `hardn rollback --boot` (the watch's stop deferred before the hold's: the mark comes whatever the hold's own goroutine is busy with, its console line for an earlier SIGTERM, through `revertWarnLog`, being a write that could block on the full pty before the hold reads the hangup). The engine's hold marks it too, on SIGHUP, before logging its line, not on SIGTERM; its release leaves the mark, which cannot be undone (`pkg/engine/hold`, read). Outside those windows SIGHUP keeps Go's default: hardn dies (§3, Go's runtime, read), a write blocked in the kernel with it (**[unverified]**, §3: not observed with hardn blocked).
  - *What is kept, what dropped:* hardn's log file keeps its lines. A stdout that is a regular file (`hardn -g > report.txt`) is used as it is, outside the gate: a write to a file never waits on a reader, and what hardn writes there after a hangup is still read (a review's finding: the first build dropped it). A terminal, a pipe or the null device goes through the gate, so after a hangup what is written there is dropped: the screens' redraws and report, `-g`'s report, `hardn confirm`'s report and what it says is left, `hardn rollback`'s console lines. p2drive (a dev tool) is unchanged: its hold marks hardn's terminal, which nothing of p2drive's writes through; its output under the hold, about 500 bytes, no spinner, measured in review, is not gated, by choice.
  - *Run:* on macOS (§9): the writer on a real pty whose master is never read, its slave a blocking file outside Go's poller, as stdout is (the second 1 KiB write blocked; after `Seen` it returned, and a later one too); `cmd/hardn`'s writers through a pipe in a child process, and to a regular file; the screens and `-g` on hostfake, with a terminal that blocks every write once the hangup comes. The pty test's Linux helper is written, vetted by `check-cross`, not run. On the VMs, Ubuntu 26.04, and Debian 13 the next day (above, "Run on the VMs").
- **Registered again for each apply.** The hold around an in-process rollback (`hold.Signals`) ignores SIGINT (and ignored SIGHUP too until "Yes, catch it"), which ends a registration of it made before it (`signal.Ignore`, engine.md §2.14), and its release gives it Go's default. The first build registered once for the screen's whole visit, so after one change failed and was rolled back, a Ctrl-C or a hangup during a later change's apply in the same visit ended hardn with that change half applied (a review found it).
- **Outside an apply** (at a prompt, while the screen reads the host, during a plan) nothing of `cmd/hardn`'s is registered, so the signals act as they always have: Ctrl-C at a prompt ends hardn by SIGINT (the prompt's own interception, `prompt.ErrInterrupted`), SIGTERM and a hangup by Go's default (the screens' SIGHUP channel too, dropped by the stop: `TestEndByHangup`, run). The first build caught them for the whole visit, and the prompt watches no context, so a SIGTERM at a prompt was swallowed until the user typed, and the visit then ended with "context canceled", exit status 1 (a review found it). A plan interrupted so has written nothing but its run directory (§2.5).

*Chosen over* registering for the visit and registering again in a hold of `cmd/hardn`'s own (`Options.Hold` wrapping `hold.Signals`): that fixes the first defect from `cmd/hardn` alone, but not the second, as a signal the visit catches at a prompt cannot end hardn there. The cost is one field in `pkg/screens/dns.Options` (§6).

17. **The hold catches SIGHUP, and the commands the rollback runs get sessions of their own** (`pkg/engine/hold`, `host.OwnSessions`; engine.md §2.14, [system.md](../safety/system.md) §2.5). The hold logs a hangup and leaves a caller's registration of SIGHUP be, so the screens' channel receives a hangup during the rollback, and hardn ends once the apply has returned (§2.6); while it holds, `host.Real`'s `Run` and `RunInput` start each command with `setsid`, so the hangup sent to hardn's process group reaches neither the `ufw` nor the `systemctl` the rollback runs, which on exec would get SIGHUP back at its default action. *That premise is classic sudo's (and a shell's or the kernel's): sudo-rs 0.2.13 sends the hangup to hardn alone (§3, read in review and observed on the VMs, 2026-10-28). Observed on Debian 13 since: the rollback's `systemctl`, in a session of its own, ran to its end after classic sudo's hangup, which reached hardn's group in the run's 43, the session dropped the same way (§2.6, "Run on the VMs").* `-g` ends once reported after such a signal, rather than running the flags after it (§2.5, decision 18). *Alternatives:* keep `SIG_IGN` (the kernel discards an ignored signal, so nothing in hardn can see it, and under sudo-rs hardn waits at its prompt: [screen-backup.md](screen-backup.md) §4.2); `Setpgid` alone (a process group of its own is a background job of the terminal, which a read of it stops with `SIGTTIN`: system.md §2.5; `setsid` leaves the command no controlling terminal, so no `SIGTTIN`, and `/dev/tty` cannot be opened, **[unverified]** here); caught in hardn while its children ignore it (one disposition per process, and a caught one goes back to the default on exec, so not possible in Go); `Setsid` for every command, always (it changes Ctrl-C for every legacy-equivalent command outside a rollback, the job-control change system.md §2.5 left out). *Held by* hold's `TestGroupHangupDuringHold` and `TestReleaseGivesUpSessions` (without `OwnSessions`, "the command: killed by hangup" in the first) and, the old hold put back, `TestScreenHangupDuringRollback` (both screens), `TestScreenApplyContext`'s hold cases ("SIGHUP during the hold", "SIGHUP after the hold"), `TestEndByHangup`'s ignored mode, the `-g` rollback case and both `TestHoldSignals` failing (mutations, run, §9), and the session's choice by `TestOwnSessions` alone (`Setpgid` in its place fails nothing else: engine.md §2.14).
18. **`-g` ends hardn once reported after any signal that reached its apply or its report, with 130 for a change applied** (§2.5; changed after review). The signal is read after the report (`signalled`), so one while the report is written counts. A failure rolled back keeps its status, 1, after `SIGTERM` or a hangup during the rollback; a change applied, a signal after the apply's last step or during the report, Ctrl-C included, is 130, not 0, the flags after it not run: 130 is output.md §3's decided status for a run interrupted by Ctrl-C, `SIGTERM` or a hangup, here hardn's invocation rather than the apply. *Alternatives:* the run's status, 0 for a change applied, which a script would read as success though the flags after `-g` did not run (as first built; the six cases of §9 fail it, run); the signal read before the report, so that one during it went unseen and the flags after it ran (the three "during the report" cases fail it, run); ending only after a failure (`signalled && run.Err != nil`), the flags after an applied change run as before this branch (the same six fail it, run). *The cost:* hardn exits 130 under a report that says the change applied, the one case where `-g`'s status is not `output.ExitCode`'s (§11).

From `next/s3-hangup`, after "Yes, fix it" (the maintainer, 2026-10-28, to §11's "under sudo-rs, hardn hangs mid-apply once its terminal output blocks": "Make hardn stop writing to its terminal once a hangup is caught, so that under sudo-rs a full pty cannot hang it mid-apply; then rerun Ubuntu's checks, the group hangup included"; the how is this unit's, for review; built in `4a0079e`):

19. **hardn stops writing to its terminal once a hangup is caught** (`pkg/host/hangup`; `termStdout` and `termStderr`; `watchHangup`; the hold's mark; §2.6). A write after the hangup writes nothing and reports success (`len(p)`, no error), so that a report written to a terminal nothing reads does not fail the run; a write already blocked is given up on, the file's own write left on a goroutine of its own, with a copy of what it was given. A stdout that is a regular file is kept (`hardn -g > report.txt`): it never waits on a reader, and what is written there after a hangup is still read (a review's finding: the first build dropped it). The watch comes first in every window that catches SIGHUP (the screens' apply, `-g`'s apply and report, `hardn confirm`'s clean-up, `hardn rollback`'s and `--boot`'s hold), registered before the signals that cancel the work, so that no hangup they catch goes unmarked, and it marks as each hangup comes, the write that would block being the apply's or the rollback's own, before any stop. `hardn rollback` and `--boot` have a watch of their own beside the hold's mark (a review's finding): the hold's goroutine may be logging its console line for an earlier SIGTERM, a write that can block on the full pty, before it reads the hangup. *Alternatives:* a write with a deadline (§11's other suggestion): hardn's stdout is a blocking file outside Go's poller, whose `SetWriteDeadline` fails (`TestWriterOnAnUnreadTerminal` checks so, run on macOS); a dropped write returning an error, so that a report written after the hangup would fail the run; a regular file gated too (its report lost, though read after the session: the first build's); the hold's mark alone for `hardn rollback` (the review's case above). *The cost:* after a hangup the console gets nothing more, `hardn confirm`'s report of what is left included, the log keeping its lines; a write given up on leaves its goroutine blocked until the pty is closed or hardn ends, at most one per writer, as it holds the writer's turn and a write after the hangup returns without one (read); the legacy menus' `fmt.Print` calls and p2drive's output are not gated (no hangup is caught while the first run; the second about 500 bytes under its hold, measured in review). *Held by* §9's tests and 30 mutations (`go test -overlay`, not committed), each failing a test: the writer's turn, copy, re-check and goroutine; the hold's mark and its order; the watch marking at the stop, its stop's wait; every wiring of `termStdout`, `termStderr`, fatih/color and the log's fallback; files kept; each window's watch, its order and its stop. Run on the VMs on Ubuntu 26.04, and on Debian 13 the next day, as at `440a7b0` (§2.6, "Run on the VMs").
