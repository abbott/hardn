# The main menu from the real checks, in the gallery (`internal/tools/uigallery`: `status`, `play status`)

> **Unit:** refactor plan Phase 4, `next/p4-gallery-status` (plan header, "Phase 4 started", item 5: "the review surface (the gallery's main menu from the real checks over the simulated hosts)"; brief Phase 4, "Connect the Phase 1 main-menu slice to the live status model", here in the gallery alone; brief Phase 5, "gallery first"). It shows what the five checks ([check-ssh.md](check-ssh.md), [check-firewall.md](check-firewall.md), [check-users.md](check-users.md), [check-apparmor.md](check-apparmor.md), [check-updates.md](check-updates.md)), the header probe ([header.md](header.md)) and the risk level ([risk.md](risk.md)) make of a host, as `pkg/output` maps them. No V-number, no proposal decided, and no behaviour of hardn changes: the unit is dev-only, in a binary no build target makes ([design-system README](../design-system/README.md) §9.14, "Never released").
> **Status:** built and tested on macOS, in process, over hostfake: each host read by the real code, its main menu pinned as a golden on the core set, every call the checks made checked to be a read, the race detector run on the package. No real terminal and no host were used; nothing here runs on Linux, and nothing needs to: the gallery runs no command (§2.7). **No wording is new here**: every status line, level, gloss and factor is the checks', the probe's or the score's, proposed on their pages (§5).
> **Amended by `next/s2-menu-live`** (refactor plan slice 2; the maintainer, 2026-10-23: "Main menu goes live"): each host is read over the main menu's one list of status controls (`controls.Status`, `pkg/engine/controls`), which adds **the DNS row** after Auto Updates, checked against the host's `hardn.yml` as hardn loads it (`statusConfig`: `/etc/hardn/hardn.yml` through the host, or hardn's defaults, listing no nameserver, where there is none). The hardened host, and so `figma` and the two lockouts, now also has DNS as Configure DNS leaves Debian 13 (`dnsConfigured`). DNS weighs 0 ([risk.md](risk.md) §5.1): every golden gained the DNS row and nothing else, every score and line as before (§5, [menu-live.md](menu-live.md) §4). The passages it changes are marked below; the rest stands.

The checks, the probe and the score each have their tests, and `pkg/output`'s golden `human/status` draws the risk summary and the status rows over synthetic reports. None draws the main menu as hardn will draw it from a host. Now `uigallery status` lists, and `uigallery play status` plays, hardn's main menu whose header, distribution bar, host block, risk summary and status rows are read from a simulated host by the real code, so the maintainer can review every line in its place.

## 1. Why

A status line is reviewed in its place: beside the six others, under the level they score, below the header the same host fills. The pages' tables list each line alone; the risk page computes levels over synthetic rows. Which lines a platform gives as installed, and what level they add up to, was not shown anywhere, nor how the main menu takes a factor or a pending reboot at 80×24 (risk.md §8 (i)).

Its formats are the ones the checks' and the probe's own tests pin (their site builders and testdata), written again: a main package cannot import them. Some hosts change it as installed: ufw as Ubuntu ships it (`ufwAsShipped`), the cloud image's `60-cloudimg-settings.conf` and cloud-init's sudo rule (`cloudImage`), the ISO install's `50-cloud-init.conf` (`isoInstall`), ufw stopped with its `ENABLED=yes` kept (`stopUFW`). `fakehost.go` gains a Proxmox VE 9 platform (`pve9Platform`: Debian 13 underneath, `pve-manager` 9.0.10 in dpkg, `pveversion`, pmxcfs mounted on `/etc/pve`, no sudo, no ufw), doas as a platform's flag (Alpine's, as before), `apt-config` not shipped on Alpine and `apk` only there, and on a status host `dpkg-query`'s answer for every package. **The scenarios' hosts carry no readings** (`fakeHost.status` nil): every command their engine runs is answered as before, one the model does not answer is still kept as unanswered (`dpkg-query` but for `pve-manager` among them), and every existing golden is unchanged. Tested: `TestScenarioHostsKeepTheirs`; `TestReadingsAnswer` (the answers no host asks for: a unit not active or not enabled, an interface with no address, crond stopped, a host with no readings); `TestFakeHost`, `TestScenarioHosts`, `TestPlayEngine` as they were.
4. **The setuid bit.** hostfake keeps none (its package doc), and the users check counts only a tool that is setuid root (check-users.md §5), so the checks read a status host through `statusSys`, whose `Stat` shows the bit on the elevation tools the platform installs (`/usr/bin/sudo`, `/usr/bin/doas`), as the users check's own tests do. Tested: `TestStatusSys`.

### Play and the listing

5. **`play status`** opens a menu of the hosts (the sub-menu layout, "Status hosts", `0` to return), and **`play status/<host>`** one host: its note, an info `Callout` titled `status/<host>`, then its main menu, set apart as a scenario's is. Its items are the mock's and lead where the mock's do (`links`, through `session.open` with the mock's name), to the screen mocks on their fixture plans, which show Figma's host, not this one; so `-sequence` and `-fail` are taken as for the mocks. Play's note says both; `0` goes back from it (to the hosts' menu, or out of play), `q` quits, and the end of the input aborts (130), as everywhere in play. Play ends with the simulated system's record, "Nothing was applied." unless a mock's workflow applied. Tested: `TestPlayStatus` (an item leading to User Management and back, the host's main menu drawn again from the same reading; `-sequence typed -fail 2` in the note; the end of the input at the hosts' menu), `TestPlayStatusGolden`, `TestStatusWriteFails` (a failed write of the host's note, played directly or chosen from the menu: exit 1; a host that cannot be read: its name in the error).
6. **`status [flags] [host | all]...`** lists the hosts with no input: for each, a header `status <host>`, its note, then its main menu as `screen.MainMenu.Render` draws it, down to its prompt, a write each. `-list` prints the hosts' names; `-theme`, `-profile`, `-ascii`, `-override`, and `-width` and `-height` sized as play's (`look.sizeTo`): on a terminal of 40 rows or more, from 64 columns, the full form, as 00-TUI-MAIN.png; below, the compact form; off a terminal 80×24. A name that is not a host, a flag after a name, or a bad flag exits 2 before anything is read; a failed write, or a host that cannot be read (only when the reading's context ends: detection fails for nothing else), exits 1 with the host's name. Tested: `TestStatusGolden`, `TestStatusUsage` (also `-h` and a bad `-override`), `TestStatusWriteFails`, `TestStatusSmoke` (every profile, both themes and glyph sets, at 60 and 80 columns: every host's header, no line wider than the terminal but a header).

### Nothing on this machine

7. **The checks only read, and only the fake.** Every host's engine is built on its fake (`engine.New(h.sys(), engine.Options{…, Hold: s.hold})`), which `TestPlayTouchesNothing` holds to the gallery's own hold as before; `TestStatusHosts` checks every call the checks and the probe made on every host: reads, and commands that only read (`statusReads`: the scenarios' reads and `apt-config dump`, `ip -4 addr show`, `doas -C`, `apk info -e`, `rc-service crond status`), each answered by the model, and the hold never taken. The new code links nothing play did not link already (`pkg/output` imports the checks, the probe and the score).

### Goldens

8. **One golden per host, and two of play**, on `uitest.Core()` (truecolor dark Unicode at 80 columns, plain at 80, truecolor dark Unicode at 60): `testdata/golden/status/<host>.golden` (the listing), `play/status/menu.golden` (the menu, Figma's host chosen, back, out) and `play/status/lockout.golden` (the lockout played directly, then `q`), written with `go test -run 'TestStatusGolden|TestPlayStatusGolden' ./internal/tools/uigallery -update` (`make golden-update` writes the same). At 24 rows a terminal's cells take the compact form; plain mode, which is not a terminal, the full form. `next/p4-gallery-status` left the existing goldens unchanged; `next/p4-risk-lines` rewrote the six whose hosts have a factor, `status/pve9`, `ubuntu2604-cloud`, `figma`, `lockout-at-start`, `apparmor-unread` (the line moved from under the level to under its row, in the maintainer's words and colour) and `reboot` (the host block's line dash-led, the factor under the level gone), and `play/status/menu` (Figma's host chosen); p4status's fixtures, the hosts' readings, are unchanged (rewritten with its README's command, no diff).

### Decisions of this unit

9. None is the maintainer's; each is the gallery's, and none changes hardn:
   - **The rest of the main menu is the mock's**: its items, heading, mode and prompt are `MainMenuFixture`'s, and its items lead to the mocks. The status model fills the blocks it owns (plan row `p4-risk`, `p4-header`); the items, the mode and the sub-screens are slice 2's and each area's slice.
   - **The hosts are the gallery's catalogue**, beside the engine's scenarios, not `pkg/ui/screen` mocks: `pkg/ui` renders only, and a host is read through the engine.
   - **Detect once.** `Engine.Check` detects the facts itself; the gallery keeps them (`Options.Detect`) for the header probe, rather than detecting twice, so the header and the rows are of one reading.
   - **Hosts as installed are hosts of their own.** The scenarios' Debian 13 and Ubuntu 26.04 keep ufw active and allowing 22, as the scenarios need; Ubuntu's cloud image, its ISO install and Debian 13 with root alone are the platforms as installed, each fact sourced or marked in §3.
   - **AppArmor's eight lines are hosts**, one line each, on `debian13` but for AppArmor where the line is not a platform's own (Alpine's, a container's).
   - **No `pkg/ui` change**: every line shows with the components as they are. The compact form's overflow at 80×24 (§5, (a)) is shown, not fixed.

## 4. Written, not run (gate 5)

Nothing here runs on a host, and nothing needs to: the gallery runs no command (§2.7). A VM run of the main menu needs a driver that calls `Engine.Check` on a real host, which is not this unit. **By hand, not done here:** `go run ./internal/tools/uigallery status -height 40` and `play status` on a terminal.
