# The output contract (`pkg/output`, `host.System.AppendFile`)

> **Unit:** refactor plan Phase 3, `next/p3-output` (plan §2, row `p3-output`; brief §2, the decision "A fixed exit-code set and versioned JSON output"; brief Phase 3: non-interactive use, the exit codes, the JSON contract, the audit log and its [Verify]; decision §3.17, approved 2026-10-17: the deprecation warning for a bool `permitRootLogin`; §3.11 is **not** approved, so no flag is added). It takes up the "`p3-output` and `p3-startup`" items of [docs/safety/README.md](../safety/README.md) that are this unit's, and the `p3-output` inputs of [engine.md](engine.md) §7, [steps.md](steps.md) §7, [engine-boot.md](engine-boot.md) §7, [revert.md](../safety/revert.md) §7 and §8.5, [revert-boot.md](../safety/revert-boot.md) §6 and every Phase 2 page's §6. V-numbers: none; the one behaviour change is the escape codes the VM runs found in the journal ([vmtest.md](../safety/vmtest.md) §4.9), and the warning §3.17 approved.
> **Status:** built and tested on macOS: the documents and human reports as goldens, the exit statuses, the registry against a scan of the sources, the flow adapter and the engine's own unjournalled, interrupted and lockout-risk runs over the real engine on the recording fake (`hostfake`), the audit log on the fake, `AppendFile` on the fake and on real files in `t.TempDir()`, `cmd/hardn`'s two wirings through its seams with no binary run. Nothing has run on Linux: everything host-specific is "written, not run (gate 5)" (§4).

The public contract, what a script may rely on, is [docs/reference/output.md](../reference/output.md). This page says what the package guarantees, on what, and how it is tested.

## 1. Why

The engine returns `Plan`, `Report` and `Result` as data, and the Phase 2 primitives return sentinels and typed errors, each page listing the codes it hands on. Nothing turned those into what the brief decided: one versioned JSON document on stdout, stable codes a script can match, five exit statuses, an audit record per run. `Plan`, `Report` and `Result` are not a wire format: their errors marshal as `{}` and their words follow the constants (engine.md §7). And two things were owed to the command line already: §3.17's deprecation warning, which nothing printed ([sshd-migrate.md](../safety/sshd-migrate.md) §2.20), and `hardn confirm` and `hardn rollback`'s colour codes in the journal (vmtest.md §4.9).

## 2. Guarantees

### The document (`Document`, `Build`)

1. **Wire types of their own** for the nine top-level fields (`schemaVersion`, `hardnVersion`, `host`, `mode`, `result`, `changes`, `status`, `findings`, `errors`), shared with the audit log's `Record`. `Build(Run) Document` is pure: it maps a `Run` (the mode, `Engine.Check`'s reports, `Engine.Plan`'s plan, `Engine.Apply`'s result, the run's error, the configuration's deprecations) into them. Every word comes from a table of this package (`stateWords`, `riskWords`, `stageWords`, `stepWords`, and detect's `Tri`, `InitKind`, `SSHMode`, `Support`, `Distro` and `SudoFlavor`), never from a `String` method, so a change of an engine or detect constant is not a change of the schema; detect's facts are mapped to the schema's `Host`, not written as they are ([detect.md](../safety/detect.md) §6). Arrays are never `null`. Tested: `TestDocuments`, a golden per document the plan row names (a check, a plan, a refused plan, an applied lockout-risk change waiting for confirmation with its deadline approximate, a failed apply rolled back: `testdata/json/*.json`), `TestRealUnjournalled` (`unjournalled.json`, from the engine's own run), and `TestHostAndConfirm` (Alpine's words, no facts at all).
2. **`schemaVersion` 1** and the documented rule for bumping it ([reference](../reference/output.md) §1.1): additions and new values of open fields keep it; anything that would break a script reading version 1 bumps it. The goldens pin the documents, the codes and each sentinel's code, so such a change cannot land unseen.
3. **Each change's status** comes from the result, as the engine's progress events report it (engine.md §7, §2.15): `planned` for a check or a plan; for an apply, `applied` for a change in `Result.Applied` (and for the boot unit, from `Result.Boot`, since it is never in `Applied`: engine-boot.md §2.1); `failed` for `Failed.Change`, but `not-run` (with why) when the apply stopped before it started (`StepStart`: Ctrl-C between two changes; `StepWindow`); `unjournalled` for `Failed.Unjournalled.Change`; for one applied before an `ApplyError`, `rolled-back` when the rollback in this run finished (`RollbackErr` nil, the case where the engine sends `EventRolledBack` for each done change but the unjournalled one), and `unknown` when it did not finish or another process had the change (`ErrIncomplete`, `ErrRollingBack`), since whether it still stands is then not established (brief §3: Unknown before guessing); `not-run` for the rest. Tested over the real engine: `TestRealUnjournalled` (the change before rolled back, as the engine reported it), `TestRealCancelBetweenSteps` (the next change `not-run`, its reload never run); `TestRollbackNotFinished` (`unknown`).
4. **Each error once**, with its code ([reference](../reference/output.md) §1.8): a failed check's; a plan's refusals one by one (from `Plan.Refused`, or split out of `Plan.Err()`'s join when only the error is given, as `Apply` returns it); an `ApplyError` as its step's error, its rollback's error, and a change the journal did not cover (`CHANGE_UNJOURNALLED`, its message ending with what undoes it, in the engine's words: each undo step, each reload, each backup to restore from the run directory); the boot unit's failure; the run's own error unless it is one of those, the `ApplyError` wrapped by the caller included (`TestWrappedApplyError`). Not errors: `nav.ErrQuit` and `nav.ErrBack` (declining, §2.8), and the policy's `ErrConfirmationRequired` for a plan with nothing to change (§2.15). A refusal with a report (`steps.Refusal`) carries its `Why` and `Fix`; an error about a change carries the change's control. Errors are compared by identity only for comparable types that are neither structs nor arrays (a struct holding an interface is comparable, and comparing two whose dynamic values are not panics), so no error value can make `Build` panic (`TestBuildNeverPanics`).

   **What undoes an unjournalled change** is in the document, as engine.md §7 asks ("`Unjournalled`'s undo and backups shown as what may be left"): `result.rollback.unjournalled`, an object (the change, its undo as words, its backups with their sequence numbers, the run directory, why the journal does not hold it), the same words in `CHANGE_UNJOURNALLED`'s message, the human report's next step and the flow's `Failure.Next` (`TestRealUnjournalled`, with a human golden).

### The code registry (`codes.go`, one file)

5. **One ordered list**, the first entry that matches an error by `errors.Is` or `errors.As` giving its code (`CodeOf`), with steps.md §7's precedence: the more specific first ([reference](../reference/output.md) §2 states the order). An `*engine.ApplyError` takes its step's code; anything unmatched is `UNCLASSIFIED_ERROR`, a code like the others. Each entry carries its kind (`error`, `finding`, `boot`), the exit status an error of it gives a run, and a line saying what it means, which the reference page lists.
6. **What it covers:**
   - **Every exported `Err*` sentinel of `pkg/host/...` and `pkg/engine/...`** (144; `hostfake.ErrUnscripted`, a test double's, is exempt, with its reason): the Phase 2 pages' codes (`SSHD_CONFIG_INVALID`, `SSHD_ENV_NO_RUNDIR`, `UFW_VERIFY_FAILED`, …), `plans.ErrPlan`, `reload.ErrRestoredListeners` and `ErrNotInEffect` ([revert-plans.md](../safety/revert-plans.md) §6), the engine's sentinels with `ErrBootUnit` and the steps' with `SSH_LISTEN_CONF_NOT_IN_EFFECT`, the locks' (`revert.ErrNoLock`), and `pkg/config`'s two ([sshd-migrate.md](../safety/sshd-migrate.md) §6). One code for the three "directory another user can change" sentinels, as [sudoers.md](../safety/sudoers.md) §6 asks, and `AppendFile`'s `host.ErrUntrustedDir` (`UNSAFE_DIRECTORY`).
   - **The typed errors told apart by a field:** `*sshd.EnvError` by `Kind` (`SSHD_ENV_NO_RUNDIR`, `SSHD_ENV_NO_HOSTKEYS`, `SSHD_ENV_NO_PRIVSEP_USER`; [sshd-validate.md](../safety/sshd-validate.md) §6); `*revert.LockedError` by `Run` (`RUN_LOCK_HELD`, `JOURNAL_LOCK_HELD`; engine-boot.md §7); `*revert.NoRollbackError` by `NoRollbackKind`, seven codes, so that none is read as its sentinel's "nothing to confirm" (revert.md §8.5); `*revert.NotPendingError` (the change rolled back, or its rollback given up); `*sudoers.CheckError` by stage (`SUDOERS_INVALID` for the candidate, `_BEFORE`, `_AFTER`, `_RESTORED`, and `SUDOERS_CHECK_FAILED` for a check that could not run); `*ufw.RollbackError`; `*host.ExitError` (`COMMAND_FAILED`). The other exported error types match through the sentinel they `Is` (`HoldError`, `BlockError`, `NarrowError`, `ConfigError`, `PendingError`, …).
   - **Every finding** the primitives' kinds give, under the prefix `pkg/engine/steps` derives (steps.md §2.23), for the six packages with finding kinds, `SSH_MIGRATE_LINE_DROPPED`, and `CONFIG_DEPRECATED_VALUE` for a configuration value read in a deprecated form.
   - **`hardn rollback --boot`'s** four `BootAction`s and 21 `BootReason`s (revert-boot.md §6), by their stable values (`BootCodes`).
   - This package's own (`USAGE`, `CONFIRMATION_REQUIRED`, `AUDIT_DIR_UNSAFE`), the interruption (`CANCELLED`: `context.Canceled`, `prompt.ErrAborted`) and three of the standard library's.
7. **Tested:** `TestSentinelsRegistered` parses every non-test Go file under `pkg/host` and `pkg/engine` (`go/parser`) and fails for an exported `Err*` the test's table does not name, for a name the scan does not find, for a table value whose text is not its `errors.New` literal (a value paired with the wrong name), and for a sentinel no entry matches, alone or wrapped; `TestTypedErrors` does the same for exported error types (a name ending in `Error`, and `steps.Refusal`), each with a sample the registry must code; `TestSentinelCodes` and `TestCodes` pin each sentinel's code and the whole list with kinds and exit statuses (`testdata/sentinels.golden`, `codes.golden`), and `TestCodes` checks that codes are unique SCREAMING_SNAKE; `TestPrecedence` (38 rows: each wrapping case above), `TestAbandonCodes`, `TestFindingCodes` (each kind enumerated through its `String`, derived as steps does, and no registered finding left over), `TestBootCodes` (read from `boot.go`'s constants), `TestReferenceListsEveryCode` (the reference page names every code).

### The exit statuses (`ExitCode`)

8. **One function over a run's results and errors**, `ExitCode(Run) int`, the same that writes `result.exitCode`: 130 when anything was interrupted; else 2 for a usage error (a code whose `Exit` is 2); else 1 for any other error (an apply that failed, a refusal, an error before anything was armed, a failed check); else 3 when a check found a control not as asked, a plan has changes, or the user declined them; else 0. `ExitOK` … `ExitInterrupted` are constants, equal to `pkg/cmd`'s `ExitUsage` and `pkg/ui/prompt`'s `ExitInterrupted` (`TestExitStatuses`). **Decisions of this unit**, none the maintainer's:
   - a check's `unknown` state is 3, not 0: a state not established is not taken as hardened (brief §3: prefer Unknown to guessing; Phase 4 counts Unknown as not configured);
   - a refusal is 1 (the run did not do what was asked, and changed nothing), which also registers `hardn rollback --boot`'s 1 for `BootLeft`, as revert-boot.md §6 asked: no code of its own;
   - a confirmation the user declines is 3, outcome `declined`: the plan found changes, and none were made. **Quitting (`q`) or going back (`0`)** at one of the flow's prompts (`nav.ErrQuit`, `nav.ErrBack`, which `pkg/ui/flow` returns with `NotRun`) is declining too, before or after the plan: 3, `declined`, no error, as design-system README §9.8 asked this unit to decide (the end of the input stays an abort, 130). `Build` reads them from `Run.Err`, so any caller of a flow gets the same;
   - an interrupted apply is 130 even though it was rolled back: the shell's convention says what happened, and `result.rollback` what was undone. The outcome, `cancelled`, says nothing of the rollback: one that did not finish after Ctrl-C is still `cancelled`, with `result.rollback.finished` false and `result.rollback.command` to finish it (the timer is stopped then, revert.md §2.14);
   - a lockout-risk change waiting for confirmation is 0.

   Tested: `TestExitCode`, 34 rows, each also checking the outcome word and `result.exitCode`; and each fixture's.

### The renderers (`WriteJSON`, `Emit`, `Human`, `FlowEngine`)

9. **Exactly one document on stdout.** `WriteJSON` writes one value and a newline in one write (`encoding/json`'s `Encoder.Encode`, §3), HTML not escaped. `Emit` routes a run: as `FormatJSON`, stdout gets the document and nothing else, and `Emit` writes nothing for a person (what a caller shows a person besides, progress and notices, goes to stderr); as `FormatHuman`, stdout gets `Human`'s report through its `Env.Writer`. **The configuration's deprecated values** are findings of the document (`CONFIG_DEPRECATED_VALUE`) and are not warned about by `Emit`: the one warning is `cmd/hardn`'s, on stderr as the configuration loads (§2.16), so that wiring `Emit` (`next/p3-startup`) cannot print it twice. Tested: `TestStdoutIsOneDocument` decodes stdout once, then expects `io.EOF`, and checks the nine fields, the finding, and no warning text, for every fixture; `TestEmitHuman`.
10. **The human report through `pkg/ui` only** (design-system README §9.15): `StatusList`, `PlanView` (with the dry-run footer), `StepProgress`, `Callout`, `ConfirmCountdown`, `Message` and `ErrorReport`, composed by a pure function of the run, the `Env` and the clock (`Human`). A change waiting for confirmation shows the countdown, its port when every listener it adds has one, and the command in the host's elevation tool (`doas hardn confirm` with doas and no sudo: engine.md §7, "doas on Alpine"), then when it is rolled back unless confirmed, **"at about"** when the deadline is approximate, and how to undo it now. A refusal is shown by its `Why`, with its code, and its `Fix` as the next step ("To go on: …", steps' words); an apply's failure by its change and code, the changes rolled back (last first, as the engine undid them), the failing command with its output, and the next step: finishing a rollback that did not finish, in the host's elevation tool; for one another process had, waiting for it, or, when the journal no longer held the change, the rollback's own reason; what undoes a change the journal did not cover. **One code for a failed step**, the code of the `ApplyError`'s step error, on the step's line, in the `ErrorReport`'s headline and in the flow's progress alike; a change that never started is "Skipped", with that code. `Human` is for a run no flow drew (§2.11). Tested: `TestHuman`, a golden per fixture on the core cells (`testdata/golden/human/*.golden`), which `uitest` checks for width and determinism, `unjournalled.golden`, `TestRollbackNotFinished`, `TestRealCancelBetweenSteps`.
11. **`pkg/ui/flow`'s `Engine`** over the engine, as engine.md §7 describes (`FlowEngine`): `Plan` is `Engine.Plan`, each change a `component.PlanChange` in `Plan.Changes`' order (summary, target, diff, states, commands, lockout risk), the plan `RiskLockout` when the engine's is; a refused plan a `*flow.Failure`. `Apply` is `Engine.Apply` of that plan, with `Options.Progress` (the adapter's `Progress`) the one source of the steps' states: `EventRunning`, `EventDone`, `EventFailed` (its detail the error's code) and `EventRolledBack` to `StepRunning`, `StepDone`, `StepFailed` and `StepRolledBack`, `Index` -1 and events outside an apply ignored. The shown plan's `Change.Apply` functions are never wrapped, and a plan is never applied twice. A failure is a `*flow.Failure` whose text is the change's summary, the error and its code, which still unwraps to the engine's error (`errors.Is(err, engine.ErrRolledBack)`), with the failing command and its output, the log, and the next step (as the human report's, §2.10). `Run(outcome, err)` gives the `Run` for `Build`, `ExitCode`, `AfterFlow` and the audit log; `DryRun`, set as the flow's, tells a dry run that found nothing to change (`ModePlan`) from an apply that did (`ModeApply`), since the flow returns `Unchanged` for both. **`AfterFlow`** renders what the flow does not draw: the flow ends a lockout-risk apply with "Operation Successful" alone, so the caller writes `AfterFlow` on the flow's writer right after `Flow.Run`, and the person sees the countdown, the confirm command, when the change is rolled back ("at about" when approximate) and how to undo it now (revert.md §7: "the original session shows the countdown and the command"), then the plan's findings, which the flow's `PlanView` has no place for. `FlowEngine`'s doc says so. Tested over the real engine on the fake, with a control that writes a file: `TestFlowEngineApplies` (the reports in order; none after `Apply` returns), `TestFlowEngineFailure` (the rollback reported, the file restored, the document), `TestFlowEngineRefused`, and `TestFlowEngineInAFlow`, which runs the canonical flow on it: a dry run (3), applied (0), the same action again with nothing to change, as an apply and as a dry run (0), aborted at the confirmation by the end of the input (130), declined with `n` and quit with `q` (3, `declined`, no error, nothing changed), back from the form (3); `TestRealLockoutFlow`, a lockout-risk change through the flow's typed confirmation, then `AfterFlow` below "Operation Successful"; `TestAfterFlow` (`after-flow.golden`).

### The audit log (`Append`, `AuditPath`)

12. **One JSON line per run**, a `Record`: the run's time (UTC) and its document, the same nine fields as stdout's, so the plan, the results and any rollback (`result.rollback`) are there. `Append(ctx, sys, path, rec)` makes the directory when missing (`0750`), refuses it unless it is a directory owned by root that neither group nor others can write (`ErrAuditDir`, `AUDIT_DIR_UNSAFE`: a record holds the plan's diffs), then appends the line through `host.System.AppendFile`, creating the file `0600`; `AppendFile` checks the directory again on the descriptor it opened (§2.13), so a directory put in place of the checked one in between (a member of a group that can write `/var/log`) is refused too, as `ErrAuditDir` wrapping `host.ErrUntrustedDir`. It runs **without the caller's cancellation**, bounded by `AuditTimeout` (10 s): the run's context is done after Ctrl-C, `SIGTERM` or a hangup, and that run's record is the one an audit trail most needs. The path is a constant, `AuditPath`, `/var/log/hardn/audit.jsonl`, as the plan proposes. **Not wired** into `cmd/hardn`: its first writer is `next/p3-startup`'s (§7). Tested: `TestAppend` (two runs, two lines, each a `Record`; the modes; appended, never rewritten), `TestAppendRefuses` (a directory others can write, another user's, a symlink at the log's path: refused, nothing written, the link's target untouched), `TestAppendSwappedDir` (another user's directory swapped in after the check: refused, nothing written), `TestAppendInterrupted` (a done context: written).
13. **`host.System.AppendFile`**, new: the seam had no append, and the audit log needs one (§5). One write on a descriptor opened with `O_APPEND`, so two runs appending at once never overwrite each other's lines, which a read-and-rewrite with `WriteFileAtomic` would (the second rename wins, and the first run's record is lost), at a cost that grows with the log; then `fsync`. It is guarded like `WriteFileAtomic`: a symlink at the path refused (`O_NOFOLLOW`, after `lstat`), a directory or anything else that is not a regular file refused (`O_NONBLOCK`, so a FIFO swapped in does not block the open), symlinks on the way followed only in trusted directories; and **the directory it opens to hold the file must be trusted** (root's or hardn's own user's, writable by neither group nor others), checked on that open descriptor, else `ErrUntrustedDir` (registered as `UNSAFE_DIRECTORY`): what is appended goes where no other user can rename, replace or link in front of it, and the check binds the write. A file with a second hard link is then accepted: in a trusted directory no other user linked it (the rule `Chmod` and `Chown` keep). Tested: the contract test runs the create, the append and every refusal, an untrusted directory included, on `host.Real` in `t.TempDir()` and on the fake alike; `TestRealAppendRefuses` (a FIFO; an untrusted directory, holding a hard link or not; the hard link once the directory is trusted; a done context).
14. **The legacy log's path and format**, as the brief's [Verify] asks, recorded as `LegacyLogPath` and in the reference (§4 there), from [phase0-findings.md](../refactor/phase0-findings.md) §6 (**[V]**). It is unchanged. The run log (`host.Real`'s record of each command, [system.md](../safety/system.md) §2.6) goes where its caller sends it: `cmd/hardn`'s `revertLog` sends it to the legacy log, and **that is the run log's path, a decision of this unit**, until `next/p3-startup` makes the startup writes lazy and can move both.

### The non-interactive policy (`Confirmation`)

15. **Never prompt without a terminal; apply non-interactively only with an explicit yes**, as a library function of what decides it (`Interaction{InputTTY, JSON, Yes}`): yes is `Apply`, with or without a terminal; no terminal on stdin, or JSON output, without yes is `PlanOnly`, with `ErrConfirmationRequired` (exit 2) naming `--yes`, which is the plan row's "print the plan and exit 2"; otherwise `Ask`. **A decision of this unit:** a JSON run never prompts, even with a terminal, since its stdout is a script's and a prompt there would break the one document. The policy is about confirming changes: a plan with nothing to change asks nothing and exits 0, and `Build` treats `ErrConfirmationRequired` with such a plan as nothing to do, not an error, so a scheduled run on a hardened host exits 0. It is not wired (§7). Tested: `TestConfirmation`, `TestExitCode`.

### What `cmd/hardn` now does (`cmd/hardn/output.go`)

16. **§3.17's deprecation warning**: right after the root command loads the configuration, each `Config.Deprecations()` entry is printed to **stderr**, once, as a warning `component.Message` through `pkg/ui`, after the file it was read from, with `pkg/ui/term`'s detection for stderr (`warnDeprecations`, `deprecationWarnings`, in `cmd/hardn`: rendering it there keeps `pkg/output` and the engine out of the release binary until `next/p3-startup` wires them, §5). It is the one warning: `Emit` does not repeat it (§2.9). The run goes on: the value still works. Stdout, where the legacy logger writes, does not repeat it. **A limit:** with no operation flag, `sudo hardn` goes on to the legacy main menu, whose loop starts by clearing the screen (`utils.ClearScreen`), so on that path the warning is gone at once; every other command keeps it on screen. Showing it in the menu is a change to the legacy menu's screen, the main menu slice's (Phase 4, §7), as the revert notices' same limit is (revert.go's `showRevertNotices`). Tested: `TestDeprecationWarning` (a `hardn.yml` in `t.TempDir()` with `permitRootLogin: false`, loaded by `pkg/config`, through the real root command with the provider mocked: the warning once, with the line and what to write instead, no escape codes; none for a configuration without it).
17. **No colour codes from `hardn confirm`, `hardn rollback <id>`, `--abandon` and `--boot`** unless both stdout and stderr are colour terminals by `pkg/ui/term`'s detection (`term.Detect` with the stream as its output: a terminal, `TERM`, `NO_COLOR`, `HARDN_PLAIN`, and `--no-color` as `--color=never`; the theme fixed, so the terminal's background is never queried). `setRevertColour` runs first in both commands and sets `fatih/color`'s `NoColor`, which the root command's `initializeColor` sets to false before every run. **Why both streams, where the task named stderr:** the legacy logger these commands print through writes to stdout (fatih/color's `Output`, §3), the notices to stderr, and the journal takes both. Tested: `TestRevertColour`, each of the four commands with colour off (no `ESC[` in what it printed) and on.

### Through `host.System`

18. Depguard rule `output-through-host`, the last of the rules, denies `os`, `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` (but `net/netip`) and `plugin` to `pkg/output`'s non-test files: it reaches the host only through `host.System`, and writes only to the writers it is given. It renders through `pkg/ui`, which it may import; the `charm` rule keeps Lip Gloss out of it.
