## 1. Why

## 2. Guarantees

### Where the screen lives

1. **The drawing in `pkg/ui`, the reading and the running outside it.** `pkg/ui/screen` holds the screen's view-model, `screen.DNS` (what manages `/etc/resolv.conf`, the nameservers and search domains in use, hardn.yml's list), which draws origin/main's screen on the sub-menu layout (`SubMenu`), its workflows' review (`Review`) and title bar (`Step`), and the presets (`DNSPresets`). `pkg/screens/dns`, new, reads the host and hardn.yml, fills the view, binds the items, runs each change's form and flow on `output.FlowEngine` with the DNS control, and draws the screen again. **One entry point**, `Run`, which unit (d) calls (§6, §7).
2. **Through `host.System` only.** `pkg/screens/dns` reaches the host only through the `host.System` it is given, the DNS control, `pkg/host/dns` and the engine it is given, and draws only through `pkg/ui` and `pkg/output`: depguard rule `screens-dns-through-host` (the end of the rules, naming this unit) denies `os`, `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` (but `net/netip`) and `plugin` to its non-test files, and `screens-through-host` (after it, from this unit's review fixes) denies the same to every package under `pkg/screens`, so that the next area's glue is guarded from its first file (probed as below: a file of a new `pkg/screens/zz` importing `os` fails lint under it). **`pkg/ui` reads nothing of the host**: rule `ui-renders-only`, new, denies `pkg/host`, `pkg/engine`, `pkg/config`, `pkg/output` and `pkg/screens` to `pkg/ui`'s non-test files, which none imported. Both probed in a scratch copy outside the repository: a file of `pkg/screens/dns` importing `os`, and one of `pkg/ui/screen` importing `pkg/host`, each fail lint under its rule. It never calls `engine.New` (§8, decision 2), so the gallery's `TestPlayTouchesNothing` walks it unchanged but for naming it among the packages it must reach.

### The screen (decisions 2, 3, 4, 8)

Drawing reads only (`TestScreen`: no write, no engine, no run).
4. **The title bar and sections as the adopted mock**, origin/main's words: "DNS Configuration"; "Current DNS Configuration" with three rows; "Configured Nameservers", hardn.yml's list as written there, "Nameserver 1" and on, or with none P-30 (b)'s muted item, "No nameservers configured" (`ValueNone`, DEV-061).
5. **"DNS Implementation"** is what `dns.Read` found manages `/etc/resolv.conf`: "direct (/etc/resolv.conf)" (a file hardn writes), "Proxmox VE (/etc/resolv.conf)", "systemd-resolved"; a manager hardn only reports as its name and "reported only" in `status.warn` (P-37 (a)): "NetworkManager, reported only", "resolvconf, reported only", "another program, reported only" (a link hardn does not know, or a file a running resolved reads as another's), and in a container "container, reported only" (`dns.ErrContainer`); Unknown where it is not established (the family not established, a family hardn does not configure, `/etc/resolv.conf` unreadable or neither a file nor a link).
6. **"Nameservers" and "Search Domains" in use, only where they were read**: a file's lines (a file or Proxmox VE's); on systemd-resolved while it runs, its global list, then each delegate's and each link's own, each with its name as the DNS findings give it, "192.0.2.1 (eth0)", "192.0.2.9 (delegate corp)"; the route-only domains ("~corp.example", "~.") left out of the search domains, as they route queries and search nothing. A file's nameservers are its first three, the ones glibc and musl use (`dns.MaxNameservers`, [dns.md](../safety/dns.md) §3); a fourth line is not shown as in use (`TestReadNoneOrMore`). 7. **The six items and Return**, origin/main's labels and descriptions (decision 1 (i): Add's and Remove's understate the action; the alternatives stay proposed, not built); **item 3 only when hardn.yml lists a nameserver**, so that with none it is neither shown nor taken: the hint is `[0-2, 4-6 or q]`, and 3 is refused as any option the menu does not show; origin/main's prompt, "Enter selection" (P-29 (a)). No status row and no main-menu row: decision 8 is the main menu's (P-01).

### After a change (W1, W2)

11. **The result stays on the screen, and the screen is drawn again under it from a fresh reading** of the host, with hardn.yml's list as the configuration holds it, the saved one once the change saved it (§2.12): after Add on Debian 13 the nameservers in use are the three applied and the list has three; after Configure DNS on Ubuntu 26.04, resolved's global servers then eth0's; after a failure, the host as it was. What the flow does not draw, `output.AfterFlow` (a refused plan's findings; no DNS change has a countdown), is written under the flow first.
12. **The configuration adopts hardn.yml as saved.** Each change plans a copy of the configuration with the list it asks for, which the save writes and records (`config.Save`: `LoadedFrom` the bytes written). Once the change has applied, the screen reads hardn.yml at its path (not through a link) and, when the file holds the bytes the copy saved and not the ones the configuration records, the configuration becomes the copy: its list, its recorded bytes, every other setting as it was in memory (the save wrote the list alone, `dns.Setting`, so a flag's value in memory is never saved). **So the next change's save is not refused `CONFIG_CHANGED`** (control-dns.md §11's open item): two presets in a row both save (`TestPresets`, `play/dns-presets`). A save the engine rolled back, a dry run, a decline and a failure adopt nothing (`TestFailedSave`, `TestNothingWritten`). Mutation-checked: with the adoption removed, `TestAdd`, `TestRemove` and `TestPresets` fail; `TestAdopt` holds each branch (saved; not saved; the file a link or gone; no file read). **hardn.yml edited elsewhere while the screen is open is not shown**: the file is read back only after a change, so the screen keeps listing the configuration's list, and a change that saves the list is refused `CONFIG_CHANGED` before anything is written (`TestRefusedByThePlan`; §11).
13. **Return goes back** to the caller (`Run` returns nil); **q quits** from the screen and from any prompt of a change (`nav.ErrQuit`); the end of the input and Ctrl-C abort (`prompt.ErrAborted`), at the screen and at a form's field (`TestNavigation`). `Options.Ran` is given what each planned change did (`output.Run`), for the audit log (§7).

## 6. API

```go
package dns // pkg/screens/dns (new)

type Options struct {
	Prompter  nav.Prompter                                   // the one line reader, the writer, the render context (its term.Env)
	System    host.System                                    // the host
	Facts     detect.Facts                                   // detect's
	Config    *config.Config                                 // hardn.yml as loaded; adopts the file as saved (§2.12). Required
	NewEngine func(progress func(engine.Event)) *engine.Engine // one per change, progress its Options.Progress. Required
	DryRun    bool
	LogPath   string                                         // a failure's report names it
	Now       func() time.Time                               // AfterFlow's clock; nil is time.Now
	Ran       func(output.Run)                               // what each planned change did, for the audit log
}

// Run shows the DNS screen and runs its items until 0 (nil) or q (nav.ErrQuit);
// prompt.ErrAborted on the end of the input or Ctrl-C; fs.ErrInvalid, writing
// nothing, without System, Config or NewEngine.
func Run(ctx context.Context, o Options) error

package screen // pkg/ui/screen, added: the DNS screen's view-model (the mocks retired)
type DNS struct { Manager DNSManager; InUse, Search []DNSEntry; Read bool; Configured []string }
func (DNS) SubMenu() SubMenu; func (DNS) Review(nameservers []string) flow.Review; func (DNS) Step(label string) WorkflowStep
type DNSManager uint8 // DNSManagerUnknown, DNSFile, DNSProxmox, DNSResolved, DNSNetworkManager, DNSResolvconf, DNSOther, DNSContainer
type DNSEntry struct{ Value, Link string }; func (DNSEntry) String() string
const DNSConfigure, DNSAdd, DNSRemove = "1", "2", "3"
type DNSPreset struct { Key, Label string; Nameservers []string }; func DNSPresets() []DNSPreset

package dns // pkg/engine/controls/dns, added
// HostRefusal is the refusal, with its report, every plan on the host makes
// of any list dns.Validate takes (the manager, an unread fact, resolved
// stopped or overridden, its drop-in path blocked); nil when there is none. Pure.
func HostRefusal(s hostdns.State, readErr error) error
```

No new error sentinel and no new code: every refusal and failure the screen shows is the control's, the engine's or the save's, already in `pkg/output`'s registry; `Run`'s misuse error wraps `fs.ErrInvalid`. **The screen's own refusals take no code**, as the form's inline errors take none: "Please add nameservers first." and "The last nameserver cannot be removed." stop an item before any plan, so no run and no document carries them; in meaning they are `DNS_NO_NAMESERVERS`, which the plan would give (the empty list now, or after the removal). No change to `pkg/engine`, `pkg/host`, `pkg/output`, `pkg/config`, `pkg/ui/flow`, `pkg/ui/nav` or the components.

## 8. Decisions of this unit

None is the maintainer's; each is for review.

1. **`pkg/screens/dns`**, one package per area's screen, beside `pkg/engine/controls/<area>`: not `pkg/ui`, which draws and must not reach the host (§2.2), nor `pkg/output`, the output contract of every area. The glue is not a main package either: unit (d) calls it from `pkg/menu` or `cmd/hardn`, and the gallery plays it.
2. **The engine comes from the caller, built by `NewEngine(progress)`**, one per change, rather than `Run` taking `engine.Options` and calling `engine.New`: the flow's adapter needs the engine built with its `Progress`, and the gallery's guard allows `engine.New` outside the gallery only in `pkg/engine/confirm`, with every engine of play given the gallery's hold; with the constructor the gallery builds it so, and the guard is unchanged. cmd/hardn's constructor is then a few lines over the `engine.Options` unit (d) assembles once (§7), which `cmd/hardn` does not build today.
3. **Every host-level refusal before asking, not only P-37's managers**: a container, a family hardn does not configure, a fact not established, systemd-resolved stopped, a later drop-in setting `DNS=` and a blocked drop-in path refuse every plan of any list `dns.Validate` takes, so asking Add's address first would ask for an answer refused anyway. The control gives them (`HostRefusal`, new, pure, held to the plan's words by `TestHostRefusal`): it plans one address of 192.0.2.0/24, which `dns.Validate` takes on every manager and is never written, so that what `PlanDNS` refuses is the host, not the list (the review fixes; first built with an empty list, which `PlanDNS` refuses before it reaches the resolved checks, so those were left to the plan after Add's question). The screen copies no words but one Fix (decision 13). *Alternative:* the reported-only managers alone, the task's minimum, and the others refused by the plan after Add's question.
4. **The configuration adopts a copy only when the file holds the copy's saved bytes** (§2.12), read back after the apply, rather than on the flow's outcome alone: a save that ran and was rolled back, or any other path that leaves the file as it was, adopts nothing.
5. **Unknown rather than "None" while systemd-resolved is stopped**, and for every manager hardn only reports (§2.6): the nameservers in use are not read there.
6. **The route-only domains are left out** of "Search Domains" (§2.6): they route queries to a link and are no search domain.
7. **Add's check judges the entry first, then the count** (§2.8), and **a list already invalid takes any usable entry**, its fault the plan's report to name. The check calls `dns.Validate` itself, with the host's manager, where the mock copied its rules.
8. **`output.AfterFlow` inside the screen, `Ran` for the caller**: the screen writes what the flow does not draw before drawing itself again; the audit record, which needs the host's facts and hardn's version, is the caller's.
9. **The DNS mocks are retired, not kept as a design record** ([gallery-dns.md](gallery-dns.md) §11): the real screen draws the same eight hosts in play, with every sequence the mocks had a transcript of; kept, their fixture plans and their copy of `dns.Validate` would drift from the real code, held only by five tests of their own. git keeps them (`next/s2-flow-review`, f0111c4), and gallery-dns.md records them. `screen.Mock.Refusals`, which only they used, is kept for the next slices' mocks.
10. **The DNS scenarios of `play engine` stay** ([gallery-engine.md](gallery-engine.md) §8): they run the control with no screen, as the CLI and Run All will, and they are not a DNS screen.
11. **The gallery plays the screen with a note** above it, its simulated host named (`dns/<host>`), also from the main menu's 3, whose mock shows Figma's Debian 12 host while the screen reads web-01's Debian 13.

From the review fixes:

12. **With no hardn.yml read, Add, Remove and the presets are refused before asking** (§2.9), in `steps.PlanSave`'s words, as decision 3's reasoning has it: each saves the list, which there is no file to save to. Configure DNS is left to the plan, which reports a host already as asked unchanged rather than refusing it. *Alternative:* §11's record alone, every item asking first.
13. **A fact not established says what failed** (§2.9), in place of the control's "see the log for what failed": before a plan no log holds it. 14. **No nameserver listed is Unknown, not "None"** (§2.6), on systemd-resolved and on a file alike: the resolver then uses a default nothing read. A file's nameservers in use are its first three.
15. **hardn.yml is not read again to draw** (§2.3, §2.12): `Run`'s doc and §2.11 said it was, and now say what is done.
