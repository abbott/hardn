Figma's main menu has an Auto Updates row ("Not Configured" in `00-TUI-MAIN.png`, with no detail). It is now a check-only control, `updates.auto`, titled "Auto Updates", whose `Check` reads whether the host upgrades its packages by itself: on Debian, Ubuntu and Proxmox VE whether apt's daily job runs `unattended-upgrade`, read as `apt.systemd.daily` decides it from the effective `APT::Periodic` values, with the package and the systemd timers that start the job; on Alpine apk-cron's daily script and crond, through `alpine.ReadUpdates`. `Plan` returns `engine.ErrNotMigrated` until slice 7, which builds both directions (P-43 (1)).

*Since `next/s7-replace`: slice 7 built both directions ([control-updates.md](control-updates.md)), and main menu 6 opens the Auto Updates screen on them.*

## 1. Why

origin/main's row (`checkUnattendedUpgrades`, `pkg/security/status.go:414-437`) is Configured on Debian and Ubuntu when `dpkg -l unattended-upgrades` and `systemctl is-enabled unattended-upgrades` both exit 0. The first holds for a package removed with its files kept, which dpkg still lists (**[I]**, dpkg-query(1)'s exit status); the second asks about `unattended-upgrades.service`, which only lets an upgrade in progress finish at shutdown (`unattended-upgrade-shutdown --wait-for-signal`, §3), not the job that upgrades. Neither reads `APT::Periodic` or apt's timers, so a host with `Unattended-Upgrade "0"`, or with `apt-daily-upgrade.timer` disabled, shows Configured (by code reading, not run). On Alpine the row is whether origin/main's own `apk-upgrade` exists ([alpine.md](../safety/alpine.md) §1). No state is Unknown. A status that says a host is updating itself when it is not is the worst error of this phase (brief Phase 4: prefer Unknown to guessing). The legacy row stays as it is until the main menu goes live (plan, "Phases 3–5 together").

## 2. Guarantees

1. **The line describes the host now** (decision of this unit, as [check-apparmor.md](check-apparmor.md) §5.2 decided "logging only" over "off after restart"): **Configured** is the upgrade job running now and after the next boot, taking packages from at least one origin, with apt's package lists refreshed; **Partial** is upgrades running with a piece missing: the lists not refreshed, or a timer that runs now and does not start at the next boot ("off after restart"); **NotConfigured** is no upgrade running now, whichever piece stops it (no origin allowed among them, §2.4); **Unknown** is "can't read". [checks.md](checks.md) §1.3 reads `Partial` as "some of it": here a piece missing that stops every upgrade (the package there, its timer off) is `NotConfigured`, since the host gets no update (for the maintainer, §6 (a)).
2. **Which tool** is detect's distribution: Alpine reads apk-cron (§2.8); Debian, Ubuntu, Proxmox VE, a distribution hardn does not list whose `ID_LIKE` names Debian or Ubuntu (`DistroOther` with `Like`), and Debian whose Proxmox VE is not established (apt either way) read apt; Rocky Linux and AlmaLinux are `Unknown` with `DETECT_UNRECOGNISED` until dnf-automatic is read ([el-readonly.md](el-readonly.md)); another distribution hardn does not list is `Unknown` with `DETECT_UNRECOGNISED`, and one not established with detect's error. **On a derivative** (`DistroOther` with `Like`) the `NotConfigured` lines stand (nothing runs), but a line that would be `Configured` or `Partial` is `Unknown` with `UPDATES_ORIGINS_UNKNOWN`, "raspbian, like debian", and no error: unattended-upgrade takes a package only from an origin that matches the archive's Release file (§2.4), a derivative's own archives say their own `Origin` (Raspbian's is not Debian's **[I]**), and hardn does not know them for a distribution it does not list, so whether anything is upgraded is not established (decision of this unit, as [check-apparmor.md](check-apparmor.md) §2.3 reads `DistroOther` conservatively; §6 (j)). `Applies` is true on every host but **Proxmox VE, where it is false with the reason "updated by hand"** (slice 7 decision 7 (a), adopted 2026-11-03; [control-updates.md](control-updates.md)): the row is Not Applicable and leaves the risk level, so the uptime's `UPTIME_NO_AUTO_UPDATES` is not raised there. Elsewhere a container upgrades its own packages, and leaving a host whose tool hardn does not read out of the risk level would understate it.
3. **The effective values, never the files** (brief §3 principle 3): one command, `apt-config dump APT::Periodic Unattended-Upgrade::Origins-Pattern Unattended-Upgrade::Allowed-Origins`, which prints the configuration apt itself built from every file, in the order and with the overrides apt applies (§3). Its environment is `host.Real`'s (`PATH` and `LC_ALL=C`, nothing inherited), so `APT_CONFIG` is unset and the files read are the host's own. Names are compared without case, as apt compares them; the dump prints each name as the file that first set it spelt it. Each line must be `name "value";`, apt-config's default format, with a name that is one of the three roots or under one (compared without case); a line in another form (an `APT::Config::Dump::Format` a host file sets, say), a name outside the roots, or an item printed twice, is a form hardn does not know (`DETECT_UNRECOGNISED`), never values read as unset. A dump that prints nothing (none of the subtrees set) is every value unset.
4. **Each value ranked as `apt.systemd.daily` reads it** (§3), and no other way:
   - `APT::Periodic::Enable`: unset is on (the script's default 1); a decimal is ranked, `0` (or `00`, since the script tests `-eq 0`) off, any other on; another form ("yes", "") is not ranked.
   - `APT::Periodic::Unattended-Upgrade` and `APT::Periodic::Update-Package-Lists`, intervals: unset is `0` (the script's default) and `0` never runs; `always`, a decimal (days) and a decimal with one of `s`, `m`, `h`, `d` run (`0d` and `00` at every start of the job, as `check_stamp` reads them: P-43 (3)'s "`"0d"` counts as on"); another form ("1w", "weekly", "") is not ranked.
   - `Unattended-Upgrade::Allowed-Origins` and `Unattended-Upgrade::Origins-Pattern`, the origins: unattended-upgrade builds its list from the values of each root's **direct children**, list items (`Origins-Pattern::`) and named children (`Origins-Pattern::local`) alike, with no default, and takes a package only from an origin one entry matches (only the local `now` origin otherwise); an empty entry matches nothing (§3). So the origins counted are the direct children's values that are not empty (a deeper name, `Origins-Pattern::x::y`, is not one), and **none is `NotConfigured`, "no origins allowed"**: the job runs every day and installs nothing (proposed). On Debian and Ubuntu the entries are counted, not matched against the host's archives (§6, not modelled); on Proxmox VE they are matched against Proxmox VE's repository (§2.9).
   - A value not ranked is `Unknown` with the finding `UPDATES_APT_VALUE_UNKNOWN` naming it (`Unattended-Upgrade "1w"`), no error ([checks.md](checks.md) §1.5's second kind), where the line depends on it.
5. **The package** `unattended-upgrades` is `detect.DpkgInstalled`, the rule detect reads `pve-manager` with: installed, or not (`not-installed`, `config-files`, no such package, no `dpkg-query`); any other status (`half-installed`, `unpacked`, ...) is `DETECT_UNRECOGNISED`, and a `dpkg-query` that fails otherwise its error. The package installed is taken as `unattended-upgrade` on the job's `PATH`, which the script checks with `command -v` (§6, not modelled).
6. **The timers and their services**, on a host systemd booted (detect's `Init`): for `apt-daily-upgrade` (upgrades: `apt.systemd.daily install`) and `apt-daily` (lists: `apt.systemd.daily update`), `systemctl is-active <name>.timer` (running now: `active`; not: `inactive`, `failed`), `systemctl is-enabled <name>.timer` (at the next boot: `enabled`; not: `disabled`, `masked`, `linked`, `not-found`) and `systemctl is-enabled <name>.service` (can be started: any documented state but `masked`, `masked-runtime`, `not-found` and `bad`), through detect's `SystemctlIsActive` and `SystemctlIsEnabled`, which run that verb only. A timer's other states (`activating`, `maintenance`, ...; `enabled-runtime` and the other `-runtime` states, `static`, `indirect`, `generated`, `transient`, `alias`, `bad`, which say nothing of the next boot, as [check-apparmor.md](check-apparmor.md) §2.8 reads them) and a service's `bad` are `Unknown` with `UPDATES_SCHEDULE_UNKNOWN`; a state systemctl(1) does not list is detect's `DETECT_UNRECOGNISED`, and a `systemctl` that cannot run its error; where such a read is left open on a line the other facts decide (§2.7), it is the finding `UPDATES_SCHEDULE_UNKNOWN`, "can't read apt-daily.timer", with the command as its source. **Masking the services** is a common way to stop the upgrades while the timers keep running, so a masked `apt-daily-upgrade.service` is `NotConfigured`, "upgrade job masked", and a masked `apt-daily.service` "lists not refreshed".
   Off systemd, apt's cron job `apt-compat` runs the job instead; it is not read (cron's own state is not a fact detect establishes), so every timer fact is `Unknown` with `UPDATES_SCHEDULE_UNKNOWN`, "no systemd timers"; an init system not established is detect's error.
7. **The order** (§5.2): the facts the upgrade depends on decide `NotConfigured` first (the package, `Enable`, `Unattended-Upgrade`, the origins, the upgrade timer running, its service); then the lists and the next boot decide `Partial`. Every fact is read before the line is decided, and **a state the facts read establish is reported whatever else could not be read** ([checks.md](checks.md) §1.5): the package not installed is `NotConfigured` whether or not `apt-config` or `systemctl` answered. A fact not established decides only when nothing in its tier is established `No`: then the line is `Unknown`, with the errors and the findings of the facts left open, each once. Within the second tier, a `No` decides `Partial` with its own detail even when another fact of the tier is open: the state holds either way, and **the line carries the findings of the tier's facts left open** (a value not ranked, a state not ranked, a timer that could not be read), since its two details mean different things to `next/p4-risk` (§6) and a fact left open may be the other one: `Partial`, "off after restart", with `UPDATES_APT_VALUE_UNKNOWN`, `Update-Package-Lists "1w"`, says the lists' refresh is not established. A `NotConfigured` line carries none: no upgrade runs, whatever the facts left open say.
8. **Alpine** reads `alpine.ReadUpdates`, `next/p2-alpine`'s reader, whose facts are its own (apk-cron installed by `apk info -e`, its daily script an executable regular file, crond's `rc-service` status, its link in the default runlevel). **Configured is `next/p2-alpine`'s rule** (`Updates.Status`: package AND script AND runlevel AND running). The other lines follow §2.1, which **departs from `Updates.Status`** (decision of this unit, §6 (b)): apk-cron not installed is `NotConfigured`, "no apk-cron", as there; its script not run, and crond stopped, crashed or not installed, are `NotConfigured` here (Partial there), since nothing upgrades; crond started and out of the default runlevel is `Partial`, "off after restart", as there. A fact `ReadUpdates` could not establish decides only as in §2.7. The departure is never kinder than `Updates.Status`: `Configured` and `Partial` only where it says so, its `NotConfigured` kept (`TestNoKinderThanAlpine`, over every combination of package, script, crond and runlevel). A host OpenRC did not boot (the Alpine container image), which `ReadUpdates` refuses with `ErrNoOpenRC`, is `Unknown`, as [alpine.md](../safety/alpine.md) §2.1 decided, with the finding `UPDATES_SCHEDULE_UNKNOWN`, "openrc not running", and **no error** (exit 3), as apt's job on a host systemd did not boot (§2.6): nothing failed, and nothing read says whether a crond runs the job; whether apk-cron is installed is not read there, since `ReadUpdates` reads nothing before refusing (decision of this unit, §6 (o)). An init system not established is `ReadUpdates`' error, `ALPINE_UNKNOWN`. Not read, by `next/p2-alpine`'s reader or here: root's crontab (`/etc/crontabs/root`, whose daily line makes crond run `run-parts /etc/periodic/daily`) and the daily script's content (§6, not modelled). apk-cron's `apk -U upgrade` refreshes the index itself, so Alpine has no "lists not refreshed".
9. **Proxmox VE is reported as it is** (P-43 (6) decision 5 is the maintainer's and **open**: NotApplicable with a note, on with a warning, or on with Proxmox's origin added). It reads as Debian. Where upgrades run (`Configured` or `Partial`) and no origin (§2.4) matches Proxmox VE's repository, the line carries `UPDATES_PROXMOX_NOT_UPGRADED`, "Proxmox packages not upgraded": Debian's default origins never match Proxmox's packages, whose Release files say `Origin: Proxmox` (P-43 (6) decision 5, [V] there), so the kernel and Proxmox VE itself are left to `apt full-upgrade` by hand. **An origin matches** when every one of its comma-separated `key=value` tokens matches, as unattended-upgrade matches them (fnmatch, §3), the repository's Release file: `o`/`origin` `Proxmox`, `l`/`label` `Proxmox Debian Repository`, `a`/`suite`/`archive` `stable`, `n`/`codename` the host's codename (os-release's), with `${distro_codename}` replaced by it. An `Allowed-Origins` entry is converted first as unattended-upgrade converts it (`Proxmox:stable` to `o=Proxmox,a=stable`), so `Proxmox:${distro_codename}` does not match (the Suite is `stable`, not `trixie`). A token or form not modelled (`c`, `site`, another variable, an escape, a bracket, a comma in an `Allowed-Origins` entry, a codename not known) is not a match, so the finding stays: it errs towards saying the packages are not upgraded. `origin=Proxmox,codename=bookworm`, left from Proxmox VE 8 on a trixie host, and any text that merely contains `Proxmox` (`origin=NotProxmox`) do not match. Where Proxmox VE is not established, the origins are not compared, and the evidence says so. The state is not changed by the finding. **Decided (slice 7 decision 7 (a)):** `Applies` is false on Proxmox VE, "updated by hand", so the engine never calls `Check` there and the finding is no longer raised through it; the branch and the code stay (a code never goes once released, and `Check` called directly on Proxmox VE still gives it).
10. **`Unknown` is always "can't read", in two kinds** ([checks.md](checks.md) §1.5). A read that fails, or a form neither the command nor apt documents, is the error, which `Engine.Check` reports (exit 1): `COMMAND_NOT_FOUND`, `COMMAND_FAILED`, `DETECT_UNRECOGNISED`, `PERMISSION_DENIED`, detect's codes, `ALPINE_UNKNOWN` and `ReadUpdates`' read errors; several reads that fail are joined, each said once. A documented value the control does not rank, or a host whose state the facts read do not establish, is a finding with no error (exit 3): `UPDATES_APT_VALUE_UNKNOWN`, `UPDATES_SCHEDULE_UNKNOWN`, `UPDATES_ORIGINS_UNKNOWN`. No `Unknown` path returns another state.
11. **Findings**: this package's four codes, exported constants registered in `pkg/output` (appended, `codes.golden` regenerated, a row each in [docs/reference/output.md](../reference/output.md) §2.2), and on Alpine `ReadUpdates`' two, `ALPINE_LEGACY_SCRIPT` and `ALPINE_FOREIGN_SCRIPT`, coded by `steps.FindingCode` and `steps.SourceAt` as a plan codes them, with this unit's short details ("old apk-upgrade script", "other apk-upgrade file") rather than the primitive's, which describe what a plan does (decision of this unit, §6 (h)). They explain a state; none sets one.
12. **Evidence** is each fact as it was read, one line per source: `apt-config dump: APT::Periodic::Unattended-Upgrade "1"`, or `... unset`; `apt-config dump: Allowed-Origins 0, Origins-Pattern 3`; `dpkg-query --show unattended-upgrades: installed` (`not installed`); `systemctl is-active apt-daily-upgrade.timer: active`, `systemctl is-enabled apt-daily-upgrade.timer: enabled`, `systemctl is-enabled apt-daily-upgrade.service: static`, the same for `apt-daily`; `init: openrc, running yes: no systemd timers`; on Proxmox VE `apt-config dump: origins matching Proxmox VE's repository 0`; on Alpine `ReadUpdates`' own lines, or `init: openrc, running no: OpenRC did not boot the host`. A read that failed has no line; its error says what. Tested: `TestEvidence`.
13. **Read-only, through `host.System`.** On a host apt manages the check runs exactly `apt-config dump` with its three roots, `dpkg-query --show --showformat=... unattended-upgrades`, and on systemd six `systemctl` queries (`is-active` once, `is-enabled` twice, per timer); on Alpine `ReadUpdates`' reads (`apk info -e apk-cron`, `rc-service crond status`, and `lstat`, `stat` and `ReadFileNoFollow` of its files). Nothing else, and none of them changes the host (`readOnly` in every test). depguard rule `controls-through-host` ([checks.md](checks.md) §1.11) covers the package; no rule was added.
14. **`Plan` returns `engine.ErrNotMigrated`** (`engine.CheckOnly`), and `Engine.Plan` over `Controls()` is refused, its item's error coded `CONTROL_NOT_MIGRATED`, with no change (`TestCheckOnly`).
