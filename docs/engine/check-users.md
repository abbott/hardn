# User: the user status row (`pkg/engine/controls/users`, `pkg/host/accounts`)

> **Unit:** refactor plan Phase 4, `next/p4-check-users` (plan §2, row `p4-check-<area>`, users; brief Phase 4, "Prefer `Unknown` to guessing"; brief §3 principles 1 and 3; brief 2.5, Proxmox VE's root SSH; decision §3.21, approved: doas alongside sudo on Alpine; [P-13](../refactor/proposals.md#p-13), "User" and the sudo method, proposed; Figma `00-TUI-MAIN.png`, "User Configured non-root, sudo", and `01-USER.png`, "Non-root Configured UID ≥ 1000"). Follows the pattern of [checks.md](checks.md), set by `next/p4-check-ssh`. It reads the elevation rules where [sudoers.md](../safety/sudoers.md) §2.5 reads them, and takes up that page's "not here" for the status (`sudo -l` as an effective check, parsing other files' rules). V-numbers: the elevation half of V14 (Alpine has no sudo: this row reads doas there) and V16 (origin/main's `/etc/sudoers.d/<user>` is read as any drop-in); V17 is not modelled (§6).
> **Status:** built and tested on macOS against the recording fake (`hostfake`) only, with `visudo -c` and `doas -C` answered by a test handler that accepts every file but the one a case rejects, the tools' setuid bit added by the tests (the fake has none), and synthetic stock files per platform (`testdata/README.md`). Review fixes (`next/p4-check-users`, second commit): the stock Alpine `doas.conf`, sudo's `Defaults`, rules for other accounts, the tools' setuid bit, the shells, the evidence. Nothing has run on Linux: everything host-specific is "written, not run (gate 5)" (§4). Every detail below is **proposed wording**, for the maintainer's review (§5).

Figma's main menu has one user row: User "non-root, sudo". It is now a check-only control (`users.admin`) whose `Check` reads the accounts (`/etc/passwd`, `/etc/group`, through a new reader, `pkg/host/accounts`), each candidate's shell, and the rules of the elevation tools detect found (sudo or sudo-rs, doas on Alpine), after the tool's own check of its files. `Plan` returns `engine.ErrNotMigrated` until slice 5.

## 1. Why

origin/main's Users row is `Configured` when `/etc/sudoers.d` holds any entry other than `README` and `root`, or `/etc/group`'s `sudo` or `wheel` line lists members and the list does not contain "root" (`checkUserSecurity`, [interaction.md](../refactor/phase0/interaction.md) §7). So hardn's own `env_keep` file, cloud-init's file for a user since removed, a member with no login shell, or one of a group no rule grants, shows "non-root, sudo"; and on Alpine, whose `wheel` lists root, a doas user in `wheel` shows "root user only". Its Sudo Method row builds a repository while rendering and reads `/etc/sudoers.d/<user>` only. The row matters because it is what a user checks before turning root's SSH login off (`disable_root_menu.go`: "You have created at least one non-root user with sudo privileges"): a row that shows an account to become root from where there is none tells the user that the next step is safe when it locks them out of root (brief §3 principle 1). A status that says a host is safe when it is not is the worst error of this phase: Unknown rather than a guess.

## 2. Guarantees

### The baseline (decision of this unit, for the maintainer)

1. **`Configured` is an account other than root to log in with and become root from:** an account of `/etc/passwd` with uid 1000 or more (Figma's "UID ≥ 1000", origin/main's `GetNonSystemUsers`; no upper bound), the first of its name, with a login shell (§2.3), whom an installed elevation tool, setuid root (§2.4), lets run every command as root (§2.5 to §2.7). Figma's detail names the two facts, "non-root, sudo", and so does this row; **an SSH key is not part of it**: neither the brief's sources for Phase 4 nor Figma's detail ask for one; whether the user can log in over SSH (a key sshd reads, `AllowUsers`, the SSH Auth row's key-only) is the plan's to check before a change that needs it (brief 2.3 step 1, slices 5 and 6), and a key check here would make the row depend on `sshd -T` and `AuthorizedKeysFile` (§6). `Partial` is such an account that no tool lets become root; `NotConfigured` is none (root only).

### Reading

2. **The accounts** (`accounts.Read`): `/etc/passwd` and `/etc/group` through `host.System`, every line in order. A line in neither file's form (not 7 or 4 fields, no name, an id that is not a decimal from 0 to 2³²−2, a group member with a blank in it) is `accounts.ErrMalformed` (`ACCOUNTS_MALFORMED`) with its file and line, never skipped: it may be the account or the group the row is about. Blank lines and lines starting with `#` are skipped, as glibc's files backend skips them **[I]**. A name's first line is the account (`getpwnam`'s **[I]**). `/etc/shadow` is never read. Group membership (`DB.Member`) is the first group of the name's gid being the account's primary group, or any group line with that gid listing the account, as sudo's `%group` and doas's `:group` match through the user's group list **[I]**. Tested: `TestParse`, `TestMalformed`, `TestMember`, `TestRead` (two reads, nothing else).
3. **A login shell** is not `nologin`, `false`, `true` (they exit) or `git-shell` (git's commands only) by its base name, an absolute path, and an executable regular file by `Stat` (a missing shell is not one), which sshd requires of a user's shell **[I]**; an empty shell is `/bin/sh` (passwd(5) **[I]**). Any other program is taken for a shell, and `/etc/shells` is not read: sshd does not consult it **[I]** (§6, an optimistic error). A `Stat` that fails otherwise leaves the account's login `Unknown` with the error. Tested: `TestSudo` ("nologin", "true", "git-shell", "shell not installed").
4. **The tools** come from detect's facts ([detect.md](../safety/detect.md) §2.10), never detected again: sudo (sudo or sudo-rs, one path, as [sudoers.md](../safety/sudoers.md) §2.1 takes them), then doas. Not installed, the tool grants no one. Its presence not established, every grant of it is `Unknown`, with detect's error. **Installed, it must be setuid root:** `Stat` of the path detect found (links followed) must show the setuid bit and owner root, as sudo and sudo-rs refuse to run otherwise (§3); a tool that is not grants no one (evidence `sudo: /usr/bin/sudo not setuid root`), and a `Stat` that fails leaves its grants `Unknown` with the error. A `nosuid` mount and `no_new_privs` are not read (§6). doas is read on Alpine only (`sudoers.Choose`: Alpine's doas reads `/etc/doas.d`); elsewhere, or where the distribution is not established, its grants are `Unknown` with `Choose`'s error (`SUDOERS_DOAS_UNSUPPORTED`).
5. **Where the tool reads its rules** is `sudoers.Read`'s ([sudoers.md](../safety/sudoers.md) §2.5): sudo's main file (`/etc/sudoers`, or sudo-rs's `/etc/sudoers-rs` when it exists), which must include `/etc/sudoers.d` (else `SUDOERS_NOT_INCLUDED`), and the names it reads there (no `.`, no trailing `~`), in C byte order, read at each `@includedir /etc/sudoers.d` line, the main file's later lines after them; doas's `/etc/doas.conf`, then the `*.conf` names of `/etc/doas.d`. A file that cannot be read leaves the tool's grants `Unknown` with the error.
6. **The tool's own check first** (`sudoers.CheckInstalled`, new: the check `sudoers.Apply` makes before it writes, `StageBefore`): `visudo -c`, or each doas file's owner and mode and `doas -C <file>`. A file the tool cannot parse may stop it applying any rule **[I]**, which the lines hardn reads would not show; so a rejection (`SUDOERS_INVALID_BEFORE`) leaves every grant of the tool `Unknown`, "sudo config invalid" or "doas config invalid", not `No`: on sudo-rs `visudo -c` also rejects a tag sudo-rs only ignores ([sudoers.md](../safety/sudoers.md) §3), so a rejection does not establish that the tool refuses. A check that cannot run is `SUDOERS_CHECK_FAILED`, "can't read". Whether sudo's own `visudo -c` checks the included files is **[unverified]** (sudo-rs's does, [sudoers.md](../safety/sudoers.md) §3).
7. **The rules hardn reads, and the last match** (`rules.go`). One form per tool is read: sudo's `<user or %group> ALL=(ALL or root[:ALL]) [NOPASSWD:] ALL` (Debian's and Ubuntu's `root`, `%sudo` and `%admin` lines, origin/main's and hardn's grants, cloud-init's), and doas's `permit|deny [nopass|persist|nolog|keepenv|setenv { … }] <user or :group> [as root]` (Alpine's `20-wheel.conf`, hardn's rules). Blank lines, comments, sudo's other `Defaults` and alias definitions grant no one anything and are passed over. A comment starts at a `#` that starts a word, with no quote or backslash before it on the line (a line with one there is kept whole); sudo's `#include` and `#<digits>` (a user ID) are not comments. **A line whose first character is `#` is a comment whatever follows**, quotes included, as Alpine's stock `doas.conf` has (§3). **Every other rule is kept as one hardn does not read**: a negation, an alias, a command list, another host or target, a continued line (`\` at its end), a doas line with a quote. Its user is read where it is one plain name or one group (sudo: the first word, no comma after it; doas: the word after the options): such a rule is for an account when the name is the account's, and passed over for one whose name it is not, so a rule for another account does not leave the row `Unknown`. It may be for the account, and is then not read for it, when the name is the account's in another case (sudo ignores case by default **[I]**) or another account's of the same uid (doas compares uids, sudo takes the uid's first account's name **[I]**); when, in a rule not read, its group is one `/etc/group` lacks (NSS may have it) or has in another case; and for an alias, a list, `ALL`, a uid, a netgroup or a quoted name, it may be for anyone. The last rule that matches decides, as in sudo and doas (both [V], [sudoers.md](../safety/sudoers.md) §3): the user is granted (`nopass` with it) or, by a doas `deny`, not; no matching rule, not. **A rule not read after the last one that matches, and that may be for the account, leaves its grant `Unknown`**, by that rule; one before it does not (§2.6 checked the files parse). **sudo's settings that change how it asks a password apply wherever they are**: a `Defaults` that sets `rootpw`, `targetpw` or `runaspw` (root's, the target's or the runas user's password: on a host whose root password is locked, no one can give it), turns `authenticate` off (a grant then asks none, unseen by `USERS_NOPASSWD`), or has a parameter hardn does not read, and a file included other than `/etc/sudoers.d` (its `Defaults` are not read), leave a granted account's grant `Unknown`, by that line, unless its scope (`Defaults:bob`) names another account or a group the account is not in. Tested: `TestSudo`, `TestPlatforms`, every form and each place.
8. **Read-only.** The check makes reads and runs exactly `visudo -c` and `doas -C <file>`, which write nothing **[I]** (visudo(8)'s check-only mode, doas(1)'s `-C`; §4). Tested: every call of every test makes a read or runs one of those two (`readOnly`), and `TestCheckInstalled` in `pkg/host/sudoers` (the commands, nothing written through `host.System`).

### States

9. **In this order** (`verdict`):
   - **`Configured`**: an account established to log in (§2.3) that a tool established to grant (§2.7): "non-root, sudo" or "non-root, doas", the first such account's first tool. What else is not established does not matter then ([checks.md](checks.md) §1.5); another tool's failed read is in the evidence;
   - **`NotConfigured`**, "root only": no account with uid 1000 or more whose shell may let it log in (a login shell, or one whose `Stat` failed, §2.3). No tool is read then, and `visudo -c` is not run;
   - **`Unknown`**, when an account that may log in may become root, or when none is established to log in: the first error (a shell's `Stat`, "can't read"; a tool's, with the tool's detail, §5) is the check's error; with none, "can't tell who has sudo" (or doas) with a `USERS_RULE_NOT_READ` finding at each rule or setting not read that decides an account (§2.7);
   - **`Partial`**, "non-root, no sudo" ("no doas", "no sudo or doas": the tools installed and setuid root; when none is, "no doas" on Alpine and "no sudo" elsewhere): an account established to log in, and every account that may log in established to be granted by no tool.
10. **Proxmox VE** (brief 2.5, [pve.md](../safety/pve.md) §1, §2.13): root stays there, its SSH key-only for the cluster and its password for `root@pam` (the web UI, the cluster join), and `pve.CheckAccount` refuses locking it. The row asks the same question there and **does not say that root can be turned off**: `Configured` is an account beside root to log in with. A stock node has no sudo (**[I]**, [detect.md](../safety/detect.md) §3) and no account with uid 1000 or more, so it is "root only"; an account added without sudo is "non-root, no sudo". `NotApplicable` there would leave the row out of the risk level ([checks.md](checks.md) §1.6); for the maintainer (§6).
11. **Findings**, each with its code registered (tested: each test checks that every finding's code is a registered finding code):
    - `USERS_NOPASSWD`, with `Configured`: each account the row counts (uid 1000 or more) established to log in whose deciding grant has `NOPASSWD` or `nopass`, at the rule ("alice: sudo without password"). An account below uid 1000 is not looked at, so a service account's passwordless grant is not reported (§6). Figma's `01-USER` shows "No password" in the error colour and origin/main's Sudo Method row warns on it; whoever wrote the rule (cloud-init's default user, hardn's own `GrantNoPassword` grant). It does not change the state (§6);
    - `USERS_RULE_NOT_READ`, with `Unknown`: §2.9 ("may decide sudo for alice"), at the rule or the `Defaults` (§2.7);
    - `USERS_UID0`, in every state: each account other than root whose first line has uid 0 ("george has uid 0"), at its line: it is root by another name, never a candidate.
12. **Evidence**: with an account that may log in, each tool that grants no one or is not read (`doas: not installed`, `sudo: /usr/bin/sudo not setuid root`, `sudo: not read`); each account that may log in, `passwd: alice, uid 1000, /bin/bash` (`, shell not read` when its `Stat` failed), or `passwd: no account with uid 1000 or more and a login shell`; and, for each tool read, what decided for each account, with the rule as written, white space collapsed: `sudo: alice by /etc/sudoers:22: %sudo ALL=(ALL:ALL) ALL`, `doas: alice denied by /etc/doas.d/zz-site.conf:1: deny alice`, `sudo: no rule for bob`, `doas: alice may be decided by /etc/doas.d/zz.conf:2: permit :wheel cmd apk`. An error that is the check's is in its errors, not repeated here; any other follows its line, short: the tool's check and the last line it printed (`visudo -c: syntax error at line 1`), the file operation (`stat /bin/bash: permission denied`), or the innermost error (`doas: not read: doas drop-ins are established on Alpine only`). No GECOS field, home or password field is shown. Tested: `TestEvidence`.

### Check-only

13. **`Applies` is true everywhere**, Proxmox VE and containers included (§2.10).
14. **`Plan` returns `engine.ErrNotMigrated`** (`engine.CheckOnly`), and `Engine.Plan` over `Controls()` is refused, the item's error coded `CONTROL_NOT_MIGRATED`, with no change and no call but the run directory's (`TestCheckOnly`).
15. **Through `host.System` only:** depguard rule `controls-through-host` ([checks.md](checks.md) §1.11) covers the control; `pkg/host/accounts` has its own block, `accounts-through-host` (the last of the rules), denying `os`, `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` and `plugin` to its non-test files, and `host-stdlib` holds it to the standard library and `pkg/host`.

## 4. Written, not run (gate 5)

Nothing here has run on Linux or as root. On the VMs of [vmtest.md](../safety/vmtest.md) (Debian 13, Ubuntu 26.04, Alpine 3.24) and by hand on Proxmox VE 9, through a dev-only driver or the gallery's status scenario once one calls `Engine.Check` with this control, each compared with `sudo -l -U <user>` (doas: `doas -C /etc/doas.d/<file> <command>` as the user) and `getent passwd`:

- each stock host: Debian 13 from debian-installer with a root password ("non-root, no sudo", or "root only" without the first user) and without one (the first user in `sudo`: "non-root, sudo", **[I]**); Ubuntu 26.04 ("non-root, sudo", sudo-rs; with and without `/etc/sudoers-rs`); Alpine 3.24 after `setup-alpine` ("non-root, doas"); Proxmox VE 9 ("root only");
- a cloud image's default user with cloud-init's file: "non-root, sudo" and `USERS_NOPASSWD`;

- hardn's own grant from `sudoers.Apply`, with and without `NOPASSWD`; `deny alice` in a doas file after `20-wheel.conf`: "non-root, no doas";
- `chsh -s /usr/sbin/nologin alice`: "root only"; a shell removed: "root only";
- Alpine 3.24's stock `/etc/doas.conf` with an account outside `wheel`: "non-root, no doas";
- `Defaults rootpw` in `/etc/sudoers.d/zz-site` with root's password locked: "can't tell who has sudo", and `sudo` asking a password no one can give; `Defaults:bob rootpw`: "non-root, sudo"; a drop-in for another account (`bob ALL=(root) NOPASSWD: /usr/bin/systemctl restart app`): "non-root, sudo";
- `stat -c '%a %U' $(readlink -f /usr/bin/sudo)` on each platform (4755 root; doas on Alpine), and `chmod u-s` on it: "non-root, no sudo", and `sudo` refusing;
- that `visudo -c` and `doas -C <file>` change no file (a tree's checksums before and after);
- the time `visudo -c` adds to a main-menu draw.
