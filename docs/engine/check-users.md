Figma's main menu has one user row: User "non-root, sudo". It is now a check-only control (`users.admin`) whose `Check` reads the accounts (`/etc/passwd`, `/etc/group`, through a new reader, `pkg/host/accounts`), each candidate's shell, and the rules of the elevation tools detect found (sudo or sudo-rs, doas on Alpine), after the tool's own check of its files. `Plan` returns `engine.ErrNotMigrated` until slice 5.

## 1. Why

origin/main's Users row is `Configured` when `/etc/sudoers.d` holds any entry other than `README` and `root`, or `/etc/group`'s `sudo` or `wheel` line lists members and the list does not contain "root" (`checkUserSecurity`, [interaction.md](../refactor/phase0/interaction.md) §7). So hardn's own `env_keep` file, cloud-init's file for a user since removed, a member with no login shell, or one of a group no rule grants, shows "non-root, sudo"; and on Alpine, whose `wheel` lists root, a doas user in `wheel` shows "root user only". Its Sudo Method row builds a repository while rendering and reads `/etc/sudoers.d/<user>` only. The row matters because it is what a user checks before turning root's SSH login off (`disable_root_menu.go`: "You have created at least one non-root user with sudo privileges"): a row that shows an account to become root from where there is none tells the user that the next step is safe when it locks them out of root (brief §3 principle 1). A status that says a host is safe when it is not is the worst error of this phase: Unknown rather than a guess.

## 2. Guarantees

### The baseline (decision of this unit, for the maintainer)

1. **`Configured` is an account other than root to log in with and become root from:** an account of `/etc/passwd` with uid 1000 or more (Figma's "UID ≥ 1000", origin/main's `GetNonSystemUsers`; no upper bound), the first of its name, with a login shell (§2.3), whom an installed elevation tool, setuid root (§2.4), lets run every command as root (§2.5 to §2.7). Figma's detail names the two facts, "non-root, sudo", and so does this row; **an SSH key is not part of it**: neither the brief's sources for Phase 4 nor Figma's detail ask for one; whether the user can log in over SSH (a key sshd reads, `AllowUsers`, the SSH Auth row's key-only) is the plan's to check before a change that needs it (brief 2.3 step 1, slices 5 and 6), and a key check here would make the row depend on `sshd -T` and `AuthorizedKeysFile` (§6). `Partial` is such an account that no tool lets become root; `NotConfigured` is none (root only).

### Reading

2. **The accounts** (`accounts.Read`): `/etc/passwd` and `/etc/group` through `host.System`, every line in order. A line in neither file's form (not 7 or 4 fields, no name, an id that is not a decimal from 0 to 2³²−2, a group member with a blank in it) is `accounts.ErrMalformed` (`ACCOUNTS_MALFORMED`) with its file and line, never skipped: it may be the account or the group the row is about. Blank lines and lines starting with `#` are skipped, as glibc's files backend skips them **[I]**. A name's first line is the account (`getpwnam`'s **[I]**). `/etc/shadow` is read only for the lock sshd checks without PAM, its password fields' first characters alone, and only where an account the row would count exists (§7, `next/p4-locked`). Group membership (`DB.Member`) is the first group of the name's gid being the account's primary group, or any group line with that gid listing the account, as sudo's `%group` and doas's `:group` match through the user's group list **[I]**. Tested: `TestParse`, `TestMalformed`, `TestMember`, `TestRead` (two reads, nothing else).
3. **A login shell** is not `nologin`, `false`, `true` (they exit) or `git-shell` (git's commands only) by its base name, an absolute path, and an executable regular file by `Stat` (a missing shell is not one), which sshd requires of a user's shell **[I]**; an empty shell is `/bin/sh` (passwd(5) **[I]**). Any other program is taken for a shell, and `/etc/shells` is not read: sshd does not consult it **[I]** (§6, an optimistic error). A `Stat` that fails otherwise leaves the account's login `Unknown` with the error. Tested: `TestSudo` ("nologin", "true", "git-shell", "shell not installed").
4. **The tools** come from detect's facts ([detect.md](../safety/detect.md) §2.10), never detected again: sudo (sudo or sudo-rs, one path, as [sudoers.md](../safety/sudoers.md) §2.1 takes them), then doas. Not installed, the tool grants no one. Its presence not established, every grant of it is `Unknown`, with detect's error. **Installed, it must be setuid root:** `Stat` of the path detect found (links followed) must show the setuid bit and owner root, as sudo and sudo-rs refuse to run otherwise (§3); a tool that is not grants no one (evidence `sudo: /usr/bin/sudo not setuid root`), and a `Stat` that fails leaves its grants `Unknown` with the error. A `nosuid` mount and `no_new_privs` are not read (§6). doas is read on Alpine only (`sudoers.Choose`: Alpine's doas reads `/etc/doas.d`); elsewhere, or where the distribution is not established, its grants are `Unknown` with `Choose`'s error (`SUDOERS_DOAS_UNSUPPORTED`).
5. **Where the tool reads its rules** is `sudoers.Read`'s ([sudoers.md](../safety/sudoers.md) §2.5): sudo's main file (`/etc/sudoers`, or sudo-rs's `/etc/sudoers-rs` when it exists), which must include `/etc/sudoers.d` (else `SUDOERS_NOT_INCLUDED`), and the names it reads there (no `.`, no trailing `~`), in C byte order, read at each `@includedir /etc/sudoers.d` line, the main file's later lines after them; doas's `/etc/doas.conf`, then the `*.conf` names of `/etc/doas.d`. A file that cannot be read leaves the tool's grants `Unknown` with the error.
6. **The tool's own check first** (`sudoers.CheckInstalled`, new: the check `sudoers.Apply` makes before it writes, `StageBefore`): `visudo -c`, or each doas file's owner and mode and `doas -C <file>`. A file the tool cannot parse may stop it applying any rule **[I]**, which the lines hardn reads would not show; so a rejection (`SUDOERS_INVALID_BEFORE`) leaves every grant of the tool `Unknown`, "sudo config invalid" or "doas config invalid", not `No`: on sudo-rs `visudo -c` also rejects a tag sudo-rs only ignores ([sudoers.md](../safety/sudoers.md) §3), so a rejection does not establish that the tool refuses. A check that cannot run is `SUDOERS_CHECK_FAILED`, "can't read". Whether sudo's own `visudo -c` checks the included files is **[unverified]** (sudo-rs's does, [sudoers.md](../safety/sudoers.md) §3).
7. **The rules hardn reads, and the last match** (`rules.go`). One form per tool is read: sudo's `<user or %group> ALL=(ALL or root[:ALL]) [NOPASSWD:] ALL` (Debian's and Ubuntu's `root`, `%sudo` and `%admin` lines, origin/main's and hardn's grants, cloud-init's), and doas's `permit|deny [nopass|persist|nolog|keepenv|setenv { … }] <user or :group> [as root]` (Alpine's `20-wheel.conf`, hardn's rules). Blank lines, comments, sudo's other `Defaults` and alias definitions grant no one anything and are passed over. A comment starts at a `#` that starts a word, with no quote or backslash before it on the line (a line with one there is kept whole); sudo's `#include` and `#<digits>` (a user ID) are not comments. **A line whose first character is `#` is a comment whatever follows**, quotes included, as Alpine's stock `doas.conf` has (§3). **Every other rule is kept as one hardn does not read**: a negation, an alias, a command list, another host or target, a continued line (`\` at its end), a doas line with a quote. Its user is read where it is one plain name or one group (sudo: the first word, no comma after it; doas: the word after the options): such a rule is for an account when the name is the account's, and passed over for one whose name it is not, so a rule for another account does not leave the row `Unknown`. It may be for the account, and is then not read for it, when the name is the account's in another case (sudo ignores case by default **[I]**) or another account's of the same uid (doas compares uids, sudo takes the uid's first account's name **[I]**); when, in a rule not read, its group is one `/etc/group` lacks (NSS may have it) or has in another case; and for an alias, a list, `ALL`, a uid, a netgroup or a quoted name, it may be for anyone. The last rule that matches decides, as in sudo and doas (both [V], [sudoers.md](../safety/sudoers.md) §3): the user is granted (`nopass` with it) or, by a doas `deny`, not; no matching rule, not. **A rule not read after the last one that matches, and that may be for the account, leaves its grant `Unknown`**, by that rule. **A rule before it still decides the requests it matches that no later rule for the account matches**, as sudo takes the last match for each request, its runas group included. Host and command are `ALL` in every rule read, so a later rule read covers an earlier one by its runas: sudo's `(ALL:ALL)` matches every request, `(root:ALL)` root with any group, `(ALL)` any user with that user's own groups, `(root)` root with root's (sudoers(5), Runas_Spec); doas's rule with no `as` every target, `as root` root alone. A rule not read may match any request, so only `(ALL:ALL)`, or a doas rule with no `as`, covers it. So after `bob ALL=(ALL:ALL) NOPASSWD: ALL`, `bob ALL=(ALL) ALL` (hardn's own line, [sudoers.md](../safety/sudoers.md)) leaves `sudo -u root -g bob sh` to the first: uid 0 with no password. With the grant `Yes`, each earlier rule not covered that may be for the account is a finding (§2.11): `USERS_RULE_NOT_READ` when it is not read, `USERS_NOPASSWD` when it is read without a password. The state stands on the deciding rule, the last match for `sudo <command>` (root, no `-g`). **sudo's settings that change how it asks a password apply wherever they are**: a `Defaults` that sets `rootpw`, `targetpw` or `runaspw` (root's, the target's or the runas user's password: on a host whose root password is locked, no one can give it), turns `authenticate` off (a grant then asks none, unseen by `USERS_NOPASSWD`), or has a parameter hardn does not read, and a file included other than `/etc/sudoers.d` (its `Defaults` are not read), leave a granted account's grant `Unknown`, by that line, unless its scope (`Defaults:bob`) names another account or a group the account is not in. Tested: `TestSudo`, `TestPlatforms`, every form and each place.
8. **Read-only.** The check makes reads and runs exactly `visudo -c` and `doas -C <file>`, which write nothing **[I]** (visudo(8)'s check-only mode, doas(1)'s `-C`; §4). Tested: every call of every test makes a read or runs one of those two (`readOnly`), and `TestCheckInstalled` in `pkg/host/sudoers` (the commands, nothing written through `host.System`).

### States

9. **In this order** (`verdict`):
   - **`Configured`**: an account established to log in (§2.3) that a tool established to grant (§2.7): "non-root, sudo" or "non-root, doas", the first such account's first tool. The state stands on that grant ([checks.md](checks.md) §1.5): another tool's rules and a rule for another account cannot take it away, a rule before it decides only requests it does not match, and a rule not read after it that may be for its account leaves it `Unknown` (§2.7). **For the accounts the row counts, what else is not established is never silence** (`exposure`): of every account with uid 1000 or more that may log in (§2.3), each grant not established, each grant without a password, and each rule before the deciding one that it does not cover (§2.7) is a finding (§2.11), which the risk level weighs ([risk.md](risk.md) §5.3); a tool not read is in the evidence too. Other accounts, and NSS's, are not looked at (§6);
   - **`NotConfigured`**, "root only": no account with uid 1000 or more whose shell may let it log in (a login shell, or one whose `Stat` failed, §2.3). No tool is read then, and `visudo -c` is not run;
   - **`Unknown`**, when an account that may log in may become root, or when none is established to log in: the first error (a shell's `Stat`, "can't read"; a tool's, with the tool's detail, §5) is the check's error; with none, "can't tell who has sudo" (or doas) with a `USERS_RULE_NOT_READ` finding at each rule or setting not read that decides an account (§2.7);
   - **`Partial`**, "non-root, no sudo" ("no doas", "no sudo or doas": the tools installed and setuid root; when none is, "no doas" on Alpine and "no sudo" elsewhere): an account established to log in, and every account that may log in established to be granted by no tool. Every grant is established then, so `exposure` finds nothing.
10. **Proxmox VE** (brief 2.5, [pve.md](../safety/pve.md) §1, §2.13): root stays there, its SSH key-only for the cluster and its password for `root@pam` (the web UI, the cluster join), and `pve.CheckAccount` refuses locking it. The row asks the same question there and **does not say that root can be turned off**: `Configured` is an account beside root to log in with. A stock node has no sudo (**[I]**, [detect.md](../safety/detect.md) §3) and no account with uid 1000 or more, so it is "root only"; an account added without sudo is "non-root, no sudo". `NotApplicable` there would leave the row out of the risk level ([checks.md](checks.md) §1.6); for the maintainer (§6).
11. **Findings**, each with its code registered (tested: each test checks that every finding's code is a registered finding code):
    - `USERS_NOPASSWD`, with `Configured`: each account the row counts (uid 1000 or more) that may log in (a login shell, or one whose `Stat` failed, §2.3) whose deciding grant has `NOPASSWD` or `nopass`, or who has such a rule before the deciding one that it does not cover (§2.7), at the rule ("alice: sudo without password"; "bob: sudo without password" at `/etc/sudoers.d/10-bob:1`, `bob ALL=(ALL:ALL) NOPASSWD: ALL`, beside hardn's `bob ALL=(ALL) ALL`). The account whose shell was not read is counted too (`next/p4-users-grants`): its grant is established, and the risk level counts what may log in. An account below uid 1000 is not looked at, so a service account's passwordless grant is not reported (§6). Figma's `01-USER` shows "No password" in the error colour and origin/main's Sudo Method row warns on it; whoever wrote the rule (cloud-init's default user, hardn's own `GrantNoPassword` grant). It does not change the state (§6);
    - `USERS_RULE_NOT_READ`, with `Unknown`: §2.9 ("may decide sudo for alice"), at the rule or the `Defaults` (§2.7). **With `Configured`** (`next/p4-users-grants`): for each account that may log in and each tool whose grant for it is not established, "may decide sudo for bob", at the rule or `Defaults` that leaves it open (§2.7: a continued line, an alias, a list, a command rule, `Defaults:bob !authenticate`), or with no source when the tool's rules are not read (detect's or the file's error, the tool's check rejecting a file, doas off Alpine; the evidence says why); and, for each account with a grant, a rule not read before the deciding one that it does not cover (§2.7), the deciding account's own included. The deciding account's other tool counts: it may grant without a password. A rule for an account that cannot log in (§2.3) or below uid 1000 is not looked at (§6). Tested: `TestOtherGrants` (the risk review's four cases, read, a continued line, an alias, a list; a `Defaults`; a command rule; a tool not read: doas off Alpine, its presence not established, its `Stat` failing, its file not read beside a sudo grant, `doas -C` rejecting beside a sudo grant; and the rules before the deciding one, covered or not), `TestPlatforms` (doas's `as root`), `TestSudo` (a rule not read before hardn's grant), `TestEvidence` (`visudo -c` rejecting beside a doas grant), and `TestUsersFromTheCheck` in `pkg/engine/risk`;
    - `USERS_UID0`, in every state: each account other than root whose first line has uid 0 ("george has uid 0"), at its line: it is root by another name, never a candidate.
12. **Evidence**: with an account that may log in, each tool that grants no one or is not read (`doas: not installed`, `sudo: /usr/bin/sudo not setuid root`, `sudo: not read`); each account that may log in, `passwd: alice, uid 1000, /bin/bash` (`, shell not read` when its `Stat` failed), or `passwd: no account with uid 1000 or more and a login shell`; and, for each tool read, what decided for each account, with the rule as written, white space collapsed: `sudo: alice by /etc/sudoers:22: %sudo ALL=(ALL:ALL) ALL`, `doas: alice denied by /etc/doas.d/zz-site.conf:1: deny alice`, `sudo: no rule for bob`, `doas: alice may be decided by /etc/doas.d/zz.conf:2: permit :wheel cmd apk`. An error that is the check's is in its errors, not repeated here; any other follows its line, short: the tool's check and the last line it printed (`visudo -c: syntax error at line 1`), the file operation (`stat /bin/bash: permission denied`), or the innermost error (`doas: not read: doas drop-ins are established on Alpine only`). No GECOS field, home or password field is shown. Tested: `TestEvidence`.
