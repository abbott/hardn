# The plan/apply engine (`pkg/engine`, `pkg/engine/hold`, `host.System.Lock`)

> **Unit:** refactor plan Phase 3, `next/p3-engine` (plan §2, row `p3-engine`; brief Phase 3, its `Control`/`Change` sketch and "Engine: orders changes by dependency, following §2.3"; brief 2.3, the ordering rule; brief 2.4 and the brief §2 decision "Confirm-or-revert"; decision §3.16, approved 2026-10-17: rollback-required backups). It takes up the `p3-engine` items of [docs/safety/README.md](../safety/README.md) "Open items for Phase 3 and later" that are the engine core's; the rest go to `next/p3-steps` (§7). V-numbers: the engine half of V6 (no confirm-or-revert) and V18 (no rollback anywhere), V8's order (the firewall before sshd moves) as a rule every plan follows, and V1's "a dry run applies" for the new path: a dry run is the plan, which changes nothing ([side-effects.md](../refactor/phase0/side-effects.md)).
> **Status:** built and tested on macOS against the recording fake (`hostfake`), with synthetic controls and changes only; the run lock also on real files in `t.TempDir()`, including a holder process killed with `SIGKILL`. Nothing has run on Linux, and no Phase 2 primitive is driven by the engine yet (that is `next/p3-steps`): everything host-specific here is "written, not run (gate 5)" (§4).

A **control** is one setting hardn checks and changes. Its `Check` reports a `Status`; its `Plan` returns the `Change`s that bring the host to what the configuration asks, and none once it is there. `Engine.Plan` asks every control, puts their changes in one stable order (brief 2.3 as stages, then each change's prerequisites, then the order planned), and refuses there everything that would stop an apply later, so the dry run, which is the plan alone, shows every refusal. `Engine.Apply` carries a plan out: one apply per host at a time (a run lock), the plan made again under the lock and compared with the one shown, `revert.Arm` before the first change (the revert timer for a lockout-risk plan), each change backed up and journalled write-ahead before it runs and journalled again after it ran, and on the first failure, Ctrl-C or `SIGTERM` every change started rolled back in reverse from the journal, with `SIGHUP` and `SIGINT` held; `revert.MarkApplied` (or `Done`) last. The engine returns data and renders nothing; it reaches the host only through `host.System`.

## 1. Why

origin/main has no plan: each operation writes as it goes, in the order its code happens to run (the SSH port before the firewall, V8), with no journal, no backup and no rollback (V18), and its `-n` applies (V1). Phase 2 built the primitives that make one change safe (validation in context, the reload that keeps sessions, ufw's allows before its enable, the journal and the timer); `internal/tools/p2drive` composed four changes in the right order by hand ([vmtest.md](../safety/vmtest.md) §2). The slices need that order, the write-ahead journal and the rollback for every change of every area without each one getting them right again. Brief §3 principle 1: never lock the user out; principle 4: plan, then apply.

## 2. Guarantees

### Controls, statuses and changes

1. **A control** (`Control`) has a stable `ID` and a `Title`, `Applies(detect.Facts) (ok, reason)`, `Check(ctx, sys, facts) (Status, error)` and `Plan(ctx, sys, Input) ([]Change, error)`. A control that does not apply is `NotApplicable` with its reason and is neither checked nor planned (`Engine.Check`, `Engine.Plan`; `TestCheck`). The brief's sketch is adjusted to the codebase, as the brief allows: `Applies` takes detect's facts, which `detect.md` §6 asked for, and says why not; `Check` takes the facts too, so a check does not detect the platform again (six commands, [detect.md](../safety/detect.md) §6); `Plan` takes `Input`, the configuration with the facts, the plan's id and its run directory.
2. **A status** (`Status`) is a `State` (`Unknown`, the zero value, `Configured`, `NotConfigured`, `Partial`, `NotApplicable`), a one-line `Detail`, the `Evidence` it was read from and `Findings`, each with a stable `Code` (p3-output's registry); Phase 4 fills in the sources. `State`, `RiskClass` and `Stage` write words, not numbers (`MarshalText`), so nothing persisted depends on the constants' order.
3. **A change** (`Change`) is data with one function: `ID` (unique in the plan), `Control` (set by the engine), a one-line `Summary`, `Diff`, `Risk` (`RiskPlain`, `RiskPackageInstall`, `RiskServiceRestart`, `RiskLockout`), `Stage`, `After` (prerequisites), `Backups` (the files it writes or removes), `Rollback` (its undo, as the journal holds it) and `ConfirmVia` (for a lockout-risk change that adds listeners), and `Apply(ctx, sys, Run) (Ran, error)`. A struct rather than the sketch's interface, so that the plan made again under the lock can be compared with the one shown field by field (§2.9).
4. **The journal is not optional; there is no undo but the journal's.** Before `Apply` runs, the engine backs up `Backups` (`backup.RollbackRequired`, taken whatever `enableBackups` says, §3.16) and journals them with `Rollback` (`revert.Record`): revert's own inverse steps (`OpRun` for ufw's commands, `OpChmod`, `OpChown`, `OpRemoveDir`) or a unit's kept plan (`OpPlan`, made with the unit's step function in `pkg/host/revert/plans`), and the reloads a rollback runs once the files are back. After `Apply` returns, error or not, the engine journals what `Ran.Rollback` says the step that ran needs instead (ufw's `Report.Undo` for its `PreUndo`; the `ssh` reload without `IfUp` once its gated step ran), under `context.WithoutCancel` bounded by `Options.JournalTimeout` (30 s), so it is written after Ctrl-C too ([README](../safety/README.md) "Journal what already ran under a context of its own"). An empty `Ran.Rollback` removes the change's undo: an apply its unit refused before it wrote anything, or a DNS or Alpine apply that undid its own writes, whose plan rollback must not run (revert-plans.md §6, dns.md §6, alpine.md §6). The rollback is `revert.Rollback` over that journal, in this process after a failure and from the timer after hardn died alike, so the two cannot differ: the sketch's `Rollback(ctx, sys)` method is the `Rollback` field, the undo as data. Tested: `TestApplyLockout` (each change, when it starts, finds its own undo and every earlier one's in the journal, last first, and the write its backup), `TestCancelledDuringApply`, `TestPlanStepDropped`.

### The order

5. **Brief 2.3 as stages, then prerequisites, then the plan's order** (`order`, pure). Every change of a stage runs before any change of a later one: `StagePackages`, `StageAccounts` (2.3 step 1: the user and key in place), `StageFirewall` (step 2: the new port allowed, the old kept), `StageFiles` (step 3: the writes, each after its backups), `StageReload` (steps 3 and 4: a reload that makes them take effect), `StageVerify` (the effective values after the reload). Around the stages, by construction: every validation and check at plan time, before anything changes; `revert.Arm` before the first stage; `MarkApplied` (or `Done`) last. Within a stage a change runs after those its `After` names; a tie goes to the change planned first (Kahn's algorithm taking the earliest ready change), so one input always gives one order, which the plan shows (`Plan.Changes`). A prerequisite in an earlier stage is met by the stages; **a prerequisite in a later stage, one no control planned, and a cycle are `ErrOrder` at plan time**, naming the changes; an id planned twice is `ErrChange`. Tested: `TestOrder` (each rule, stability, cycles of two and three), `TestPlanOrder` (across controls, planned out of order; a cycle refused by the plan and by `Apply`, with no call made).

### Planning (the dry run)

6. **Every refusal is the plan's** (`Plan.Refused`, `Plan.Err()` wrapping `ErrRefused`), so the dry run shows it and `Apply` refuses the plan before it takes the lock: a control's own refusal (in its `Item` too); a change the engine could not order, back up or journal (an id, a summary of more than one line, a stage or risk out of range, no `Apply`, a backup path that is not absolute and clean or is given twice, a prerequisite given twice or naming itself, `ConfirmVia` without lockout risk, an undo `revert.Record` would refuse, checked under the plan's id as `Journal.Check` checks it, and a plan step whose unit has no registered rollback, `revert.ErrNoPlanRollback`: `Record` checks only that, revert-plans.md §2.7b); a control id that is not one, given twice, or a title of more than one line; the order (§2.5); and, for a plan with changes, what `Arm` would refuse later: **the platform's support level** (only `detect.Supported` and `BestEffort` pass; anything else is `ErrUnsupported`: dns.md §6 leaves this gate to the engine), **a change journalled already** (`*revert.PendingError`, with its words on how to go on), and for a lockout-risk plan **the timer's preconditions** (`revert.TimerFor`: a running systemd or OpenRC, a window of at least `MinTimeout` in whole seconds, hardn's path clean; `revert.CheckExecutable`) and **a session established** (`revert.ReadSession`'s, else `ErrSessionUnknown`). The plan changes nothing on the host but its run directory, `/run/hardn/<id>`, root's alone (checked from `/` down, `revert.ErrUnsafe` otherwise), which it removes before `Plan` returns. Tested: `TestRefusedBeforeArm`, one row per refusal: refused by `Plan` and by `Apply`, with no command run and nothing changed outside `/run/hardn` (no journal, no timer, no backup) and the run directory gone.
7. **Idempotency.** A plan with no changes applies nothing at all: no lock, no journal, no command (`Result.Nothing`). The rest is the controls': `Plan` is a function of the host and its input, and plans nothing once the host is as asked. Tested with a control that reads the fake (`TestIdempotent`): planned, applied, planned again on the result, empty; the `Apply` of that plan made no call.

### Applying

8. **One apply per host at a time** (the run lock; [README](../safety/README.md): `Arm`'s one-at-a-time check reads, then writes, so two applies at once would both pass it). `Apply` takes `host.System.Lock` (new, §5) on `/run/hardn/engine.lock` after checking that `/run/hardn` is root's alone, and writes a holder line (`pid 5000, change <id>, since <time>`, the pid from `Options.PID`). A second apply is `host.ErrLocked`, naming the holder, before it plans or arms anything. **Stale locks:** the lock is `flock(2)`'s, which belongs to the open file and is released when its last descriptor closes, so the kernel releases it when its holder exits, however it exits (a crash, `SIGKILL`): a lock file a dead process left is not held, and nothing times a lock out or cleans one up. The descriptor is close-on-exec, so no command hardn starts keeps the lock after hardn exits (flock locks survive `execve(2)`, so without it the revert timer's sleeper would). A holder that is alive but stuck keeps the lock; the refusal names its pid. The file is emptied, never removed (a process that opened it before a removal would lock a file nobody else sees). The lock is released after the rollback and the run directory's removal. Tested: `TestRunLock` (a second apply while the first runs, refused with the holder named, then let through once it has finished; a lock file with a dead holder's line taken, the new line written during the apply and emptied after), `TestLockContract` (Real and the fake: one holder, a file a dead holder left, a file replaced since, a symlink, a directory, a missing parent, a done context), `TestLockReleasedWhenHolderDies` (Real: a helper process holding the lock killed with `SIGKILL`; its file left, not held), and `assertReleased` in every apply test.
9. **What was shown is what runs.** Under the lock, `Apply` plans again with the same id, on facts detected again; the plan must have no refusals (a change journalled since, a control refusing now) and be the one given, change by change and field by field (`Apply` aside) with the same risk, else `ErrPlanChanged`, before `Arm`. Tested: `TestRefusedUnderTheLock` (each, with nothing changed outside `/run/hardn` and the controls planned twice).
10. **Armed first, by risk** (brief 2.4; [revert.md](../safety/revert.md) §7). A plan with any `RiskLockout` change is journalled `revert.RiskLockout` with the confirm window (`Options.Timeout`, `revert.ResolveTimeout`'s, 180 s by default), the applying session and `ConfirmVia`, every lockout change's listeners once each; `Arm` starts the timer before the first change. Any other plan is journalled `revert.RiskOther`, with no timer (revert's rule), and ended by `revert.Done` once applied. Tested: `TestApplyLockout` (`systemd-run` first, then the firewall, the reload, `list-timers`; the journal applied, waiting, `confirmVia` 2230), `TestIdempotent` (no command at all for a plain change, the journal gone after `Done`).
11. **Each change in the plan's order:** `ctx` checked; its files backed up into the plan's backup run (`<backupPath>/<id>/`, the journal's, backup's and timer's one id); its undo journalled with every backup taken so far (`Journal.Backup`) and every started change's undo, the last change's first and each change's steps in its own order (`Journal.Undo`, `Journal.Reload`); `Apply`, given the run's id, directory, facts and this change's backups; a panic in it is a failed step (the rollback runs while the session is open rather than waiting for the timer); then the journal of what ran (§2.4).
12. **The first failure rolls everything started back, in reverse, from the journal.** A failed backup, journal write, `Apply`, after-step journal write, `MarkApplied` or `Done`, and `ctx` done between two changes or inside one (Ctrl-C, `SIGTERM`: the caller cancels it), run `revert.Rollback` with `ReasonFailed` (restores, inverse steps, reloads, and the timer stopped: revert.md §2.14), which runs without the apply's cancellation; around it `SIGHUP` and `SIGINT` are ignored and `SIGTERM` caught (`Options.Hold`, by default `hold.Signals`), which the commands the rollback runs inherit ([revert.md](../safety/revert.md) §2.17, [vmtest.md](../safety/vmtest.md) §2.7). `Apply` then returns `Result.Failed`, an `*ApplyError` (the change, the step, the error, revert's `RollbackResult`), which is `ErrRolledBack` when the rollback finished. A rollback another process has under way or has finished (the timer's, the user's `hardn rollback`) is left to it: revert reports `Nothing`, and the `ApplyError` is then `revert.ErrRollingBack`, not `ErrRolledBack`, since this process undid nothing (`TestRolledBackElsewhere`: the journal gone during a change, the next change not run). Tested: `TestFailureRollsBack`, a row per stage (the firewall's command refused, a backup refused, the write failing with `host.ErrNotDurable` once written, the reload refused, the effective-value check failing, a panic in it, `MarkApplied` unable to list `/proc`) and Ctrl-C after the firewall: for each, the journal the rollback started from held exactly the started changes' undo, the commands after the failure end with the undo in reverse and `systemctl stop hardn-revert-<id>.timer`, the file is as it was, the journal is gone, signals were held once and released, the lock released after the last command.
13. **A rollback that does not finish is reported, and stops the timer all the same** (`TestIncompleteRollback`): the `ApplyError` wraps `revert.ErrIncomplete`, whose text names `sudo hardn rollback <id>`, `rollback.json` stays for it, and the next run's notice says so (revert.md §2.20). **Decision of this unit**, on the README's question whether `Rollback` should leave the timer when it returns `ErrIncomplete`: it keeps stopping it. A timer left armed would run a resumed rollback whose reason is still `failed`, which stops `hardn-revert-<id>.timer` from inside `hardn-revert-<id>.service`; whether stopping a timer stops the service it started is **[unverified]** (revert.md §3), and a rollback that stops itself half-way is worse than one the notice and the error send the user to. `pkg/host/revert` is unchanged.
14. **Ctrl-C and `SIGTERM`.** The engine sees them as `ctx` done: the caller makes `ctx` with `signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)` and keeps it registered until `Apply` returns, so a second Ctrl-C before the hold is delivered to it, not to Go's default handler. The hold's release puts the default handlers back for `SIGHUP` and `SIGINT` (`hold.Signals`), so after a rollback a Ctrl-C ends the program. **Decision of this unit**, on [system.md](../safety/system.md) §7's question (process groups, or wait before rolling back): wait. A step runs to its return before anything else, and `host.Real.Run` returns once the command it killed has exited and its output pipes are closed or `pipeWaitDelay` (10 s) has passed; hardn's children stay in its process group, where the terminal's Ctrl-C reaches them too. A grandchild that let go of the pipes and runs on (ufw's iptables helpers, **[I]**) is not waited for; process groups would change the seam and job control and are left until a VM shows the need (§4).
15. **The result is data** (`Result`): the change's id, its risk, the changes applied (`Applied`: id and a detail line), and for a lockout-risk plan `Confirm`: the id, the listeners a confirming connection must reach, and the deadline. **The deadline is the timer's own trigger time where it can be read**: on systemd `systemctl list-timers --all --output=json --no-pager hardn-revert-<id>.timer`, whose `next` is microseconds since the epoch (§3), taken when it is no earlier than the change's creation and no later than a minute past the journal's deadline. Otherwise (the command fails, an older systemctl prints a table, another timer's row, a time far off, and always on OpenRC, whose sleeper's start is not read) it is the journal's deadline, `Approximate`: the journal's creation is truncated to the second and the timer starts after it, so the timer fires up to a few seconds later (1 to 2 s on Ubuntu 26.04, [vmtest.md](../safety/vmtest.md) §4.9), the safe side for a countdown. A confirmation in that gap is still accepted: the claim decides (vmtest.md §4.9). How to word it (`sudo hardn confirm`, doas on Alpine) is the renderer's. Tested: `TestConfirmDeadline` (read, and each approximate case).

### Diffs

16. `FileDiff(path, before, after *string)` is `pkg/diff`'s unified diff under the file's path, with `/dev/null` for the side that does not exist and the two headers alone for a file created or removed empty; `CommandDiff(what, before, after)` is the same diff of what reading the state shows before and after a command, under `<what> (before)` and `<what> (after)`; both `""` when nothing changes. Tested: `TestDiff`, and the file change's diff in `TestIdempotent`.

### Through `host.System`

17. Depguard rule `engine-through-host` (the last of the rules) denies `os`, `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` (but `net/netip`), `plugin` and `pkg/ui` to `pkg/engine`'s non-test files: the engine reads, writes and runs only through `host.System`, and renders nothing. `pkg/engine/hold`, the one package that touches the process's signal disposition, is outside the rule. hardn's pid, its path, the session's environment and the signal context come from the caller.

## 4. Written, not run (gate 5)

Nothing here has run on Linux or as root, and no real change has gone through the engine: `next/p3-steps` gives it the Phase 2 primitives and the 2230 scenario. On the VMs of [vmtest.md](../safety/vmtest.md), once `p3-steps` (or a later driver revision) puts the engine behind a command:

- **the run lock** on `/run/hardn/engine.lock` as root: two applies at once, the second refused naming the first; the first killed with `SIGKILL` mid-apply and a new apply let through (the timer, armed, rolls the first back); the lock not kept by the `systemd-run` timer or the OpenRC sleeper after hardn exits;
- **the deadline**: `systemctl list-timers --all --output=json --no-pager hardn-revert-<id>.timer` on Debian 13, Ubuntu 26.04, Debian 12 and Ubuntu 24.04, its `next` against `systemctl show -p NextElapseUSecMonotonic` and against when the timer fires; on a systemctl without JSON, the approximate deadline;
- **Ctrl-C and a hangup during an apply**: a Ctrl-C while `ufw` or `systemctl reload` runs, rolled back with the after-step journal written; a second Ctrl-C during the rollback held off; the commands' children (ufw's iptables helpers) after the cancelled step **[I]** (§2.14);
- **the support gate** on each image (Ubuntu 26.04 and Debian 13 Supported; an interim Ubuntu refused);
- the brief's 2230 scenario through the engine (`p3-steps`), every refusal shown by the dry run before the timer.

## 5. Changes to the seam (`pkg/host`, `hostfake`)

- **`host.System` gains `Lock(ctx, name, holder) (unlock, error)`**, and `host.ErrLocked`. The seam had no exclusive operation: `WriteFileAtomic` and `Rename` replace, `MkdirAll` succeeds on what exists. A lock built from them (a directory renamed into place, its holder's pid checked for liveness) needs a stale-lock takeover that two contenders can both win (both read the same dead holder; one replaces the lock, the other then removes the new one), whereas a kernel lock cannot outlive its holder. `Real.Lock` (`pkg/host/lock.go`) opens the file in its guarded parent (`openParent`), refuses a symlink, a directory or anything that is not a regular file before and after opening it (lstat first, so a FIFO is never opened; `O_NOFOLLOW|O_NONBLOCK`), creates it `0600`, close-on-exec, and takes `flock(LOCK_EX|LOCK_NB)`; the holder line replaces the content once the lock is held; `unlock` empties the file and closes it, once. The fake (`hostfake/lock.go`) keeps its locks by file, as the kernel keeps them by open file: a file replaced since is not locked, a seeded one (a dead holder's) is not held; it records `lock` and `unlock`. `TestLockContract` runs every case against both.
- [system.md](../safety/system.md)'s API list predates this method; that page is `next/p2-system`'s.
- No dependency changes: `go.mod` and `go.sum` are unchanged (`flock` is `golang.org/x/sys/unix`'s, already required).
