The DNS control is the first control that both checks and plans. `Check` gives the status model its DNS row: whether the host uses `hardn.yml`'s nameservers. `Plan` gives the engine the change that makes it so, with the host's search domains kept, and, when the list it applies is not the one `hardn.yml` holds, the save of `hardn.yml` after it. Every refusal comes before any change, with a report. A failure is undone, with no confirm-or-revert timer (brief 2.4), and reported as undone.

## 1. Why

origin/main's DNS screen applies on selection, with no confirmation and no backup; its Add, Remove and presets change `./hardn.yml` alone, whole, without a word on its comments; an empty list is applied; `lan` is forced; `resolved.conf` is overwritten and the symlink written through (gallery-dns.md §6 and §7, V18, V19). Unit (a) drew the replacement and the maintainer adopted it. Phase 2 built the primitive (`pkg/host/dns`, [dns.md](../safety/dns.md)) and Phase 3 its change kind (`steps.DNS`), which unit (a) found to drop the plan's findings, show a created file as edited, and report a failure that `dns.Apply` had undone as never undone (§8). This unit puts DNS on the engine, fixes those, and gives every later slice the save of `hardn.yml` as a change kind of its own.

## 2. Guarantees

### The row (`Check`)

1. **One control, `dns.nameservers`, titled "DNS"** (`Nameservers`; `Controls(cfg)`). **It carries `hardn.yml` as loaded** (`Nameservers.Config`), since the engine's `Check` takes no configuration (engine.md §2.1): `Check` compares the host with that list. No engine API changes for it (§10, decision 1).
2. **`Applies` is true on every host.** A container, a family hardn does not configure and the managers hardn only reports are Not Applicable through `Check` (decision 8) and refused by `Plan` with a report (P-37 (a)), because a control that does not apply plans nothing, and an empty plan reads "Nothing needs changing." on a host whose nameservers are not `hardn.yml`'s (§10, decision 3). **A departure from [checks.md](checks.md) §1.6** ("NotApplicable only through `Applies`"), as [check-apparmor.md](check-apparmor.md) §2.2 departs from it: which manager owns `/etc/resolv.conf` is a reading, not one of detect's facts.
3. **What is read:** `dns.Read` (reads only, dns.md §2.2), its manager and what it holds: for a file (`file`, `proxmox`), its `nameserver` lines in order; for systemd-resolved, its global servers (`resolvectl dns`'s `Global:`), and each link's servers and search domains, the latter since this unit (D4, §8).
4. **The line**, decided in this order (§5 lists every one):
   - a container (`dns.ErrContainer`): Not Applicable, "container";
   - a family other than Debian, Ubuntu, Alpine and Proxmox VE (`dns.ErrUnsupported`, from detect's established `Distro` `other`): Not Applicable, "not supported" (a review finding of this unit: it read Unknown, "can't read", though nothing failed to be read);
   - a manager hardn only reports (`resolvconf`, `networkmanager`, `foreign`): Not Applicable, naming it;
   - anything `dns.Read` could not establish (`ErrUnknown`, the manager, or any fact in `State.Err`): Unknown, "can't read", with the error, whose code is the read's own (`DNS_UNKNOWN`, `COMMAND_FAILED`, `PERMISSION_DENIED`, ...); never a pass;
   - `hardn.yml` lists none: Not Configured, "none in hardn.yml";
   - `hardn.yml`'s list is one `dns.Validate` refuses for the manager (an entry that is no address, a duplicate, four for a file, resolved's own stub): Not Configured, "not valid in hardn.yml";
   - `/etc/resolv.conf` is resolved's link and resolved does not run: Not Configured, "resolved not running";
   - **the nameservers in use are `hardn.yml`'s, in order, as `dns.Validate` writes them** (`2001:DB8:0::54` is `2001:db8::54`): Configured, the list ("192.0.2.54, 2001:db8::54");
   - otherwise Not Configured, "not hardn.yml's".
5. **In order** (§10, decision 4): resolvers query the servers in the order listed (resolv.conf(5) **[unverified]**, not re-read for this unit), and `dns.PlanDNS` changes the host when only the order differs, so Configured is "the plan's DNS change is empty or refused", save where the row reads Configured and "Configure DNS" still plans or refuses a change: a file whose nameserver lines are scattered (the plan gathers them); a resolved whose global servers come from a file other than hardn's drop-in (the plan writes the drop-in); Alpine with udhcpc's question answered y (the plan stops udhcpc, alone: "Stop udhcpc rewriting resolv.conf"); and, refused, a resolved whose servers are the list while hardn's drop-in path is masked (`DNS_DROPIN_BLOCKED`) or a later drop-in sets the same `DNS=` (`DNS_OVERRIDDEN`), each failing safe. Per-link servers do not change the line: they are a finding (decision 8: "the file's nameservers, or resolved's global ones").
6. **Findings explain the line; none sets it**: the host's (`dns.State.Findings`), coded and worded by `steps.DNSFinding` (§7): `DNS_PER_LINK`, `DNS_DHCP_CLIENT`, `DNS_UDHCPC`, `DNS_PROXMOX_NODE`, each in `pkg/output`'s registry already.
7. **Evidence**, one line per source: `/etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf` (a link), `/etc/resolv.conf: absent`, or a reported manager's first line, quoted; for a file `/etc/resolv.conf: nameservers 192.0.2.1` and `/etc/resolv.conf: search example.net`; for resolved `systemctl is-active systemd-resolved.service: active` (or `not active`), `resolvectl dns: Global: ...`, each link with servers (`resolvectl dns: link 2 (eth0): 192.0.2.1`), `resolvectl domain: Global: ...` and each link with domains (`resolvectl domain: link 2 (eth0): example.net`); and `hardn.yml`'s list (`/etc/hardn/hardn.yml: nameservers 192.0.2.54, 2001:db8::54`).
   Tested: `TestCheck` (every line on every host, an error exactly for Unknown, the findings' codes registered, nothing written), `TestEvidence`, `TestCheckGolden`.

### The plan (`Plan`)

8. **The change that brings the host to `in.Config`'s list**: `dns.Read`, then `dns.PlanDNS` with `Nameservers` `in.Config`'s, `ReplaceSearch` false (the host's search domains kept: decision 2, no `lan`, no configuration key) and `UDHCPCNoResolv` the control's `StopUDHCPC` (decision 6: the answer to "Stop udhcpc rewriting /etc/resolv.conf?", asked on Alpine only, with no configuration key; y adds `RESOLV_CONF="no"` to `udhcpc.conf` in the same change and the `dns-udhcpc` finding goes; refused off Alpine), then `steps.DNS` (`dns.nameservers/set`; `StageFiles`, plain: brief 2.4). None when the host uses the list already: a configured host plans nothing, and a plan applied then planned again is empty (idempotency: `TestApply`, every platform). Titled and summarised by the steps the change holds, so it never says it sets what it does not: "Set the nameservers", "Set the nameservers to 192.0.2.54, 2001:db8::54", when it writes the file or resolved's drop-in or reloads; "Set nameservers; stop udhcpc rewriting", with ", and stop udhcpc rewriting /etc/resolv.conf", when it stops udhcpc too; "Stop udhcpc rewriting resolv.conf", "Stop udhcpc rewriting /etc/resolv.conf", when it stops udhcpc alone, the file already listing the nameservers (a review finding of this unit: that change was titled as setting them). `Plan` reads `in.Config`, the engine's; the caller gives `Engine.Plan` the same `hardn.yml`, or a copy with the list edited (Add nameserver, a preset). The engine plans again under the run lock with the same control values and configuration, so the answer and the list shown are the ones applied.
9. **The save of `hardn.yml`** (decision 1, §3.19; the change kind is `steps.PlanSave`, [steps.md](steps.md) §2.24): when `in.Config`'s list is not the one the file at `in.Config.Path()` holds, read now and compared as written, the plan adds `dns.nameservers/save` after the change (`After`; the save alone when the host uses the list already), which `config.Save`s `in.Config` to that path, atomically (`host.WriteFileAtomicKeep`); *since `next/s2-config-edit`'s review fixes* its list alone (`dns.Setting`, `nameservers`), every other setting as the file has it, whatever `in.Config` holds in memory (a flag's value): the path it was loaded from, never a fixed `./hardn.yml` as origin/main saved (a `./hardn.yml` that `FindConfigFile` found, and so loaded, is saved there, as §3.19 asks). **Its diff is the file against what `config.Save` writes**: *amended by `next/s2-config-edit`:* `config.Edit`'s bytes, the list's lines alone edited in place, every other line and comment of the file kept (a five-line `hardn.yml` keeps its five lines, two of them changed for a preset), where it was `config.Marshal`'s whole configuration, about fifty keys, defaults included (§10, decision 10). With no file loaded (`in.Config.Path()` empty), a host already as asked plans nothing, and a change is refused (`CONFIG_NOT_LOADED`), since it could not be saved (§10, decision 11). The engine backs the file up and journals it before the save, so the rollback restores the previous bytes; **a save that fails after the change applied rolls the change back too** (decision 1 (iii): the engine rolls back every change started), so the host and `hardn.yml` agree; **n at the confirmation changes and saves nothing** (the plan wrote nothing: `TestDeclined`). It has no finding: the comments-lost warning ("Saving hardn.yml loses its comments", `CONFIG_COMMENTS_LOST`) was dropped by the maintainer's amendment (`next/s2-config-edit`). Refused before anything changes, each with a report: a configuration loaded from no file, with a change (`CONFIG_NOT_LOADED`); a file whose bytes are not the ones it was read from, gone, or no longer decoding (`CONFIG_CHANGED`: the save compares the list with the file as it was read, so saving would undo an edit made since; §10, decision 6; read for every plan, "Configure DNS" included, to compare the lists; its decoding error is `config.ErrInvalidFile`, `CONFIG_FILE_INVALID`, new); an edit `config.Edit` refuses (`CONFIG_NOT_EDITABLE`, `CONFIG_EDIT_UNSAFE`, since `next/s2-config-edit`: [config-edit.md](config-edit.md) §5); and a `hardn.yml` that is a symlink, which `config.Save` would refuse (`SYMLINK_REFUSED`; it is read through the link, as `LoadConfig` reads it, to compare the lists, so "Configure DNS" goes on). Another read failure (a permission denied) is the read's own error and code, without a report. "Configure DNS", whose list is `hardn.yml`'s, never rewrites `hardn.yml`.
10. **Every refusal before any change, with a report** (`steps.Refusal`: its `Why` and `Fix`, which `pkg/output` shows as the error and "To go on: …"; §6 lists each): `pkg/host/dns`'s `ErrContainer`, `ErrUnsupported`, `ErrManaged` (for each reported manager, what manages DNS and how to change it by hand: P-37 (a)), `ErrNotRunning`, `ErrOverridden` (naming the drop-in), `ErrDropInBlocked`, `ErrNoNameservers` ("No nameservers configured", "add nameservers first"), `ErrNotApplicable`, `Validate`'s `ErrInvalid` (naming the entry and why) and `ErrUnknown`; then the save's. Each keeps its registered code (the `Refusal` wraps the primitive's error, which the registry matches; the control's own `Code` field is that code, pinned by the tests). The plan is the dry run: `Engine.Plan` refuses, nothing is written but the plan's run directory. Tested: `TestRefusals` (each, its code, its words, nothing written), `TestRefusalGoldens`.
11. **The words of the plan** are the adopted mock's (§7): the steps' titles, the findings in a few words (D1), a created file shown created (D2), and a failure that the change undid, or left to the journal's rollback, which finished, reported undone, in a few words, with its next step (D3; §8).

### Through `host.System`

12. **Reads and plans only through `host.System`**, `pkg/host/dns`, `pkg/config` and `pkg/engine/steps`, and renders nothing. depguard rule `dns-control-through-host` (the last of the rules, naming this unit) denies `os`, `io/ioutil`, `golang.org/x/sys`, `syscall`, `net` (but `net/netip`), `plugin`, `pkg/ui` and `pkg/output` to the package's non-test files, as `controls-through-host` already does for every control. Probed in a scratch copy outside the repository: a file importing `os` and `pkg/output` fails lint, under `controls-through-host`, and under `dns-control-through-host` once that rule's glob is narrowed to leave the directory out. The gallery's `TestPlayTouchesNothing` allows `pkg/config`'s `Read`, `Save` and `Edit` (`HasComments` until `next/s2-config-edit` removed it), which `steps.PlanSave` names: they reach the host only through the `host.System` they are given, or not at all.

## 6. The refusals

Each is a `steps.Refusal`; `pkg/output` shows the Why with the code, then "To go on: " and the Fix. All **proposed**, each describing the host, not hardn; "No nameservers configured" and "add nameservers first" are origin/main's "No nameservers configured. | Code | When | Why | Fix |
|---|---|---|---|
| `DNS_MANAGED` | NetworkManager | NetworkManager manages DNS here | set the nameservers with nmcli |
| `DNS_MANAGED` | resolvconf | resolvconf manages DNS here | set the nameservers through resolvconf |
| `DNS_MANAGED` | a link hardn does not know | /etc/resolv.conf links to `<target>`, which another program writes | set the nameservers with that program |
| `DNS_MANAGED` | a plain file beside a running resolved (a copy of its stub file among them) | systemd-resolved runs, and /etc/resolv.conf is not its link | link /etc/resolv.conf to /run/systemd/resolve/stub-resolv.conf (not "or stop systemd-resolved": a copy listing 127.0.0.53 alone would then answer nothing; §3) |
| `DNS_CONTAINER` | a container | This is a container: its manager provides /etc/resolv.conf | set the nameservers in the container's settings on its host |
| `DNS_UNSUPPORTED` | not of the four families (the engine refuses the platform too, `PLATFORM_UNSUPPORTED`) | This host is not Debian, Ubuntu, Alpine or Proxmox VE | set the nameservers by hand |
| `DNS_UNKNOWN` | a fact not established | The host's DNS settings could not all be read | see the log for what failed, then try again |
| `DNS_RESOLVED_NOT_RUNNING` | resolved's link, resolved stopped | systemd-resolved is not running | start it with systemctl start systemd-resolved, then try again |
| `DNS_OVERRIDDEN` | a drop-in after hardn's sets `DNS=` | `<path>` sets DNS= after zz-hardn.conf; for several, `<path>, <path>` set DNS= after zz-hardn.conf | remove DNS= from it (them), then try again |
| `DNS_DROPIN_BLOCKED` | a mask or a directory at hardn's drop-in | /etc/systemd/resolved.conf.d/zz-hardn.conf is not a file | remove it, then try again |
| `DNS_NO_NAMESERVERS` | `hardn.yml` lists none | No nameservers configured | add nameservers first |
| `DNS_INVALID` | an entry `dns.Validate` refuses | Nameserver `<entry>` is not an IP address / is listed twice / is not a usable address; or /etc/resolv.conf takes 3 nameservers at most | correct the nameservers in `<hardn.yml's path>` |
| `DNS_OPTION_NOT_APPLICABLE` | udhcpc's question answered y off Alpine | This host is not Alpine | leave udhcpc as it is |
| `CONFIG_NOT_LOADED` | a change, with no `hardn.yml` read | No hardn.yml was read, so there is none to save to | create /etc/hardn/hardn.yml, then try again |
| `CONFIG_CHANGED` | `hardn.yml` changed since it was read: other bytes, gone, or no longer decoding | `<path>` changed since it was read | start again, so that the file is read as it is now |
| `SYMLINK_REFUSED` | the save, `hardn.yml` a symlink | `<path>` is a link | edit the file it links to by hand |
| `CONFIG_NOT_EDITABLE` | the save, `hardn.yml` in a form not edited in place (`next/s2-config-edit`) | `<path>` holds more than one YAML document; `nameservers in <path>` uses a YAML anchor or alias; and the others of [config-edit.md](config-edit.md) §5 | set nameservers in `<path>` by hand, then try again |
| `CONFIG_EDIT_UNSAFE` | the save, the edit not reading back as the configuration (`next/s2-config-edit`) | `<path>` cannot be edited safely (`nameservers in <path>` when the list is what would not read back; another setting is never named) | set nameservers in `<path>` by hand, then try again |

`CONFIG_CHANGED` is new (`steps.ErrConfigChanged`), and so is `CONFIG_FILE_INVALID` (`config.ErrInvalidFile`, the decoding error `CONFIG_CHANGED` wraps here), both added to the registry; the others were registered by `next/p3-output` and Phase 2. Their words were first "changed since hardn read it", "run hardn again, …" and "… after hardn's drop-in": a review finding of this unit, as the words describe the host, never hardn.

## 10. Decisions of this unit

1. **How `Check` gets `hardn.yml`'s list:** the control's value carries it (`Nameservers.Config`), built with `Controls(cfg)` from the configuration the caller loaded. *Alternatives:* `Control.Check` taking `Input` (every control changes); an optional interface with a configuration and a new `Engine.Check` parameter (an engine API change for one control). The value is zero engine change, and the status model builds its rows from the loaded configuration anyway.
2. **How Alpine's answer reaches `Plan`: a field of the control (`StopUDHCPC`), not an `Input` field** (the task proposed "the smallest Input addition"). The engine builds `Input` from `Engine.Plan`'s own parameters and `Options`, so any `Input` field needs a new `Engine.Plan` parameter or an engine-wide option for one control's per-plan answer; the control value already travels with the plan to the plan made again under the run lock (`Plan.controls`), so the answer the user gave is the one applied, with no engine change. Say if an `Input` field is wanted instead.
3. **`Applies` always true** (§2.2): Not Applicable through `Check`, refused through `Plan`, for a container, a family hardn does not configure and the managers hardn only reports.
4. **In order** (§2.5).
5. **Unknown for any fact not established**, even with the nameservers read: `dns.State.Err` does not say which fact failed, and `PlanDNS` refuses the same state.
6. **A `hardn.yml` changed since it was read is refused, not saved over** (`CONFIG_CHANGED`, `config.Config.LoadedFrom`): the save writes the whole configuration, so saving over another edit would undo it while the plan said "Save the configuration". The loader records the bytes it read (`LoadConfig` and `config.Read`), and `Save` the bytes it wrote. A configuration created by `CreateDefaultConfig` records the file as written. *Since `next/s2-config-edit`* the save edits the list alone, in place, but compares it with the file as it was read, so an edit of the list made since would still be undone, and one of another setting would be saved over a plan that did not read it: the refusal stands, and `config.Save` makes it too (`config.ErrChanged`, the same code).
7. **An invalid list is Not Configured, "not valid in hardn.yml"**, not Unknown: the host is established not to use a list that cannot be used, and `Plan` refuses it with the entry named.
8. **The save only when the list differs from the file's, compared as written**: "Configure DNS" never rewrites `hardn.yml`; a host already as asked with another list in `hardn.yml` gets the save alone.
9. **The words of a step's failure** are a type of `pkg/engine/steps` (`Failure`), which any change kind can return, and `pkg/output` shows alone, without the change's summary or the code, which the step's line gives (the mock's `failure-proposed`); the JSON document's `message` keeps the whole error. Only DNS's reload without effect and the save are worded; other DNS failures keep `dns`'s error.
10. **The save shows its diff**: the file against what `config.Save` writes, every key, canonical, defaults included (a review finding: "Save the configuration" alone hid that a short `hardn.yml` is rewritten whole). *Alternative:* no diff, and a finding that the file is rewritten with every setting. The diff says exactly what is written, as every other change kind's does; the maintainer may prefer the finding, or the screen may fold the diff (unit (c)). *Amended by `next/s2-config-edit`:* the save edits the list alone, in place, so the diff is the list's few lines; the question of folding a fifty-key diff is gone.
11. **With no `hardn.yml` loaded**, a host already as asked plans nothing (as `Check` reads it Configured), and a change is refused (`CONFIG_NOT_LOADED`): applied without a save, the host and the configuration would disagree, which decision 1 (iii) rules out. Only a caller building a `Config` reaches it: the loader gives a configuration with no file an empty list, which `DNS_NO_NAMESERVERS` refuses first. *Unchanged by `next/s2-config-edit`*, which leaves the refusals of a save before the edit as they were, and saves the list alone (`dns.Setting`), so a configuration given with flags' values in it (`-u`, `-n`) saves none of them.
12. **A family hardn does not configure is Not Applicable, "not supported"**, in `Check`, not Unknown: detect establishes the family, and nothing failed to be read. `Applies` stays true, so `Plan` refuses it with its report (`DNS_UNSUPPORTED`) rather than planning nothing.
