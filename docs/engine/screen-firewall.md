## What it does

Main menu 4 as adopted on 2026-11-01 ([gallery-firewall.md](gallery-firewall.md) §5, all ten decisions, §6's words), drawn from `firewall.Read` and the Firewall row (`Incoming.Check` through `output.StatusViewOf`, no engine), writing nothing, under plan only too. The row is Check's own reading, a second `ufw status`, kept on purpose so that it is the main menu's row to the letter.

- **ufw's screen:** sections ufw, SSH, Rules, Application Profiles. Item 1 by `Reading.First`: Install, Enable in the words of what its plan does (`Reading.Does`), Disable. A refused item 1 keeps its words and says the control's refusal when selected, before asking. Item 2 where ufw is installed; item 3, Disable, where `DisableBeside`.
- **The profiles' screen:** Add, and with a profile Remove and Apply. Add's fields are checked at the field by `ufw.ValidProfile`; a name held in any case is a warning. Remove's Select refuses a number no profile has. Apply's refusal is said by planning `ActionApplyProfiles` first. Add and Remove with no hardn.yml read say `screenkit.NotLoaded`'s words before asking. After a save, `Config` adopts it (`screenkit.Adopt`).
- *Since 2026-11-07 (the maintainer: "A and B2"):* **a profile may name an interface**, Add's fifth question, optional ("Interface", "Such as tailscale0. Empty for every interface."; refused where `ufw.ValidInterface` refuses it); its row and review read "<ports> on <interface>", and Apply runs `ufw allow in on <interface> from any to any app <name>`. "Applied" is the profile's own rule (`ufw.AppApplied`: allow, in, from anywhere, its interface), where it was the name alone. **Item 3, Trusted Interfaces**, where ufw is installed, Disable moved to 4: its screen ("Manage UFW Trusted Interfaces") is Add ("Interface", "Such as tailscale0."; "This interface is trusted already." a warning), Remove ("Remove which interface?") and Apply (`ufw allow in on <interface>`, plain, ufw running), as the profiles' screen is; its rows "<interface> Every port", "Applied" or "Not applied"; the main screen's section "Trusted Interfaces" where hardn.yml has one. Tested: `TestAdd`, `TestTrust`, `TestApplyProfileInterface`, `TestApplyInterfaces`, `TestPlanInterfaces`.
- **Proxmox VE:** "Firewall Configuration", read only, Return alone. No ufw call, and no item offered, so hardn.yml plays no part. Decision 7's row, from `PVEUFWEnabled`.
- **Rocky Linux, AlmaLinux and RHEL:** the firewalld screen, with no profiles or interfaces items ([el-firewalld.md](el-firewalld.md) §1.6).
- **Each change** runs through `screenkit.Session.Change`: the review, y/N, or the hostname typed for a lockout-risk plan (`p.Typed()`), the apply, the screen read again. A lockout-risk item 1, live, whose hostname can't be read, says so before asking; a plan that turns lockout-risk by the key says so in place of the question. The question's words are the draw's; only the confirmation follows the plan made at the key. Plan only stops every item at its plan, Add and Remove too, and needs no hostname.
- *Since 2026-11-10 (the maintainer: "A: Warning, before asking"; [el-rhel.md](el-rhel.md) §8):* **a control's refusal is a warning before asking, on item 1 and Disable.** The reading plans item 1 where it can (Install ufw, Enable, Install iproute2, also behind Enable firewall where `ss` is missing: `TestEnableSS`). What it doesn't plan (Disable; Install firewalld and Install iproute on Rocky Linux, AlmaLinux and RHEL) is planned on the engine when chosen (`screenkit.Session.Preplan`), as Auto Updates' item is, and its refusal said in `screenkit.RefusalWords`, with no review or question. Those were refused at the flow's plan, after the review, as an Operation Failed report. The engine plans again for the change, so dnf simulates firewalld's install twice. *Since 2026-11-11 (the maintainer: "A line before the check"):* "Checking the host…", muted, is said before that plan, which may wait on dnf's network. *Not yet:* the engine's own refusals (a change waiting for hardn confirm, the change journal) of an item the reading planned with its control alone (Install ufw, Enable and Install iproute2 on ufw; Enable on Rocky Linux, AlmaLinux and RHEL) still come at the flow's plan, after the review, as an Operation Failed report; `Preplan` says them for the rest. Tested: `TestELRefusedBeforeAsking`, `TestRefusalGolden` (`refusal/no-repos.golden`), `TestEnableSS`.
- *Since 2026-11-11 (the maintainer's decision: in a detected container, the ufw and firewalld sections end with one muted line, that the host may filter traffic too, out of hardn's sight, plus a JSON evidence line; the row's state, detail, the score and the main menu do not change):* **in a container** (`Container.Detected` Yes, `Reading.Container`), ufw's section, and firewalld's on Rocky Linux, AlmaLinux and RHEL, end with that line, muted, after their rows; the JSON's evidence ends with `container: <signal>` ([check-firewall.md](check-firewall.md) §2.16). Not on Proxmox VE, and not where the container is not established. The line adds one line to the screen, counted from the title to the prompt as `TestHeights` counts: with no ufw (`alpine-lxc`) 22, and firewalld stopped (`rocky-lxc`) 21, both within 80x24; with ufw active (`alpine-lxc-active`) 32, over 24 as every host with ufw active already is (decision 9). Tested: `TestContainerLine`, `TestContainerHeights`, `TestContainerGoldens` (`screen/alpine-lxc`, `screen/alpine-lxc-active`, `screen/rocky-lxc`); the gallery's `firewall/alpine-lxc`.
- **0** returns (nil), **q** quits (`nav.ErrQuit`), the end of the input and Ctrl-C abort (`prompt.ErrAborted`), from every screen, question and the form.

## Decisions made here

- On Proxmox VE no item is offered, so hardn.yml plays no part; `firewall.Read` gets it as on any host.
- Proxmox VE not established: ufw's title, the row ("can't tell if Proxmox"), and item 1 "Enable firewall", refused in the control's words. No section.
- pve-firewall not read (a done context, `/etc/pve` not mounted): each row Unknown under the row's own words. ufw's state not read: Installed Unknown, item 1 refused.
- Decision 7's row goes last in pve-firewall, above the muted line. Nothing is drawn where ufw.conf says No.
- Only item 1 is checked for the hostname before asking, its plan read with the screen. Apply's plan is plain (`steps.PlanUFWApps`), so it is not. A plan that turns lockout-risk by the key says the same in place of the question, as Environment's does (`TestHostnameAtTheQuestion`).
- Add checks each field with the others filled with what ufw takes. So a name may hold spaces and `+`, which the gallery refused, and "all" or a number is refused. Ports split on commas, each one entry; ufw's file joins them with `|`.
- `NotLoaded` gets the control's save id, `firewall.ID+"/profiles"`, which the control does not export. Its words don't depend on it. Apply saves no hardn.yml, so it is not refused there.
- The profiles' screen reads the host again each round, the Firewall row too, which it does not draw.
