# The gallery on the real engine (`internal/tools/uigallery`: `play engine`)

> **Unit:** refactor plan Phase 3, `next/p3-gallery-engine` (plan §2, row `p3-gallery-engine`: "Gallery playable mode drives the real engine against the recording fake `System`, so each slice's gallery review shows real plans"; brief 1D, the playable mode: "Once the Phase 3 engine exists, it uses the real engine against a fake `System`"; brief Phase 5, "gallery first"; refactor plan §2 "Phases 3–5 together", unit (a) of each slice, "real plans via p3-gallery-engine"). It shows the decisions of the units below it, each in a scenario of its own: [P-39](../refactor/proposals.md#p-39) (a), [P-40](../refactor/proposals.md#p-40) and [P-41](../refactor/proposals.md#p-41), decided by the maintainer on 2026-10-19 and built by `next/p3-steps` and `next/p3-confirm-cleanup`. No V-number and no behaviour of hardn changes: the unit is dev-only, in a binary no build target makes ([design-system README](../design-system/README.md) §9.14, "Never released").
> **Status:** built and tested on macOS, in process: each scenario played through the gallery's own entry point with scripted answers (`uitest.Typist`), its transcript pinned as a golden on the core set, the simulated host it leaves checked, and the race detector run on the package. No real terminal and no host were used; nothing here runs on Linux, and nothing needs to: the gallery runs no command (§4).

[engine.md](engine.md), [steps.md](steps.md), [output.md](output.md) and [confirm-cleanup.md](confirm-cleanup.md) built the engine, its change kinds, the flow adapter and `hardn confirm`'s clean-up, each tested on the recording fake. The gallery's playable mode still ran its workflows on fixture plans written by hand (`flow.Fixture`). Now `uigallery play engine` runs the real engine on a simulated host, through the same canonical flow, so the maintainer sees the plans, steps, confirm countdown and outcome hardn would show, and how they look in every render environment.

## 1. Why

Brief 1D asks for a playable mode that runs "the real screens and prompts against a simulated system", on fixture plans in Phase 1 and on "the real engine against a fake `System`" once the engine exists. The refactor plan makes each slice's first unit its gallery review, with "real plans via p3-gallery-engine". A fixture plan is a guess at what the engine plans: the boot unit's change, the firewall before the file, `ssh.socket`'s three commands, the check after the reload, the D9 refusal's report and the clean-up's steps were not in any fixture, and a review on fixtures would sign off on screens the engine never draws.

The platform facts are given, as the engine's own tests give them (`engine.Options.Detect`), for the host the scenario builds.
2. **Through the flow and the adapter, as hardn will run them.** Each scenario is `pkg/ui/flow`'s canonical flow on `output.FlowEngine` (output.md §2.11), the engine built with the adapter's `Progress`, then `output.AfterFlow` on the flow's writer: the plan (`PlanView`), the confirmation, the steps (`StepProgress`, from the engine's events alone), "Operation Successful" or the `ErrorReport` with each code, what was rolled back and the failing command's output, then the confirm countdown, when the change is rolled back unless confirmed, how to undo it now, and the plan's findings. A plan of lockout risk is confirmed by typing the host's name, a y/N question otherwise (`flow.Plan.Typed`); `n` and `0` decline at a y/N, `0` at a typed confirmation, `q` quits and the end of the input aborts (130), as everywhere in play. Above the flow the scenario's note, an info `Callout`, says what the host is and what to type; it is set apart as a workflow screen is (`screen.WorkflowStep.Run`'s gaps). Tested: `TestPlayEngine` (each scenario's screen, in order), `TestPlayEngineEnds`.
3. **`hardn confirm`, as `cmd/hardn` runs it** (P-40; `confirmAndCleanUp`, [confirm-cleanup.md](confirm-cleanup.md) §2.9). After the 2230 change of `confirm-cleanup-debian13` is applied, a new SSH connection to 2230 (another machine's, its `sshd-session` started after the apply) runs `confirm.Claim`, then `confirm.Cleanup` through the engine on the same host; the clean-up's run is `output.Human`'s, and `Held.Report` is `pkg/ui` messages, as `showCleanup` renders them. **One departure:** the claim's line, "Change <id> confirmed (<summary>): it will not be rolled back.", which `hardn confirm` prints through the legacy logger, is an OK `Message`, the gallery having no legacy logger (and `pkg/logging` writing `/var/log/hardn.log`). Tested: `TestPlayEngine` (the claim, the clean-up's four steps, the report; the host left with 2230 alone in `00-hardn.conf`, in what sshd binds and in ufw, and the change in `confirmed.json`).
4. **Real plans, so real refusals.** The D9 scenario's refusal is the planner's (`steps.Refusal`): the flow's `ErrorReport` shows its `Why` with its code and its `Fix` as "To go on: …", and nothing changes on the host, not even the journal (`TestPlayEngine`: no command but reads, nothing written, made, removed or renamed outside the plan's run directory, `/run/hardn`). The failed reload is the engine's rollback from its journal: the steps done reported rolled back, last first, the boot unit kept (engine-boot.md §2.1), and the host as it was (no `00-hardn.conf`, ufw's 2230 rule deleted, sshd on 22, no journal left).
5. **What the fake recorded closes play** (`recorder`), as the fixture simulator's record does: for each apply, under the scenario's name, a `PlanView` whose entries are what each step of the engine ran on the simulated host and the files it changed, in order, split by the engine's progress events ("Applied: <change>", "Failed: <change>"), with what the engine did between them ("Armed the revert timer" for the calls that start the timer, systemd-run or OpenRC's sleeper; "Rolled back from the journal" after a failure; for `hardn confirm`, "Confirmed: the revert timer stopped" before the clean-up's first change). Reads (`sshd -T`, `sshd -t`, `ss`, `ufw status`, `systemctl`'s queries, `visudo`'s and the boot unit's checks) and hardn's own state (`/var/lib/hardn`, `/run/hardn`, `/var/backups/hardn`) are left out, and the record says so. A scenario that applied nothing (declined, refused, a dry run) records nothing; with nothing applied at all, play says "Nothing was applied.", as before. Tested: `TestPlayEngine` (the host's changes in brief 2.3's order: the timer armed, then the firewall, the file, the reload; the rollback's undo after the failure), `TestPlayEngineEnds`, `TestRecorderSteps` (the split on synthetic events: the timer armed with no boot unit's change before it, a failed command under its change, the rollback; reads and the journal left out).
6. **The menu** is the sub-menu layout (`screen.SubMenu`) filled with the scenarios: the title bar "Engine scenarios", an item per scenario, `0` to return, Figma's prompt. Each item plays its scenario on a fresh host and comes back to the menu, which is drawn again; nothing carries from one scenario to the next. The main menu does not link it, so every existing play golden is unchanged (§2.9).

### Nothing on this machine (`fakehost.go`, `TestPlayTouchesNothing`)

7. **The simulated host** is hostfake's recording `host.System`, its commands answered by a model of the host (`fakeHost.run`), ported from `internal/tools/p2drive`'s fake VM (`fake_test.go`, which a main package's test file cannot share): `sshd -T` by a model of sshd's reading of its files (first value wins, `Port` and the others accumulate, a `ListenAddress` with a port as it is), `ss -Htln`, `systemctl` (`is-active`, `is-enabled`, `reload ssh.service`, `daemon-reload`, `show -p Listen ssh.socket`, `restart ssh.socket`, the timer's stop, the boot unit's enable, `list-timers`), `rc-service sshd reload`, `rc-update add`, ufw 0.36.2 (status, `allow`, `delete allow`, `--force enable`), `visudo`, `systemd-run` and OpenRC's sleeper. Each changes the model as the host would (a reload binds what the files configure; `daemon-reload` reruns the generator's model, `listen.conf` included; `restart ssh.socket` binds it). A command the model does not answer fails, as hostfake's unscripted commands do, and is kept (`unanswered`), which every scenario's test fails on. Its values are synthetic: `web-01.example.net` (`web-01`) at 192.0.2.20, alice from 192.0.2.10, port 2230.
8. **The gallery links what changes a host, and never reaches it** (`TestPlayTouchesNothing`, rewritten). The engine links `host.Real`, the engine's signal hold (`pkg/engine/hold`), and `pkg/config` and `pkg/logging`, which write files. The test still parses the gallery and every package of the module it links, and refuses `os/exec`, a `net` package but `net/netip`, an `os` function that writes, removes, renames, starts a process or changes the environment, and any `syscall` or `x/sys/unix` name but the line reader's, an errno value and `Stat_t`. Those four packages' files that do (twelve, named in the test with why) are exempt, and the test checks instead that nothing can reach them: no file makes a `host.Real` or names `NewReal` but `NewReal` itself; no file names a function of `pkg/config` or `pkg/logging` (`pkg/config`, unreached itself, aside); `hold.Signals` and `SignalsAs` are named only by the engine's default hold; and every `engine.Options` and `confirm.Options` the gallery writes sets its own `Hold`. So every `host.System` the engine and `confirm` get is the gallery's fake. Checked by mutation in a scratch copy of the tree: an `engine.Options` without `Hold`, a `host.NewReal` call, a `host.Real` literal, an `os.WriteFile`, a `pkg/logging` call, a `hold.Signals` call and a `pkg/config` function each fail the test. **The gallery's hold holds nothing** (`session.hold`): `hold.Signals` would ignore `SIGINT` and `SIGHUP` in the gallery's own process around a rollback that has nothing real to protect, and the line reader's Ctrl-C would stop working while it ran; it counts, and `TestPlayEngine` checks that the failed reload's rollback took it once.

### Goldens

9. **One golden per scenario, and one of the menu**, on `uitest.Core()` (truecolor dark Unicode at 80 columns, plain at 80, truecolor dark Unicode at 60): `internal/tools/uigallery/testdata/golden/play/engine/<scenario>.golden` and `menu.golden` (the menu, the D9 scenario chosen from it, and back), written with `go test -run TestPlayEngineGolden ./internal/tools/uigallery -update` (`make golden-update` writes the same). Each is a play transcript, as `play/*.golden` are: the answers echoed after their prompts. **The change id** is the engine's (`revert.NewID`: the clock's second and a random suffix, `crypto/rand`), so the goldens write its suffix `xxxxxxxx` (`sameIDs`), which keeps every line's width; a message may wrap after the id's hyphen, and the test fails for an id cut anywhere else, which would leave part of it random. The clock is fixed (`galleryNow`, 2026-10-20 12:00:00 UTC), so the deadline and countdown are the same on every run. **The existing goldens are unchanged**: no scenario replaces a mock (§7), and `TestPlayGolden`'s five transcripts, the screen goldens and the component goldens pass as they were. Also tested: `TestPlayEngineSmoke` (the confirm-and-clean-up scenario in every profile, both themes and glyph sets, at 60 and 80 columns: no line wider than the terminal but a header and a prompt's echoed answer), `TestPlayEngineUsage` (a scenario that is not one; `-fail` or `-sequence` with a scenario: exit 2 before stdin is read), and the race detector on the package.

### Decisions of this unit

10. None is the maintainer's; each is the gallery's, and none changes hardn:
    - **The scenarios are a catalogue of the gallery's, beside the mocks**, not mocks of `pkg/ui/screen`: `screen.Mocks()` is the screen goldens' catalogue and `pkg/ui` renders only, so it cannot plan through the engine; and every workflow mock is a Figma frame (root login, a sudo method, a new user) whose control no slice has built.
    - **No title bar above a scenario's flow.** A workflow screen (`screen.WorkflowStep`) names the screen of a slice, which the slices design (slice 6 for SSH, 4 the firewall, 5 users); a note says what the scenario is until then.
    - **The confirmation's words are placeholders**: each question ("Change the SSH port to 2230?") is the gallery's, until the slices word their actions; the typed phrase is the host's short name, `web-01`, as `hostname(1)` prints it, under nav's example label "Type the hostname", as the mocks ask `bos-san-l01` (P-10 decides the words; P-24 and P-27 the steps' and the flow's). The FQDN would not fit after its prompt at 60 columns once echoed.
    - **The deadline on systemd is the timer's own**: the model's `list-timers` gives the timer's trigger a second after the window, as the Ubuntu 26.04 run found it firing 1 to 2 s after the deadline hardn prints ([vmtest.md](../safety/vmtest.md) §4.9), so the countdown reads 3:01 and "at 12:03:01 UTC"; OpenRC's sleeper is not read, so Alpine's says "at about 12:03:00 UTC" (engine.md §2.15).
    - **`-sequence` and `-fail` are refused with a scenario**: they are the fixture plans'; the failure path is the engine's own, in `failed-reload-debian13`.

## 4. Written, not run (gate 5)

Nothing here runs on a host, and nothing needs to: the gallery runs no command and changes no file (§2.8). What the screens show is what the engine does on the model (§2.7), which is a model: where a host would answer otherwise, the real screens would differ. The model's sequences ran on Debian 13 and Ubuntu 26.04 through p2drive (§3); Alpine's OpenRC, the D9 refusal, the failed reload's rollback, the clean-up after a confirmation and Ubuntu 22.04 are the model's alone, and their host runs are the units' own, written, not run: [steps.md](steps.md) §4, [confirm-cleanup.md](confirm-cleanup.md) §4, [engine-boot.md](engine-boot.md) §4. **By hand, not done here:** `go run ./internal/tools/uigallery play engine` on a terminal (Ctrl-C at a prompt, a terminal resized, the sizing as §9.14 of the design-system README checked it for the mocks), and `-override` with a scenario (§5).

## 5. Changes to other units' code, limits

- **`internal/tools/uigallery`** (`next/p1d-gallery-*`'s): `engine.go`, `fakehost.go` and `engine_test.go` new; `play.go` starts at an engine scenario (`engineStart`, `startPlay`, the session's `play` taking its title, note and first screen), its record closes with the engine's applies, and the fixture simulator's comment says where the mocks go; `play_test.go`'s `TestPlayTouchesNothing` as §2.8 says; `main.go`'s package doc and usage. No other package changes: **no `pkg/ui` and no engine API change**, `go.mod` and `go.sum` unchanged, no depguard block (no new package: the gallery's `gallery` and `dev-tools` rules apply as they were).
- **Limits:**
  - `-override`'s colours do not reach what `pkg/output` renders (the confirm countdown, the findings, `hardn confirm`'s clean-up): it builds its render context from the environment, not from the gallery's theme. Passing a context would change `pkg/output`'s API, which no scenario needs to show.
  - P-41's warning shows below the dry run's footer, after the plan, not above the confirmation: the flow's limit (confirm-cleanup.md §2.12), shown as it is.
  - The engine's scenarios are play's alone: `-screens` draws the mocks' sequences, whose goldens are `pkg/ui/screen`'s.
  - The gallery's context is never cancelled: Ctrl-C at a prompt aborts play, and an apply on the model takes no time, so no apply is interrupted.
  - Every lockout-risk plan on a host without the boot unit shows the unit's change in full (23 lines of diff): the real plan.

## 6. API

The gallery is a main package; its interface is the command line:

```text
go run ./internal/tools/uigallery play [flags] engine              # the scenarios' menu
go run ./internal/tools/uigallery play [flags] engine/<scenario>   # one scenario
  scenarios: ssh-port-debian13, ssh-port-ubuntu2604, ssh-port-alpine324, keyonly-debian13,
             ufw-enable-debian13, sudoers-grant-debian13, refused-d9-ubuntu2604,
             failed-reload-debian13, confirm-cleanup-debian13, best-effort-ubuntu2204
  flags: -theme, -profile, -ascii, -width, -height, -override (as for the mocks); -sequence and -fail refused
```

```go
package main // internal/tools/uigallery, added
type scenario struct { name, label, about string; note []string; host func() *fakeHost; facts detect.Facts
	controls []engine.Control; question string; dryRun, confirm bool; answers []string; ends flow.Outcome }
func scenarios() []scenario; func findScenario(name string) (scenario, bool); func scenarioMenu() screen.SubMenu
func (*session) openEngine(name string) func() error; func (*session) runScenario(scenario) error
type fakeHost struct { f *hostfake.System; allowed []uint16; inactive, noUFW, socket bool; bound, configured []string; failReloads int /* … */ }
func newHost() *fakeHost; func socketHost() *fakeHost; func openRCHost() *fakeHost; func (*fakeHost) unanswered() []string
type recorder struct { /* the fake's calls of one apply, split by the engine's events */ }; func (*recorder) steps() []component.PlanChange
```

## 7. Not in this unit; inputs to later units; size
