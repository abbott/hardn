# The gallery on the real engine (`internal/tools/uigallery`: `play engine`)

> **Unit:** refactor plan Phase 3, `next/p3-gallery-engine` (plan §2, row `p3-gallery-engine`: "Gallery playable mode drives the real engine against the recording fake `System`, so each slice's gallery review shows real plans"; brief 1D, the playable mode: "Once the Phase 3 engine exists, it uses the real engine against a fake `System`"; brief Phase 5, "gallery first"; refactor plan §2 "Phases 3–5 together", unit (a) of each slice, "real plans via p3-gallery-engine"). It shows the decisions of the units below it, each in a scenario of its own: [P-39](../refactor/proposals.md#p-39) (a), [P-40](../refactor/proposals.md#p-40) and [P-41](../refactor/proposals.md#p-41), decided by the maintainer on 2026-10-19 and built by `next/p3-steps` and `next/p3-confirm-cleanup`. No V-number and no behaviour of hardn changes: the unit is dev-only, in a binary no build target makes ([design-system README](../design-system/README.md) §9.14, "Never released").
> **Status:** built and tested on macOS, in process: each scenario played through the gallery's own entry point with scripted answers (`uitest.Typist`), its transcript pinned as a golden on the core set, the simulated host it leaves checked, and the race detector run on the package. No real terminal and no host were used; nothing here runs on Linux, and nothing needs to: the gallery runs no command (§4). Review fixes: the simulated hosts are what `detect` establishes, and the engine detects them itself (§2.1); the confirming connection is new by the model's own `/proc` (§2.3); `TestPlayTouchesNothing` refuses `host.Real` named in any form and any engine built with a hold that is not the gallery's (§2.8).

[engine.md](engine.md), [steps.md](steps.md), [output.md](output.md) and [confirm-cleanup.md](confirm-cleanup.md) built the engine, its change kinds, the flow adapter and `hardn confirm`'s clean-up, each tested on the recording fake. The gallery's playable mode still ran its workflows on fixture plans written by hand (`flow.Fixture`). Now `uigallery play engine` runs the real engine on a simulated host, through the same canonical flow, so the maintainer sees the plans, steps, confirm countdown and outcome hardn would show, and how they look in every render environment.

## 1. Why

Brief 1D asks for a playable mode that runs "the real screens and prompts against a simulated system", on fixture plans in Phase 1 and on "the real engine against a fake `System`" once the engine exists. The refactor plan makes each slice's first unit its gallery review, with "real plans via p3-gallery-engine". A fixture plan is a guess at what the engine plans: the boot unit's change, the firewall before the file, `ssh.socket`'s three commands, the check after the reload, the D9 refusal's report and the clean-up's steps were not in any fixture, and a review on fixtures would sign off on screens the engine never draws.

3. **`hardn confirm`, as `cmd/hardn` runs it** (P-40; `confirmAndCleanUp`, [confirm-cleanup.md](confirm-cleanup.md) §2.9). After the 2230 change of `confirm-cleanup-debian13` is applied, a new SSH connection to 2230 (another machine's) runs `confirm.Claim`, then `confirm.Cleanup` through the engine on the same host; the clean-up's run is `output.Human`'s, and `Held.Report` is one run of `pkg/ui` messages (`component.Messages`), as `showCleanup` renders it since `next/s2-row-grammar`: what was done one "Operation Successful" callout, what is left one "Warning", how to finish it prose (P-42 R5), a blank line under the clean-up's report, as the gallery sets every block apart. **The connection is new by the model's own processes** (`fakeHost.connect`): every simulated host's `/proc` holds init, sshd's listener and the `sshd-session` of alice's connection that applies the change, all started before the applying hardn (500000 clock ticks after boot), so `MarkApplied` lists the listener and alice's (`Applied.SSHD`); the confirming connection's `sshd-session` is added to `/proc` only after the apply, a minute later, and `/proc/self` becomes the `hardn confirm` it runs. So `CheckConfirm`'s refusal of a connection open at the apply (`ErrOldConnection`) passes for the reason it should, and refuses the same connection made before the apply. **Departures from `confirmAndCleanUp`**, none of which a scenario reaches: the claim's line, "Change <id> confirmed (<summary>): it will not be rolled back.", which `hardn confirm` prints through the legacy logger, is an OK `Message`, an "Operation Successful" callout since P-42, the gallery having no legacy logger (and `pkg/logging` writing `/var/log/hardn.log`); a claim's error is a bad `Message` likewise, and the timer's rollback notice it reports is not acknowledged (`acknowledgeRolledBack`, a write of revert's state); the console's warning (`Confirmed.Local`) and the info line before a clean-up of a change finishing or carried (`Finishing`, `Carried`) are not drawn; and play exits 0 where `hardn confirm` exits 1 (a claim's error, a clean-up that did not finish). Tested: `TestPlayEngine` (the claim, the clean-up's four steps, the report; the host left with 2230 alone in `00-hardn.conf`, in what sshd binds and in ufw, and the change in `confirmed.json`, whose `Applied.SSHD` is alice's and the listener's), `TestConfirmFromNewConnection` (the confirming connection open before the apply: refused with `ErrOldConnection`, the change left waiting with 22 held; a clean-up whose reload fails: rolled back under the gallery's hold, the confirmation standing, port 22 left, the report's warning and how to finish).

### Nothing on this machine (`fakehost.go`, `TestPlayTouchesNothing`)

7. **The simulated host** is hostfake's recording `host.System`, its commands answered by a model of the host (`fakeHost.run`), ported from `internal/tools/p2drive`'s fake VM (`fake_test.go`, which a main package's test file cannot share) and kept in step with it by hand (§3, §7): `sshd -T` by a model of sshd's reading of its files (first value wins, `Port` and the others accumulate, a `ListenAddress` with a port as it is), `ss -Htln`, `systemctl` (`is-active`, `is-enabled`, `reload ssh.service`, `daemon-reload`, `show -p Listen ssh.socket`, `restart ssh.socket`, the timer's stop, the boot unit's enable, `list-timers`), `rc-service sshd reload`, `rc-update add`, ufw 0.36.2 (status, `allow`, `delete allow`, `--force enable`), `visudo`, `systemd-run` and OpenRC's sleeper, and detect's questions (`sudo --version`, `dpkg-query` for `pve-manager`). Each changes the model as the host would (a reload binds what the files configure; `daemon-reload` reruns the generator's model, `listen.conf` included; `restart ssh.socket` binds it). **Each host is a platform** (`platform`, `simulate`): Debian 13, Ubuntu 26.04, Ubuntu 22.04 and Alpine 3.24, each with its os-release, its init system's files (systemd's run directory and unit directory, or OpenRC's run directory, `openrc-run`, sshd's init script, started and in the default runlevel), sudo and `/etc/sudoers` or doas, ufw's files where it is installed, and `/proc`'s processes (§2.3), PID 1's environment, the PID namespace's link and the mount table. A command the platform does not ship (systemd's on OpenRC, OpenRC's on systemd, ufw on Alpine, sudo's with doas, `dpkg-query` on Alpine) is not found, as on the host. Where the VM runs settled what a host answers, the model answers so ([vmtest.md](../safety/vmtest.md) §4.9): `sshd -T` prints `permitrootlogin without-password` on Debian 13 (OpenSSH 10.0p2) and `prohibit-password` on Ubuntu 26.04 (10.2p1), Ubuntu 26.04's sudo is sudo-rs 0.2.13, and ufw answers "Rules updated" to `delete allow` while inactive, as to `allow`. A command the model does not answer fails, as hostfake's unscripted commands do, and is kept (`unanswered`), which every scenario's test fails on. Its values are synthetic: `web-01.example.net` (`web-01`) at 192.0.2.20, alice from 192.0.2.10, port 2230. Tested: `TestFakeHost` (a command not shipped is not found and not kept, one not modelled fails and is kept; sudo's and sudo-rs's versions; ufw's words while inactive and active; `permitrootlogin` by platform), `TestScenarioHosts`.
8. **The gallery links what changes a host, and never reaches it** (`TestPlayTouchesNothing`, rewritten). The engine links `host.Real`, the engine's signal hold (`pkg/engine/hold`), and `pkg/config` and `pkg/logging`, which write files. The test still parses the gallery and every package of the module it links, and refuses `os/exec`, a `net` package but `net/netip`, an `os` function that writes, removes, renames, starts a process or changes the environment, and any `syscall` or `x/sys/unix` name but the line reader's, an errno value and `Stat_t`. Those four packages' files that do (twelve, named in the test with why) are exempt, and the test checks instead, **by name**, that nothing play links can reach them:
   - **`host.Real`**: no file but its own five (`real.go`, `guard.go`, `lock.go`, `append.go`, `detach.go`) names the type, in any form: `host.Real` outside `pkg/host`, `Real` in its other files, so a literal, `new(host.Real)`, a declaration and a conversion are all refused; in its own files, a literal or `new(Real)` only in `NewReal`, which no file names but its own.
   - **`pkg/config` and `pkg/logging`**: no file names one of their functions (`pkg/config`, unreached itself, aside).
   - **The hold**: `hold.Signals` and `SignalsAs` are named only by the engine's default hold, which a nil `Options.Hold` takes. So outside the gallery only `pkg/engine/confirm`, which passes its caller's `Hold` on, calls `engine.New`, and nothing calls `confirm.Cleanup`; in the gallery, every call of either takes an `Options` literal, every `engine.Options` and `confirm.Options` literal sets `Hold` to the gallery's own (`session.hold`; not left out, not `nil`, not a variable), and neither function is named but to call it.

   So every `host.System` the engine and `confirm` get is one the gallery gives them, its fake, and the hold they take is the gallery's. **A check of names, not of types or values**: it holds the gallery to its literals and the linked packages to never naming what reaches the real side, and trusts `host.Real`'s own five files and `pkg/engine/confirm`'s pass-through. Checked by mutation in a scratch copy of the tree (the test reads the files from disk, so `go test -overlay` cannot mutate them): in the gallery, `new(host.Real)`, `var r host.Real` and `&host.Real{}`, an `engine.Options` built field by field, one with `Hold: nil` and one with no `Hold`, a `confirm.Options` with no `Hold`, `engine.New` taken as a value, and `os.WriteFile`; `new(Real)` in a new file of `pkg/host`; `engine.New` called in `pkg/output`; `new(Real)` in `real.go` outside `NewReal`: each fails the test, and the gallery's own form (`Hold: s.hold`) passes. The earlier mutations (a `host.NewReal` call, a `pkg/logging` call, a `hold.Signals` call, a `pkg/config` function) are refused by checks this rewrite kept. **The gallery's hold holds nothing** (`session.hold`): `hold.Signals` would ignore `SIGINT` and `SIGHUP` in the gallery's own process around a rollback that has nothing real to protect, and the line reader's Ctrl-C would stop working while it ran; it counts, and `TestPlayEngine` checks that the failed reload's rollback took it once (`TestConfirmFromNewConnection`, the failed clean-up's).
   **What play reads on this machine**, besides what the design-system README §9.14 lists for the gallery (its flags, the override file, stdin, the terminal's size, Lip Gloss's and x/ansi's init effects): linking the engine adds `github.com/fatih/color` (through `pkg/config` and `pkg/logging`), whose package initialisation reads `NO_COLOR` and `TERM` and asks whether stdout is a terminal (go-isatty, an `ioctl`; `color.go`, v1.19.0), and go-colorable and `go.yaml.in/yaml/v3`, whose initialisation touches nothing outside the process. At run time the engine's own code reads the process's effective uid (`pkg/host/backup`'s trust check, `os.Geteuid`), the real clock (a backup manifest's `Created`, the journal lock's wait; the journal's own times are the gallery's clock) and `crypto/rand` (the change id's suffix). All of these only read.

### Goldens

9. **One golden per scenario, and one of the menu**, on `uitest.Core()` (truecolor dark Unicode at 80 columns, plain at 80, truecolor dark Unicode at 60): `internal/tools/uigallery/testdata/golden/play/engine/<scenario>.golden` and `menu.golden` (the menu, the D9 scenario chosen from it, and back), written with `go test -run TestPlayEngineGolden ./internal/tools/uigallery -update` (`make golden-update` writes the same). Each is a play transcript, as `play/*.golden` are: the answers echoed after their prompts. **The change id** is the engine's (`revert.NewID`: the clock's second and a random suffix, `crypto/rand`), so the goldens write its suffix `xxxxxxxx` (`sameIDs`), which keeps every line's width; a message may wrap after the id's hyphen, and the test fails for an id cut anywhere else, which would leave part of it random. The clock is fixed (`galleryNow`, 2026-10-20 12:00:00 UTC), so the deadline and countdown are the same on every run. **The existing goldens are unchanged**: no scenario replaces a mock (§7), and `TestPlayGolden`'s five transcripts, the screen goldens and the component goldens pass as they were. Also tested: `TestPlayEngineSmoke` (the confirm-and-clean-up scenario in every profile, both themes and glyph sets, at 60 and 80 columns: no line wider than the terminal but a header and a prompt's echoed answer), `TestPlayEngineUsage` (a scenario that is not one; `-fail` or `-sequence` with a scenario: exit 2 before stdin is read), and the race detector on the package.

### Decisions of this unit

10. None is the maintainer's; each is the gallery's, and none changes hardn:
    - **The scenarios are a catalogue of the gallery's, beside the mocks**, not mocks of `pkg/ui/screen`: `screen.Mocks()` is the screen goldens' catalogue and `pkg/ui` renders only, so it cannot plan through the engine; and every workflow mock is a Figma frame (root login, a sudo method, a new user) whose control no slice has built.
    - **No title bar above a scenario's flow.** A workflow screen (`screen.WorkflowStep`) names the screen of a slice, which the slices design (slice 6 for SSH, 4 the firewall, 5 users); a note says what the scenario is until then.
    - **The confirmation's words are placeholders**: each question ("Change the SSH port to 2230?") is the gallery's, until the slices word their actions; the typed phrase is the host's short name, `web-01`, as `hostname(1)` prints it, under nav's example label "Type the hostname", as the mocks ask `bos-san-l01` (P-10 decides the words; P-24 and P-27 the steps' and the flow's). The FQDN would not fit after its prompt at 60 columns once echoed.
    - **The deadline on systemd is the timer's own**: the model's `list-timers` gives the timer's trigger a second after the window, as the Ubuntu 26.04 run found it firing 1 to 2 s after the deadline hardn prints ([vmtest.md](../safety/vmtest.md) §4.9), so the countdown reads 3:01 and "at 12:03:01 UTC"; OpenRC's sleeper is not read, so Alpine's says "at about 12:03:00 UTC" (engine.md §2.15).
    - **`-sequence` and `-fail` are refused with a scenario**: they are the fixture plans'; the failure path is the engine's own, in `failed-reload-debian13`.
    - **The engine detects the simulated host itself**, where the engine's own tests and p2drive's give it facts: what a scenario shows is then what hardn would establish on that host, and a model that drifts from its platform shows as detect's error in `TestScenarioHosts`, not as given facts the model contradicts.

### 8.7 Decisions of this unit

None is the maintainer's; each is the gallery's, and none changes hardn:

1. **The scenarios plan as the DNS screen will**: hardn.yml read from the simulated host (`config.Read`), the control carrying it as loaded, the engine given it, or a copy with a preset's list (control-dns.md §2.8). A scenario's controls are built on its host by a hook of its own (`scenario.setup`, which returns the flow's form and the controls with the configuration, built when the flow plans; `dnsSetup` for DNS), so that a later slice whose control reads or saves hardn.yml, or Run All's one plan of several controls, is another hook, not another field; `withHardnYML` writes any settings.
2. **Alpine's question is asked in the flow's form**, "Stop udhcpc rewriting /etc/resolv.conf?", y/N, default N, before the plan, as the mock asks it (gallery-dns.md decision 6), on a host where udhcpc writes the file (the model's resolver; the screen will ask from `dns.Read`'s finding); the control is built from the answer when the flow plans. `output.FlowEngine` reads its `Controls` then, after the form, so this needs no change to it (control-dns.md §11). The golden plays y; `TestPlayEngineDNSKeepsUDHCPC` plays n. *Superseded:* the unit first took the answer as y with no form, on the wrong premise that the adapter takes its controls before the flow runs.
3. **No review before the plan**: the scenarios run as hardn's flow does today, so the findings show after the flow (`AfterFlow`), not in the review where decision 5 places them, which is unit (c)'s.
4. **Ubuntu 24.04 shows the restart**; Debian 12's cloud image, which draws the same screen (the finding's words do not name its uplink link), is modelled and read in `TestResolverModel`. Alpine 3.23 likewise.
5. **The failed save is an immutable hardn.yml**, through a wrapper of the fake the engine gets (`engineSys`), so that the save fails as on a host, not by a change of the control.
6. **Every simulated host has its platform's resolver**, the status hosts' too: one model per platform; nothing on a status host reads it, and no golden of theirs changed.
