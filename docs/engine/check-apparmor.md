# AppArmor: the AppArmor status row (`pkg/engine/controls/apparmor`)

> **Unit:** refactor plan Phase 4, `next/p4-check-apparmor` (plan §2, row `p4-check-<area>`, AppArmor: "enabled? NotApplicable in containers, and on Alpine unless enabled", and the maintainer's decision of 2026-10-20 in the same row; brief Phase 4, "Where each status comes from"; brief 2.5, Alpine and containers; brief §3 principle 3). **Decided by the maintainer (2026-10-20): AppArmor is status only in v0.4**, with exactly the eight status lines of [P-43](../refactor/proposals.md#p-43) (3), "AppArmor in v0.4: status only", and a place in the risk level (plan §3.12; [P-16](../refactor/proposals.md#p-16)). It follows the pattern of [checks.md](checks.md) and takes up the "Status sources" item of [docs/safety/README.md](../safety/README.md) for AppArmor and, in part, [alpine.md](../safety/alpine.md) §6's `p4-check-apparmor` item (§2.11). No V-number covers origin/main's AppArmor row; [interaction.md](../refactor/phase0/interaction.md) §7 records it ("no container or Alpine NotApplicable state"), and V23 (Run All's claim that AppArmor ran) stays slice 7's and Run All's.
> **Status:** built and tested on macOS against the recording fake (`hostfake`) only, with the kernel's files and `systemctl is-enabled apparmor.service` as each case sets them (§3). Nothing has run on Linux: everything host-specific is "written, not run (gate 5)" (§4). The eight lines are the maintainer's; the only new wording is the details of two findings, *proposed* (§5.3).

Figma's main menu has an AppArmor row ("Not Configured" in `00-TUI-MAIN.png`, with no detail). It is now a check-only control, `apparmor.enforce`, titled "AppArmor", whose `Check` reads what the kernel enforces: whether the AppArmor LSM is on, each loaded profile's mode, the global mode, and whether AppArmor's service loads the profiles at the next boot. `Plan` returns `engine.ErrNotMigrated`, and in v0.4 nothing replaces it: hardn neither turns AppArmor on nor off.

## 1. Why

origin/main's AppArmor row (`checkAppArmorStatus`, `pkg/security/status.go:355-412`) matches `aa-status`'s text: Configured when it says "profiles are in enforce mode" and not "0 profiles are in enforce mode", a substring that "10 profiles are in enforce mode" contains, so a host whose count of enforcing profiles ends in 0 (10, 20, 110) shows Not Configured (by code reading, not run); inside a container it reads the host's kernel, and on Alpine it asks for the package and `rc-status default` first. It has no `NotApplicable` and no `Unknown`: a failure of any command is Not Configured. A kernel with the LSM on and no profile loaded restricts nothing [V, kernel `Documentation/admin-guide/LSM/apparmor.rst`, via [P-43](../refactor/proposals.md#p-43) (3)], so "installed" and "loaded" are not "confined", and a status that says a host is safe when it is not is the worst error of this phase (brief Phase 4: prefer Unknown to guessing). The legacy row stays as it is until the main menu goes live (plan, "Phases 3–5 together").

## 2. Guarantees

1. **One line per host state, the eight of P-43 (3), decided in a fixed order** (§5.2). Each fact is read from the kernel or the init system, never from a configuration file (brief §3 principle 3), and the first that decides the line ends the reading: nothing past it is read, apart from the evidence of "off in kernel" (`/proc/cmdline`, §2.4) and, on Alpine, `alpine.CheckAppArmor`'s `lstat` of the bootloader files, whose results are dropped (§2.11).
2. **Not Applicable in two cases only.** In a container (detect's `Container.Detected` Yes), through `Applies`: "set by the host" (brief 2.5); `Check` returns the same line when called without `Applies`, and reads nothing. On Alpine with AppArmor off, through `Check`: "Alpine default" (brief 2.5: not automated, left out of the risk score). **A departure from [checks.md](checks.md) §1.6** ("NotApplicable only through `Applies`"): `Applies` takes detect's facts and reads no file, and whether Alpine's kernel has AppArmor on is a reading of `/sys`. `Engine.Check` passes the state through (it overrides only a failed check's), and `pkg/output` exits 0 for it as for any `NotApplicable` ([output.md](output.md) §2.8). A fact that is not established is never grounds for `NotApplicable`: a container check not established is `Unknown`, and nothing under `/sys` is read then, since inside a container `/sys/module` shows the host's kernel ([alpine.md](../safety/alpine.md) §2.12).
3. **Whether the LSM is on** is the kernel's parameter `/sys/module/apparmor/parameters/enabled`: on Alpine through `alpine.CheckAppArmor` (its `Enabled`), elsewhere read by its rules, which `TestSameAsAlpine` checks give the same answer and the same code for the same file: `Y` on; `N` off; no `/sys/module/apparmor` in a `/sys/module` that is there, off (a kernel built without it); anything else not established. Off is "Alpine default" on Alpine, "uses SELinux" (Not Applicable) on Rocky Linux, AlmaLinux and RHEL while SELinux enforces, else "off in kernel" ([el-readonly.md](el-readonly.md) §1.4), and "off in kernel" elsewhere. Where whether the host runs Alpine is not established (no os-release), the two differ, so it is `Unknown`; Debian whose Proxmox VE is not established is not Alpine, and is "off in kernel". A distribution hardn does not list (`DistroOther`) is not Alpine either, whatever its `ID_LIKE`.
4. **The kernel command line is evidence, not a source of the state.** With the LSM off elsewhere than on Alpine, the evidence lists its `apparmor=`, `lsm=` and `security=` parameters from `/proc/cmdline`, or that it has none (the kernel's built-in order leaves AppArmor out); the state is the kernel's parameter, which is what the kernel made of that line (§3). A command line that cannot be read is said in the evidence, and the state stands.
5. **The loaded profiles** are `/sys/kernel/security/apparmor/profiles`, one line per profile, `name (mode)`, or `:ns:name (mode)` for a namespace below root's, as root sees them; hats such as `nvidia_modprobe//kmod` count as profiles. **Every namespace's profiles count, as `aa-status` counts them**: a namespace below root's is not only a container's. The Phase 4 VM run (2026-10-21, Ubuntu 26.04) found glycin's namespace (`:glycin:bwrap`, `:glycin:loaders`), which confines the image loaders of a program on the host itself, and `aa-status` counting 103 enforcing profiles where an earlier rule of this unit, counting the root namespace only, said 101. The evidence says how many of the profiles are in other namespaces. The profiles LXC generates for each container (`lxc-101_</var/lib/lxc>`) are in the root namespace. No profile loaded at all is "no profiles loaded", whatever the global mode and the boot service say. The modes the kernel names are `enforce`, `complain`, `kill`, `unconfined` and `user` (§3): **`enforce` and `kill` count as enforcing** (decision of this unit: a violation of a kill-mode profile kills the task rather than being allowed), `complain`, `unconfined` and `user` do not. A mode the kernel's list does not name (a vendor's patch, say) is not counted; it is not ranked, so with nothing enforcing beside it the line is `Unknown`, and beside an enforcing profile it changes nothing but the evidence. A line in another form is `Unknown`.
6. **The global mode** `/sys/module/apparmor/parameters/mode` (`enforce` unless changed): `complain` makes every profile complain whatever its own mode (§3), so it is "logging only" even with profiles listed as enforcing; `enforce` leaves each profile's mode as listed; `kill` and `unconfined`, the kernel's other values, are not ranked, so `Unknown` with the finding `APPARMOR_GLOBAL_MODE_UNKNOWN` (§2.10); a value the kernel does not name is `DETECT_UNRECOGNISED`. The kernel prints it with no newline (v6.18, §3); one newline after it is accepted.
7. **Nothing enforcing** (no profile in `enforce` or `kill` mode, or the global mode `complain`) is "logging only", whatever the boot service says: the line describes the host now (decision of this unit; §5.2).
8. **The next boot.** With profiles enforcing, AppArmor's own service must load them again at boot, or the line is "off after restart". On systemd, `systemctl is-enabled apparmor.service` (`detect.SystemctlIsEnabled`, which runs that verb only), read for the next boot by this package's own table, not detect's `UnitState.IsEnabled`, which reads `enabled-runtime` as Yes: `enabled` (an enabling link in `/etc/systemd/system`) loads them; `disabled`, `masked`, `linked` and `not-found` do not. The `-runtime` states are links in `/run/systemd/system`, set "for only this boot" (systemctl(1)), and say nothing of what stays (§3): systemd prints `enabled-runtime` even beside an enabling link that outlives the boot, `masked-runtime` hides the state under the mask, and `linked-runtime` can stand beside an enabling link in `/usr/lib`. They, and `static`, `indirect`, `generated`, `transient`, `alias` and `bad`, are not ranked: `Unknown` with the finding `APPARMOR_BOOT_UNKNOWN`. A state systemctl(1) does not list is detect's error, `DETECT_UNRECOGNISED`. On OpenRC, `apparmor` in the `sysinit`, `boot` or `default` runlevel (`detect.ServiceRunlevels`) loads them; in no runlevel it does not; only in another runlevel is `Unknown` with `APPARMOR_BOOT_UNKNOWN`, unless a runlevel entry could not be checked, which may hold it: then `Unknown` with that entry's error. `apparmor.service`'s stop unloads nothing, so a disabled service leaves the profiles loaded until the next boot (§3).
   **A departure from P-43 (3)'s "one test of on"** (research marked [I], for "the menu, the read-back, the drift check and Phase 4": "`apparmor` installed; `apparmor.service` enabled and active"; §6 (k)): neither the package nor `is-active` is read. The kernel's list shows what is loaded, whoever loaded it, so the package adds nothing to the line; a stopped or failed service changes nothing that the profiles loaded do not show, and the next boot starts an enabled one again.
9. **Configured** is everything above at once: the LSM on, the global mode `enforce`, one profile or more enforcing, and the service loading them at boot. Its detail is the count of enforcing profiles: "34 profiles enforced", and "1 profile enforced" for one (the one grammatical adjustment of P-43's string, which the maintainer's decision allows).
10. **`Unknown` is always "can't read", in two kinds** ([checks.md](checks.md) §1.5). Never a pass: no `Unknown` path returns another state.
    - **A fact not read, or read in a form neither the kernel nor systemctl documents:** `Unknown` with the error, which `Engine.Check` reports, exit 1. A read that fails (`PERMISSION_DENIED` for hardn run as another user than root, since the kernel refuses the profiles list and the mode to it, §3; `FILE_NOT_FOUND`; `COMMAND_NOT_FOUND`), detect's fact that is not established (its own code: `DETECT_NO_SIGNAL`, `DETECT_SIGNALS_DISAGREE`, ...), and a form hardn does not know, wrapped as `detect.ErrUnrecognised` (`DETECT_UNRECOGNISED`): `enabled` neither `Y` nor `N`, as `alpine.CheckAppArmor` gives for the same file; a profiles line not in the kernel's form, or a profile mode or global mode the kernel does not name; a state systemctl(1) does not list, as detect gives. **A departure from [checks.md](checks.md) §1.5's second kind** for these forms ("a value in a form hardn does not know" as `Unknown` with findings and no error), so that the same file or command gives the same code here as in `alpine.CheckAppArmor` and detect (§6 (e)).
    - **A documented value the control does not rank:** §1.5's second kind, `Unknown` with no error and one finding, exit 3: a global mode `kill` or `unconfined` (`APPARMOR_GLOBAL_MODE_UNKNOWN`, §2.6), and a boot service state that does not say (`APPARMOR_BOOT_UNKNOWN`, §2.8).
11. **Two findings, no others:** `APPARMOR_GLOBAL_MODE_UNKNOWN` and `APPARMOR_BOOT_UNKNOWN` (§2.10), exported constants registered in `pkg/output` (appended, `codes.golden` regenerated, a row each in [docs/reference/output.md](../reference/output.md) §2.2), each with a detail naming the value read and its source (§5.3); the eight details and the evidence say the rest. [alpine.md](../safety/alpine.md) §6 hands on `AppArmor.Note` (what enabling takes on Alpine, per bootloader) for rendering: **not taken up here** (decision of this unit). The note was written for an AppArmor screen, which is deferred past v0.4, and as a finding it would be wording the maintainer has not agreed (long, and about what hardn does not do). The bootloader files `alpine.CheckAppArmor` finds are left out of the evidence for the same reason: they say where enabling would start, not what the state is.
12. **Evidence** is each fact as it was read, one line per source: `/sys/module/apparmor/parameters/enabled: "Y\n"` (quoted, as `alpine.CheckAppArmor` writes it), or `/sys/module/apparmor: absent`; `/sys/kernel/security/apparmor/profiles: 15 enforce, 1 complain, 4 unconfined` (the host's, the kernel's modes in its order, then others), or `: none`, with `; 1 in other namespaces` after it where there are such; `/sys/module/apparmor/parameters/mode: "enforce"`; `systemctl is-enabled apparmor.service: enabled`, or `/etc/runlevels: apparmor in boot` (`in no runlevel`); `/proc/cmdline: apparmor=0`. Tested: `TestEvidence`.
13. **Read-only, through `host.System`.** The check reads files (on Alpine with `alpine.CheckAppArmor`'s `lstat` of the bootloader files) and runs exactly `systemctl is-enabled apparmor.service`, on systemd; `detect.SystemctlIsEnabled` takes no verb, so no caller can pass it one that changes the host. The calls of every test that reads a host are checked (`readOnly`; `TestCheckOnly` allows the engine's run lock besides). depguard rule `controls-through-host` ([checks.md](checks.md) §1.11) covers the package, checked to report `os` and `pkg/output` imports in a throwaway file of it (in a temporary copy of the tree; nothing committed); no rule was added.
14. **`Plan` returns `engine.ErrNotMigrated`** (`engine.CheckOnly`), and `Engine.Plan` over `Controls()` is refused, its item's error coded `CONTROL_NOT_MIGRATED`, with no change (`TestCheckOnly`).

## 4. Written, not run (gate 5)

Nothing here has run on Linux or as root. On the VMs of [vmtest.md](../safety/vmtest.md) (Debian 13, Ubuntu 26.04, Alpine 3.24) and by hand on Proxmox VE 9, through a dev-only driver or the gallery's status scenario once one calls `Engine.Check` with this control:

- each stock host: the line as installed, its count against `aa-status`'s profiles in enforce and kill mode;
- Debian 13: `systemctl disable apparmor.service` ("off after restart"), then a reboot ("no profiles loaded"); `systemctl enable --runtime apparmor.service` after the disable (`enabled-runtime`, "can't read" with `APPARMOR_BOOT_UNKNOWN`); a boot with `apparmor=0` and with an `lsm=` without it ("off in kernel", the parameter in the evidence); the global mode set to `complain` ("logging only"); every profile put in complain mode with `aa-complain` ("logging only");
- Ubuntu 26.04: the same run as a user other than root ("can't read", `PERMISSION_DENIED`); a host without the `apparmor` package, if it can be removed ("no profiles loaded");
- Proxmox VE 9 with containers running (their `lxc-<id>_</var/lib/lxc>` profiles counted), one of them nested and running AppArmor inside (its namespace's profiles counted too, as `aa-status` counts them, with the `:ns:` form of §3), and from inside an LXC container ("set by the host");
- Alpine 3.24 stock ("Alpine default"), then after `alpine.AppArmorNote`'s steps ("N profiles enforced", or "no profiles loaded" without a profile package), and with `apparmor` dropped from the boot runlevel ("off after restart");
- whether `/sys/module/apparmor/parameters/mode` ends in a newline on each platform's kernel (§3);
- the time `Check` takes (a few file reads and at most one command).

## 5. The status lines

### 5.1 The eight lines (decided, P-43 (3))

```text
   ▽  AppArmor             Configured 34 profiles enforced
   ⛬  AppArmor             Partial logging only
   ⛬  AppArmor             Partial off after restart
   ○  AppArmor             Not Configured no profiles loaded
   ○  AppArmor             Not Configured off in kernel
   ∅  AppArmor             Not Applicable set by the host
   ∅  AppArmor             Not Applicable Alpine default
```

Drawn since the maintainer's glyphs of 2026-10-21 ([gallery-glyphs.md](gallery-glyphs.md) §1): Partial ⭘ in `status.warn`, Not Applicable – and Unknown ? in `text.muted`; the quote keeps P-43's markers.

### 5.2 Which line when several apply

The facts are read in this order, and the first row that matches decides (§2.1). Decisions of this unit, for the maintainer, are marked.

| # | Fact | Decides |
|---|---|---|
| 1 | container | Yes: "set by the host"; not established: "can't read" |
| 2 | the LSM | not established: "can't read"; off: "Alpine default" on Alpine, "off in kernel" elsewhere, "can't read" where Alpine is not established. **Off in kernel beats everything about profiles**, which an LSM off has none of |
| 3 | the profiles list | not read: "can't read"; empty: "no profiles loaded". **No profiles loaded beats logging only and off after restart** (the decided "off after restart" is "with profiles still loaded"; a global `complain` with nothing loaded confines nothing either) |
| 4 | the global mode | not read: "can't read"; `complain`: "logging only"; `kill` or `unconfined`: "can't read", with a finding; another: "can't read" |
| 5 | the profiles' modes | none enforcing: "logging only", or "can't read" with a mode hardn does not know beside them |
| 6 | the boot service | not established: "can't read" (with a finding where a state was read, §5.3); not loading them: "off after restart". **Logging only beats off after restart** (decision of this unit): the line describes the host now, and nothing is enforced now; the service's state is in the evidence |
| 7 | — | "N profiles enforced" |
