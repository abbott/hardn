### 2.1 How dry run is set (read)

- **`-n`/`--dry-run`**, default false (`cmd/hardn/main.go:96`). After loading hardn.yml, `cfg.DryRun = dryRun` (`:152`; trunk `:159`) sets the mode from the flag whatever the file says.
- **hardn.yml's `dryRun`** (`pkg/config/config.go:29`, default false `:104`; the example's line `dryRun: false # Preview changes without applying them`, `embed.go:20`) is read by the loader and then overwritten (**V3**, "Ignored YAML key"; run: `pkg/characterization`'s `config/full-flag.golden` loads `dryRun: true`; v0.3.2 the same, [v032-reference.md](../refactor/phase0/v032-reference.md) §2 item 3, where `hardn -g` applied with `dryRun: true`). So `dryRun: true` in hardn.yml gives a live session.
- **With an operation flag**, origin/main's flag paths never read `cfg.DryRun`, so `-n -r` applied (**V1**). The trunk refuses `-n` with an operation flag, exit 2 (`pkg/cmd/dry_run.go:46-61`, P0.8), but `-g`, whose `-n -g` shows the DNS control's plan and writes nothing, exit 3 where there are changes (trunk `cmd/hardn/dns.go:47-55`, slice 2). `-n` alone opens the menus in dry run.
- *Since unit (b), `next/s2b-mode`: `-n`/`--dry-run` given wins, `true` or `false`, otherwise the loaded file's `dryRun`, otherwise live (`config.Config.ResolveDryRun`, its source `DryRunSource`); an operation flag under the file's plan only is refused as under `-n` (exit 2), `-g` planning; the legacy saves write `dryRun` as loaded ([dryrun-mode.md](dryrun-mode.md)). The bullets above and below are origin/main's.*
- **Inside a session**, two items set the mode: the Dry-Run item, 6 (§2.2), and Run All's option 2, "Enable dry-run mode and run" or "Disable dry-run mode and run", which flips it, asks a typed "yes" when it goes live and saves `./hardn.yml` (`run_all_menu.go:108-120`, `:144-180`, read); declining the "yes" returns with the mode already flipped, so dry run stays off for the rest of the session (`:146`, `:160-170`, read; the trunk's `confirmRealChanges` the same). The trunk's DNS screen reads the mode when item 3 is chosen (trunk `cmd/hardn/dns.go:84-86`, `:112`), so it follows a toggle.

## 4. Decisions for the maintainer

**Adopted (the maintainer, 2026-10-23):** "adopt all ten of the slice 2b recommendations, with one clarification: i'd like to avoid using a compact menu. if we need to reduce row counts, we can explore that later, but a two-column menu is not a desired method". Every recommended answer below is adopted, but decision 5's compact form: the main menu takes the layout's **full form at every height** (decision 5's alternative (b), descriptions kept), and the compact two-column form is not used (gated, not deleted, in unit (c), §8). Fewer rows are for later (§3.2).

1. **What dry run becomes (brief §7.3, P-03).** *Recommended:* one global mode, "Plan only": every change's flow stops at its plan with origin/main's footer, as the DNS screen does; set once, as hardn starts, by `-n` or by hardn.yml's `dryRun` (decision 2); no item turns it on or off; **item 6 is removed, its key left unused** (refused as any key no item has), so no key changes meaning; `-n` kept for the menus and the flags (`-n -g`). Reasons: once each area is on the flow, every change shows its plan and asks y/N, so n is a dry run of that change (on the trunk only DNS does); plan only is for looking around with no question asked at all (an audit, a shared host), which a start flag gives; a switch inside the session is one key from "nothing changes" to "changes apply", which a restart makes deliberate; item 6 is a mode, not an area of the host (P-01 lines items up with rows); the defects "Enabled menu never printed" and "3 pauses" go with it; renumbering would put Run All on 6, the key that turned dry run on. Cost: until each area migrates, a legacy screen with no question (Firewall's Configure, Environment) can be previewed only by starting with `-n`; and removing an item needs P-03's deprecation note (decision 10). Mocked: `menu-proposed`, `menu-proposed-plan-only`, `play dryrun/proposed`. *Alternatives:* (a) P-03 (a): item 6 kept as the switch, on the sub-menu layout with origin/main's words, or proposed "Plan only" "Preview changes only" (mocked in origin/main's: `screen`, `screen-enabled`, `play dryrun`); (b) P-03 (b): item 6 removed and 7 to 10 renumbered 6 to 9, Run All on 6; (c) no global mode in the menus: `-n` for the flags alone, `hardn -n` with no flag refused, the legacy screens without preview.
2. **The precedence of §3.19 (approved: "explicit flag wins, otherwise config"), shown.** *Recommended:* the indicator names where plan only came from, after the word: "(-n)" or "(hardn.yml)"; live names nothing. hardn.yml's key is out of sight and lasts, so a user whose changes never apply must see why; `--dry-run=false` is then how to apply on such a host, the explicit flag winning. Consequence to accept: with `dryRun: true` in hardn.yml, `hardn -g` from a script shows its plan and exits 3 where there are changes, applying nothing; files origin/main left may already say so (decision 10). Where plan only can also be set inside the session (decision 1's alternative (a), item 6 kept, or decision 7's, Run All's option 2 kept), the indicator names no source for it, the user having just set it on screen. *Alternatives:* (a) no source, as origin/main; (b) the source in live too, "(default)", "(--dry-run=false)"; (c) hardn.yml's alone named; (d) the flag as typed ("(--dry-run)" where it was) and the file's path ("(/etc/hardn/hardn.yml)", "(./hardn.yml)"), longer but exact; (e) a source for the session's own setting, such as "(item 6)".
