# User Management on the engine: the User control (`pkg/engine/controls/users`)

> **Unit:** refactor plan slice 5 (User Management), unit (b), `next/s5-control`, from `ebf87b11`. It builds on unit (a) ([gallery-users.md](gallery-users.md)), whose eight decisions and Made here calls the maintainer adopted on 2026-11-03 ("Adopt all, start (b)").
> **Status:** built and tested on macOS, in process, on `hostfake`, through the real engine. Nothing has run on Linux or as root (§6). Nothing is wired into `cmd/hardn` or the main menu; `pkg/menu` and `pkg/characterization` goldens are unchanged. Words: gallery-users.md §6's, used exactly; the rest proposed (§5). *Since `next/s5-replace` (unit (d)), main menu 1's screen and `-c` call it ([cmd-engine.md](cmd-engine.md) §2.14, §2.15).*

The User control is Figma's User row and every change the User Management screen makes: admin rights, a user's SSH keys, a new user. `Read` gives the screen what it draws; `Plan` refuses before anything is written, in the decided words, or plans the change on the real engine.

*Since `next/sudo-password-opt-in` (2026-11-11): admin rights without a password are opt-in (§8), which replaces decision 3 (a)'s grant for Create and the Made here call for Grant. Where §1 to §6 say a new user's grant asks no password, or that a password asked of a new user is refused, §8 is current.*

## 1. What it does

- **Admin rights** (`plan.go`): Grant, Remove, Ask for password, Don't ask password, as hardn's own file (`sudoers.PlanFor`, `steps.Sudoers`; decision 2 (a)). Remove takes hardn's file alone and refuses where another rule grants or would still grant (`StillAdmin`), for the session user's own, and for the last admin with the session user not known, another admin counted only where it can become root (a rule asking no password, or one it has set; decision 4). Grant is plain for a user not an admin; for one already an admin, the planner's risk (a password asked where none was is a lockout risk).
- **SSH keys** (`keys.go`): Add and Remove in `~/.ssh/authorized_keys` alone, and only where sshd reads it; keys counted in every file sshd reads ([authkeys.md](../safety/authkeys.md)). Add refuses a home or `~/.ssh` StrictModes would ignore a key in; Remove refuses the session user's last key and a key also in another file sshd reads. Removing the session user's key, anyone's with the session not known, or anyone's last key is a lockout risk (typed hostname, confirm or revert); adding is plain.
- **Create** (`create.go`): one plain plan: `useradd --home-dir /home/<name> --create-home --shell /bin/bash` (`/bin/ash` on Alpine), with `--password '*'` where sshd's PAM is not established as on (decision 3 (a)), undone by `userdel --remove` only where useradd made the user (the name and home checked again before it; useradd failing undoes nothing); then hardn's grant without a password, where asked; then the keys, where given, every one in one change, the same key once. A name useradd refuses, one a user or group has, and one whose `/home/<name>` is there are refused; so is a password asked for admin rights, and a key that is not one, before anything is written. On Alpine, Create is refused where `useradd` is not installed (`USERS_NO_USERADD`): it is the `shadow` package's, and BusyBox has `adduser` alone. With admin rights asked and doas missing too, one refusal names both packages.
- **Install shadow** (`create.go`, `ActionInstallShadow`; the maintainer, 2026-11-11, [screen-users.md](screen-users.md) Decisions): the User Management screen's alone. On Alpine where `useradd` is missing, `apk add shadow` as one change, modelled on Firewall's Install iproute2: `steps.PlanPackage` simulates it first (`apk add --simulate shadow`) and refuses anything but new packages; `RiskPackageInstall`, y/N; its state after "installed, with <the other new packages>"; its undo a plain `apk del shadow` (run as it is, not simulated, as iproute2's). Where `useradd` is there, and off Alpine, nothing to do; shadow installed without its `useradd`, a refusal (`USERS_NO_USERADD`). `-c`, `-u` and Run All never install it: they refuse.

## 2. The API

- `Admin{Action, User, Key, Fingerprint, New, Getenv}`; `Action`: `ActionNone` (the status list's: `engine.ErrNotMigrated`), `ActionGrant`, `ActionRemove`, `ActionAskPassword`, `ActionNoPassword`, `ActionCreate`, `ActionAddKey`, `ActionRemoveKey`, `ActionInstallShadow` (reads only `useradd` and the package). `New{Name; Admin, Password bool; Keys []string}`: the screen passes one key, `-c` hardn.yml's `sshKeys`. Change ids `ChangeGrant`, `ChangeCreate`, `ChangeKeys`, `ChangeShadow` (`users.admin/grant`, `/create`, `/keys`, `/shadow`).
- `Read(ctx, sys, facts, getenv) (Reading, error)`: `Reading{Choice, NotRead, Invoker, Status, StatusErr, PAM, KeyEntries, KeyErr, Users}`; `User{accounts.User, Admin, Tool, Decided, NoPassword, Password, Policy, PolicyErr, Files, Keys, KeyDir, Locked}`. It writes nothing; it runs `visudo -c` or `doas -C` and `sshd -T`.
- Before asking: `Reading.Refusal(ctx, sys, Admin)`, `ToolRefusal()`, `KeysRefusal()`, `CheckName(ctx, sys, name)`, `CheckNew(ctx, sys, New)`, `ParseKey(s)` and `CheckKey(user, s)` (Add's key: `ParseKey`'s, or one a file sshd reads holds already): each a `*steps.Refusal` whose words `screenkit.RefusalWords` says. `StillAdmin(ctx, sys, Reading, user) Still{By, Unknown}`. `User.NewGrant()`: the grant Grant plans (`GrantPassword` where `Password` is `Set`, else `GrantNoPassword`), which the screen's review says.
- Refusal codes: `USERS_*` (twelve for admin rights; `USERS_KEY_FILES_NOT_READ`, `_LAST_KEY`, `_KEY_ELSEWHERE`, `_KEY_THERE` (Add's key there already), `_KEY_GONE` (Remove's key no longer in `~/.ssh/authorized_keys`, `PlanRemove`'s `fs.ErrNotExist`), `_NAME_FORM`, `_NAME_TAKEN`, `_HOME_THERE`, `_NEW_PASSWORD`) and `AUTHKEYS_NOT_PLANNED`, `_STRICT_MODES`, `_NOT_KEY`; findings `USERS_LOCKED` on Add for a locked user, `USERS_NO_KEY` on Create with no key, `USERS_PASSWORD_NOT_SET` on a grant asking a password the user has not got (§8) ([output.md](../reference/output.md)).
- Beside it: `accounts.Password` (`PasswordNotRead`, `Set`, `None`, `Empty`; `Shadow.PasswordOf`); [authkeys](../safety/authkeys.md) (`Read`, `Keys`, `ParsePublic`, `PlanAdd`, `PlanRemove`, `CheckStrict`); `sshd.Effective`'s `StrictModes` and `AuthorizedKeysFile`; `ssh.ReadKeyFiles`, read as `ssh.ReadPAM` reads sshd.

## 4. Engineering calls

- `ssh.ReadKeyFiles` beside `ReadPAM`: one more `sshd -T` per `Read`; `Plan` reads sshd and the keys only for the key actions and Create.
- `Locked` is a `!` password where sshd's PAM is not established as on, not only where it is off [I].
- The key actions skip the tool's and hardn's-file-edited refusals: a key needs neither.
- A key in another file sshd reads is refused from `Read`'s files, naming that file, before `PlanRemove`.
- The last key is the session user's last key not `Restricted` (options that may stop a login: `command=`, `from=`, `restrict`, …), counted once across every file sshd reads; a restricted key is listed and removable.
- The keys change is in `StageAccounts` (the engine's "the user and the key in place"); the mock's was `StageFiles`.
- The keys change always backs up `authorized_keys`: a new one is removed on rollback, then a `~/.ssh` it made.
- The file's uid and gid are read from `/etc/passwd` at apply, so a user Create makes in the same plan has them.
- Create makes `~/.ssh` with `install -d -m 700 -o <name> -g <name>`: useradd gives the user its own group (USERGROUPS_ENAB yes), and `CheckName` refuses a group of the name already there.
- Create's grant is plain and after the account; its key after the account; `CheckStrict` is not run for a home that does not exist yet [I].
- Create with no key has a finding, `USERS_NO_KEY`, in place of the mock's review notice.
- Add for a locked user reuses `USERS_LOCKED` as the plan's finding.
- The name check is doas's (`sudoers.CheckUser(ToolDoas, …)`, the stricter) on every host, as the mock's.
- The gallery's engine sees the tools' setuid bit as `Read` does (`usrSys`), so its plans read the host the screen read.

## 7. CVE-2026-123158: Create refused on Alpine

Where the new user's field would be `*` (sshd's PAM not established as on) on Alpine, `CheckNew` ends with `bypassRefusal`, reading sshd as SSH Auth does (`ssh.ReadBypass`, [check-ssh.md](check-ssh.md) §11). With `openssh-server` (or the `-pam`, `-krb5` build that runs) established to lack the fix and a password path not established off, Create is refused before anything is written, `USERS_PASSWORD_BYPASS`: the new user would be a target the moment it exists. Whether a donor (`$5$`, `$6$`) exists is not asked; one may be set later. With the fix not established and a password path not established off, Create plans as before with the finding `SSH_FIX_UNKNOWN` on the account's change, beside `USERS_NO_KEY`. Where no sshd can run (`ReadBypass`'s `NoSSHD`: sshd not installed, or no `sshd_config`, which sshd does not start without), there is nothing to refuse or warn of, and Create plans with no CVE finding: an Alpine 3.23 LXC with no openssh showed the false warning on 2026-11-07. `-c`, Run All's Create and the User Management screen (its password field's `CheckNew`, and its plan) all reach it. Tested: `TestCreateBypass` (the control: refused, through a Match block; fixed, password off, PAM on, no database; no sshd, sshd not installed), `TestCreateUserFlagBypass` (`-c`, `-n -c`).

Words (*proposed*): "sshd would let anyone log in as carol with a long password, since carol has no password (CVE-2026-123158). Upgrade openssh in SSH Login (5), or turn password login off there (2)." *Since 2026-11-08 (`next/alpine-openssh-upgrade`, proposed):* the fix names SSH Login's Upgrade openssh ([alpine.md](../safety/alpine.md) §7.1), where it said "Run apk -U upgrade, then rc-service sshd restart"; Run All defers such a Create while it plans the upgrade. The fix is written lower case, as the others, so `-c`'s "To go on:" reads on; the screen capitalises it. The finding: "can't tell if openssh-server has the fix for CVE-2026-123158: /lib/apk/db/installed is missing".

## 8. Admin rights without a password are opt-in

> **Unit:** `next/sudo-password-opt-in`, from `e0014917`. The maintainer, 2026-11-11: "hardn should not default to looser restrictions"; the five choices below adopted that day ("Adopt all").
> **Status:** built and tested on macOS, in process, on `hostfake` and the gallery's hosts; `go test ./...` passed on `deb13-vm` and `alpine323-vm`; Create User with `passwd` run on both (below). Run 2026-11-11 with the linux-amd64 build of the v0.8.0 tree: `-c` with and without `adminNoPassword`, and Run All for the user alone, on `deb13-vm`, `ubuntu26-vm`, `alpine323-vm`, `alpine324-test-116`, `alma9-test-111`, `rhel9-test-115`, `rhel10-test-114`, `rocky9-test-113` and `rocky10-test-110`; Grant for a user with no password on `deb13-vm` and `alpine323-vm`. Not run: `passwd` failing; Create User's `passwd` on ubuntu26-vm and the EL hosts; arm64.

**What changed.** hardn writes the no-password rule (`NOPASSWD`, `nopass`) only where asked.

- **Create** (`create.go`): `New{Name; Admin, NoPassword; Keys}`. With `Admin`, the grant is `GrantPassword`, with the finding `USERS_PASSWORD_NOT_SET` on its change; with `NoPassword` too, `GrantNoPassword` as before, no finding. `New.Password`, its refusal `USERS_NEW_PASSWORD` and `ErrNewPassword` are gone.
- **Grant** (`plan.go`): always `GrantPassword`, with the same finding for a user whose password is not set. `User.NewGrant` is gone. Ask for password still refuses for a user with none (`USERS_NO_PASSWORD_TO_ASK`): there it would take a working way to root away.
- **hardn.yml** (`pkg/config`): `adminNoPassword`, false by default, not written when false. `-c` (`createNew`) and Run All (`runall.Asked`) pass it as `New.NoPassword`; Create User's "Require password for admin rights?" defaults to its opposite. `sudoNoPassword` is a retired key whose old default is true (`retiredOn`): `false` warns "hardn.yml's sudoNoPassword isn't used", `true` never does and is never the opt-in.
- **The screen** (`pkg/screens/users`): "Require password for admin rights?" [Y/n]; after yes, "Set carol's password now?" [Y/n], not asked under plan only. Once the plan is applied and carol reads back with no password, `passwd carol` has the terminal (`host.System.RunInteractive`, as the Logs screen's pager). A user with rights that ask a password not set is drawn "Enabled, No password set", a cost.

**The choices** (recommended, adopted):

1. **Where the password comes from:** hardn never handles it. The screen hands the terminal to the host's `passwd`; `-c` and Run All set none and say so. Not taken: hardn asking twice and piping to `chpasswd`; a `passwordHash` key.
2. **The opt-in:** a new key, as a saved file's `sudoNoPassword: true` is hardn's old default, not a choice; and Grant asks the password too, Don't ask password being the menu's opt-in.
3. **Create's question:** the words kept, the default yes.
4. **Hosts hardn already granted no-password rights on:** left as they are. Switching one unasked would lock out an admin with no password. The check's `USERS_NOPASSWD` and the screen's row already show it.
5. **CVE-2026-123158 on Alpine** (§7): no change. `useradd` writes `*` before any password, and it stays where `passwd` is skipped ([alpine.md](../safety/alpine.md) §7).

**What follows.** A new admin with no password cannot become root, and the lockout proofs already say so: `-d` and Run All's root login off count an admin only where the rule asks no password or the password is set (`sshchange.LoginPaths`, `User.canRoot`). So `-c -d` on a host with no other admin refuses `-d`, the user created (`SSH_NO_ADMIN_LOGIN`). Run All plans each row against the host as it is, so the user it creates never proved root login off.

**Made here.** `sudoNoPassword: true` does not warn, against the adopted "a warning naming the new key": every saved file holds it, and the project's rule is that a value at the old default is hardn's, not the file's. `passwd` failing, or no terminal, is a warning, the user kept: "carol's password isn't set. Run passwd carol." Create's review still carries `USERS_PASSWORD_NOT_SET` when the password is about to be set: the finding is the plan's.

**Words** (*proposed*): the finding, "carol can't use sudo until a password is set: run passwd carol" (doas where it is the tool); the row, "Enabled, No password set"; "Set carol's password now?"; "Setting carol's password"; "carol's password isn't set. Run passwd carol."

**Run on `deb13-vm` (Debian 13, sudo) and `alpine323-vm` (Alpine 3.23.6, doas, no hardn.yml)**, 2026-11-11, the linux-amd64 build of `b40fe586`, through main menu 1 on a terminal over SSH, driven by `expect` with a throwaway user `dfoptin` (`vm-runs/optin/dogfood.exp`, `dogfood-*.log`): the defaults taken at "Require password for admin rights? [Y/n]" and "Set dfoptin's password now? [Y/n]", no key. The review drew "Enabled, No password set" and the finding, naming sudo or doas. Applied, hardn said "Setting dfoptin's password" and `passwd` took the terminal ("New password:", "Retype new password:", "passwd: password updated successfully"); the screen then drew dfoptin "Enabled", "Granted by hardn", Password "Set". Read back: `dfoptin ALL=(ALL) ALL` in `/etc/sudoers.d/hardn-grant-dfoptin`, `permit persist dfoptin` in `/etc/doas.d/zz-hardn-dfoptin.conf`; the shadow field a hash (`$y$` on Debian, `$6$` on Alpine, the kind CVE-2026-123158 borrows from, §7, on a VM whose openssh-server read 10.2_p1-r0 with password login off). As dfoptin, `sudo -n true` and `doas -n true` were refused ("a password is required", "Authentication required"), and each succeeded once its password was given.
