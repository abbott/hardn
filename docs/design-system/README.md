## 1. Purpose and Figma fidelity

The design system is the one place that decides how hardn's terminal output looks: which colour a state takes at each colour profile, which glyph marks it, where the columns fall and how output degrades without colour, Unicode, width or a terminal. Screens are assembled from its components rather than styled by hand.

The refactor brief (kept outside the repository) sets these rules:
- **Renderers are pure functions** of a view-model and the render environment (`term.Env`). They return strings and do no I/O. `term.Detect` is the only code that looks at the terminal, with one exception: `prompt.Stdin` asks whether stdin is a terminal itself, with the same ioctl, because importing `term` would link Lip Gloss (§2.3, §9.7).
- **No raw ANSI escape codes outside `pkg/ui`.** Feature code gets its styling from the theme (usage and import rules: §9.15).
- **Muted and faint text come from gray colour tokens, never from SGR 2 (faint).** No style slot sets faint, blink or reverse (DEV-009).
- **Never colour alone.** Every state also has a word or a glyph, so it reads the same without colour.
- **Degrade gracefully** with no colour, no Unicode, a narrow terminal, no TTY or a light background.

**Figma fidelity.** The Figma screenshots and token export set the intended direction; they are not a spec, and nothing fails because output differs from them.
- **The Go theme is the runtime source of truth.** `pkg/ui/theme` is derived from the export. The export is a reference kept outside the repository: it is never loaded at runtime and never committed.
- **Drift is resolved by meaning.** Near-duplicate values for one role become one token. Values with no terminal equivalent (font family and size, line height, letter spacing, radius, shadow, opacity, sub-cell spacing) map to the nearest terminal concept or are dropped.
- **Two logs, two owners.** A *deviation* is a difference forced by a terminal limit or by drift in the export; the implementer decides it and records it in [deviations.md](deviations.md). An *enhancement* changes meaning, flow or wording; it waits for the maintainer in [proposals.md](../refactor/proposals.md). Small, obvious fixes, such as an alignment fix, are deviations.
- **Figma is not updated from the code.** The two logs and this document are the only record of where the code departs from the screenshots.

## 2. Lip Gloss

### 2.1 Choice

## 3. Render environment

`pkg/ui/term` builds one `term.Env` at startup and every renderer takes it. Nothing else inspects the terminal or the environment.

| Field | Meaning |
|---|---|
| `Width`, `Height` | Terminal size in cells |
| `Profile` | The `colorprofile.Profile` that `Env.Writer` downsamples to: TrueColor, ANSI256, ANSI (16 colours), ASCII (no colour; bold and underline kept) or NoTTY (no escape sequences at all) |
| `Unicode` | The Unicode glyph set; false selects ASCII |
| `TTY`, `InputTTY` | stdout and stdin are terminals |
| `Dark` | The dark theme; false selects the light theme |
| `Theme` | The theme mode Resolve settled on: `ThemeDark`, `ThemeLight` or `ThemeAuto` |
| `Plain` | Plain mode: ASCII glyphs, no animation and, unless `--color=always`, no colour or attributes |
| `Animate` | Spinners and in-place updates are allowed |

`Env.HasColor` reports a profile of ANSI or better. `Env.Writer(w)` returns a `colorprofile.Writer` around `w` with the profile fixed; the profile was resolved for stdout, so it wraps stdout.

**Precedence** (`term.Resolve`, a pure function of `term.Options` and the observed `term.Facts`). An option beats an environment variable, which beats detection. A boolean variable is true for `1`, `true`, `yes` or `on`, in any case.

| Field | Rule, first match wins |
|---|---|
| `Plain` | `Options.Plain`, or `HARDN_PLAIN` true, or stdout is not a terminal |
| `Profile`, `--color=never` | NoTTY when `Plain`, else ASCII |
| `Profile`, `--color=always` | `colorprofile.Env` with `NO_COLOR` removed from the environment, raised to at least ANSI, even when `Plain` |
| `Profile`, auto or unset | NoTTY when `Plain`; ASCII when `NO_COLOR` is non-empty or `TERM=dumb`; else `colorprofile.Env`, which reads only the environment (`TERM`, `COLORTERM`, `CLICOLOR`, `CLICOLOR_FORCE`, `WT_SESSION`, `GOOGLE_CLOUD_SHELL`; no isatty, terminfo or tmux) |
| `Unicode` | false with `Options.ASCII`, `HARDN_ASCII` true or `Plain`; false when `TERM` is `linux` or `dumb`; false when the effective locale (first non-empty of `LC_ALL`, `LC_CTYPE`, `LANG`) has no UTF-8 codeset (`.UTF-8`, `.utf8`, any case; a bare `UTF-8` counts) or its language is `zh`, `ja` or `ko`; else true |
| `Theme` | `Options.Theme`, else a valid `HARDN_THEME` (an invalid value is ignored), else dark. `Dark` is false only for light |
| `Width`, `Height` | Each on its own: the terminal size when stdout is a terminal and the size is known, else `COLUMNS` / `LINES` when a positive integer, else `DefaultWidth` 80 / `DefaultHeight` 24 |
| `TTY`, `InputTTY` | As observed |
| `Animate` | stdout is a terminal, not `Plain`, and `TERM` is set, non-empty and not `dumb` |

`term.Detect` observes the process (isatty on stdin and stdout, the terminal size, `os.Environ`), calls `Resolve`, and only then, when `Theme` is `ThemeAuto`, both streams are terminals and the Env is not plain, calls `lipgloss.HasDarkBackground` once (§2.3). `term.Fixed(width, profile, unicode, dark)` builds an Env for tests and goldens without reading anything: height 24, no animation, and plain with no TTY when the profile is NoTTY or lower.

*Amended by `next/p7-surface`* (§3.14 approved 2026-10-17, §3.11 2026-11-04): `cmd/hardn` takes these flags and variables, as the table below maps them; the paragraph that follows is the state before it.

Once the maintainer approves refactor plan §3.14 (and §3.11 for the alias), they map onto `term.Options` and the variables `Resolve` already reads:

| Option field | Flag | Variable |
|---|---|---|
| `Color` (`term.ParseColorMode`) | `--color=auto\|always\|never`; the existing `--no-color` becomes an alias of `--color=never` with a deprecation warning (§3.11) | `NO_COLOR` (standard) |
| `ASCII` | `--ascii` | `HARDN_ASCII` |

## 8. Golden tests

**Matrices** (`pkg/ui/uitest`, from brief Phase 6):
- `uitest.Full()`, for components: 48 cells, colour {truecolor, 256, 16, none} × background {dark, light} × glyphs {unicode, ascii} × width {60, 80, 120}, the first axis varying slowest. - The gallery's play goldens alone: `go test ./internal/tools/uigallery -update`. Until `next/p1d-lint` the make target listed `./pkg/ui/...` only and left them out, though their header says "regenerate with make golden-update".
- `-update` is defined once, in `uitest`. A package that uses `uitest` must not define its own `-update` or link `github.com/charmbracelet/x/exp/golden`, which defines one too; the flag package panics on the second definition. Packages that do not link `uitest` reject `-update`, which is why `make golden-update` selects packages instead of passing it to `./...`.

**Notation.** A golden file starts with a three-line `#` header naming the test. Each cell is a section: a line `=== <cell>: <env>`, where the env text describes the whole `term.Env` (width, height, profile, background, glyphs, plain mode, and any field that differs from `term.Fixed`), then the output as the terminal receives it:
- control characters other than newline are Unicode Control Pictures (U+2400 plus the code; DEL is ␡), so ESC is the single character ␛;
- every output line ends with `$`, so trailing spaces stay visible, and header lines never do.

Golden rejects output it could not show unambiguously: invalid UTF-8, C1 controls, and the Control Pictures themselves (U+2400 to U+2421). Reading the SGR: `␛[38;2;R;G;Bm` and `␛[48;2;R;G;Bm` are truecolor foreground and background, `38;5;N` and `48;5;N` the 256-colour index, `30`-`37` and `90`-`97` the 16-colour foreground (`40`-`47` and `100`-`107` background), `1` bold, `4` underline, `␛[m` reset.

**Guards:** each cell renders twice and the two results must match; Golden stops if `RUNEWIDTH_EASTASIAN` makes x/ansi measure ─ as two cells; a line wider than the cell or holding a tab fails. On a mismatch the report names the changed, added and removed cells and shows a line diff of each, numbered by line of the golden file.

**Limit: stale goldens.** `uitest.Golden` reads and writes only the file of the case it renders, so a golden file whose case was removed or renamed stays behind, unread, and nothing fails (a refactor plan Phase 1A follow-up). That holds in `pkg/ui/nav`, `pkg/ui/form`, `pkg/ui/flow`, `pkg/ui/theme` and `pkg/ui/uitest`, and for the gallery's `play/` goldens. The component and screen goldens have catalogue checks, which fail for a file with no state or mock and for a state or mock with no file: the gallery's `TestCatalogueMatchesGoldens` against `fixture.States()`, and `screen.TestMocks` against `screen.Mocks()`. The legacy `pkg/menu` and `pkg/characterization` harnesses check nothing of the kind either (`pkg/menu` deleted since `next/legacy-rehome`). The manual check, after a case is removed or renamed: `git status --short` shows nothing after `make golden-update`; then delete the package's `testdata/golden` directory, run `make golden-update` again, and any golden file `git status --short` lists as deleted is stale (`git rm` it).

## 9. Components, screens and usage rules

### 9.1 Component conventions

`pkg/ui/component` holds the components; its package doc is the full statement of these rules, which every `next/p1b-*` unit follows.
- **Render context:** `component.NewCtx(env)` builds a `Ctx` holding the `term.Env` and the `theme.Theme` built once from it. The brief's `Render(vm, env)` is `vm.Render(ctx)`.
- **View-models** are exported structs of plain data (no funcs, actions or I/O handles) with a pure value method `Render(c Ctx) string`.
- **Output:** no line wider than the content width, `min(Env.Width, ContentWidth)`, which a bar fills; if `BarsFillContent` is refused, a bar fills the terminal's width instead. No trailing newline; no trailing space outside a painted background. The caller joins blocks with `SectionGap` blank lines.
- **Grid:** rows at `Indent`, the header and bars at column 0; a state glyph centred in the marker column (DEV-020); labels at `LabelCol`, values at `ValueCol`. Below `StackBelow` two-column layouts stack, values at `StackCol` (DEV-021).
- **Off a terminal:** `component.OffTerminal` is the render context of what is written off a terminal: plain mode at the default width, and `Whole`, under which nothing is cut and a bullet item does not wrap (DEV-067). `NewCtx` leaves `Whole` false, so "no line wider than the content width" holds on every screen.
- **Text:** view-model strings are shown as one line of plain text (escape sequences removed, control characters dropped or turned into spaces, trimmed), measured with `lipgloss.Width`, and cut with `Glyphs.Ellipsis`. Only prose wraps, at spaces, under its own first line: a `Message`'s text, a `Callout`'s body, an `InlineResult`'s text and a bullet item, which have the rest of their line to themselves (§9.5). Typographic quotes in view-model text, ‘ ’ and “ ”, are shown as ASCII `'` and `"` (C12, DEV-036); components add none. With the ASCII glyph set (`Env.Unicode` false) view-model text's ≥ ≤ ≠ … – — × → and • are shown as `>=` `<=` `!=` `...` `-` `-` `x` `->` and `*` as well, before the text is measured, so that 01-USER's "UID ≥ 1000" reads "UID >= 1000" on the terminals the ASCII set is for (DEV-036). A menu's keys, a prompt's hint, which lists the inputs it accepts, and an `ErrorReport`'s log path keep their characters: what must be typed or opened shows as it is. An answer an `AnsweredField` echoes says what was typed or taken, not what must be typed, so it is mapped, as the review's rows that sum the answers up are (§9.10); what a plan applies is code, which keeps its characters (below).
- **Code:** a diff's lines, a plan's target and commands, and captured output keep their characters, indent and quotes, typographic ones too, in both glyph sets: the ASCII map above does not apply, as a plan shows a file's line as it is (escape and control characters dropped, a tab as 4 spaces, and a character that draws as nothing or as a blank other than the space shown as its code point, such as `<U+200B>`); a command keeps its line breaks. Code is never cut: a line too long breaks at its last space after the indent, else inside a word, and each further piece starts with `Glyphs.Wrap`, then the spaces at the break (DEV-038, §9.6).
- **Degrading:** a bar's stub and fill are `Glyphs.Shade` at every profile, uncoloured without colour (`Env.HasColor` false; DEV-018); without colour a callout's accent bar is `Glyphs.Bar` and a badge is bracketed (DEV-015, DEV-019). At every colour profile a state has a glyph and a word, a callout's kind its title's word (DEV-032), or on a key-value row a marker beside the value that says it (DEV-034), even where Figma draws it in colour only. A value hardn could not read shows "Unknown" in `text.muted` (DEV-022; the maintainer, 2026-10-21).
- **Empty lists** render as the empty string, so the caller leaves out the block and its gap.
- **Goldens:** each state on `uitest.Full()`, in `pkg/ui/component/testdata/golden/<component>/<state>.golden`. A state is defined once, in `pkg/ui/component/fixture` (`fixture.States()`), which the tests and the gallery share (§9.14).

**Accepted inputs as data** (`pkg/ui/keys`, brief 1C's Bubbles `key.Binding` pattern). A `keys.Binding` names the inputs that select one choice (`Keys`, each a typed line such as `1`, `10` or `q`) and what it does (`Help`, the words after "to"). A `keys.Set` generates both:
- the hint, `Set.Hint`: the prompt's own inputs (bindings with no `Help`: a menu's items, a question's answers, a phrase) before the inputs every prompt shares (bindings with `Help`, such as `keys.Navigation`'s), each input once; in each part numbers first, in order, each run of two or more consecutive numbers collapsed into a range, then the other inputs in first-seen order; joined as "x, y or z": `0-10 or q`, Figma's main menu's since back is `0` only (P-25), and hardn's until `next/s2b-replace` removed item 6 (`0-5, 7-10 or q` since), `1-3, 5 or q`, and `bos-san-l01, 0 or q` for a phrase (since `next/p1c-nav`; before it every number came first);
- the help line, `Set.Help`: `q to quit`, `0 to go back, q to quit`;
- for a question, a Set with a `Default` binding, its answers as one term, the first default in capitals: `y/N`, `y/N, 0 or q` (§9.8).

(The other prompt this list held, a `y/N` confirmation with its default in capitals, was added by `next/p1c-nav`: `keys.Binding.Default` and the question's hint form `[y/N]:`, DEV-045, §9.8.)

### 9.7 Line reader (`next/p1c-reader`)

`pkg/ui/prompt` is the one reader every prompt in hardn uses (brief §2 and 1C); its package doc is the full statement. It renders nothing, so it has no goldens.

| Part | What it does |
|---|---|
| `New(in, tty)` | A `Reader` over `in`, with `tty` from `term.Env.InputTTY`. For stdin, `Stdin` |
| `Stdin()` | The process-wide `Reader` over `os.Stdin`, built on first use (`sync.OnceValue`) and the same at every call (added by `next/p1c-legacy-input`): the legacy menus, the first-run config prompts and the new screens (`nav.Prompter.In`) read through it, so stdin has one buffer and no line one reader took ahead is lost to another (plan risk R17). It asks whether stdin is a terminal as `term.Detect` does, by reading the terminal's attributes (`IsTerminal` in `github.com/charmbracelet/x/term` v0.2.2, `term_unix.go:14-17`: `TCGETS` on Linux, `term_unix_other.go:9`, and `TIOCGETA` on macOS, `term_unix_bsd.go:9`; build-tagged `tty_*.go`, no terminal elsewhere), so on Linux and macOS it agrees with `term.Env.InputTTY` without importing `term`, which links Lip Gloss |
| `ReadLine` | One line without its ending (`\n` or `\r\n`), otherwise as typed: nothing trimmed, nothing checked. A last line with no ending is returned, and the call after it reports the end. A line over `MaxLine`, 64 KiB (`bufio.MaxScanTokenSize`), is `ErrLineTooLong` and is dropped up to its ending, never cut short |
| `ErrAborted`, `ErrEndOfInput`, `ErrInterrupted`, `ExitCode` | The end of the input (Ctrl-D on an empty line, the end of a pipe or file) returns `ErrEndOfInput` and Ctrl-C `ErrInterrupted`; both wrap `ErrAborted`, and a caller tells them apart with `errors.Is`. `ExitCode` maps any abort to `ExitInterrupted`, 130, brief Phase 3's code for Ctrl-C; a caller that wants another code for the end of the input tests `ErrEndOfInput` first. `pkg/menu`'s legacy reads call it (`next/p1c-legacy-input`) |
| `Reraise` | Ends the process as Ctrl-C ends a program that does not catch SIGINT, for a caller that ends hardn on `ErrInterrupted` (added by `next/p1d-acceptance`): `signal.Reset(os.Interrupt)`, then SIGINT to the process, which dies of it; if it still runs 500 ms later, as when SIGINT is ignored, `os.Exit(ExitInterrupted)`. | `Flush` | On a terminal Reader, discards typeahead: the terminal's input queue (`TCFLSH` with `TCIFLUSH` on Linux, `TIOCFLUSH` with `FREAD` on macOS, nothing elsewhere; build-tagged `flush_*.go`) and the Reader's own buffer, which it keeps when the terminal flush fails. | `Ask(w, prompt)` | `Flush`, then the prompt and exactly one space in one write to `w`, the `Env.Writer` around stdout, then `ReadLine`. `PromptLine` ends at its colon (C8, DEV-029); the space puts the terminal's own cursor one cell after it. **Ctrl-C.** The terminal stays in cooked mode (DEV-042), so Ctrl-C is SIGINT. Only while `ReadLine` waits on a file does it relay `os.Interrupt` with `signal.Notify`; `signal.Stop` gives SIGINT back its default action, which ends hardn, before `ReadLine` returns, and an ignored SIGINT stays ignored. It waits with select(2) on the input and on a wake pipe, and reads only once the input is readable, so a call that Ctrl-C ends has read nothing, and no goroutine is left reading that could take the next line from the next call or from a process hardn runs. macOS's poll(2) does not support devices (poll(2), BUGS), hence select on both systems. Rejected:
- a goroutine reading ahead into a channel: it loses nothing, but after an interrupt its read stays blocked on the terminal, and a line it takes just before a flush can slip past the flush;
- `github.com/muesli/cancelreader` v0.2.2, already linked through Lip Gloss and ultraviolet: it cancels a read of a pipe or a terminal (a probe on a macOS pseudo-terminal named `/dev/stdin` took its kqueue path and cancelled), but on Linux epoll rejects a regular file (epoll_ctl(2), `EPERM`), so stdin redirected from a file fails (`cancelreader_linux.go:44-51`); its fallback for other readers drops the data of a read it cancels (`cancelreader.go:53-62`); a cancelled reader stays cancelled (`cancelreader.go:49-51`), so each call would need a new one; and it takes the descriptor with `File.Fd`, which sets the file to blocking mode.

A reader that is not a file, such as a test's `strings.Reader`, is read directly, as on systems other than Linux and macOS: there Ctrl-C keeps its default action.

**Typeahead.** On a terminal, what was typed during a long step, a line not yet ended included, is discarded before the next prompt (brief 1C). The same flush drops a late reply to the background query (§2.3) that has arrived by the first prompt, since it is pending input like any other; that case is not tested with a real reply.

**Without a terminal** (plain mode) the Reader needs nothing special: it never flushes, the end of the input aborts, and `Ask` ends each prompt's line. Whether hardn prompts at all without a terminal is `next/p3-output`'s (brief Phase 3: never prompt without a TTY).

**Stdin a terminal, stdout not** (`hardn | tee hardn.log`): brief Phase 3 rules out prompting only when stdin is not a terminal, but here the terminal echoes the answer and its Enter to itself, not to stdout, so the captured output holds neither and each prompt runs into what follows it. `Ask` does not end the line there, since that would put an empty line on the screen `tee` writes to; where hardn writes its prompts when stdout is not a terminal is `next/p3-output`'s.

**Echo.** The terminal echoes the answer in its own colour; a screen that shows it again uses `AnsweredField`, muted (DEV-043).

**The legacy menus** (`next/p1c-legacy-input`). *Since `next/legacy-dead`:* `ReadInput` and `Reader.AnswerNext` are deleted with the legacy menus that asked free-text questions (`a17955d1`, `eaa7e00b`); what follows of them is the record. `pkg/menu`'s `ReadKey` and `ReadMenuInput` each read one line with `Stdin().Answer(os.Stdout)`, and `ReadInput` with `Stdin().AnswerNext(os.Stdout)`, trimmed of spaces, a menu choice in lower case so that `Q` quits as `q`: a choice, `q` included, and a pause now take effect on Enter. On a terminal a menu choice and a pause discard typeahead first, since they follow long steps; a free-text question keeps it, as origin/main's one bufio reader did, since such questions come back to back (create-user's, the firewall profile's four fields), so answers pasted at once each reach their own. The first build flushed before `ReadInput` too, and dropped them; the Phase 1 acceptance audit found it (`next/p1d-acceptance`). `pkg/config`'s first-run prompts read through `Stdin` too, with `ReadLine`, and print nothing more, as their bufio readers did. On a terminal the first question, "No configuration file found. ...", `Flush`es before it is printed, since it can follow a long step (`LoadConfig` also runs mid-session, from the main menu's status and the user screens, and asks again while no file exists); the four that may follow it are asked back to back and keep what is typed ahead of them, as the bufio reader did. No `stty` runs, and no other reader is left on stdin; the exported `menu.ReadRawKey`, origin/main's raw-mode key read, which nothing but `ReadMenuInput` called, went with the `stty` calls. Each pause says "Press Enter ..." (DEV-050), and since `q` needs Enter there too, the legacy main menu's exit row and `style.Menu`'s default one say DEV-030's "q to quit" and "Tip: q to quit" (commit 56f0d93), so the four `pkg/menu` `main_menu/*` goldens changed on that line; no other words change. The legacy screens have no error path, so an abort ends hardn in the read itself, once the prompt's line is ended: Ctrl-C at any legacy prompt ends it by SIGINT (`Reraise`), the end of the input exits with status 130 (`ExitCode`), and any other read error is printed and exits with 1, as `cmd/hardn` does for an error. That includes Ctrl-D on an empty line at a pause, which now ends hardn with 130, where origin/main's `ReadKey`, in cbreak mode, read it as a key (0x04) and went on. At the config prompts Ctrl-C ends hardn by SIGINT too, and the end of the input still takes the default, as before. So where origin/main died of SIGINT (at a pause, a `ReadInput` prompt or a config prompt), hardn still does: a shell reports status 130, and a shell running hardn in a loop or a script stops, as it does for any program Ctrl-C ends. The first build exited with 130 instead, which a waiting parent sees as a normal exit, so `while :; do hardn ...; done` went on; the Phase 1 acceptance audit found it. The new screens will ask through the same `Stdin`, so the legacy screens stay reachable from them on one buffer.

### 9.8 Navigation grammar (`next/p1c-nav`)

`pkg/ui/nav` decides what each typed line does at a prompt, the same at every level (brief 1C), and asks until a line is accepted; its package doc is the full statement. The inputs are data in `pkg/ui/keys` (`Back`, `Quit`, `Navigation`, `YesNo`), defined once there because the components' tests use them and cannot import `nav`, and because `keys` imports only the standard library, so the legacy menus can use them without Lip Gloss. A `nav.Prompter` holds the render context, the one `prompt.Reader` over stdin and the `Env.Writer` around stdout. It renders nothing of its own: menus ask with `PromptLine`, questions with `AnsweredField` (no answer yet, so the line reads as Figma draws it once answered), and a refused line with `InlineResult` (a `Message` until `next/s2-row-grammar`), so no Lip Gloss helper applies.

| Line | At | Does |
|---|---|---|
| a number | a menu (`Choose`, `Run`) | selects the item with that key |
| `0` | every prompt | goes back (`ErrBack`); at the top level, exits. On a menu `0` is also the Exit or Return item's number, shown as "0)". Back is `0` only (P-25, decided 2026-10-17) |
| `q` | every prompt | quits hardn (`ErrQuit`, returned level by level to the top) |
| `y`, `yes`, `n`, `no`, or Enter | a y/N question (`Confirm`) | the answer; Enter takes the default, the capital in the hint |
| the phrase | a typed confirmation (`Typed`) | confirms: exactly, case included |
| any other line | a free-text question (`Text`) | the value, the white space around it removed; `b` too, an ordinary line at every prompt |
| end of input, Ctrl-C | every prompt | aborts (`prompt.ErrAborted`, exit 130), never back |
| anything else | every prompt | a failed `InlineResult` under the prompt (⨳, `(x)` in ASCII, and the words in `status.bad`, no word for the kind; DEV-062), then the prompt again; nothing above is drawn again |

Lines match as `keys.Set.Match` compares them: the white space around a line ignored, letters in any case, numbers as typed (`01` is not `1`).

**Hints**, generated from what each prompt accepts, list the prompt's own inputs, then the navigation inputs, so these end every hint alike (DEV-044, DEV-045): the main menu `[0-5, 7-10 or q]` (Figma's own `[0-10 or q]` until slice 2b's unit (d) removed item 6, its key left unused) and a sub-menu `[0-2 or q]`, Figma's own (with item 1 disabled, `[0, 2 or q]`), a y/N question `[y/N, 0 or q]` (`[Y/n, 0 or q]` when yes is the default), a typed confirmation `[bos-san-l01, 0 or q]`, free text `[0 or q]`. On a menu `0` is one of the menu's own keys, the Exit or Return item's, so it is not repeated.

**Decisions:**
- **0 and q at every prompt**, as brief 1C ("the same at every level") and the plan's p1c-nav row ("identical back/quit on the main menu, a sub-menu and a workflow step") have it. **Back is `0` only**, by the maintainer's decision of 2026-10-17 over brief §1C, whose grammar, and the plan's row after it, had `b` go back too: origin/main and v0.3.2 never read `b`, and every Figma hint is "[0-N or q]" (P-25). So `b` is an ordinary line: a menu and a y/N question refuse it as any input they do not take, a typed confirmation compares it with the phrase, and free text takes it as a value (`TestBIsALine`). A `0` typed at a y/N question goes back, and is never taken for "no". The first build took `0` as back on menus only; that narrowing changes the brief's meaning, so it is now P-25 (b)'s alternative for the maintainer.
- **Back at the top level** exits, so `0` is accepted and shown on the main menu too, as the Exit item's number: no input is accepted that its hint leaves out (DEV-044).
- **q from a sub-menu quits hardn**, as brief 1C decides; in origin/main it returned to the parent menu ([interaction.md](../refactor/phase0/interaction.md) §5, anti-pattern 7), so a user who types `q` from habit there now leaves hardn (DEV-044).
- **Free text:** `0` and `q` navigate there too, so a value can never be `0` or `q`, and the hint `[0 or q]` says so; `b` is a value as any other line. Linux allows the user name `q`, which hardn's forms cannot create; a user named `b` they can. origin/main's free-text fields take no `0` as a value (their numbered prompts start at 1, and one already takes "0 to cancel", interaction.md §5, anti-pattern 7). That changes meaning, so it is built pending P-25 (a).
- **Explaining the navigation inputs:** only the main menu's Exit row says "q to quit" (DEV-030); nothing says what `0` does, and in the brackets where `[y/N]` lists answers, `1. Username [0 or q]:` can read as if the name must be one of them. Built as it stands, pending P-25 (e), which offers a help line (`keys.Set.Help`: "0 to go back, q to quit") or a hint that sets the navigation apart.
- **A typed phrase** is shown as the answer the hint offers, and always whole: the prompt cuts the label first, and `Typed` asks only when the whole hint shows after some of the label. Otherwise it returns `ErrPhrase` before writing anything, and the caller asks with a shorter phrase or label (P-10); `CheckTyped` returns the same error without asking, so that a caller writes nothing above a prompt that is never asked (added by `next/p1c-flow`). With the label "Type the hostname" that is a phrase of up to 48 cells from 64 columns up and 44 at 60 in Unicode glyphs, 46 and 42 in ASCII (`TestTypedWhole`); Linux allows a hostname of 64 bytes (`HOST_NAME_MAX`), so a long one needs another phrase, such as its first label. `CheckPhrase` refuses, at any width, a phrase that is empty, not printable ASCII (components drop control characters and map typographic quotes, C12, so it would show other than it must be typed), has a space at either end, is `0` or `q` in any case (it could never be typed; `b` is a phrase, since back is `0` only), or holds a comma, a slash, a bracket or " or " (the hint would read two ways). The layout is built pending P-25 (d).
- **A disabled item** stays out of the hint, as P-22 has it; its key typed anyway is answered "<Label> is unavailable.". `nav` decides which items are shown as the menu does (`component.MenuItem.Shown`).
- **An item the session rules out** (`nav.Option.Refusal`, since `next/s2b-replace`) stays shown and in the hint: asked as the item is chosen, before its action, a reason refuses the line under the prompt in its words, as an invalid one is, and the prompt is asked again, nothing drawn again. pkg/menu's main menu refuses User Management and Backup so under plan only, "Not available in plan only." ([dryrun-replace.md](../engine/dryrun-replace.md) §3). *Since `next/s3-replace` (slice 3, decision 10), User Management alone: Backup's screen opens, each change stopping at its plan.*
- **The end of the input** aborts at every prompt and never goes back, so a script that runs out of answers ends as an abort rather than unwinding to the top and exiting 0.
- **Words:** origin/main's "Invalid option. Please try again." on a menu; new (P-25 (c)): "<Label> is unavailable." for a disabled item, "Invalid answer. Please try again." at a y/N question and for the one line free text refuses (longer than `prompt.MaxLine`), and "That does not match exactly. Please try again." at a typed confirmation. That one does not repeat the phrase: the prompt under it shows the phrase whole, while the message's prose would then wrap at a hyphen inside it (x/ansi `wrap.go:270-276`: a hyphen is always a breakpoint; prose breaks at spaces only since 2026-11-10). The labels of confirmations are the flow's (P-10).

**Menus bound to actions.** A `nav.Menu` pairs each `component.MenuItem` with its `Action` (`nav.Option`), after arch3's option ↔ action binding (refactor plan §6), as an idea only. The one list gives the items rendered (`View`), the accepted inputs and their hint (`Accepts`), and the dispatch, which matches against the same bindings the hint comes from, so no key reaches an action the menu does not show (origin/main's hidden options, [interaction.md](../refactor/phase0/interaction.md) §1 item 4). `Check` refuses a shown item with no action, a key that is not a whole number from 1 or is used twice, and an exit item not numbered 0. `Run` draws a menu screen (what is above the menu, the menu, then the prompt after `PromptGap`), asks, and runs the chosen action, until the user goes back (it returns nil) or quits (`ErrQuit`); the next round draws again below what the action wrote, clearing nothing. Once any prompt has been asked (`prompt.Reader.Asked`), each drawing starts after `SectionGap` blank lines, so a sub-menu stands apart from the answer that opened it and the menu drawn again from the result above it; only the first drawing of a run starts at once. An action starts on the line under its answer, so one that writes, such as a result `Message` or a flow's first step, writes the gap first, as `Run` does.

**Tested.** Matching and `Check` table-tested; the loops on scripted input, a typist that echoes each line as a terminal would: `TestGrammar` puts `0`, `q`, `Q` and the end of the input to a main menu, a sub-menu, a y/N question, a typed confirmation and free text, and `TestBIsALine` `b` and `B`, which the menus and the y/N question refuse, the typed confirmation compares with the phrase and free text takes as a value; `TestRun` nests a sub-menu, goes back and quits from it; `TestRunGap` checks the gaps of a nested run; `TestTypedWhole` every phrase length from 1 to 64 at 40, 60, 64, 80 and 120 columns in both glyph sets, `CheckTyped` refusing exactly what `Typed` refuses. Goldens on `Core()`, each asked a line it refuses: `nav/main-menu` (left with `0`, which exits), `nav/sub-menu` (a disabled item; left with `q`), `nav/workflow-step` (free text, then y/N, left with `0`), `nav/typed-confirmation` (left with `q`) and `nav/rounds` (a result, the menu again, a sub-menu left with `0`, then `q`): so `0` and `q` are on record on the main menu, a sub-menu and a workflow step alike. No real terminal was used: the reader's own tests cover the terminal (§9.7).

**Open for later units.** `next/p1c-form` asks its fields with the same loop, exported as `Prompter.Ask`, and refuses a value its validation rejects with `Refuse` (`RefuseFor` since `next/s2-row-grammar`, which keeps a `Warn` refusal's kind), so a validation error looks like any refused line, an `InlineResult` since `next/s2-row-grammar` (§9.9); `next/p1c-flow` words the confirmations, chooses y/N or typed per step, picks a phrase `Typed` can show whole, and writes the gap before its first step (built: §9.10); `next/p1d-slice` composes what `Run` draws above the menu, including the title bar sub-screens open with (brief 1C's breadcrumb, which P-08 put inside the bar, off by default), as `Screen.Above`, and added `Screen.Compact` for the main menu's two-column menu, drawn on the line under the heading (built: §9.12); `next/p3-output` decides the exit codes of a quit and of a script that ran out of answers.

### 9.9 Forms (`next/p1c-form`)

`pkg/ui/form` collects a flow's answers, the Collect step of brief 1C's canonical flow, after huh's patterns, none of huh imported; its package doc is the full statement. A form only collects: it has no actions, so no prompt is interleaved with a change, and the caller acts on the answers only once `Run` returns nil.

| Part | What it is |
|---|---|
| `Form{Fields}`, `Run(p nav.Prompter)` | The fields asked in order. nil once the last is answered; `nav.ErrBack` when the user goes back from the first field asked; `nav.ErrQuit`; `ErrAborted` (`prompt.ErrAborted`) at the end of the input or Ctrl-C; `ErrField` for a field that cannot be asked (a nil field, no `Value`, no title, a `Select` with no options or an option with no label). On any error every `Value` is put back as it was before `Run` |

| `Text` | Free text: the line without the white space around it, an empty line giving `Default`. `0` and `q` navigate there too (P-25 (a)); `b` is a value |
| `YesNo` | A y/N question (`keys.YesNo`): y, yes, n or no in any case, an empty line giving `Default`, the capital in the hint |
| `Select[T]`, `Option[T]` | A numbered choice the form collects: `Options`, or `OptionsFunc` called each time, listed as a menu's items keyed from 1; the number of one is taken, at a prompt that asks "Option", as a menu's does. Lip Gloss helpers: none, as for `Menu` and `Message`: spans, `lipgloss.Wrap`, then `Menu` |

**One field structure** (DEV-046; brief 1C: one structure, defined by Figma, for every kind of field). A text field refused by its validation, then answered; a choice with a head; a y/N question whose default Enter took. Plain, with the trailing spaces after an empty answer left out:

```text
0 2 4 6
   1. Username [0 or q]: George
  (x) Username must start with a lowercase letter and contain
      only lowercase letters, numbers, hyphens, and underscores
   1. Username [0 or q]: george

   2. Select a user

   1) george
   2) alice

   2. Select a user: alice
```

- **Asked on one line** when the field has neither description nor options, and the line shows its question and hint whole (`AnsweredField.ShowsWhole`): an `AnsweredField` with no answer, as `nav` asks a question and as Figma draws its form.
- **Asked on a prompt line of its own** when it has either, or when the one line would cut its question: the `FieldHead`, `PromptGap` blank lines, then a `PromptLine`. A `Select`'s says "Option", as every menu's does (P-29 (a); Figma's frames say "Enter your choice", origin/main's "Enter selection"); a text or y/N field's has no label, since the question is the line right above and no Figma or origin/main screen words such a prompt. Its hint is the field's inputs, then the navigation's. The prompt must be the last line written, so whatever a field shows besides its question goes above the prompt.
- **Narrow terminals and long titles:** on one line the hint is kept whole and the question is cut first, then dropped, so the form moves such a question under its head, where the title has the content width to itself: at 40 columns "Grant sudo privilege?" is asked as `   2. Grant sudo privilege?`, a blank line, then `  > [y/N, 0 or q]:`; and so, below 64 columns, is origin/main's "Enter new username (leave empty to keep current)" in a numbered form, which from 64 fills its one line with `[0 or q]:` exactly. The title is still one line, cut when even that is too narrow (below 27 columns for "Grant sudo privilege?"), so words a user must read whole, such as what a default is, belong in the `Description`, which wraps. `TestNarrow` checks the create-user form at every width from 20 to 130. A form can so mix one-line fields and fields under a head; at the core widths, 60 and 80, every field of Figma's form is one line.
- **Refused:** a line the field does not take, in `nav`'s words ("Invalid answer. Please try again." at text and y/N, origin/main's "Invalid option. Please try again." at a choice), or a value its `Validate` rejects, in the validation's words (such as origin/main's username rule), is answered under the prompt by a failed `InlineResult`, ⨳ (`(x)`) and the words in `status.bad`, no word (the maintainer, 2026-10-22; DEV-062), and the prompt alone is asked again: the head is not written again (brief 1C: re-ask only that field, keeping context). A value `Validate` refuses with `nav.Warn`'s error, valid but not taken, such as a nameserver already configured (origin/main's warning), is answered by a warning one, in `status.warn`. This is `nav`'s loop, exported as `Prompter.Ask`, with `RefuseFor` for the validation's error, which keeps `Warn`'s kind; the inline result has no `Field` slot: its colours are `Inline.*`.
- **Answered:** the terminal's echo shows the answer (DEV-043). The form writes the field again as an `AnsweredField` with the answer, muted, under it only when the line typed does not read as the answer: after a prompt line of its own, where a `Select`'s echo names the option rather than its number, and after an empty line that took a default (DEV-047). The echo keeps a y/N's `[y/N]` and drops the navigation, as Figma's answered line shows `(y/n)`.
- **Numbers:** in a form of more than one field, by place among the fields asked, so a skipped field takes none and the numbers run on (DEV-047). Every field asked is numbered, even when `Skip` leaves only one: its number is shown as it is asked, before the later fields' `Skip`, which may read its answer, can tell. A form of one field is unnumbered, as Figma's single questions are (USER-MANAGE_SUDO-CONFIRMATION, SSH_LOGIN-TOGGLE_CONFIRMATION).
- **Gaps:** `SectionGap` blank lines before each field once any prompt has been asked (`prompt.Reader.Asked`), as Figma spaces its form and as `nav.Run` sets a drawing apart, so a form run by a menu's action starts apart from the answer that chose it. Before any prompt, `Run` cannot tell whether anything stands above its first field and writes no gap there. So the rule for `next/p1c-flow` and `next/p1d-slice`: a caller that draws something above a form, such as the "Create User" title bar Figma sets a blank line under, ends it with `SectionGap` blank lines itself when `Asked` reports false, and leaves them to `Run` when it reports true.
- **Choices: menu or form.** A choice that opens a screen of its own is a `nav.Menu` screen, drawn as Figma draws one (an underlined `MenuHeading`, the items, "0) Return", the prompt; hardn's heading "Select an option" and prompt "Option", P-29 (a)): Figma's "Select a user" (USER-MANAGE_USER-SELECT_USER), whose choice opens that user's management menu, is one, built in `next/p1d-slice`. `form.Select` is for a choice a flow collects and acts on after its review, such as origin/main's "Select a key to remove" (pkg/menu user_options.go:502), which no Figma screen draws. It keeps the form's field structure: its title is a field's question, numbered with the others, not a menu heading; Figma's blank line between heading and items is kept; it has no Return row, since `0` in a form goes back to the field before; and its prompt says "Option", as a menu's does (P-29 (a)).
- **Plain mode** (huh's accessible mode): the same definitions through `term.Env`, with no colour, ASCII glyphs and nothing animated (the `plain-80` cell of every form golden).

**Values and navigation:**
- A `Value` is bound as soon as its field takes a line, so a later field's `TitleFunc`, `OptionsFunc` and `Skip` read the earlier answers from the caller's own variables. On any error every `Value` is put back as it was before `Run`, and a skipped field is put back each time it is skipped, so an answer given on a path the user then left does not stay.
- `0` goes back to the field asked before, asked again from the start: its earlier answer stays on screen above, but Enter takes the field's `Default`, not that answer. From the first field asked, it leaves the form (`nav.ErrBack`). Built pending P-26 (a) and (b). `q` quits and the end of the input aborts from any field.
- `Skip` is called again when back returns to its field, so it should read only the fields before it and the host.
- A text field's `Default` shows before the answer only where the screen's words say so, as origin/main's labels do; the echo shows it after. Built pending P-26 (c). A title is one line: "Enter new username (leave empty to keep current)" shows whole as a numbered field's title from 54 columns: beside the hint it needs 64 cells, so it is asked under its head below 64 columns and on its one line from 64; but "Enter filename to export system status (default: system_status.txt)", 67 cells, never does under the 64-cell content cap, so a screen that must show such words whole puts them in the `Description`.
- `Validate` may read the system, such as whether a user exists, and must change nothing.

**Tested.** Scripted readers, a typist echoing each line as a terminal would (as `nav`'s tests): Figma's create-user form answered as Figma shows it; a value refused by its validation, then fixed, at a text field with a head (the head written once), a y/N question and a choice; refusals in `nav`'s words; defaults taken by Enter and their echo; skip rules, a skipped field put back and the numbers running on; `TitleFunc` and `OptionsFunc` called again after back; `0`, `q` and the end of the input at every field of the form, with every value put back on failure, and `b` a text field's value and refused by a y/N field; fields that cannot be asked (`ErrField`, nothing written for them, a nil field included); a failed write at the prompt (the reader's), and at the gap and the echo (the form's own, `form: write`); when a field is asked on one line and when under its head (`TestLayout`, a description that shows nothing staying on one line, and origin/main's long label under its head at 63 columns and on its line at 64), and the create-user form at every width from 20 to 130 (`TestNarrow`). Goldens on `Core()`: `form/text`, `form/text-description`, `form/yes-no` and `form/select` (its options set apart and its prompt labelled since the review fixes), each asked, refused and answered; `form/create-user`; `form/back` (back from field 3 to 2, whose new answer skips 3, so the key question is 4). No real terminal was used: the reader's own tests cover the terminal (§9.7).

**Open for later units.** `next/p1c-flow` runs a form as its Collect step, then reviews the answers (Figma's "User Configuration" list), plans and confirms; the confirmation Figma numbers as a form's last field ("5. Create user 'george'?") is the flow's Confirm step there, unnumbered (P-10, §9.10). Whether hardn prompts at all without a terminal, and whether a form then echoes each answer for a log, is `next/p3-output`'s. No screen uses a form before `next/p1d-slice`.

### 9.10 Canonical flow (`next/p1c-flow`)

`pkg/ui/flow` runs brief 1C's canonical action flow, which every action that changes the system follows: Collect, Review, Plan, Confirm, Apply, Return. Its package doc is the full statement. It renders nothing of its own: each step is written as components, through the `Prompter`'s writer (`Env.Writer` around stdout), and asked through its reader, so no Lip Gloss helper applies.

| Part | What it is |
|---|---|
| `Flow{Form, Review, Engine, Confirm, DryRun}`, `Run(ctx, p nav.Prompter)`, `Check(ctx)` | One action. `Run` returns an `Outcome` once a result is on screen, with a nil error unless writing it failed, so a menu's action carries on after a failure; and `NotRun` with an error when the flow ends before a result: `nav.ErrBack` from the form's first field, `nav.ErrQuit`, `prompt.ErrAborted`, the context's error before Apply, `ErrFlow` (no `Engine` or `Confirm`, or a typed confirmation with neither label nor question), `form.ErrField`, `nav.ErrPhrase` (a phrase `CheckPhrase` refuses), a failed write. | `Outcome` | `NotRun`, `Applied`, `Failed` (planning or a step), `Cancelled` (declined, or too narrow to confirm), `Planned` (dry-run), `Unchanged` (no changes), for `next/p3-output`'s exit codes |
| `Review{Notice, Title, Items}`, `Notice{Callout, Items}` | The Review step, built from the answers once collected: the action's notice, if any, a `Callout` and its checklist as bullet items outside the bar, as Figma's Warning before disabling root SSH login; then a `SectionHeader`, `SectionGap` blank lines and a `BulletList` of `KeyValue` rows, as Figma's "User Configuration"; then the plan's findings as the section's last rows (`next/s2-flow-review`, DEV-063). | `Plan{View, Risk, Findings}`, `Plan.Typed` | The `PlanView` and the risk class, `RiskLow` (y/N) or `RiskLockout` (typed: lockout risk, and Run All); a plan with a lockout-risk change is typed whatever its class, so it never asks less than it shows; and the plan's findings (`next/s2-flow-review`) |

| `Fixture` | An `Engine` that touches nothing: a fixed plan, applied by reporting each step, failing at `FailAt` with a `Failure`. Phase 1 runs only on it; nothing in the package reads or changes the system |

**Decisions** (DEV-048, DEV-049; P-27 puts the flow's own to the maintainer):
- **Collect** is the form, run to its end before anything is planned, so no prompt is interleaved with a change.
- **Review:** the action's `Notice`, such as Figma's Warning and checklist before disabling root SSH login, then the answers' section; both built after the Collect step. The title bar and a subject line such as "Managing sudo method for: george" name the screen, so the workflow screen draws them above the flow (`next/p1d-slice`). **The plan's findings close it** (`next/s2-flow-review`, slice 2's decision 5, DEV-063): the Engine plans before the review is drawn, so that the review and its findings are one block, one write, then the plan follows; each finding is one more row of the section, or with no rows a list of its own after the gap, and every path that reaches the plan lists them, a dry run and a plan with nothing to change included.
- **Plan:** dry-run stops after the plan, whose footer says "No actual changes were made to your system." (origin/main's). A plan with no changes says "Nothing needs changing." (brief Phase 3's words), an info `Message`, muted prose since P-42, and asks nothing (P-27 (b)). A plan that cannot be made is an `ErrorReport` with nothing rolled back. The plan follows the review with no heading of its own (P-27 (c)).
- **Confirm:** a y/N question is asked as a one-field form, unnumbered, its default no, so an Enter that took the default is echoed (DEV-047); Figma numbers it as the form's fifth field, but it now comes after the plan (DEV-048, P-10). A plan `Typed` reports is confirmed by typing the phrase (`nav.Prompter.Typed`, P-25 (d)), under the action's question, which keeps its line (a `FieldHead`, then `PromptGap` blank lines), so the label stays short; one with no phrase is refused with `nav.ErrPhrase`, never asked as y/N. A phrase too long to show whole at the width, such as a hostname over 48 cells at 64 columns (§9.8), is asked by the short phrase the action gives, `Confirm.Short`, such as its first label; the flow never cuts a phrase itself, so 192.0.2.123 is never confirmed by 192. When neither shows, for "Type the hostname" and "bos-san-l01" below 27 columns in Unicode glyphs and 29 in ASCII and plain mode, nothing is asked or written for it: "Operation Cancelled" says "The terminal is too narrow to confirm. Widen it and try again.", and `Run` returns `Cancelled` with no error, so the menu carries on (P-27 (e)). Every check is made with `nav.Prompter.CheckTyped` before the gap is written. n, and 0, decline: Figma's "Operation Cancelled" callout, nothing applied (P-27 (a)); q quits and the end of the input aborts.
- **Apply:** one step per change, titled by it. With `Env.Animate`, and a block shorter than the terminal (a line per step, two where the rows stack), the `StepProgress` block is drawn in place, moving up over it with CPL and erasing each line with EL, the spinner turning every 100 ms while a step runs; otherwise each step's row is written once it settles, done, failed or skipped, on the whole list's status column (`StepProgress.Row`; DEV-049, P-27 (d)). Steps never reached after a failure are skipped. Then Figma's "Operation Successful" callout, or an `ErrorReport` naming each change reported rolled back, in the order undone, its rows on the steps' status column (DEV-040, P-42 R4). A step whose title `StepProgress` would leave out, such as a zero-width space alone, is titled "Unknown", as `PlanView` shows the change. The terminal's echo stays on, so an Enter typed while a step is drawn in place moves the cursor and leaves the block's first line stale above the redrawn steps: a terminal limit (DEV-049), whose remedies P-27 (d) puts to the maintainer.
- **Return:** `Run` returns; nothing is cleared, and no continue prompt is asked (P-09): `nav.Run` draws the menu again under the result, its status read again.
- **Gaps:** each block after `SectionGap` blank lines once anything stands above it (a prompt asked or a block written), as for a form (§9.9): a caller that draws a title bar above a flow that asks nothing first ends it with the gap itself while `Asked` is false, and checks the flow (`Check`) before it draws.

### 9.14 Gallery (`next/p1d-gallery-components`, `next/p1d-gallery-screens`, `next/p1d-gallery-playable`)

`internal/tools/uigallery` is brief 1D's dev-only gallery; its package doc is the full statement. It shows the components and, with `-screens`, the screen mocks, and `play` runs the screens on a simulated system (**Playable mode**, below); `status` lists the main menu as the real checks read it from simulated hosts (**The status hosts**, below). Its `compare` mode, P-42's mock of Figma's row grammar beside the pattern the components drew (`next/p3-gallery-engine`), was removed in `next/s2-row-grammar`, once the components drew the grammar the maintainer chose on 2026-10-22 and its two sides were alike; git keeps it, and its helpers serve the `glyphs` mode (`draw.go`).

**What it shows.** Every state of `fixture.States()` (`pkg/ui/component/fixture`): the 154 states of the 27 components that the component goldens pin (§9.11), in that order, each under a `SectionHeader` with its name. The goldens and the gallery take the states from that one place, so the gallery cannot show anything the goldens do not hold. `TestCatalogueMatchesGoldens` fails for a golden file with no gallery entry or an entry with no golden, and the fixture package's `TestEveryComponent` fails for a type of `pkg/ui/component` with a `Render(Ctx) string` method and no state. Moving the states there left every golden byte-identical.

**Screens** (`next/p1d-gallery-screens`, brief 1D). With `-screens` the gallery shows `screen.Mocks()`, the catalogue the screen goldens pin (§9.12), by layout, then by screen. Each mock comes under a `SectionHeader` with its name, then an info `Callout` holding its source label, the origin/main-vs-v0.3.2 delta and what waits on a proposal, then its drawing. A workflow's mock is its sequences: each step under a header naming its sequence and step, such as `failure/2-failed`, printed in order, so that a sequence reads as the transcript of one run, non-interactively; a step's own blank lines, which set it apart from the step before, give way to the header's. A sequence that ends otherwise at the width than it says (`screen.Diverged`), as one whose typed confirmation the terminal is too narrow to ask, is printed whole under a header with its name and a note naming the cell and how it ended, and the other mocks still show: below 27 columns (29 in ASCII) the root-login toggle's and the sudo change's `typed` sequences show the flow's "too narrow to confirm" cancellation. A step is drawn by playing its sequence (`Sequence.Play`): scripted answers on a `flow.Fixture` plan, which read no terminal and change nothing. `TestScreensRenderAsGoldens` holds every drawing to its golden file in each golden cell the flags can name (the core set, and the main menu at 80x40 on both themes and at 60x40); `screen.TestMocks` holds the catalogue to the golden files.

**Environment.** Each one is built with `term.Fixed` from the flags alone (height 24 unless `-height` says), as the goldens build theirs (play's size alone may come from the terminal, below); `TestMatrix` holds `-matrix`'s cells to `uitest.Full()` and `uitest.Core()`'s plain cell. Each state is written through that environment's `Env.Writer` to stdout in one write: byte for byte what its golden file holds for the same cell, under the gallery's header (`TestRendersAsGoldens`, every state in every cell of `Full()`). Usage errors exit 2, a failed write or a bad override file 1, and so does a true `RUNEWIDTH_EASTASIAN` (below).

**Colour iteration** (brief 1D). `-override FILE` reads a JSON file of new token values for one run, per palette: a token name as §4.1 names it, and any of a truecolor hex, an xterm-256 index and a 16-colour index; what is left out keeps the palette's value. The file is decoded strictly (no unknown field, one JSON value) and both palettes are checked before anything renders. A `comment` field holds free text.

```json
{
  "comment": "why these values",
  "dark":  {"text.faint": {"hex": "#565B6B", "256": 59, "16": 8}},
  "light": {"text.faint": {"hex": "#81869C"}}
}
```

- **The hook** is `theme.NewWithOverrides(env, overrides)`: the theme `New` builds, from a copy of the palette with the overrides in place. It errors on an unknown token or a value out of range, and never changes the palettes.
- **Production code cannot reach it.** `TestOverrideReach` (in `pkg/ui/theme`) parses every Go file of the module, test files included, and fails if one names `NewWithOverrides`, `Overrides` or `TokenOverride`, under any import name, unless it is in package `theme` in `pkg/ui/theme` or in package `main` in `internal/tools/uigallery` (or their external test packages). A subdirectory of either does not count: a package there could pass the hook on, as module-root `internal/` is open to the whole module (`TestStrayUses` has such a package in each). With nothing in `cmd/hardn` referring to it, the linker leaves the hook out of the release binary, and the file-reading code lives only in the gallery.
- **The file stays local.** The repository commits only the template, `internal/tools/uigallery/uigallery.local.json.example`; a copy named `uigallery.local.json` is ignored by the allow-list `.gitignore` (`git check-ignore -v` names rule `*`; the template matches `!*.example`).

**Never released.** Every build target builds `./cmd/hardn` alone: the makefile's `build`, `linux`, `darwin`, `arm`, `dev`, `dev-build` and `check-cross`, and `deb` and `rpm` through `linux`; `go build ... ./cmd/hardn` in `.github/workflows/release.yml`'s build job (`CGO_ENABLED=0`, `-trimpath`, `-tags=netgo`; linux/amd64, linux/arm64, darwin/amd64); and `go build -o build/hardn ./cmd/hardn` in `ci.yml`. `go list -deps ./cmd/hardn` holds neither the gallery nor `pkg/ui/component/fixture`, and a main package cannot be imported. `make check` compiles, vets, tests and lints the gallery (`go build ./...` discards what it builds, and `check-cross`'s `go vet` for Linux writes no binary), as CI's `go test ./...` runs its tests; depguard's `dev-tools` rule keeps any package outside `internal/tools` from importing one inside it (§9.15).

**What it touches.** Its own code reads only its flags, the override file and, in play, stdin and the terminal's size: no root, nothing under `/etc`. The components and `-screens` read no environment variable and query no terminal for their output. Play, only where `-width` or `-height` is not given, calls `term.Detect` once to size itself, giving it the dark theme so that it never queries the terminal's background: Detect asks whether stdin and stdout are terminals (`IsTerminal`), reads the size of the terminal stdout is (`GetSize`, the `TIOCGWINSZ` ioctl) and `os.Environ` (`COLUMNS` and `LINES` serve a terminal whose size it cannot read), and play takes the size alone of what it resolves. Play reads stdin through `prompt.Stdin`, the line reader every hardn prompt uses (§9.7), which asks whether stdin is a terminal by reading its attributes (`TCGETS` on Linux, `TIOCGETA` on macOS), on a terminal discards typeahead before each prompt (`TCFLSH` or `TIOCFLUSH`), and while it waits for a line relays Ctrl-C (`signal.Notify`, waking its `select(2)` through a pipe of its own), giving `SIGINT` back its own handling before it returns; it never changes the terminal's mode. The package initialisation of Lip Gloss and x/ansi still runs in it, as in every binary that links Lip Gloss (§2.3: today the `pkg/ui` test binaries and this gallery; `cmd/hardn` links none): an `ioctl` on stdout and, on a terminal, a terminfo read (and `/etc/passwd` without cgo) and `tmux info` under tmux, all read-only, and x/ansi's read of `RUNEWIDTH_EASTASIAN` ([side-effects.md](../refactor/phase0/side-effects.md) §13.1). Since play runs the engine (`next/p3-gallery-engine`), it also links `github.com/fatih/color`, whose initialisation reads `NO_COLOR` and `TERM` and asks whether stdout is a terminal (an `ioctl`), and the engine's code reads, at run time, the process's effective uid (`pkg/host/backup`'s trust check), the real clock (a backup manifest's time, the journal lock's wait) and `crypto/rand` (a change id's suffix): all read-only ([gallery-engine.md](../engine/gallery-engine.md) §2.8). The gallery ignores the profile Lip Gloss detects. The variable is the one init effect that changes output: when it is true, x/ansi measures ambiguous-width glyphs such as `─` and `…` as two cells, and every layout moves off its golden. So the gallery, like `uitest.Golden`, checks that `─` measures one cell and otherwise refuses to render (exit 1, a message naming the variable, no output); `-list` still works (`TestEastAsian`, which runs its test binary again with the variable set). *Since `next/legacy-rehome`:* fatih/color is gone; colour comes from `pkg/ui/term`, and console lines are messages on stderr.

### 9.15 Usage rules (`next/p1d-lint`)

The rules for code that shows anything to the user or reads from them. The import rules below enforce what an import can show; the tests named, and review, hold the rest.

- **Screens are built from the layouts and the components.** A screen is one of the three layouts of §9.12 filled with a view-model of plain data; a screen that fits none is a proposal for a new layout in [proposals.md](../refactor/proposals.md), never a one-off. Feature code fills view-models: it picks no colour, glyph or column.
- **No raw ANSI and no Lip Gloss outside `pkg/ui`.** Colours and attributes come from the theme's slots, glyphs from `theme.Glyphs`, columns and gaps from the grid constants (§4 to §7). Inside `pkg/ui` too a component hard-codes no colour, glyph or escape sequence: a missing one is added to `pkg/ui/theme` first (below). Widths are measured with `lipgloss.Width` or x/ansi, never `len()`.
- **Input only through `pkg/ui/prompt`:** the one `Reader` over stdin, `prompt.Stdin()`, which the new screens reach through `nav.Prompter` and `form` (§9.7 to §9.9). Never `os.Stdin`, another `bufio.Reader` on it, `stty`, raw mode or a key read: every input is a line ended by Enter.
- **Output only through `Env.Writer`.** A renderer is a pure function of its view-model and `component.Ctx`: it returns a string and does no I/O, reads no clock and no environment variable. The caller writes the string through `term.Env.Writer(w)`, `w` the `io.Writer` it was handed (stdout in hardn), one whole string per write. Never `os.Stdout` directly, `fmt.Print*`, or Lip Gloss's `Print*`, `Fprint*` and `Sprint*`, which ignore `term.Options` (§2.3).
- **One render environment:** `term.Detect` once at startup, `term.Fixed` in tests and the gallery, whose play mode takes the terminal's size from `term.Detect` (§9.14); only `pkg/ui/term` looks at the terminal, and `prompt.Stdin` asks whether stdin is one (§3, §9.7).
- **States read without colour:** a glyph and a word for every state (a callout: its title's word, DEV-032; a step's row: its state's word in the status column, whatever its marker, P-42), muted text from gray tokens and never SGR 2 (faint), and output that degrades without colour, Unicode, width or a terminal, and on a light background (§1). **The one exception, the maintainer's** (2026-10-22, "glyph and text in the state's colour, no word"): an inline result under a prompt (`InlineResult`) has no word, so without colour its kind is told by its text alone, which must say what it is ("Invalid IP address format", "Nameserver 192.0.2.53 added to configuration"; DEV-062).
- **Runs of messages are grouped** (P-42 R5; the orchestrator's call, for the maintainer): messages written one after another, such as a report's lines of what was done and what is left, go to one `component.Messages` in reading order, rendered once, so that each kind's callout title shows once over its lines and the info lines after them stay prose; a `Message` rendered alone for each would repeat its title over every line. A run written under another block starts `SectionGap` blank lines down, as every block does, so that its first callout does not continue the last one (`hardn confirm`'s run after its clean-up's report). Open for the maintainer (DEV-031): a run's callout right after a callout of its kind repeats the title (`hardn confirm`'s done lines after the report's "Operation Successful", `pkg/output`'s further errors after the `ErrorReport`), and an info line between two lines of one kind ends the group (each further error with its fix).
- **Informational text as short as it can be** (maintainer, 2026-10-20). A step's title, a status line or a notice says what happens in the fewest words that still say it, in the user's terms, and leaves the exact lines to what shows them in full (the plan's diff, the journal, `--output json`): "Add SSH port 2230", not "Set Port 22, Port 2230"; "sshd -T shows ports 22, 2230"; "Drop SSH port 22"; "ufw: drop 22/tcp"; "Disallow root login" and "Disallow root password login", not "Set PermitRootLogin no" and "Set PermitRootLogin prohibit-password". Repeated words are dropped (a callout's body does not repeat its title). A change's `Title` names what changes, not the file's whole result; `engine.TitleMax` is a ceiling, not a target.
- **Don't borrow** (brief 1C): the event loop and full-screen redraws, focus/blur state machines, Tab navigation between fields, or arrow-key selection. They conflict with the line-based model; the maintainer may opt into one later, through a proposal. Bubble Tea, Bubbles and huh lend the patterns brief 1C pairs with hardn's adaptations, and are not imported; the brief's one exception is Bubbles' `textinput`, only if the maintainer approves richer in-field editing (brief: Rejected approaches), and would take a change to the `never` rule.
- **Test helpers stay in tests:** `pkg/ui/uitest` and `pkg/ui/component/fixture` only in `_test.go` files and under `internal/tools`. So do the screens' and the flow's fixtures (`screen.Mocks`, `MainMenuFixture` and its kin, `flow.Fixture`), and `theme.NewWithOverrides` is the gallery's alone (§9.14).

**Adding a component.** A view-model struct of plain data in `pkg/ui/component` with a pure `Render(c Ctx) string`, by the conventions of §9.1; evaluate Lip Gloss's table, list, tree, join and place helpers first and record the outcome in its group's section. Its states go in `fixture.States()`, which gives each a golden on `Full()` and a gallery entry (`TestEveryComponent` fails for a component with none); then `make golden-update`, each new file checked by eye (at least `truecolor-dark-unicode-80`, `none-dark-ascii-60` and the light cells), a row in §9.11, a DEV row in [deviations.md](deviations.md) for each departure from Figma, and a proposal for any word Figma and origin/main do not have.

**Adding a token.** A `token{hex, ansi256, ansi}` field in the `palette` struct of `pkg/ui/theme/palette.go`, named by its `token` tag, with a value in `darkPalette` and in `lightPalette`: the 256-colour index the nearest by CIE76 (`TestANSI256Nearest`) unless an override is logged, the 16-colour pick by hand. Then its contrast floor in `TestContrast`, the slots that use it in `theme.New` (`TestColourRoles`), the swatch golden regenerated, its rows in §4.1 and §4.3, and a DEV row where it departs from the export. Values can be tried first without editing code, with the gallery's `-override` (§9.14).

**Adding a glyph.** A role in `theme.Glyphs` with a value in both sets: printable ASCII in the ASCII set (`TestGlyphSetsComplete`), an East Asian ambiguous one listed in the `Glyphs` doc comment (`TestAmbiguousGlyphs`), and a state's marker within the three-cell marker column and unlike every other state's, unless the maintainer has decided a shared marker, which the state's word and colour then tell apart, a `StatusRow` keeping its state's word (`TestStatusMarkers`, `TestSharedMarkerColours`, `TestInlineMarker`, `TestStepMarkers`; §6). Then the swatch golden, a row in §6, and a DEV row for a glyph Figma does not draw.

**Updating goldens deliberately.** A golden diff is a change in what the user sees. Run `make golden-update` only after a change meant to alter output, never to make a failing test pass; read the diff cell by cell, the cells above at least; the commit body says why each file changed, and the review description lists each changed golden with its reason (refactor plan, review template item 4). A golden file is never edited by hand: its header says so.

**Limits.**
- golangci-lint lints the files of the host's build only, so on a darwin host a Linux-only file goes unlinted; `pkg/ui/prompt`'s and `pkg/ui/keys`'s `TestImports` read every non-test file whatever its build tags, so they stay. `make check`'s `check-cross` type-checks and vets the whole module, tests included, for linux/amd64 and linux/arm64, so a Linux-only file at least compiles (§9.7).
- depguard matches import paths, not identifiers, so it cannot keep `theme.NewWithOverrides` to the gallery: `component`, `nav`, `form`, `flow` and `screen` import `pkg/ui/theme`, for the grid constants and, in `component`, the theme itself, so a call of `NewWithOverrides` in one of them adds no import. `TestOverrideReach` holds that (§9.14); depguard could if `NewWithOverrides` had a package of its own. Review holds the screen and flow fixtures. Nor does depguard see string literals: an escape sequence written out, as in `pkg/utils`'s `ClearScreen` (`"\033[H\033[2J"`) and `pkg/style`'s constants, is review's to refuse. golangci-lint v2.14.0 ships forbidigo ("Forbids identifiers"), the linter for such identifier rules, and for Lip Gloss's `Print*`, `Fprint*` and `Sprint*` and `os.Stdin` and `os.Stdout`, should the maintainer want them linted; it is not enabled, the linter set staying as it was.
- golangci-lint shows one issue per line, so an import two rules deny (`compat`, x/term or Bubble Tea outside `pkg/ui`) is reported once, with either rule's reason. An import of a module not in `go.mod`, such as Bubble Tea, fails to type-check before depguard sees it; adding the module is a reviewed `go.mod` change, and the `never` rule then reports the import.
- `charm` and `gallery` take Charm's two module hosts whole; the other entries name libraries: the terminal libraries in the module graph today (go-isatty, terminfo, cancelreader, go-colorable) and `golang.org/x/term`, the Go project's own, not in the graph. A terminal library new to `go.mod` gets its entry in the same reviewed change. Libraries that only compute are not denied: go-colorful's colour maths, and uniseg's, displaywidth's and `golang.org/x/text/width`'s widths (`pkg/ui/theme`'s glyph test uses the last); measuring with `lipgloss.Width` or x/ansi (§9.1) is review's.
